## 文档 01: LL128 Protocol 概览

**目标**：建立对 LL128 Protocol 的整体认知，理解它是什么、为什么需要它

**核心问题**：
- 为什么有了 Simple 和 LL 还需要 LL128？
- LL128 是什么？它的本质是什么？
- LL128 的核心机制是什么？

**内容结构**：

### 1.1 为什么需要 LL128？

**从应用场景入手**：
- Tensor Parallel 场景：activations 在层之间传输（中等大小数据）
- Pipeline Parallel 场景：中间 activations 传输
- MOE 场景：专家模型之间的数据交换
- 这些场景的特点：
  - 数据量：通常几十到几百 KB
  - 延迟敏感：在训练的关键路径上
  - 频繁发生：每个 forward/backward pass 都需要

**Simple 和 LL 的问题**：
- Simple Protocol：
  - 优势：带宽高（接近理论峰值）
  - 问题：启动延迟高，粗粒度同步
  - 不适合中等消息：浪费在启动和等待上的时间占比大

- LL Protocol：
  - 优势：延迟最低
  - 问题：带宽效率只有 50%（双标志开销）
  - 不适合中等消息：传输时间过长，影响训练速度

**中等消息需要什么？**
- 需要 LL 的快速启动（低延迟特性）
- 需要接近 Simple 的传输效率（高带宽）
- 这就是 LL128 的设计目标

**关键洞察**：中等消息是深度学习训练中最常见的场景之一，需要一个专门优化的协议

### 1.2 LL128 是什么？

#### 先说本质

**LL128 的本质：通过扩大传输单元（128B）和线程角色分化（Flag Thread），在保持行级完整性验证的前提下，将带宽效率提升到 93.75%，实现了延迟和带宽的平衡**

换句话说：
> **LL128 = LL 的行级完整性保证 + 接近 Simple 的传输效率**

这个本质可以从三个设计维度来理解：

#### 维度 1：传输单元 - 从 16B 到 128B

LL128 的基本传输单元是 128 字节行

内存布局：
```
128 字节 = 15 个数据 uint64_t + 1 个标志 uint64_t
[data[0]][data[1]]...[data[14]][flag]
 └────── 120 字节数据 ─────┘└─ 8B ─┘
```

**带宽效率对比**（参数级别的对比，帮助建立参照系）：
- LL: 16B 单元，8B 数据 + 8B 标志 → 50% 效率
- LL128: 128B 单元，120B 数据 + 8B 标志 → 93.75% 效率
- Simple: KB 级单元，几乎全是数据 → ~99% 效率

**为什么选择 128 字节？**（? 需确认）
- 可能与 GPU L2 cache line 大小有关
- 与 warp 处理效率匹配
- 是 LL 16 字节的 8 倍（后面会看到，这与 Flag Thread 的间隔对应）

**关键点**：扩大传输单元是提升带宽的直接手段，但挑战是如何保证完整性

#### 维度 2：线程角色分化 - Flag Thread 的引入

**这是 LL128 最重要的设计创新**

在 LL 和 Simple 中，所有线程的角色是相同的（虽然 Simple 有 worker/non-worker 分工，但那是为了流水线优化，不是为了数据处理本身）。

**LL128 引入了线程角色分化**：
```c
flagThread = (tid % 8) == 7
```

- 每 8 个线程中，第 7 个是 Flag Thread
- 一个 warp（32 线程）有 4 个 Flag Thread
- **Flag Thread 的职责**：
  - 写入时：把标志写到 128B 行的末尾
  - 读取时：验证标志是否正确

**为什么需要 Flag Thread？**

因为 LL128 使用**单标志设计**：
- LL 需要双标志：`[data1:4B][flag1:4B][data2:4B][flag2:4B]`
- LL128 只需单标志：`[data[0]:8B]...[data[14]:8B][flag:8B]`

单标志提升了效率（93.75% vs 50%），但需要有线程专门负责处理这个末尾的标志。Flag Thread 就是这个"专职人员"。

**关键点**：Flag Thread 机制让单标志设计成为可能，这是带宽效率提升的关键

#### 维度 3：完整性保证 - 两层同步机制

LL128 仍然保持**行级完整性验证**（这是 LL 的优势），同时加上 **step 级流控**（这是 Simple 的机制）：

**Layer 1：行级验证（细粒度）**
- 每个 128B 行都有标志
- Flag Thread 验证标志后，整个 warp 才继续
- 粒度：128 字节
- 作用：保证每一行数据的完整性

**Layer 2：Step 级流控（粗粒度）**
- 使用 head/tail 计数器（同 Simple/LL）
- waitSend() 检查缓冲区是否有空间
- postRecv() 更新计数器通知对端
- 粒度：一个 step（包含多个 128B 行）
- 作用：防止缓冲区溢出

**为什么需要两层？**
- 细粒度验证：确保每一行数据都是完整的（LL 的特性）
- 粗粒度流控：避免发送方跑太快，覆盖了接收方还没读的数据（Simple 的机制）
- 两者互补：既有完整性保证，又有流水线效率

**关键点**：LL128 继承了 LL 的行级完整性，同时用 Simple 的流控机制保证整体效率

#### 回到本质

现在我们可以理解 LL128 的本质了：

1. **扩大传输单元**（16B → 128B）
   - 目的：提升带宽效率
   - 挑战：如何保证完整性？

2. **引入 Flag Thread**（线程角色分化）
   - 目的：用单标志保证完整性
   - 效果：带宽从 50% 提升到 93.75%

3. **保持两层同步**（行级 + step 级）
   - 目的：既有完整性，又有流水线
   - 效果：延迟和带宽的平衡

**LL128 不是简单的"介于 LL 和 Simple 之间"，而是精心设计的平衡点，每一个设计选择都是为了达到"行级完整性 + 高带宽效率"这个目标**

**关键洞察**：LL128 的核心创新是 Flag Thread 机制，它让单标志设计成为可能，从而实现了带宽效率的显著提升

### 1.3 核心机制预览

在深入细节之前，让我们预览一下 LL128 的核心机制（后续文档会详细讲解）：

#### Flag Thread 的定义
```c
flagThread = (tid % 8) == 7
```
- 每 8 个线程中，第 7 个是 flag thread
- 在一个 warp（32 线程）中，有 4 个 flag 线程

#### 写入和读取
**写入时**：
```c
store128(ptr, v[u], flagThread ? flag : v[u+1]);
```
- 普通线程：写两个数据 `store128(ptr, v[u], v[u+1])`
- Flag 线程：写一个数据 + 标志 `store128(ptr, v[u], flag)`

**读取时**：
```c
load128(ptr, vr[u], vr[u+1]);
needReload |= flagThread && (vr[u+1] != flag);
```
- 所有线程都执行 `load128`
- 只有 Flag 线程检查标志
- 如果任何一个 Flag 线程发现标志不对，整个 warp 重试

#### 128 位原子操作
```c
load128:  ld.volatile.global.v2.u64 {%0,%1}, [%2]
store128: st.volatile.global.v2.u64 [%2], {%0,%1}
```
- 一次读写 16 字节（2 个 uint64_t）
- 保证原子性（节点内）
- 与 LL 的 `v4.u32` 不同，这里是 `v2.u64`

**为什么用 v2.u64 而不是 v4.u32？**
- 基本单元是 uint64_t（标志是 64 位）
- 更大的标志空间（2^64 vs 2^32）
- 不需要像 LL 那样的标志清理机制

#### 两阶段寄存器加载
- **Begin**: 从用户缓冲区加载数据到寄存器（但不 shuffle）
- **Finish**: 调整寄存器布局，为标志腾出空间
- **目的**：在等待接收数据的同时执行 Finish，隐藏延迟

**为什么分两阶段？**

性能优化：
```
传统方法：加载 + shuffle（串行）→ 等待接收（空闲）→ 处理
优化方法：加载（快速）→ 等待接收（同时执行 shuffle）→ 处理
```

**这些机制如何协同工作？**（留待后续文档详细解释）
- Flag Thread 负责标志的读写
- 128 位原子操作保证单次读写的完整性
- 两阶段加载优化性能
- 最终实现：93.75% 的带宽效率 + 中等延迟

### 1.4 LL128 的定位

**LL128 不是为了取代 Simple 或 LL**，而是填补它们之间的空白。

NCCL 根据消息大小选择协议（? 阈值需确认）：
- 消息大小 < 某个阈值：用 LL（延迟最重要）
- 消息大小在中间范围：用 LL128（平衡点）
- 消息大小 > 某个阈值：用 Simple（带宽最重要）

**代码位置**：协议选择逻辑在 `src/graph/tuning.cc`（具体实现需要查看）

**LL128 在 NCCL 中的意义**：
- 完善了协议矩阵，覆盖所有消息大小
- 为深度学习训练中最常见的中等消息提供最优解
- 体现了 NCCL 对性能的极致追求

**关键洞察**：LL128 是延迟和带宽的最佳平衡点，专为深度学习训练中最常见的中等消息优化

**预计篇幅**：800-1000 行

## 文档 02: Flag Thread 机制详解

**目标**：深入理解 LL128 的核心创新 —— Flag Thread 机制

**核心问题**：
- 什么是 Flag Thread？
- 为什么需要 Flag Thread？
- Flag Thread 在写入和读取时做了什么？
- 单标志设计的原理是什么？

**内容结构**：

### 2.1 问题的引入

**从 LL 的双标志说起**（简要回顾，引用 LL 02）：
- LL 使用 16 字节单元：`[data1:4B][flag1:4B][data2:4B][flag2:4B]`
- 为什么需要两个标志？
  - GPU 128 位原子读只能读 16 字节
  - 必须在一次原子读内验证所有数据
  - 两个标志保护两个 4 字节数据块

**LL128 的改进**：
- 使用 128 字节单元：`[data[0]:8B]...[data[14]:8B][flag:8B]`
- 只有一个标志，在行末
- 带宽效率：120B / 128B = 93.75%（vs LL 的 50%）

**核心问题**：只有一个标志，如何保证前面 120 字节数据的完整性？

**答案**：Flag Thread 机制

### 2.2 Flag Thread 的定义

**代码位置**：`src/device/prims_ll128.h:368`

```c
flagThread = (tid % 8) == 7
```

**含义**：
- 每 8 个线程中，线程 ID 模 8 等于 7 的是 flag 线程
- 在一个 warp（32 线程）中：
  - tid = 7, 15, 23, 31 是 flag 线程
  - 其他 28 个是普通线程

**为什么是每 8 个线程？**

这与 128 字节行的结构有关：
- 128 字节 = 16 个 uint64_t
- 16 个位置 = 15 个数据 + 1 个标志
- 一个 warp (32 线程) 如何处理 16 个 uint64_t？
  - 每个线程负责若干个 uint64_t
  - 每 8 个线程为一组，覆盖 16 个位置的一部分
  - 第 8 个线程（flagThread）负责最后一个位置（标志）

**关键点**：Flag Thread 不是一个特殊的线程类型，只是普通线程的一个角色标识

**关键洞察**：Flag Thread 机制让单标志设计成为可能，同时保持代码简洁和高性能

### 2.4 读取验证：Flag Thread 如何检查标志

**代码位置**：`src/device/prims_ll128.h:188-196`

**关键点**：
- **并行验证**：一个 warp 有 4 个 flag 线程，可以并行验证 4 个行（或 1 个行的不同部分）
- **协同重试**：只要一个 flag 线程发现问题，整个 warp 重试
- **零开销（对普通线程）**：普通线程只读数据，不做验证逻辑

### 2.5 单标志设计的原理

现在我们可以回答：为什么 LL128 可以用单标志，而 LL 必须用双标志？

**LL 的约束**：
- 传输单元 = 16 字节 = GPU 一次原子读的宽度
- 必须在一次原子读内同时获取数据和验证标志
- 因此需要双标志（每 8 字节一个）

**LL128 的突破**：
- 传输单元 = 128 字节 >> GPU 一次原子读的宽度（16 字节）
- GPU 需要多次读取才能读完一个 128 字节行
- 可以依赖分层验证：
  1. **节点内通信**：硬件保证 128 位原子写
  2. **节点间通信（非 GDR）**：Proxy 线程预先验证（稍后讲解）
  3. **所有情况**：Flag Thread 在 GPU 侧再次验证

**为什么标志必须在末尾？**
- **因果性保证**：如果 Flag Thread 读到了正确的标志
- 说明发送方已经写完了前面的 120 字节数据
- 并且执行了 fence（确保写入可见）
- 然后才写的标志

**? 关键洞察（需确认）**：单标志设计是一个工程权衡 —— 依赖硬件的顺序保证和 Proxy 的预验证，换来了带宽效率的显著提升（93.75% vs 50%）。在实践中，这个权衡是值得的。

**预计篇幅**：700-900 行

## 文档 03: 数据结构与寄存器管理

**目标**：理解 LL128 的内存布局和性能优化技术

**核心问题**：
- 128 字节行在内存中如何组织？
- 为什么需要两阶段寄存器加载？
- 如何处理非对齐的用户数据？

**内容结构**：

### 3.1 128 字节行的内存布局

**字节级布局**：
```
字节偏移:    0      8     16     24    ...   112    120
          ├──────┼──────┼──────┼──────┼───┼──────┼──────┤
uint64_t: │data[0]│data[1]│data[2]│data[3]│...│data[14]│ flag │
          └──────────────────────────────────────┴──────┴──────┘
                     120 字节有效数据                 8B 标志

uint64_t 索引:  [0]    [1]    [2]    [3]   ...   [14]   [15]
                ↑                                  ↑      ↑
              数据开始                          最后数据  标志位置
```

**环形缓冲区中的组织**（引用 Simple 03）：
- 环形缓冲区总大小：`buffSizes[NCCL_PROTO_LL128]`
- 分成 `NCCL_STEPS = 8` 个 slot
- 每个 slot 包含多个 128 字节行
- 行数 = `buffSizes / NCCL_STEPS / 128`

**与 LL 的对比**：
| 协议 | 行大小 | 数据元素 | 标志元素 | 效率 |
|------|--------|---------|---------|------|
| LL | 16B | 2 × 4B | 2 × 4B | 50% |
| LL128 | 128B | 15 × 8B | 1 × 8B | 93.75% |

### 3.2 寄存器管理：两阶段加载

**问题**：为什么不一次性加载完用户数据？

**答案**：为了隐藏内存延迟，优化性能

#### Begin 阶段

**代码位置**：`src/device/prims_ll128.h:86-133`
需要分析代码来讲解本章内容

**核心逻辑**（对齐情况）：
**关键点**：
- Flag 线程只加载一半：`if(!flagThread || g%2==0)`
- 普通线程加载全部
- 此时**不做** shuffle（数据重排）

**为什么 Flag 线程只加载一半？**
- Flag 线程的第二个寄存器位置要留给标志
- 所以只需要加载用户数据的一半
- 另一半寄存器空间用于标志

#### Finish 阶段

**代码位置**：`src/device/prims_ll128.h:136-142`
需要分析代码来讲解本章内容

**作用**：
- Flag 线程把数据移到正确的寄存器位置
- 为第二个位置（`regs[2*g+1]`）腾出空间
- 之后写入时，这个位置会被替换成标志

#### 为什么分两阶段？

**时间线对比**：

传统方法（单阶段）：
T0-T1: 加载用户数据 + shuffle（串行）
T2-T5: 等待接收对端数据（GPU 空闲）
T6:    处理数据

优化方法（两阶段）：
T0:    Begin - 只加载，不 shuffle
T1:    发起接收操作（recvReduceSendCopy）
T2-T4: 等待接收时执行 Finish shuffle（并行）
T5:    处理数据

节省：T2-T4 的 shuffle 被隐藏在等待时间中

**关键洞察**：两阶段加载是一个重要的性能优化 —— 把 shuffle 的计算开销隐藏在等待内存的时间里

### 3.3 内存对齐处理

**问题**：用户缓冲区可能不是 16 字节对齐

**代码位置**：`src/device/prims_ll128.h:105-132`

#### 对齐情况（快速路径）

- 最高效的路径
- 直接使用 128 位原子读

#### 非对齐情况（慢速路径）

**为什么用 shared memory？**
- GPU global memory 对非对齐访问性能差
- Shared memory 可以高效做非对齐访问
- 作为"中转站"重新对齐数据

## 文档 04: GenericOp 工作流程

**目标**：理解完整的数据传输流程

**核心问题**：

- recvReduceSendCopy 如何协调接收、规约、发送？

**内容结构**：

### 4.1 GenericOp 的整体结构

**代码位置**：`src/device/prims_ll128.h:291-324`

**函数签名**：
```c
template <int RECV, int SEND, int SrcBuf, int DstBuf>
__device__ __forceinline__ void GenericOp(intptr_t srcIx, intptr_t dstIx, int nelem, bool postOp)
```

**参数说明**：
- `RECV, SEND`: 模板参数，控制是否接收/发送
- `SrcBuf, DstBuf`: 源和目标缓冲区类型（Input/Output/-1）
- `srcIx, dstIx`: 用户缓冲区内的偏移
- `nelem`: 要处理的元素个数
- `postOp`: 是否应用后处理操作（如 division）

**主循环框架**：
```c
if (SEND) waitSend(nbytes);  // 等待缓冲区有空间
barrier();

while (nelem > 0) {
  const int eltInSlice = min(nelem, DataEltPerSlice);
  uint64_t regs[NCCL_LL128_SHMEM_ELEMS_PER_THREAD];

  if (SRC) loadRegsBegin(regs, srcPtr, eltInSlice);
  recvReduceSendCopy<...>(regs, wireOffset, postOp);
  if (DST) storeRegs(dstPtr, regs, eltInSlice);

  // 更新指针
  wireOffset += WireWordPerSlice*nwarps;
  srcPtr += DataEltPerSlice*nwarps;
  dstPtr += DataEltPerSlice*nwarps;
  nelem -= DataEltPerSlice*nwarps;
}

barrier();
if (SEND) { step++; postSend(); }
if (RECV) { step++; postRecv(); }
```

**关键点**：
- 只在开始时 waitSend 一次（不是每次循环）
- 循环内处理数据，粒度是 DataEltPerSlice
- 最后统一更新 step 和通知对端

### 4.2 recvReduceSendCopy 详解

**代码位置**：`src/device/prims_ll128.h:176-286`

**这是 LL128 的核心函数，协调所有操作**

#### 步骤 1：等待第一个 recv

```c
if (RECV) {
  uint64_t* ptr = recvPtr(0)+ll128Offset;
  uint64_t flag = recvFlag(0);
  bool needReload;
  do {
    needReload = false;
    for (int u=0; u<ELEMS_PER_THREAD; u+=2) {
      load128(ptr+u*WARP_SIZE, vr[u], vr[u+1]);
      needReload |= flagThread && (vr[u+1] != flag);
    }
  } while (__any_sync(WARP_MASK, needReload));
}
```

**作用**：
- 从第一个 peer 接收数据
- Flag Thread 验证标志
- 轮询直到数据到达

#### 步骤 2：Finish 用户数据加载

```c
if (SRC) {
  loadRegsFinish(v);  // 执行 shuffle
  if (SrcBuf == Input) {
    for (int u=0; u<ELEMS_PER_THREAD; u+=2) {
      v[u] = applyPreOp(redOp, v[u]);
      if (!flagThread) v[u+1] = applyPreOp(redOp, v[u+1]);
    }
  }
}
```

**关键**：
- 在等待接收的同时，执行了 Finish（性能优化）
- 应用 preOp（如果需要）

#### 步骤 3：接收其余 peers

```c
for (int i=1; i<MaxRecv && i<fan.nrecv(); i++) {
  // 类似步骤 1，轮询等待
  // 规约到 v
}
```

#### 步骤 4：应用 postOp

```c
if (postOp) {
  for (int u=0; u<ELEMS_PER_THREAD; u+=2) {
    v[u] = applyPostOp(redOp, v[u]);
    v[u+1] = applyPostOp(redOp, v[u+1]);
  }
}
```

#### 步骤 5：发送

```c
if (SEND) {
  for (int i=0; i<fan.nsend(); i++) {
    uint64_t flag = sendFlag(i);
    uint64_t* ptr = sendPtr(i)+ll128Offset;
    for (int u=0; u<ELEMS_PER_THREAD; u+=2) {
      store128(ptr+u*WARP_SIZE, v[u], flagThread ? flag : v[u+1]);
    }
  }
}
```

**关键洞察**：recvReduceSendCopy 是一个高度优化的函数，把接收、规约、发送融合在一起，最大化寄存器复用

### 4.3 三种协议的深入对比

**现在我们可以从底层原理对比三种协议了**（在讲清楚 LL128 之后，对比自然显现）

#### 传输与同步

| 协议 | 传输单元 | 同步粒度 | 标志机制 | 带宽效率 |
|------|---------|---------|---------|---------|
| LL | 16B | 每 16B | 双标志 | 50% |
| LL128 | 128B | 每 128B | 单标志 + Flag Thread | 93.75% |
| Simple | KB级 | 每 step | 无（只 head/tail） | ~99% |

#### 线程组织（详见文档 05）

| 协议 | 线程角色 | 分工方式 | 同步方式 |
|------|---------|---------|---------|
| LL | 平等 | 每个线程处理若干 16B 行 | 每行自旋验证 |
| LL128 | Flag Thread + 普通线程 | Flag Thread 负责标志 | warp 级同步 |
| Simple | Worker + Non-worker | Non-worker 负责 post | barrier 同步 |

#### 复杂度

| 协议 | 循环层数 | 寄存器管理 | 代码复杂度 |
|------|---------|-----------|-----------|
| LL | 单层 | 简单 | 低 |
| LL128 | 单层 | 两阶段加载 | 中 |
| Simple | 三层（Chunk-Slice-Step） | 循环展开 | 高 |

#### 适用场景

| 协议 | 最佳场景 | 优势 | 劣势 |
|------|---------|------|------|
| LL | 小消息 (< 某阈值) | 延迟最低 | 带宽只有 50% |
| LL128 | 中等消息（某范围内） | **平衡点** | 两头不是最优 |
| Simple | 大消息 (> 某阈值) | 带宽最高 | 启动延迟高 |

**关键洞察**：
- LL 牺牲带宽换延迟
- Simple 牺牲延迟换带宽
- LL128 在两者之间找到了最佳平衡点
- 深度学习训练中，中等消息（某范围内）是最常见的场景之一，LL128 为此而生

**预计篇幅**：800-1000 行

## 文档 05: 附录 - 三种协议的执行模型对比

**目标**：横向对比三种协议的线程组织和执行方式

**核心问题**：
- 什么是执行模型？
- 三种协议的执行模型有什么差异？
- 为什么需要不同的执行模型？

**内容结构**：

### 5.1 什么是执行模型？

执行模型描述了 GPU kernel 中线程如何组织、分工和同步：

**三个维度**：
1. **线程组织**：线程如何分组（warp、block 等）
2. **线程分工**：不同线程的角色和职责
3. **同步点**：线程在哪里需要同步

**为什么重要？**
- 不同的传输粒度需要不同的线程分工
- 不同的同步机制需要不同的同步方式
- 执行模型直接影响性能

### 5.2 Simple Protocol 的执行模型

#### 线程组织
- 启动多个线程（如 256-512 个）
- 分为 Worker 和 Non-worker
- Worker 数量：`nworkers = nthreads - (MaxSend > 0 && nthreads >= 64 ? WARP_SIZE : 0)`
- Non-worker：最后一个 warp（如果需要）

#### 线程分工
**Worker 线程**：
- 负责数据传输（memcpy、reduce）
- 参与数据处理的所有步骤

**Non-worker 线程**：
- 负责 postPeer 操作
- 更新 head/tail 计数器
- 避免 worker 线程阻塞在 post 操作上

#### 同步点
- **subBarrier**：只同步 worker 线程
- **barrier**：同步所有线程（包括 non-worker）

#### 循环结构
三层循环：
```
for each Chunk:
  for each Slice in Chunk:
    for each Step in Slice:
      waitPeer, reduceCopy, postPeer
```

**关键特点**：
- Worker/Non-worker 分离优化流水线
- 循环展开（SlicePerChunk）提高性能
- 粗粒度同步（每个 step）

### 5.3 LL Protocol 的执行模型

#### 线程组织
- 启动多个线程（如 256-512 个）
- 所有线程平等，无角色分化

#### 线程分工
- 每个线程处理若干个 16B 行
- 每个线程独立验证双标志
- 线程间完全并行，无特殊分工

#### 同步点
- 每个 16B 行：自旋验证双标志（readLL）
- Step 级：barrier 同步

#### 循环结构
单层循环：
```
for each line:
  readLL (验证双标志)
  处理数据
  storeLL (写双标志)
```

**关键特点**：
- 所有线程平等
- 每个 line 都细粒度同步
- 简单但带宽低（50%）

### 5.4 LL128 Protocol 的执行模型

#### 线程组织
- 启动多个线程（如 256-640 个）
- 以 warp 为基本单位（32 线程）
- Warp 内有角色分化

#### 线程分工
**Flag Thread**（每 8 个线程中有 1 个）：
- 写入时：把标志写到行末
- 读取时：验证标志是否正确
- 触发 warp 级重试（如果标志不对）

**普通线程**（其他线程）：
- 只处理数据
- 不参与标志验证

#### 同步点
- **loadRegsFinish 前**：Begin 完成
- **每个 128B 行**：Flag Thread 验证，`__any_sync` warp 级同步
- **Step 级**：barrier 同步

#### 循环结构
单层循环（但内部有两阶段）：
```
for each slice:
  loadRegsBegin (只加载)
  recvReduceSendCopy:
    loadRegsFinish (shuffle)
    等待接收（Flag Thread 验证）
    规约
    发送（Flag Thread 写标志）
  storeRegs
```

**关键特点**：
- Warp 级角色分化
- 两阶段加载隐藏延迟
- 单标志 + warp 级同步

### 5.5 为什么需要不同的执行模型？

#### 与传输粒度的关系

| 协议 | 传输粒度 | 执行模型 | 原因 |
|------|---------|---------|------|
| Simple | KB 级 | Worker/Non-worker | 粗粒度传输，需要流水线优化 |
| LL | 16B | 所有线程平等 | 细粒度传输，每个线程独立处理 |
| LL128 | 128B | Flag Thread + 普通线程 | 中等粒度，需要角色分化 |

#### 与同步机制的关系

| 协议 | 同步机制 | 执行模型配合 |
|------|---------|-------------|
| Simple | Step 级 head/tail | Non-worker 专门做 post |
| LL | 每 line 双标志 | 每个线程自旋验证 |
| LL128 | 每 line 单标志 + step 级 | Flag Thread 验证 + barrier |

#### 与硬件特性的匹配

| 协议 | 硬件特性利用 | 执行模型体现 |
|------|-------------|-------------|
| Simple | 大块 memcpy，循环展开 | SlicePerChunk 展开 |
| LL | 128 位原子读（v4.u32） | 每个线程独立 readLL |
| LL128 | 128 位原子读（v2.u64）+ warp 调度 | Warp 级同步 |

### 5.6 总结

**三种执行模型的本质差异**：

1. **Simple**：为粗粒度传输优化
   - Worker/Non-worker 分离 → 流水线
   - 三层循环展开 → 充分利用 memcpy

2. **LL**：为细粒度传输优化
   - 所有线程平等 → 最大并行度
   - 每 line 验证 → 最低延迟

3. **LL128**：为中等粒度传输优化
   - Flag Thread 角色分化 → 单标志设计
   - Warp 级组织 → 充分利用硬件

**关键洞察**：执行模型不是任意选择的，而是由传输粒度、同步机制、硬件特性共同决定的。LL128 的执行模型体现了它作为"平衡点"的设计哲学。

**预计篇幅**：600-800 行

# NCCL Proxy 系统

## 1. 为什么需要 Proxy

GPU 擅长并行计算，但网络操作（InfiniBand verbs、TCP sockets）是 CPU 侧的系统调用，GPU 无法直接执行。NCCL 需要一个 CPU 线程来代理 GPU 的网络通信请求，这就是 Proxy。

核心问题是：GPU kernel 生产数据的速度很快，网络传输相对较慢，如何让两者高效协同？

解决方案是流水线：
1. GPU kernel 把数据写到共享 buffer
2. CPU Proxy 线程监控 buffer，发现有数据就发送到网络
3. 两者通过 `head/tail` 指针实现流水线式的同步

```
┌──────────────────────────────────────────────────────────────────┐
│                        单个 Rank 的架构                           │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│   ┌─────────────────────┐                ┌────────────────────┐  │
│   │     GPU Kernel      │                │   Proxy Thread     │  │
│   │                     │                │                    │  │
│   │  生产数据 ──────────┼──►  head/tail ──┼─► 发送到网络       │  │
│   │                     │                │                    │  │
│   │  ◄────── 消费数据 ──┼────  head/tail ◄┼── 从网络接收       │  │
│   └─────────────────────┘                └────────────────────┘  │
│              │                                    │              │
│              └────────────── FIFO Buffer ─────────┘              │
│                         (GPU 可见内存)                            │
└──────────────────────────────────────────────────────────────────┘
```

## 2. FIFO Buffer 与 head/tail 同步

GPU 和 Proxy 之间的协同靠一个环形 buffer（FIFO）和两个指针：

```
┌────────────────────────────────────────────────────────────────┐
│                     FIFO Buffer (NCCL_STEPS slots)             │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│   slot 0     slot 1     slot 2     slot 3     slot 4    ...   │
│  ┌───────┐  ┌───────┐  ┌───────┐  ┌───────┐  ┌───────┐        │
│  │ data  │  │ data  │  │ empty │  │ empty │  │ empty │        │
│  └───────┘  └───────┘  └───────┘  └───────┘  └───────┘        │
│      ▲                     ▲                                   │
│      │                     │                                   │
│    head=2               tail=2                                 │
│   (Proxy 已发送完 0,1)  (GPU 已写入到 slot 1)                   │
│                                                                │
│  发送时：GPU 写数据 → 更新 tail → Proxy 看到 tail > head → 发送 │
│  接收时：Proxy 收数据 → 更新 tail → GPU 看到 tail > head → 读取 │
└────────────────────────────────────────────────────────────────┘
```

关键参数：
- `NCCL_STEPS`：FIFO 深度，通常是 8，决定了流水线的最大深度
- `head`：消费者已处理到的位置
- `tail`：生产者已写入到的位置

### 2.1 发送流程（GPU → Network）

```
GPU Kernel:
  1. 把数据写入 buffer[tail % NCCL_STEPS]
  2. 更新 tail = tail + sliceSteps
  3. 等待 head 追上来（避免覆盖未发送的数据）

Proxy sendProxyProgress():
  1. 检查 tail > head（有新数据）
  2. 调用 ncclNet->isend() 发送
  3. 等待 isend 完成
  4. 更新 head = head + sliceSteps
```

### 2.2 接收流程（Network → GPU）

```
Proxy recvProxyProgress():
  1. 调用 ncclNet->irecv() 发起接收
  2. 更新 posted 计数
  3. 等待 irecv 完成
  4. 更新 tail（告诉 GPU 数据已就绪）

GPU Kernel:
  1. 等待 tail > head（有新数据到达）
  2. 从 buffer[head % NCCL_STEPS] 读取数据
  3. 更新 head
```

## 3. Proxy 系统架构

Proxy 系统包含三个线程：

```
┌──────────────────────────────────────────────────────────────────┐
│                     Proxy State (ncclProxyState)                 │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│   ┌─────────────────────────────┐  ┌─────────────────────────┐   │
│   │     Service Thread          │  │    Progress Thread       │   │
│   │     (ncclProxyService)      │  │    (ncclProxyProgress)   │   │
│   │                             │  │                          │   │
│   │  • 监听 socket              │  │  • 执行实际的网络 I/O    │   │
│   │  • 处理连接建立请求         │  │  • 调用 transport 的     │   │
│   │  • 初始化 connection        │  │    proxyProgress 函数    │   │
│   └─────────────────────────────┘  └─────────────────────────┘   │
│                                                                  │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │                    Shared Ops Pool                       │   │
│   │               (ncclProxyOpsPool)                        │   │
│   │                                                          │   │
│   │   Main Thread ────► post ops ────► Progress Thread      │   │
│   │   (用户线程)          mutex+cond        (执行 I/O)      │   │
│   └─────────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────┘
```

三个线程的职责：

| 线程 | 入口函数 | 职责 |
|------|----------|------|
| Service Thread | `ncclProxyService()` | 处理连接建立请求（RPC 服务器） |
| Progress Thread | `ncclProxyProgress()` | 执行实际网络 I/O（isend/irecv） |
| UDS Service Thread | `ncclProxyServiceUDS()` | cuMem API 的 fd 传递 |

## 4. Bootstrap 阶段交换的 Proxy 信息

在 Proxy 线程创建之前，Bootstrap 阶段会通过 AllGather 交换所有 rank 的 Proxy 连接信息。这是为了让任意 rank 能够连接到其他 rank 的 Service Thread。

### 4.1 交换了什么信息

```
┌─────────────────────────────────────────────────────────────────┐
│              Bootstrap AllGather 交换的 Proxy 信息               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   peerProxyAddresses[]     每个 rank 的 Service Thread 监听地址  │
│   ─────────────────────    (IP + Port)                          │
│                            其他 rank 连接时使用                   │
│                                                                 │
│   peerProxyAddressesUDS[]  每个 rank 的 UDS 标识符               │
│   ─────────────────────    (pidHash)                            │
│                            本地进程间 cuMem fd 传递使用           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**注意**：Bootstrap 阶段不交换 Progress Thread 的任何信息，因为 Progress Thread 是惰性创建的。

### 4.2 这些信息如何被使用

当 Rank 0 需要和 Rank 1 建立网络通信时：

```
Rank 0                                              Rank 1
  │                                                   │
  │  1. 查 peerProxyAddresses[1]                      │
  │     得到 Rank 1 的 Service Thread 监听地址         │
  │                                                   │
  │  2. TCP connect ─────────────────────────────────►│ Service Thread accept
  │                                                   │
  │  3. 发送 ncclProxyMsgInit ───────────────────────►│ 分配 connection
  │                                                   │
  │  ◄────────────────────────────────────────────────│ 返回 connection 指针
```

### 4.3 代码流程

```
bootstrapInit()
    │
    ▼
createListenSocket()                    // 创建 Proxy 监听 socket
    │                                   // 得到本 rank 的监听地址
    ▼
ringAllInfo()  [bootstrap.cc:864]       // AllGather 交换所有 rank 的信息
    │
    │  交换: peerProxyAddresses[]
    │  交换: peerProxyAddressesUDS[]
    │
    ▼
ncclProxyInit()  [proxy.cc:1845]        // 保存这些地址到 proxyState
    │
    │  proxyState->listenSock = sock
    │  proxyState->peerAddresses = peerProxyAddresses
    │  proxyState->peerAddressesUDS = peerProxyAddressesUDS
    │
    │  ❌ 不创建任何线程
```

## 5. 线程创建时序

Bootstrap 阶段只交换了连接信息（见第 4 节），没有创建任何线程。线程的创建发生在后续阶段。

```
阶段 1: Init 阶段（bootstrap 之后）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
ncclProxyCreate()  [init.cc:1462 → proxy.cc:1860]
    │
    │  ✅ 创建 Service Thread (ncclProxyService)
    │  ✅ 创建 UDS Service Thread (ncclProxyServiceUDS)


阶段 2: 首次建立 Transport 连接时
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
proxyConnInit()  [proxy.cc:1422]
    │
    │  检查: connection->tcomm->proxyProgress != NULL ?
    │
    └── 如果是网络 transport：
            │
            ▼
        proxyProgressInit()  [proxy.cc:1366]
            │
            │  - 创建共享内存 ops pool
            │
            ▼
        ncclProxyProgressCreate()  [proxy.cc:1017]
            │
            │  ✅ 创建 Progress Thread (ncclProxyProgress)
```

这样设计的原因：
- Bootstrap 阶段只需要交换地址信息，不需要网络 I/O 代理
- 并非所有 transport 都需要 proxy（比如 NVLink 直连），只有真正需要时才创建 Progress Thread
- 一旦创建，线程会持续运行直到 `ncclCommDestroy()`

## 6. 线程销毁流程

当用户调用 `ncclCommDestroy()` 时，Proxy 线程需要按正确的顺序停止和清理。

```
ncclCommDestroy()
    │
    ▼
ncclProxyStop()  [proxy.cc:1896]
    │
    │  1. 发送 ncclProxyMsgStop 到自己的 Service Thread
    │     (通过 peerProxyAddresses[myRank] 连接)
    │
    │  2. 设置 proxyState->stop = 1
    │     (通知 UDS Service Thread)
    │
    ▼
Service Thread 收到 Stop 消息
    │
    │  1. 设置 stop = PROXY_STOP
    │  2. 等待所有 peer 连接断开 (npeers == 0)
    │  3. 调用 ncclProxyProgressDestroy()
    │         │
    │         ▼
    │     Progress Thread
    │         │
    │         │  收到 stop = 1
    │         │  退出主循环
    │         │
    │         └── pthread_join 等待结束
    │
    │  4. 释放 connectionPool
    │  5. 关闭 listenSock
    │  6. 退出
    │
    ▼
UDS Service Thread
    │
    │  检查 proxyState->stop
    │  退出
    │
    ▼
commFree()  [init.cc:292]
    │
    │  pthread_join(proxyState->thread)       // 等待 Service Thread
    │  pthread_join(proxyState->threadUDS)    // 等待 UDS Service Thread
    │
    ▼
ncclProxyDestroy()  [proxy.cc:1940]
    │
    │  释放 peerAddresses
    │  释放 peerSocks
    │  释放 proxyState
```

关键点：
- **顺序很重要**：Progress Thread 必须在 Service Thread 之前结束，因为 Service Thread 负责调用 `ncclProxyProgressDestroy()`
- **优雅停止**：通过发送 `ncclProxyMsgStop` 消息而不是直接 kill 线程，确保正在进行的操作能完成
- **资源清理**：connectionPool 等资源在 Service Thread 退出前释放，proxyState 在最后由 `ncclProxyDestroy()` 释放

## 7. 核心数据结构

### 7.1 ncclProxyOp（操作描述）

由 Main Thread 生成，描述一个要执行的网络操作：

```c
// proxy.h:55-110
struct ncclProxyOp {
  struct ncclProxyConnection* connection;  // 使用哪个连接
  ssize_t nbytes;           // 总字节数
  uint64_t opCount;         // 操作序号（用于聚合）
  int nsteps;               // 需要多少步
  size_t chunkSize;         // 每个 chunk 大小
  size_t sliceSize;         // 每个 slice 大小
  uint8_t pattern;          // ncclPatternRing, Send, Recv 等
  uint8_t protocol;         // LL, LL128, Simple
  int peer;                 // 对端 rank
  uint8_t* sendbuff;        // 发送 buffer
  uint8_t* recvbuff;        // 接收 buffer
};
```

### 7.2 ncclProxyArgs（执行参数）

Progress Thread 实际使用的结构，可以聚合多个 channel 的操作：

```c
// proxy.h:164-199
struct ncclProxyArgs {
  struct ncclProxySubArgs subs[NCCL_PROXY_MAX_SUBS];  // 子操作数组
  proxyProgressFunc_t progress;  // 进度函数（来自 transport）
  int nsubs;                     // 子操作数量
  int state;                     // Ready → Progress → None
  uint8_t pattern;
  uint8_t protocol;
};
```

### 7.3 ncclProxySubArgs（子操作状态）

跟踪每个 channel 的 I/O 进度：

```c
// proxy.h:119-162
struct ncclProxySubArgs {
  int channelId;
  int nsteps;           // 总步数
  ssize_t nbytes;       // 总字节数
  int peer;             // 对端

  // 进度追踪
  uint64_t posted;      // 已 post 的步数
  uint64_t transmitted; // 已发送/接收的步数
  uint64_t done;        // 已确认完成的步数

  void* requests[NCCL_STEPS];  // 网络请求句柄
};
```

### 8.2 Progress Thread 主循环

```c
// proxy.cc:939-998
void* ncclProxyProgress(void *proxyState_) {
  do {
    int idle = 1;

    // 1. 推进活跃操作
    progressOps(proxyState, state, state->active, &idle);

    // 2. 如果空闲或定期检查，获取新操作
    if (idle || 定期检查) {
      ncclProxyGetPostedOps(proxyState, &added);
      if (added == 0) {
        sched_yield();  // 让出 CPU
      }
    }

  } while (!stop && !abort);
}
```

### 8.3 progressOps - 推进操作

```c
// proxy.cc:752-774
static ncclResult_t progressOps(...) {
  struct ncclProxyArgs* op = opStart;
  while (op) {
    // 调用 transport 提供的 progress 函数
    ncclResult_t ret = op->progress(proxyState, op);

    if (op->state == ncclProxyOpNone) {
      // 操作完成，移除
      removeOp(state, &op, &prevOp);
    } else {
      op = op->next;
    }
  }
}
```

### 8.4 sendProxyProgress - 发送进度函数

网络 transport 的核心函数（`net.cc:1217`）：

```c
static ncclResult_t sendProxyProgress(struct ncclProxyState* proxyState,
                                       struct ncclProxyArgs* args) {
  for (int s = 0; s < args->nsubs; s++) {
    struct ncclProxySubArgs* sub = args->subs + s;

    // 阶段 1: Post buffer 给 GPU
    if (sub->posted < sub->nsteps && sub->posted < sub->done + NCCL_STEPS) {
      *sendHead = sub->base + sub->posted - NCCL_STEPS;
      sub->posted += sliceSteps;
    }

    // 阶段 2: 检查 GPU 是否写完，发送到网络
    if (sub->transmitted < sub->posted) {
      if (*recvTail > sub->base + sub->transmitted) {
        ncclNet->isend(comm, buff, size, mhandle, &request);
        sub->transmitted += sliceSteps;
      }
    }

    // 阶段 3: 检查网络发送是否完成
    if (sub->done < sub->transmitted) {
      ncclNet->test(request, &done, &size);
      if (done) {
        sub->done += sliceSteps;
        *sendHead = sub->base + sub->done;
      }
    }
  }

  if (args->done == args->nsubs) {
    args->state = ncclProxyOpNone;
  }
}
```

## 9. 完整示例：2-Rank Ring Send

假设 Rank 0 要通过 Ring 发送 32KB 数据给 Rank 1：
- `NCCL_STEPS = 8`
- `sliceSteps = 1`
- `sliceSize = 4KB`
- `nsteps = 8`（32KB / 4KB）

# 写文档心得

## 核心教训

### 1. 先说"是什么"，再说"怎么做"

**错误示范**：
```
Simple Protocol 的核心设计
├── 环形缓冲区机制
└── 流控机制
```
直接跳到设计细节，读者会困惑：这到底是个什么东西？

**正确做法**：
```
为什么需要 Simple Protocol？
    ↓
Simple Protocol 是什么？ ← 必须有这一节！
├── 它在通信流程中的位置
├── 核心思想是什么
└── 为什么能做到高带宽（机制层面）
    ↓
Simple Protocol 的核心设计
└── 具体的实现机制
```

**关键点**：
- "是什么"这一节要讲清楚**本质**，不是讲特性
- 要说明它在整个系统中的**位置和角色**
- 要解释它的**核心思想**（如：大块传输 + 粗粒度同步）
- 要说明为什么这个思想能达到目标（如：为什么能高带宽）

### 2. 对比不是讲解工具

**错误示范**：
在讲 Simple Protocol 的前面部分就列出与 LL、LL128 的对比表格，列出各种特性差异。

**问题**：
- 读者还不理解 Simple Protocol 本身，怎么理解对比？
- 特性列表（如"带宽高、延迟低"）是结论，不是解释
- 看起来"花里胡哨"但对理解没帮助

**正确做法**：
- 对比只能出现在**讲清楚全部内容之后**
- 对比用于**总结和巩固**，不用于引入和讲解
- 如果要对比，要对比**机制的本质差异**，不是列特性

**例外**：
- 如果对比是为了说明"为什么需要这个东西"（动机），可以出现在前面
- 但这种对比要聚焦在**问题域**，不是实现细节

### 3. 避免特性列表式讲解

**错误示范**：
```
Simple Protocol 的优势：
- 高带宽
- 实现简单
- 内存可控
```

**问题**：
- 这些是结论，不是解释
- 读者看完还是不知道"为什么高带宽"

**正确做法**：
```
为什么能做到高带宽？
├── GPU memcpy 对大块内存效率高（解释原因）
├── 流水线效应（解释机制）
└── 同步开销最小化（解释设计）
```

**关键**：每个点都要**深入解释机制**，不是罗列结论。

### 4. 层次要清晰

**好的文档结构**：
```
1. 为什么需要？（动机）
2. 是什么？（本质）
3. 怎么做？（机制）
4. 例子（串联理解）
5. 总结（巩固）
```

**注意**：
- 不要在"是什么"里讲实现细节
- 不要在"怎么做"之前就给例子
- 例子应该是前面所有概念的**串联和验证**

### 5. 类比要恰当

**好的类比**：
- 环形缓冲区 = 旋转寿司店的传送带
- 清晰、直观、贴切

**坏的类比**：
- 过多的类比（每个概念都类比）
- 牵强的类比（为了类比而类比）

**原则**：
- 只在核心概念上用类比
- 类比后要立即回到技术细节
- 不要让类比成为负担

### 6. 口语化但不啰嗦

**好的过渡**：
```
现在问题来了：发送方怎么知道某个 slot 是空的？

让我们深入一点，看看为什么这种方式能榨干硬件带宽。

你可能注意到的关键点：
```

**坏的过渡**：
```
接下来让我们来看一下...
现在我们来学习一下...
下面我将为大家讲解...
```

**原则**：
- 用问题引导，不用"我将讲解"
- 过渡要自然，不要模板化
- 保持对话感，但不要啰嗦

### 7. 代码引用要精准

**原则**：
- 只展示**正在讲解的部分**的代码
- 其他代码用 GitHub 链接引用
- 代码片段要有注释或后续的"翻译"

**示例**：
```c
// 只展示核心逻辑
while (tail - head >= 8) {
    head = loadFromGPU1();
}
```

然后用文字解释：
```
这个 while 循环的意思是：如果我已经"绕圈"回来了（写满了 8 个 slot），
就要等接收方读走一些数据。
```

### 8. 图示的使用

**原则**：
- 用 `<ImageDescription>` 标签描述图的内容
- 描述要**详细、精确**，包含所有关键元素
- 说明图要表达的**关系**，不只是元素列表

**好的图示描述**：
```
<ImageDescription>
序列图展示 GPU 0 和 GPU 1 的交互：
1. GPU 0: waitPeer（检查 head >= tail - 8?）
2. GPU 0: 写数据到 GPU 1 的 ring buffer（1MB，通过 NVLink）
3. GPU 0: fence（确保写入完成）
4. GPU 0: 更新 tail = 1
5. GPU 1: waitPeer（轮询 tail，发现 tail = 1 > head = 0）
6. GPU 1: 读数据从本地 ring buffer
7. GPU 1: 更新 head = 1
8. 箭头标注时间顺序和数据流方向
</ImageDescription>
```

### 9. 关键洞察要提炼

**每个重要章节都要有"关键洞察"**：

**好的洞察**：
```
关键洞察：高带宽的秘诀不是"传得快"，而是"少停顿"。
Simple Protocol 通过大块传输和粗粒度同步，把同步开销降到最低。
```

**坏的洞察**：
```
关键洞察：Simple Protocol 使用环形缓冲区。
```

**原则**：
- 洞察要提炼**本质**，不是重复事实
- 洞察要有**启发性**，让读者"恍然大悟"
- 洞察要**简短**，一两句话

- [ ] 有没有避免过早对比？
- [ ] 有没有避免特性列表？
- [ ] 例子是否串联了前面的概念？
- [ ] 过渡是否自然？
- [ ] 代码片段是否精炼？
- [ ] 图示描述是否清晰？
- [ ] 有没有提炼关键洞察？

## 针对 Simple Protocol 系列的特殊注意

### 避免的陷阱

1. **不要过早讲 DirectSend/NetReg 等复杂场景**
   - 第一遍只讲基础路径
   - 复杂场景用注释简单说明即可

2. **不要深入 Host 侧逻辑**
   - 聚焦 Device 侧（GPU kernel）
   - Proxy、Task/Work 调度等不在范围内

3. **不要陷入代码细节**
   - 概念系列：讲思想和机制
   - 代码系列：才逐行分析

### 必须讲清楚的点

1. **指针方向性**
   - buffs: Local for recv, remote for send
   - tail: Local for recv, remote for send
   - head: Local for send, remote for recv
   - 这个很容易混淆，要反复强调

2. **step 的语义**
   - step 不是 slot 索引
   - step 是一个递增的计数器
   - slot = step % 8

3. **wait 和 post 的不对称性**
   - wait 在传输前
   - post 在传输后
   - 但 step 更新的时机不同

## 总结

写技术文档的核心：**站在读者的角度，从不懂到懂的路径是什么？**

不要假设读者知道任何东西。不要跳跃。不要用对比和列表代替解释。

每一步都要问自己：**读者看到这里，会不会困惑？**

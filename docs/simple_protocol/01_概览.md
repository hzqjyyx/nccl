# NCCL Simple Protocol 概览

## 这篇文档要解决什么问题？

当你第一次接触 NCCL 时，可能会看到代码里有三种协议：LL、LL128、Simple。你可能会困惑：

- 为什么需要三种协议？一种不够吗？
- Simple Protocol 的"Simple"是什么意思？
- **它到底是个什么东西？**

这篇文档会从最根本的问题开始：Simple Protocol **本质上是什么**？它在 GPU 通信流程中扮演什么角色？为什么它能提供高带宽？

读完这篇文档，你会理解 Simple Protocol 的核心思想，并建立起对它的整体认知。

**说明**：为了聚焦核心概念，我们只讨论最常见的场景：
- 一个进程对应一个 GPU
- 使用 Ring 算法进行集合通信
- GPU 之间通过 NVLink 或 PCIe 直接连接（节点内通信）

---

## 为什么需要不同的协议？

在回答"Simple Protocol 是什么"之前，我们先理解为什么 NCCL 需要多种协议。

### GPU 通信的两难：带宽 vs 延迟

想象你要从 GPU 0 向 GPU 1 发送数据。有两个关键指标：

- **延迟**：发起传输到第一个字节到达的时间
- **带宽**：单位时间能传输的数据量

这两个指标往往是矛盾的。举个例子：

**场景 A：发送 1KB 数据**
- 如果你每次只发送 1KB，立即通知对方，延迟很低
- 但每次传输都有固定开销（设置 DMA、同步等），带宽利用率低

**场景 B：发送 100MB 数据**
- 如果你把 100MB 打包成一大块传输，带宽很高
- 但启动时间长，如果对方只需要前 1KB，也要等整个传输完成

不同的应用对这两个指标的需求不同。在深度学习训练中：

- **小消息**（如 activations、小的梯度片段）：需要低延迟，数据尽快到达
- **大消息**（如完整的模型梯度、参数同步）：需要高带宽，能传得快就行

这就是为什么 NCCL 提供了三种协议：
- **LL**：优化延迟，用于小消息
- **LL128**：中间方案
- **Simple**：优化带宽，用于大消息

现在问题来了：Simple Protocol 是如何做到高带宽的？

---

## Simple Protocol 是什么？

### 它在通信流程中的位置

让我们先明确 Simple Protocol 在整个通信流程中的位置。

当你调用 `ncclAllReduce` 时，在 GPU kernel 内部，会调用一系列函数来完成实际的数据传输。Simple Protocol 就是 **GPU kernel 里执行数据传输和同步的那套函数**。

<ImageDescription>
调用栈示意图：
用户代码: ncclAllReduce()
    ↓
Host 端: 创建 Task，准备参数
    ↓
Kernel 启动: ncclKernel<<<...>>>
    ↓
Device 端: allReduceRing()  ← 算法层
    ↓
Device 端: Primitives 类   ← Simple Protocol 在这里
    ↓
实际操作: memcpy, fence, 更新计数器
</ImageDescription>

**关键点**：Simple Protocol 不是某个单独的模块，而是 `Primitives` 类提供的一组函数，包括：
- `waitPeer()`: 等待对端准备好
- `postPeer()`: 通知对端完成
- `genericOp()`: 执行数据传输

这些函数封装了"如何在两个 GPU 之间传输数据"的所有细节。

### 核心思想：大块传输 + 粗粒度同步

现在让我们理解 Simple Protocol 的本质。

假设你要从 GPU 0 发送 64MB 数据到 GPU 1。有两种方式：

**方式 A：细粒度同步（LL 协议的做法）**
```
把 64MB 分成很多小块（比如每块 128 字节）
for (每个小块):
    发送数据
    写一个 flag 告诉对方"这块数据好了"
    等待对方确认
```

这样做的好处是延迟低（对方可以立即开始处理第一块），但问题是：
- 同步次数太多（64MB / 128B = 50 万次同步！）
- 每次同步都有开销
- 带宽利用率低

**方式 B：大块传输 + 粗粒度同步（Simple 协议的做法）**
```
把 64MB 分成几大块（比如每块 2MB）
for (每个大块):
    发送整块数据（2MB 的连续 memcpy）
    更新一个计数器告诉对方"又完成一块了"
```

这样做的好处是：
- 同步次数少（64MB / 2MB = 32 次同步）
- GPU memcpy 对大块连续内存效率最高
- 可以形成流水线（下一块开始传时，上一块还在被处理）

**这就是 Simple Protocol 的本质：用大块的、连续的内存传输，减少同步频率，让 GPU 的内存带宽得到充分利用。**

### 为什么能做到高带宽？

让我们深入一点，看看为什么这种方式能榨干硬件带宽。

#### 1. GPU memcpy 的特性

GPU 的内存拷贝（通过 DMA）有个特点：**对大块连续内存的效率远高于小块内存**。

原因是：
- DMA 引擎有启动开销
- 连续内存可以充分利用内存总线的突发传输（burst mode）
- 大块传输让 TLB、cache 的开销被摊薄

一个具体的数字：
- 传输 2MB 连续内存：可以达到接近理论带宽（如 NVLink 的 300GB/s）
- 传输 512 个 4KB 小块：可能只有理论带宽的 50%

#### 2. 流水线效应

Simple Protocol 使用**环形缓冲区**（我们稍后会详细讲），这带来了流水线效应：

```
时间轴：
t0: GPU 0 写 slot 0 | GPU 1 空闲
t1: GPU 0 写 slot 1 | GPU 1 读 slot 0
t2: GPU 0 写 slot 2 | GPU 1 读 slot 1
...
```

发送方和接收方可以同时工作，互不干扰。这就像工厂的流水线，每个环节专注于自己的任务。

#### 3. 同步开销最小化

Simple Protocol 只用**两个 64-bit 计数器**进行同步：
- `tail`: 发送方写到哪里了
- `head`: 接收方读到哪里了

没有复杂的 flag、没有细粒度的确认。每传输一个 slot（比如 2MB），只需要更新一次计数器。

**关键洞察**：高带宽的秘诀不是"传得快"，而是"少停顿"。Simple Protocol 通过大块传输和粗粒度同步，把同步开销降到最低，让 GPU 把时间花在数据传输上，而不是花在等待和握手上。

### 为什么叫"Simple"？

现在"Simple"这个名字应该很清楚了：

- **不是说实现简单**（虽然相比 LL 确实简单一些）
- 而是说**同步机制简单**：只有两个计数器，没有复杂的 flag 和状态管理

相比之下，LL 协议的每个数据元素都带一个 flag，需要处理 flag 的环绕、清理等复杂逻辑。Simple 协议放弃了这些，用最直接的方式：**大块传，数数就行**。

## Simple Protocol 的核心机制

理解了"是什么"和"为什么"，现在我们看看"怎么做"。

Simple Protocol 依赖两个核心机制：

### 1. 环形缓冲区：数据传输的管道

为了让发送方和接收方能流水线式地工作，我们需要一个"缓冲区"。但缓冲区大小不能无限，所以用**环形缓冲区**。

想象一个旋转寿司店的传送带：

<ImageDescription>
一个环形传送带，分成 8 个格子（编号 0-7）。
- 厨师（发送方）在一端放寿司
- 顾客（接收方）在另一端取寿司
- 传送带循环转动，当格子 7 用完后，回到格子 0
- 如果 8 个格子都满了，厨师要等
- 如果所有格子都空，顾客要等
</ImageDescription>

在 NCCL 中，这个环形缓冲区有 **8 个 slot**（定义在 [device.h:24](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L24)）：

```c
#define NCCL_STEPS 8
```

每个 slot 的大小是 `buffSizes[NCCL_PROTO_SIMPLE] / NCCL_STEPS`。比如，如果总缓冲区是 16MB，每个 slot 就是 2MB。

发送方和接收方各自维护一个索引，模 8 运算就能找到当前该用哪个 slot：

```c
int slotToWrite = (tail % 8);
int slotToRead = (head % 8);
```

**关键点**：环形缓冲区让发送方可以"跑在前面"。只要接收方不是太慢（落后不超过 8 个 slot），发送方就可以一直发，不用等。

### 2. 流控机制：用计数器协调收发

有了环形缓冲区，问题来了：**发送方怎么知道某个 slot 是空的？接收方怎么知道某个 slot 有数据？**

Simple Protocol 的答案是：**两个计数器**。

<ImageDescription>
两个 GPU 的内存布局对比：
- GPU 0 内存：有 head 计数器（本地），有 tail 计数器（本地）
- GPU 1 内存：有 head 计数器（本地），有 tail 计数器（本地）
- GPU 0 通过 P2P 可以读取 GPU 1 的 head
- GPU 1 通过 P2P 可以读取 GPU 0 的 tail
- 箭头标注：发送方写 tail，读对方的 head；接收方写 head，读对方的 tail
</ImageDescription>

**发送方的逻辑**（GPU 0）：
```
我现在要写 tail 位置对应的 slot
但这个 slot 可能还有上次的旧数据没被读走
我需要确认：接收方已经读到 head 了，而且 tail - head < 8
否则就等待
```

**接收方的逻辑**（GPU 1）：
```
我现在要读 head 位置对应的 slot
但发送方可能还没写到这里
我需要确认：发送方已经写到 tail 了，而且 head < tail
否则就等待
```

这就是流控的全部逻辑。我们会在后续文档（《流控机制》）中详细分析代码实现。

**关键洞察**：这两个计数器形成了一个"生产者-消费者"模型。发送方是生产者，接收方是消费者。8 个 slot 的缓冲区就是它们之间的队列。

## 一个端到端的例子

现在让我们看一个具体场景，把所有概念串起来。

### 场景设置

**任务**：GPU 0 向 GPU 1 发送 1MB 数据

**环境**：
- 环形缓冲区总大小：16MB
- 每个 slot：16MB / 8 = 2MB
- 初始状态：`head = 0, tail = 0`（刚启动）

### 步骤 1：发送方准备写入

GPU 0 的 kernel 调用 `waitPeer` 函数：

```c
// 我要写 slot 0
int slot = tail % 8;  // 0 % 8 = 0

// 检查接收方是否读走了 slot 0 的旧数据
// （如果 tail - head >= 8，说明我已经"绕圈"回来了，slot 0 还有旧数据）
while (tail - head >= 8) {
    head = loadFromGPU1();  // 轮询读取 GPU 1 的 head
}

// 通过检查，可以写入
```

在我们的例子中，`tail = 0, head = 0`，所以 `tail - head = 0 < 8`，**可以写**。

### 步骤 2：发送方写数据

GPU 0 计算出 slot 0 的地址，然后用多个线程并行拷贝数据：

```c
char* dest = ringBuffer + slot * slotSize;
// 注意：ringBuffer 指向 GPU 1 的内存（通过 P2P 映射）

// 多个线程并行拷贝 1MB 数据
memcpy(dest, src, 1MB);
```

数据通过 NVLink 直接写入 GPU 1 的内存。

### 步骤 3：发送方通知接收方

数据写完后，GPU 0 调用 `postPeer` 函数：

```c
// 确保数据写入完成（内存屏障）
fence_acq_rel_sys();

// 更新 tail（告诉接收方："我写完 slot 0 了"）
tail = tail + 1;  // 0 -> 1
```

这个 `tail` 在 GPU 0 的内存中，GPU 1 可以通过 P2P 读取。

### 步骤 4：接收方发现新数据

GPU 1 的 kernel 也在调用 `waitPeer`，轮询 GPU 0 的 tail：

```c
// 我要读 slot 0
int slot = head % 8;  // 0 % 8 = 0

// 检查发送方是否写好了 slot 0
while (head >= tail) {
    tail = loadFromGPU0();  // 轮询读取 GPU 0 的 tail
}

// 发现 tail = 1，而 head = 0，说明 slot 0 有数据了
```

### 步骤 5：接收方读数据

GPU 1 从本地内存读取 slot 0 的数据：

```c
char* src = ringBuffer + slot * slotSize;
// 注意：这次 ringBuffer 指向 GPU 1 自己的内存

// 读取并处理 1MB 数据
process(src, 1MB);
```

### 步骤 6：接收方释放 slot

处理完后，GPU 1 更新 head：

```c
head = head + 1;  // 0 -> 1
```

这告诉 GPU 0："我读完 slot 0 了，你可以再用它了"。

### 完整的时序

<ImageDescription>
序列图展示 GPU 0 和 GPU 1 的交互：
1. GPU 0: waitPeer（检查 head >= tail - 8?）
2. GPU 0: 写数据到 GPU 1 的 ring buffer（1MB，通过 NVLink）
3. GPU 0: fence（确保写入完成）
4. GPU 0: 更新 tail = 1
5. GPU 1: waitPeer（轮询 tail，发现 tail = 1 > head = 0）
6. GPU 1: 读数据从本地 ring buffer
7. GPU 1: 更新 head = 1
8. 循环继续...
</ImageDescription>

**你可能注意到的关键点**：

1. **数据零拷贝**：GPU 0 直接写入 GPU 1 的内存，没有中间缓冲
2. **异步性**：GPU 0 写完就继续，不等 GPU 1 读完
3. **轮询同步**：双方通过轮询对方的计数器来同步，不用中断

这就是 Simple Protocol 的工作方式。

## 总结

让我们回顾一下 Simple Protocol 的核心思想：

### Simple Protocol 是什么？

它是 **GPU kernel 里执行大块数据传输的一套函数**，通过：
- 大块连续的内存拷贝（充分利用 GPU 内存带宽）
- 粗粒度的计数器同步（减少同步开销）
- 环形缓冲区的流水线（让收发双方并行工作）

来实现**高带宽**的数据传输。

### 为什么叫"Simple"？

因为它的**同步机制简单**：只用两个计数器（head 和 tail），没有复杂的 flag 管理。

### 核心机制

1. **环形缓冲区**：8 个 slot 循环使用，形成流水线
2. **流控计数器**：tail（写到哪）和 head（读到哪），通过 P2P 互相可见

### 适用场景

大消息（通常 > 1MB）的集合通信，如梯度同步、参数更新等。

# 02 128B 行与内存组织

上一章我们知道了 LL128 的核心想法：把 LL 的 16B 行放大到 128B，用单个 flag 替代双 flag，再靠 Flag Thread 维持秩序。但这个"128B
行"到底长什么样？环形缓冲区怎么切分？warp 每轮要处理多少数据？这些问题直接决定了你能否在脑海里建立起 LL128 的内存模型。

这一章的任务就是回答：**LL128 如何在内存中组织数据，以及这些组织方式如何支撑起"单 flag + 高带宽"的承诺**。

## 1. 从全景到细节：四层嵌套结构

在深入 128B 行之前，我们先建立一个自顶向下的视角。LL128 的内存组织可以看作四层嵌套：

```
环形缓冲区（Ring Buffer）
  ↓ 包含 NCCL_STEPS 个 slot
Step（流控单位）
  ↓ 每个 step 占据 stepSize 字节
128B Line（传输与验证单位）
  ↓ 每行 16 个 uint64_t
Element（用户数据）
  ↓ sizeof(T)
```

**为什么要这样分层？** 因为每一层解决不同的问题：

- **环形缓冲区**：让发送方和接收方可以流水线工作，不必等一批数据完全消费完才能发下一批；
- **Step**：提供粗粒度的流控，防止发送方"绕圈"覆盖还未被读取的数据；
- **128B Line**：LL128 真正的创新点——传输和验证的最小单位，每行末尾带一个 flag；
- **Element**：用户视角的数据，可能是 float、half、int 等不同类型。

现在的问题是：这四层之间如何换算？warp 一次循环要处理多少行、多少元素？让我们逐层拆解。

## 2. 128B 行的布局：15 个数据 + 1 个 flag

### 2.1 LL 的"双 flag"回顾

在 LL 协议里，每 16B 为一行，布局是这样的（见
[device.h:88-101](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L88-L101)）：

```c
union ncclLLFifoLine {
  struct {
    uint32_t data1;
    uint32_t flag1;
    uint32_t data2;
    uint32_t flag2;
  };
  uint64_t v[2];
};
```

每 8B 数据就跟一个 4B 的 flag，所以有效带宽只有 50%。为什么要这样？因为 LL 需要用两个 flag 来保证"数据先到、flag
后到"的因果关系，从而避免昂贵的内存屏障。

### 2.2 LL128 的改进：单 flag 后置

LL128 把行扩大到 128B，并且只在**行末**放一个 flag。具体定义在
[device.h:105-107](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L105-L107)：

```c
#define NCCL_LL128_LINESIZE 128
#define NCCL_LL128_LINEELEMS (NCCL_LL128_LINESIZE/sizeof(uint64_t))  // 128/8 = 16
#define NCCL_LL128_DATAELEMS (NCCL_LL128_LINEELEMS-1)                // 16-1 = 15
```

换句话说，一条 128B 行包含：

```
[data0][data1][data2]...[data14][flag]
  ↑                        ↑       ↑
  15 个 uint64_t 数据      最后一个 uint64_t 是 flag
```

**有效带宽**：15/16 ≈ 93.75%，远高于 LL 的 50%。

### 2.3 为什么 flag 要放在最后？

你可能会问：为什么不把 flag 放在开头？答案藏在
[prims_ll128.h:74-82](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L74-L82) 的 `postSend()` 里：

```c
inline __device__ void postSend() {
  if (sendConnTailPtr) {
#if __CUDA_ARCH__ >= 900
    __threadfence_system();
#else
    __threadfence();
#endif
    *sendConnTailPtr = sendConnTail += 1;
  }
}
```

注意 `__threadfence()` 的位置：它在更新 tail 之前执行。这个 fence 保证了**所有之前的写入（包括数据和 flag）都对远端可见**。如果
flag 在数据之前，接收方可能看到 flag 已更新，但数据还没到——这就违反了因果性。

**关键洞察：flag 后置 + threadfence = 因果保证**。接收方只要看到 flag 匹配，就能确信前面 15 个 uint64_t 的数据已经完整到达。

## 3. 环形缓冲区与 Step 流控

### 3.1 缓冲区大小的计算

LL128 的环形缓冲区默认大小由 [init.cc:698](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/init.cc#L698) 定义：

```c
#define DEFAULT_LL128_BUFFSIZE (NCCL_LL128_ELEMS_PER_THREAD*NCCL_LL128_MAX_NTHREADS*NCCL_STEPS*sizeof(uint64_t))
```

让我们拆解这个公式：

- `NCCL_LL128_ELEMS_PER_THREAD = 120`（见 
[device.h:110](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L110)）
- `NCCL_LL128_MAX_NTHREADS = 640`（见 [device.h:109](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L109)）
- `NCCL_STEPS = 8`（见 [device.h:24](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L24)）
- `sizeof(uint64_t) = 8`

所以默认大小 = 120 × 640 × 8 × 8 = 4,915,200 字节 ≈ 4.69 MB。

**为什么是这个值？** 因为它要能容纳 8 个 step 的数据，每个 step 要能让最多 640 个线程各自处理 120 个
uint64_t。这个设计保证了即使在最大线程配置下，流水线也不会因为缓冲区太小而卡住。

### 3.2 Step 的语义

环形缓冲区被切分成 `NCCL_STEPS = 8` 个 slot，每个 slot 的大小是：

```c
stepSize = buffSizes[NCCL_PROTO_LL128] / NCCL_STEPS
```

**Step 不是 slot 索引，而是一个递增的计数器**。当你看到 `recvStep[i] = 10` 时，它表示"这是第 10 轮传输"，而不是"使用 slot
10"。真正的 slot 索引通过取模得到（见
[prims_ll128.h:44-45](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L44-L45)）：

```c
inline __device__ int recvOffset(int i) { return (recvStep[i]%NCCL_STEPS)*stepSize; }
inline __device__ int sendOffset(int i) { return (sendStep[i]%NCCL_STEPS)*stepSize; }
```

**为什么要用递增计数器而不是直接用 slot 索引？** 因为 step 还承担了 flag 的角色。在 LL128 里，flag 的值就是 `step+1`（见
[prims_ll128.h:48-49](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L48-L49)）：

```c
inline __device__ uint64_t recvFlag(int i) { return recvStep[i]+1; }
inline __device__ uint64_t sendFlag(int i) { return sendStep[i]+1; }
```

这样，每轮传输的 flag 都不同，接收方可以通过比对 flag 来判断数据是否是"这一轮"的新数据，而不是上一轮的残留。

### 3.3 流控的工作方式

发送方在写入之前会调用 `waitSend()`（见
[prims_ll128.h:57-69](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L57-L69)）：

```c
inline __device__ void waitSend(int nbytes) {
  if (sendConnHeadPtr) {
    int spins = 0;
    while (sendConnHeadCache + NCCL_STEPS < sendConnHead + 1) {
      sendConnHeadCache = *sendConnHeadPtr;
      if (checkAbort(abort, 1, spins)) break;
    }
    // ...
    sendConnHead += 1;
  }
}
```

这个循环的意思是：**如果我的 sendConnHead 已经比对方的 head 超前了 NCCL_STEPS 
轮，就要等对方读走一些数据**。换句话说，发送方最多只能"领先"接收方 8 个 step，防止绕圈覆盖。

## 4. WireWordPerSlice 与 DataEltPerSlice：warp 的工作单位

现在到了最关键的部分：**warp 每轮循环要处理多少数据？**

### 4.1 WireWordPerSlice：warp 处理的 uint64_t 总数

定义在 [prims_ll128.h:288](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L288)：

```c
static constexpr int WireWordPerSlice = WARP_SIZE*NCCL_LL128_SHMEM_ELEMS_PER_THREAD;
```

代入常量：

- `WARP_SIZE = 32`（见 [device.h:85](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L85)）
- `NCCL_LL128_SHMEM_ELEMS_PER_THREAD = 8`（见 
[device.h:112](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L112)）

所以 `WireWordPerSlice = 32 × 8 = 256` 个 uint64_t。

**这 256 个 uint64_t 对应多少条 128B 行？** 每条行有 16 个 uint64_t，所以 256 / 16 = **16 条行**。

### 4.2 DataEltPerSlice：用户数据元素个数

定义在 [prims_ll128.h:289](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L289)：

```c
static constexpr int DataEltPerSlice = (WireWordPerSlice - WireWordPerSlice/NCCL_LL128_LINEELEMS)*(sizeof(uint64_t)/sizeof(T));
```

让我们一步步拆解：

1. **减去 flag 占用**：`WireWordPerSlice / NCCL_LL128_LINEELEMS = 256 / 16 = 16`，这是 16 条行里 flag 的总数。
2. **得到数据 uint64_t 数**：`WireWordPerSlice - 16 = 256 - 16 = 240`。
3. **转换为用户元素数**：`240 × (sizeof(uint64_t) / sizeof(T)) = 240 × (8 / sizeof(T))`。

**举例**：如果 `T = float`（4 字节），则 `DataEltPerSlice = 240 × 2 = 480` 个 float。

**为什么要这样计算？** 因为 warp 在一轮循环里要写 16 条 128B 行，每条行有 15 个数据 uint64_t 和 1 个 flag uint64_t。总共 16 × 15 
= 240 个数据 uint64_t，对应 480 个 float。

### 4.3 验证：Flag Thread 的覆盖范围

回忆第一章提到的 Flag Thread：每 8 个线程挑出一个（`tid % 8 == 7`），所以一个 warp（32 线程）有 4 个 Flag Thread。

每个 Flag Thread 负责多少条行？16 条行 / 4 个 Flag Thread = **每个 Flag Thread 负责 4 条行**。

这个数字在代码里怎么体现？看 
[prims_ll128.h:274-276](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L274-L276) 的写入循环：

```c
#pragma unroll
for (int u=0; u<ELEMS_PER_THREAD; u+=2) {
  store128(ptr+u*WARP_SIZE, v[u], flagThread ? flag : v[u+1]);
}
```

这里 `ELEMS_PER_THREAD = NCCL_LL128_SHMEM_ELEMS_PER_THREAD = 8`，循环 4 次（u = 0, 2, 4, 6）。每次循环，Flag Thread 写入一个 
flag，所以 4 次循环 = 4 个 flag = 4 条行。

**关键洞察：WireWordPerSlice 和 DataEltPerSlice 的设计，让 warp 的 32 个线程刚好能协同处理 16 条 128B 行，其中 4 个 Flag Thread 
各自守护 4 条行的 flag。**

## 5. ncclProtoGrainSize：host 侧的切分粒度

在 device 侧，warp 以 `DataEltPerSlice` 为单位处理数据。但在 host 侧调度时，NCCL 需要知道"最小切分粒度"是多少，这就是 
`ncclProtoGrainSize` 的作用（见 
[device.h:309-314](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L309-L314)）：

```c
__host__ __device__ constexpr int ncclProtoGrainSize(int proto) {
  return proto == NCCL_PROTO_LL ? 16 :
        proto == NCCL_PROTO_LL128 ? 
WARP_SIZE*NCCL_LL128_SHMEM_ELEMS_PER_THREAD/NCCL_LL128_LINEELEMS*NCCL_LL128_DATAELEMS*sizeof(uint64_t) :
        proto == NCCL_PROTO_SIMPLE ? 512 :
        -1;
}
```

对于 LL128，代入常量：

```
32 × 8 / 16 × 15 × 8 = 16 × 15 × 8 = 1920 字节
```

**这个 1920 字节是什么？** 它是 warp 一轮处理的**数据字节数**（不含 flag）：

- warp 处理 16 条行
- 每条行有 15 个数据 uint64_t = 15 × 8 = 120 字节
- 总共 16 × 120 = 1920 字节

host 侧在拆分消息时，会以 1920 字节的倍数来切分，保证每个 warp 都能"吃饱"。

## 6. 从 Step 到 Offset：地址计算

现在我们知道了各层的大小，最后一个问题是：**给定一个 step 和 warp ID，如何计算出要写入的地址？**

### 6.1 Step 到 Slot 的映射

前面提到，slot 索引 = `step % NCCL_STEPS`。每个 slot 的起始地址是：

```c
int offset = (step % NCCL_STEPS) * stepSize;
```

### 6.2 Warp 内的偏移

在 [prims_ll128.h:297](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L297) 的 `GenericOp` 里：

```c
int wireOffset = WireWordPerSlice*warp + 2*wid;
```

这里 `warp` 是 warp 的索引（0, 1, 2, ...），`wid` 是线程在 warp 内的 lane ID（0-31）。

**为什么是 `2*wid`？** 因为每个线程每次用 `store128()` 写入 2 个 uint64_t（见 
[op128.h:16-18](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/op128.h#L16-L18)）：

```c
inline __device__ void store128(uint64_t* ptr, uint64_t v0, uint64_t v1) {
  asm volatile("st.volatile.global.v2.u64 [%2], {%0,%1};"
      :: "l"(v0), "l"(v1), "l"(ptr) : "memory");
}
```

`st.volatile.global.v2.u64` 是一条原子指令，一次写入 16 字节（2 个 uint64_t）。所以线程 0 写 offset 0-1，线程 1 写 offset 
2-3，以此类推。

### 6.3 多 warp 协同

如果有多个 warp，每个 warp 处理不同的数据段。在 
[prims_ll128.h:313-316](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L313-L316) 的循环里：

```c
wireOffset += WireWordPerSlice*nwarps;
srcPtr += DataEltPerSlice*nwarps;
dstPtr += DataEltPerSlice*nwarps;
nelem -= DataEltPerSlice*nwarps;
```

每轮循环后，所有 warp 一起前进 `nwarps` 个 slice，直到处理完所有数据。

## 7. 串联：一次传输的完整流程

让我们用一个具体例子串联所有概念。假设：

- 数据类型：`float`（4 字节）
- 要传输：2000 个 float
- 配置：1 个 warp（32 线程）

**Step 1：计算需要多少 slice**

`DataEltPerSlice = 480` 个 float，所以需要 ⌈2000 / 480⌉ = 5 个 slice。

**Step 2：计算需要多少字节**

每个 slice 对应 `WireWordPerSlice = 256` 个 uint64_t = 256 × 8 = 2048 字节。
5 个 slice = 5 × 2048 = 10240 字节。

**Step 3：waitSend 检查空间**

在 [prims_ll128.h:301](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L301)：

```c
if (SEND) waitSend(divUp(nelem, DataEltPerSlice)*WireWordPerSlice*sizeof(uint64_t));
```

代入：`divUp(2000, 480) × 256 × 8 = 5 × 2048 = 10240` 字节。

`waitSend()` 会轮询，直到当前 slot 有足够空间。

**Step 4：循环处理每个 slice**

warp 进入循环（[prims_ll128.h:306-317](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L306-L317)）：

- 第 1 轮：处理前 480 个 float，写入 16 条 128B 行
- 第 2 轮：处理接下来 480 个 float，写入 16 条行
- ...
- 第 5 轮：处理最后 80 个 float（不足一个 slice，但仍写入 16 条行，部分行只填充部分数据）

**Step 5：更新 step 并通知对端**

在 [prims_ll128.h:320-323](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L320-L323)：

```c
if (SEND) for (int i=0; i < MaxSend; i++) sendStep[i] += 1;
if (SEND) postSend();
if (RECV) for (int i=0; i < MaxRecv; i++) recvStep[i] += 1;
if (RECV) postRecv();
```

`sendStep` 递增，`postSend()` 执行 fence 并更新 tail，通知接收方"这一轮数据已就绪"。

## 8. 关键洞察

- **128B 行 = 15 个数据 uint64_t + 1 个 flag uint64_t**，有效带宽 93.75%，flag 后置保证因果性。
- **环形缓冲区被切分成 8 个 step**，每个 step 的大小由 `buffSizes[NCCL_PROTO_LL128] / NCCL_STEPS` 决定。
- **Step 是递增计数器，不是 slot 索引**，通过取模映射到 slot，同时 `step+1` 作为 flag 值。
- **WireWordPerSlice = 256 个 uint64_t = 16 条 128B 行**，这是 warp 一轮处理的"线上"数据量。
- **DataEltPerSlice = 240 × (8 / sizeof(T))**，这是 warp 一轮处理的用户数据量，减去了 flag 的占用。
- **ncclProtoGrainSize = 1920 字节**，是 host 侧切分消息的最小粒度，对应 warp 一轮的数据字节数。
- **地址计算 = slot offset + warp offset + thread offset**，每个线程用 `store128()` 一次写 2 个 uint64_t。

# 02 128B 行与内存组织

上一章我们刚刚回答“为什么需要 LL128 协议”，本章要顺着这个动机把内存层面的故事讲完整：
我们会从环形缓冲区的全景俯瞰开始，逐步下潜到 128B 行的内部布局，再一直走到 warp 寄存器是如何搬运这 128B。
目标是让你在脑海里建立起一张完整的“数据地图”，不论是在 GPU 内核、还是在 Host/Proxy 之间的信息流动都能找到坐标。

为了方便快速索引，本章整体遵循“全景 → 局部”的阅读路线，每一个层级都会明确说明它解决的问题、依赖的常量、以及和上下层如何换算。

## 2. 128B 行解剖：从 16B 双 flag 到 15+1 布局

### 2.1 16B LL 行回顾：双 flag 降低有效带宽

在经典 LL 协议中，每行只有 16B，通过结构体约定 8B 数据 + 4B flag 的布局。对应代码位于 [`src/include/device.h#L70-L83`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L70-L83)：

```c
union ncclLLFifoLine {
  struct {
    uint32_t data1;
    uint32_t flag1;
    uint32_t data2;
    uint32_t flag2;
  };
  uint64_t v[2];
};
```

一条 16B 行可用的纯数据只有 8B（两个 4B 数据，一个 4B flag），等价于有效带宽 50%。
这样设计的原因是需要两个 flag 来维持“数据先到、flag 后到”的因果关系，避免插入昂贵的内存栅栏。

### 2.2 128B 行的 15+1 布局与有效带宽

LL128 把单行扩展到 128B，对应的宏如下：

```c
#define NCCL_LL128_LINESIZE   128
#define NCCL_LL128_LINEELEMS  (NCCL_LL128_LINESIZE/sizeof(uint64_t))  // 128 / 8 = 16
#define NCCL_LL128_DATAELEMS  (NCCL_LL128_LINEELEMS-1)                // 16 - 1 = 15
```

宏定义位于 [`src/include/device.h#L105-L107`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L105-L107)。

换成图示就是：

```
[data0][data1]...[data14][flag]
```

等价于 15 个 `uint64_t`（120B）负责装载用户数据，最后 1 个 `uint64_t`（8B）存放 flag。有效带宽提升到 `15 / 16 = 93.75%`。

### 2.3 Flag 后置与 `__threadfence` 的因果保证

flag 为什么被固定在行尾？关键在于 `postSend()` 执行 `__threadfence()` 之后才更新 `tail`（实现见 [`src/device/prims_ll128.h#L75-L83`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L75-L83)）：

```c++
inline __device__ void postSend() {
  if (sendConnTailPtr) {
#if __CUDA_ARCH__ >= 900
    __threadfence_system();
#else
    __threadfence();
#endif
    *sendConnTailPtr = sendConnTail += 1;
  }
}
```

Fence 保障所有之前的写（数据 + flag）在可见性上早于 tail 更新。若 flag 不在最后，接收方可能读到 flag 已更新却拿到脏数据。flag 后置 + fence 让接收方只需观察最后一个 64 位即可。

flag 的语义也非常直接：写入的值等于 `step + 1`。发送方在填满一行后递增 `sendStep`，Flag Thread 在写 flag 时使用递增后的值；接收方只要看到末尾 8B 等于期望值，就知道整行 120B 数据有效。

### 2.4 Flag Thread 如何植入 flag

LL128 依旧使用 warp 内的“Flag Thread”机制。挑选规则是 `tid % 8 == 7`，意味着每 8 个线程里就有一个专职守门员。
在一个 32 线程的 warp 内共有 4 个 Flag Thread，分别负责每个 128B 行尾的 flag 写入。

写入逻辑可以从 `storeRegs()` 和 `store128()` 中看出（见 [`src/device/prims_ll128.h#L145-L172`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L145-L172)）：

```c++
inline __device__ void storeRegs(...) {
  // 省略装载数据的流程
  #pragma unroll
  for (int u = 0; u < ELEMS_PER_THREAD; u += 2) {
    store128(ptr + u * WARP_SIZE, v[u], flagThread ? flag : v[u + 1]);
  }
}

inline __device__ void store128(uint64_t* ptr, uint64_t v0, uint64_t v1) {
  asm volatile("st.volatile.global.v2.u64 [%2], {%0,%1};"
               :: "l"(v0), "l"(v1), "l"(ptr) : "memory");
}
```

每次循环写入 16B：前 8B 永远是数据，后 8B 只有 Flag Thread 才替换成 flag，其余线程则继续写数据。四个 Flag Thread 分别覆盖 16 条行中的四组行尾，达成“单 flag 覆盖整行”的效果。

### 2.5 非对齐指针如何兜底

用户指针可能不是 16B 对齐。为此 LL128 在写入前引入了 `loadRegsBegin()` / `loadRegsFinish()` 的两阶段装载（实现见 [`src/device/prims_ll128.h#L86-L142`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L86-L142)），它们的职责不止“搬到共享内存”：

- **阶段一：收拢并预留 flag 槽。** `loadRegsBegin()` 先尝试直接以 `ld.128` 把 16B 对齐的数据读入寄存器；若源地址不对齐，则借助 `ncclScratchForWarp()` 提供的共享内存，将最小包络的 16B 对齐窗口搬到本地后再读回寄存器。无论对齐与否，Flag Thread 只加载偶数编号的 16B 块，奇数编号留空，为稍后的 flag 写入预留插槽。
- **阶段二：延迟重排隐藏等待。** `loadRegsFinish()` 把 Flag Thread 漏掉的奇数槽在寄存器里补齐，让所有线程后续都能按线性顺序访问数据。这个函数被安排在 `recvReduceSendCopy()` 等主循环内部、并且在第一次轮询对端 flag 之后才执行，从而把寄存器 shuffle 的依赖延迟隐藏在等待远端数据的时间里。
- **阶段三：写回对齐。** 随后的 `storeRegs()` 会把寄存器重新拆分成偶/奇槽：偶数槽写 120B 数据，奇数槽只在 Flag Thread 手里保留待会写入的 flag；如果目的地址不对齐，同样会先落地到共享内存，再由所有线程协作逐字节刷回。

经过这三步，无论源地址或目的地址的对齐情况如何，环形缓冲区里最终看到的都是严格对齐的 `[15 个数据槽 + 1 个 flag 槽]` 布局。

### 2.6 本节小结

1. LL 的 16B 行由于双 flag 在带宽上只有 50% 有效利用率。
2. LL128 改用 128B 行和单 flag，依靠 `__threadfence` 保证因果，加上 Flag Thread 的单点写回，实现 93.75% 的有效带宽。
3. 对齐问题由共享内存缓冲和寄存器重排处理，确保环形缓冲区中的每一行始终满足 15+1 的结构。

## 3. Step 流控：计数器如何驱动环形缓冲区

### 3.1 Step 是递增计数器，不是 slot 索引

`sendStep` 与 `recvStep` 是无界递增计数器，用来标识流水线中的第几次发送/接收。真正的 slot 索引通过取模获得：

```
slotIndex = step % NCCL_STEPS
```

每个 slot 对应一段 `stepSize` 字节。`stepSize` 在 primitives 构造函数里计算：

```c++
stepSize = comm->buffSizes[NCCL_PROTO_LL128] / NCCL_STEPS;
```

因此，只要知道当前 step，就能用 `step % 8` 找到对应的 slot，然后通过 `slot * stepSize` 计算出环形缓冲区里的起始偏移。

这段初始化逻辑位于 `Primitives<...>::Primitives()` 构造函数中，源码见 [`src/device/prims_ll128.h#L359-L388`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L359-L388)。

### 3.2 `sendOffset` / `recvOffset`：把 Step 映射到地址

Primitives 提供了几个 helper，把 Step 和 `ncclConnInfo` 里的指针串起来：

```c++
inline __device__ int sendOffset(int i) { return (sendStep[i] % NCCL_STEPS) * stepSize; }
inline __device__ uint64_t* sendPtr(int i) { return sendBuff[i] + sendOffset(i); }

inline __device__ int recvOffset(int i) { return (recvStep[i] % NCCL_STEPS) * stepSize; }
inline __device__ uint64_t* recvPtr(int i) { return recvBuff[i] + recvOffset(i); }
```

这里 `i` 指 channel index。`sendBuff` 指向的是对端缓冲区的地址，`recvBuff` 指向本地缓冲区。通过 offset 的计算，发送和接收双方都能在自己的 4.69 MiB 逻辑空间内定位到正在使用的 Step。

这组 helper 定义在 [`src/device/prims_ll128.h#L45-L50`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L45-L50)。

### 3.3 `waitSend()`：最多领先 8 个 Step

为了防止发送方绕圈覆盖尚未读取的数据，`waitSend()` 会在写入前检查领先距离：

```c++
inline __device__ void waitSend(int nbytes) {
    if (sendConnHeadPtr) {
        int spins = 0;
        while (sendConnHeadCache + NCCL_STEPS < sendConnHead + 1) {
            sendConnHeadCache = *sendConnHeadPtr;
            if (checkAbort(abort, 1, spins)) break;
        }
        if (sendConnFifo) {
            sendConnFifo[sendStep[wid]%NCCL_STEPS].size = nbytes;
        }
        sendConnHead += 1;
    }
}
```

`sendConnHead` 表示当前发送端已经提交的 Step 数。只有当 `sendConnHead` 不超过 `sendConnHeadCache + NCCL_STEPS - 1` 时才能继续写，否则会 spin 等待对端确认。这里的 `connFifo[buffSlot].size = size` 会把本次 Step 实际占用的字节数记录下来，供 Proxy 线程核对。

对应实现位于 [`src/device/prims_ll128.h#L58-L69`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L58-L69)。

### 3.4 flag 与 Step 的同步关系

流程拆解如下：

1. warp 往环形缓冲区写入 16 条 128B 行。
2. Flag Thread 将 flag 写成 `sendStep + 1`。
3. warp 结束本轮循环后执行 `sendStep[i] += 1`。
4. `postSend()` 调用 `__threadfence()`，再更新 `tail` 指针。
5. 接收方看到 `tail` 前进，从对应 slot 的行尾读取 flag，并验证是否等于自己的 `recvStep + 1`。

这样一来，Step 计数器既是流控单位也是 flag 的编码方式。发送方递增 Step 的同时更新 flag，接收方收到 flag 即可锁定 Step。

### 3.5 Proxy 如何参与 Step 流控

当通信路径经过网络或主机内存时，Proxy 线程会参与检查。`transport/net.cc` 的发送逻辑会逐行检查：

```c++ 
uint64_t flag = lines[i * NCCL_LL128_LINEELEMS + NCCL_LL128_DATAELEMS];
if (flag != expected) break;
```

`expected` 就是 `connFifo` 里登记的 flag 值，等于 `step + 1`。只有所有行的 flag 匹配，Proxy 才会把数据发到 NIC，否则继续等待 GPU。
这样 CPU 与 GPU 就在 `connFifo` 这条“账本”上保持同步：GPU 先写数据→写 flag→写 size，CPU 读旗帜→读 size→搬运。

对应实现位于 [`src/transport/net.cc#L1282-L1293`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/transport/net.cc#L1282-L1293)。

### 3.6 环形缓冲区尺寸与 Step 的关系

默认缓冲区大小为：

```
DEFAULT_LL128_BUFFSIZE = 120 * 640 * 8 * sizeof(uint64_t) = 4,915,200 B
```

每个 Step 占据：

```
stepSize = DEFAULT_LL128_BUFFSIZE / NCCL_STEPS = 614,400 B
```

这 614,400B 里能放入 `614,400 / 128 = 4,800` 条 128B 行。每条行 120B 可用数据，合计 576,000B = 4,800 * 120B。
剩余的空间是 flag 以及对齐产生的填充。即使你调大缓冲区，Step 数仍固定为 8，只是 `stepSize` 跟着变大。

常量 `DEFAULT_LL128_BUFFSIZE` 定义在 [`src/init.cc#L698-L713`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/init.cc#L698-L713)。

### 3.7 本节小结

- Step 是一个全局递增计数器，通过 `% NCCL_STEPS` 映射到实际 slot。
- `waitSend()` 使用 Step 差值限制发送方最多领先 8 个 Step。
- `connFifo` 记录每个 Step 的字节数与 flag，Proxy 据此验证 GPU 的写入。

## 4. Warp 视角：16 条行如何在寄存器里排队

### 4.1 `WireWordPerSlice` 与 `DataEltPerSlice` 推导

在 `GenericOp` 里可以看到两个关键 constexpr：

```c++
static constexpr int WireWordPerSlice = WARP_SIZE * NCCL_LL128_SHMEM_ELEMS_PER_THREAD; // 32 * 8 = 256
static constexpr int DataEltPerSlice =
  (WireWordPerSlice - WireWordPerSlice / NCCL_LL128_LINEELEMS) * (sizeof(uint64_t) / sizeof(T));
```

- `WireWordPerSlice = 256` 表示 warp 内所有线程合计准备 256 个 64 位槽位。
- `WireWordPerSlice / NCCL_LL128_LINEELEMS = 16` 代表这 256 个槽位要分成 16 条 128B 行，每条行占 16 个槽位。
- `DataEltPerSlice = 240 * (8 / sizeof(T))`，因为 16 个 flag 槽位被剔除，剩下 240 个槽位用于实际数据。

这段 constexpr 定义位于 [`src/device/prims_ll128.h#L288-L304`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L288-L304)。

如果 `T = float`，则 `sizeof(uint64_t)/sizeof(T) = 2`，得到 `DataEltPerSlice = 480`。
这意味着 warp 每完成一轮循环就能搬运 480 个 float（1920B 数据 + 128B flag）。

### 4.2 线程内的 16B 对齐与 `store128`

`wireOffset` 的计算方式如下：

```c++
int wireOffset = WireWordPerSlice * warp + 2 * wid;
```

其中 `wid` 是 lane ID。
因为 `store128` 每次写入两个 `uint64_t`（16B），于是线程 0 写 0-1 槽，线程 1 写 2-3 槽，以此类推。`2 * wid` 保证所有写入天然满足 16B 对齐。

多 warp 情况下，每完成一轮，`wireOffset` 会加上 `WireWordPerSlice * nWarps`，确保下一批数据写在同一个 Step 的后续行上，不与其他 warp 冲突。

相关计算位于 [`src/device/prims_ll128.h#L297-L314`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L297-L314)。

### 4.3 Flag Thread 的覆盖范围

由于每 8 个线程挑一个 Flag Thread，一个 warp 中共有 4 个 Flag Thread。Warp 一轮循环写 16 条行，每个 Flag Thread 管理 4 条行的尾 flag。
这可以从循环次数看出：`ELEMS_PER_THREAD = 8`，循环变量 `u` 以 2 为步长共迭代 4 次。每次迭代 Flag Thread 都写一次 flag，正好覆盖 4 条行。

### 4.4 `loadRegs*` 如何处理非对齐数据

处理流程如下：

1. `loadRegsBegin()` 检查源地址是否对齐，如果不对齐则先把数据读到共享内存，Flag Thread 只装载偶数槽数据。
2. `loadRegsFinish()` 根据 `slice` 和 `lane` 位置，把数据重新排列到寄存器数组 `v` 中；如果是最后一个半对齐元素，会特别标记供 `storeRegs()` 决定是否补齐。
3. `storeRegs()` 在写回前执行逆操作，保证写到环形缓冲区的总是完整的 128B 行。

因此 Flag Thread 不需要额外的搬运操作，寄存器排布本身就为 flag 留好了空位。

### 4.5 共享内存与线程数量

`NCCL_LL128_SHMEM_SIZE = 8 * 640` 表示每个线程最多在共享内存占 8 个 64 位槽位，总线程数上限 640。乘起来就是 5,120 个 64 位槽，对应 40,960B 共享内存（宏定义见 [`src/include/device.h#L112-L113`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L112-L113)）。
这是 warp 在对齐调整时的最大需求，保障在最坏情况下也能完成寄存器重排。

### 4.6 本节小结

- Warp 每轮准备 256 个 64 位槽，减去 16 个 flag 槽后得到 240 个数据槽。
- 每个线程通过 `store128` 写两个槽，实现 16B 对齐的同时植入 flag。
- 共享内存和寄存器协同处理对齐问题，Flag Thread 只需负责把 flag 写到预留位置。

## 5. Host 与 Proxy：如何与 128B 行对齐

### 5.1 `calcBytePerStep` 与 `calcBytePerGrain`

Host 侧的 `ProtoLL128` 与 Device 共用下列函数：

```c++
__device__ static int calcBytePerStep() {
  return (ncclShmem.comm.buffSizes[NCCL_PROTO_LL128] / NCCL_STEPS)
         * NCCL_LL128_DATAELEMS / NCCL_LL128_LINEELEMS;
}
__device__ static int calcBytePerGrain() {
  return NCCL_LL128_SHMEM_ELEMS_PER_THREAD * NCCL_LL128_DATAELEMS
         * sizeof(uint64_t) / NCCL_LL128_LINEELEMS;
}
```

这段实现位于 [`src/device/primitives.h#L63-L70`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/primitives.h#L63-L70)。

代入常量可得：

- `calcBytePerStep = stepSize * 15 / 16`，代表每个 Step 中有多少字节是真正可用于传输的净数据。
- `calcBytePerGrain = 32 * 8 / 16 * 15 * 8 = 1920`，即 warp 一轮吞吐的净数据字节数。

### 5.2 `ncclProtoGrainSize`：Host 切分粒度

`ncclProtoGrainSize(NCCL_PROTO_LL128)` 返回 1920B，这直接告诉 Host 在拆分消息时的最小单位（实现见 [`src/include/device.h#L309-L323`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L309-L323)）。
也就是说，Host 会把用户消息拆分成 1920B 的整数倍交给每个 channel，保证 GPU 每次调度都能刚好处理一个 warp slice。

### 5.3 `connFifo` 中的 size 与 flag

当 GPU 完成一个 Step，它会把 `WireWordPerSlice * sizeof(uint64_t) * slices` 写入 `connFifo[buffSlot].size`。
这个 `size` 是 128B 行的整数倍，Proxy 线程会根据这个数值遍历行尾 flag，直到确认所有 flag 都匹配再发送。
因此，`connFifo` 对 Host/Proxy 来说好比一本账簿，记载了每个 Step 的“有效数据字节数”和“期望 flag 值”。

### 5.4 覆盖 `NCCL_LL128_BUFFSIZE` 的影响

如果你通过环境变量增大 `NCCL_LL128_BUFFSIZE`，Host 会在初始化时更新 `stepSize`，并据此重新计算 `calcBytePerStep`。但是：

- `NCCL_STEPS` 仍然是 8，`waitSend()` 中的“最多领先 8 Step”逻辑不会改变。
- Warp 内部的 128B 行布局完全不受影响，仍然需要 1920B 作为最小粒度。
- `connFifo` 记录的 `size` 仍然按行计，不会因为缓冲区更大就改变单位。

因此扩容缓冲区的意义在于允许更多的 Step 同时在飞，而不是改变每个 Step 的编排方式。

### 5.5 Proxy 的 flag 校验路径

在网络路径上，Proxy 会把 `connFifo` 的记录映射到主机内存缓冲区，然后执行如下检查：

1. 计算本次 Step 需要检查的行数 `lineCount = size / (sizeof(uint64_t) * NCCL_LL128_LINEELEMS)`。
2. 逐行读出尾部 8B，与 `connFifo[buffSlot].flag`（或 `step + 1`）比较。
3. 只有全部匹配才将对应行 DMA 到网卡，或者在系统内存路径上让下一跳继续处理。

这保证了即使跨越 PCIe、NVLink 或 NIC，数据与 flag 仍严格同步。

### 5.6 本节小结

- Host 与 Device 共用 1920B 的粒度，这让调度和内核执行保持一致。
- `connFifo` 串联了 GPU 写入和 Proxy 搬运，flag 与 size 都以 128B 行为单位。
- 增大缓冲区只影响每个 Step 的容量，而不会更改行、warp、flag 的组织方式。

## 6. 双尺度示例：把公式落地到具体场景

### 6.1 示例一：单 warp 搬运 2000 个 float

设定：

- 数据类型 `T = float`（4B）。
- 需要传输 2000 个元素。
- 使用 1 个 warp（32 线程）。

步骤如下：

1. **计算需要的 slice 数量**  
   `DataEltPerSlice = 480`，  
   `sliceCount = ceil(2000 / 480) = 5`。

2. **计算 wire 字节数**  
   `WireWordPerSlice = 256`，  
   `wireBytes = sliceCount * WireWordPerSlice * sizeof(uint64_t) = 5 * 256 * 8 = 10,240 B`。

3. **`waitSend()` 检查空间**  
   `waitSend(10,240)` 会阻塞，直到对应 slot 有足够剩余空间。若对端消费速度慢，发送 warp 会在这里 spin 等待，同时寄存器可以继续准备下一批数据。

4. **warp 循环搬运**  
   每一轮处理 480 个 float，写 16 条行：  
   - 行内数据写入由 `store128` 完成。  
   - Flag Thread 在每条行尾写入 `flag = sendStep + 1`。

5. **处理不足一 slice 的尾巴**  
   第 5 轮只有 80 个 float，用 `loadRegsBegin` 和 `storeRegs` 自动补齐剩余位置，仍写满 16 条行。多余的数据槽位保持原样，但 flag 仍写在行尾。

6. **Step 递增与通知**  
   循环结束后，`sendStep += 1`，`postSend()` fence + 更新 `tail`。对端在 `recvReduceSend()` 中看到 `tail` 增加，读取行尾 flag 与自己的 `recvStep + 1` 比对。

7. **接收方的规约或转发**  
   如果是 Reduce 操作，接收端会将每条行前 120B 与本地寄存器中的数据规约，再把新的 128B 行写到下一跳；若是纯粹的 `recv`，就直接拷贝到目标缓冲区。

最终，2000 个 float 被拆分成 5 个 slice，共写入 80 条 128B 行，带着 80 个 flag 安全抵达对端。

### 6.2 示例二：Ring AllReduce 中的 32MB 梯度

设定：

- 两张 Hopper GPU，执行 Ring AllReduce。
- 每张卡负责 32MB 梯度的一个切片。
- NCCL 默认通道数等于 GPU 数，即每张卡有 2 个 channel。

流程：

1. **Host 切分**  
   `ncclCollCbdPart()` 将 32MB 平分给两个 channel，得到两个 16MB 分片。每个分片再拆成约 `16MB / 1920B ≈ 8738` 个 grain。

2. **GPU 端流水线**  
   每个 channel 内部维护自己的 `sendStep` / `recvStep`。因为 Step 上限是 8，发送方可能同时在飞的 Step 最多 8 个。随着 `sendStep` 递增，flag 依序写入 16 条行尾。

3. **Proxy 介入**  
   由于是跨设备通信，Proxy 线程会在 CPU 上收集来自 GPU 的 `connFifo` 信息。每当 GPU 提交一个 Step，Proxy 会扫描对应字节范围的所有 128B 行，确认 flag 均匹配后才发往下一跳。

4. **Reduce-Send 交错**  
   Ring AllReduce 会让每张卡在接收到上一张卡的数据后立即与本地数据规约，然后再发送给下一张卡。因为 LL128 的单行只占 128B，接收方能快速确认 flag 并立即参与下一跳，不必等待大块数据。

5. **流水线稳定性**  
   即使对端处理较慢，发送方也被 `waitSend()` 限制在最多领先 8 个 Step，避免覆盖尚未消费的数据。这让 32MB 的大消息可以在所有 channel 上稳态流动。

6. **收尾**  
   当所有 Step 完成后，`sendStep` 与 `recvStep` 被写回 `ncclConnInfo.step`，为下一次 Collective 保持正确的初始值。

### 6.3 示例三：不同数据类型的吞吐比较

为了更好地体会 `DataEltPerSlice` 随数据类型变化的影响，我们列出几个常见类型的计算结果：

| 数据类型 | `sizeof(T)` | `DataEltPerSlice` | 每轮净数据字节数 | 说明 |
| -------- | ----------- | ----------------- | ---------------- | ---- |
| `float32` | 4 | 480 | 1920B | warp 每轮写 16 条行，每条行装 15 个 `uint64_t`，即 120B，乘以 16 = 1920B。 |
| `float16` | 2 | 960 | 1920B | 元素变小，但行内数据仍是 120B，因此元素数量翻倍。 |
| `int8` | 1 | 1920 | 1920B | 每条行包含 120B 数据，能容纳 120 个字节；16 条行合计 1920 个 byte。 |
| `double` | 8 | 240 | 1920B | 元素更大，单轮处理的元素数减半，但字节数相同。 |

无论数据类型如何变化，warp 的净字节吞吐始终保持在 1920B，只是元素个数会随 `sizeof(T)` 调整。这就是 `DataEltPerSlice` 和 `WireWordPerSlice` 设计时刻意保持的恒量：对于网络和 Proxy 而言，只关心字节；对于算子而言，再由 `sizeof(T)` 决定每次处理多少个元素。

### 6.4 示例四：多 warp 并行下的行分配

设定：

- `nWarps = 8`（即 256 线程）同时执行 `GenericOp`。
- 每个 warp 都处理同类型数据，仍以 `float32` 为例。

核心问题：多 warp 如何避免写入同一条行？

1. **初始 offset 计算**  
   对于第 `warp` 个 warp：
   ```
   wireOffset = WireWordPerSlice * warp + 2 * wid
   ```
   例如 warp0 lane0 写 offset0，warp1 lane0 写 offset256，二者相距整整 256 个 64 位槽，正好跨越 16 条行。

2. **循环推进**  
   完成一轮后，`wireOffset += WireWordPerSlice * nWarps = 256 * 8 = 2048`。  
   2048 个 `uint64_t` 槽位等价于 2048 * 8 = 16,384B，刚好接在前一批 16 条行的后面。

3. **Flag Thread 分布**  
   每个 warp 内仍有 4 个 Flag Thread，总计 32 个。它们各自负责自己的行尾，没有任何交叉。

4. **Step 内的行数**  
   一个 Step 里共有 4,800 条行。8 个 warp 每轮共写 `8 * 16 = 128` 条行，  
   `4,800 / 128 = 37.5`，意味着写满一个 Step 需要 38 轮循环，最后一轮不满的部分同样由 `loadRegs` 处理。

5. **带宽洞察**  
   多 warp 并行时，`waitSend()` 只发生在 Step 边界。只要 Step 足够大（默认 614,400B），8 个 warp 可以保持饱和状态，flag 的写入也以 Step 为粒度同步。

### 6.5 示例五：RecvReduceSend 的尾部粘连

考虑一个常见场景：channel 同时执行 `recvReduceSend`。

1. **Recv 阶段**  
   接收方先轮询 `recvConnTail`，当发现对端发来新的 Step，就在本地缓冲区的 `recvOffset` 上读取 16 条行。Flag Thread 在本地校验 flag。

2. **Reduce 阶段**  
   Warp 将每条行的 120B 数据与本地寄存器中的数据规约。这一步并不会改变 flag，但会在寄存器里准备新的 15 个 `uint64_t`。

3. **Send 阶段**  
   规约结果马上写入发送缓冲区。由于发送缓冲区与 `recvOffset` 指向不同区域（环形缓冲区的另一半），Step 计数分别更新，互不干扰。

4. **尾部粘连**  
   当最后一个 Step 的数据不足填满 16 条行时，规约结果仍会占据整个行，flag 写入 `sendStep + 1`。接收下一跳的 GPU 只要看到 flag，即可确认这条行包含“最后一批数据中的一部分”，不会因为行内有 padding 而误判。

5. **性能注意**  
   由于 Reduce 与 Send 使用同一 warp，为了避免 `waitSend()` 阻塞 reduce，需要确保发送缓冲区有足够空间。这也是 `DEFAULT_LL128_BUFFSIZE` 预留 8 个 Step 余量的原因。

## 7. 关键洞察与下一章预告

### 7.1 核心要点回顾

- **单 flag 行**：128B 行的 15+1 布局配合 `__threadfence`，让 flag 成为唯一的有效性标记，带宽利用率达到 93.75%。
- **Step 流控**：`sendStep` / `recvStep` 是无界计数器，通过 `% NCCL_STEPS` 映射 slot，`waitSend()` 保证最多领先 8 个 Step。
- **Warp 粒度**：`WireWordPerSlice = 256`、`DataEltPerSlice = 240 * (8 / sizeof(T))` 确保 warp 每轮吞吐 1920B，Flag Thread 无缝插旗。
- **Host/Proxy 对齐**：`calcBytePerGrain = 1920B` 让 CPU 与 GPU 在相同粒度上协同；`connFifo` 记录 size 与 flag，实现跨设备统一判断。
- **实战验证**：从 2000 个 float 的小例子到 32MB Ring AllReduce，大/小两种尺度都复用了相同的公式与流程。

### 7.2 风险与调优提示

- 若用户强行减小 `NCCL_LL128_BUFFSIZE`，应注意 Step 仍为 8，若 `stepSize` 太小可能导致频繁等待。
- 对齐问题虽然由 `loadRegs*` 兜底，但极端情况下会占用更多共享内存，应关注是否与其他内核竞争资源。
- Proxy 校验 flag 的开销在高延迟网络下更明显，建议结合 `NCCL_NET` 设置或自研网络插件优化。

### 7.3 下一章预告：Flag Thread 机制

本章聚焦在内存布局与数据流动。下一章我们将进一步分析 Flag Thread：

1. 为什么选择 `tid % 8 == 7` 作为 Flag Thread？
2. Flag Thread 如何在寄存器层面拆分数据与 flag？
3. warp 内同步如何保证单 flag 仍然安全？

带着本章建立的内存模型，理解 Flag Thread 的实现会更加轻松。

# 02 128B 行与内存组织

上一章我们刚刚回答“为什么需要 LL128 协议”，本章要顺着这个动机把内存层面的故事讲完整：
我们会从环形缓冲区的全景俯瞰开始，逐步下潜到 128B 行的内部布局，再一直走到 warp 寄存器是如何搬运这 128B。
目标是让你在脑海里建立起一张完整的“数据地图”，不论是在 GPU 内核、还是在 Host/Proxy 之间的信息流动都能找到坐标。

为了方便快速索引，本章整体遵循“全景 → 局部”的阅读路线，每一个层级都会明确说明它解决的问题、依赖的常量、以及和上下层如何换算。

下面的图把 LL128 的内存组织比喻成自动化仓库。请先整体扫一遍，后续章节会逐段拆解：

+---------------------------------------------------------------------+
|                           Ring Buffer                               |
|---------------------------------------------------------------------|
| Step0 | Step1 | Step2 | Step3 | Step4 | Step5 | Step6 | Step7       |

|<---------------------------  DEFAULT_LL128_BUFFSIZE  -------------->|

放大任意一个 Step，可以看到它是一段连续内存，内部整齐排布多个 128B 行：

```
+-----------------------------------------------------------+
| Step i (size = stepSize bytes)                            |
|-----------------------------------------------------------|
| Line0 | Line1 | Line2 | ... | LineN-1                     |
+-----------------------------------------------------------+
```

继续放大其中的 Line0，就能看到 128B 行的内部结构（15 个数据槽 + 1 个 flag 槽）：

```
+---------------------------------------+
| 128B Line (Line0 的内部视图)           |
|---------------------------------------|
| data[0] | data[1] | ... | data[14] | flag |
+---------------------------------------+
```

再继续放大一行，则可以看到面向不同数据类型时的装箱方式：

```
 Line payload (15 * uint64_t = 120B 数据)              Line flag (1 * uint64_t = 8B)
+----------------------------------------------------------------------------------+
| 8B chunk | 8B chunk | ... | 8B chunk |  flag  |
+----------------------------------------------------------------------------------+
    |                                         ^
    +-- 每个 8B chunk 可拆成多个 Elements，如 float32 时包含 2 个 4B Elements
```

## 128B 行解剖：从 16B 双 flag 到 15+1 布局

### 16B LL 行回顾：双 flag 降低有效带宽

在经典 LL 协议中，每行只有 16B，通过结构体约定 8B 数据 + 4B flag 的布局。对应代码位于 [`src/include/device.h#L70-L83`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L70-L83)：

```c
union ncclLLFifoLine {
  struct {
    uint32_t data1;
    uint32_t flag1;
    uint32_t data2;
    uint32_t flag2;
  };
  uint64_t v[2];
};
```

一条 16B 行采用交错存储：`data1 (4B) → flag1 (4B) → data2 (4B) → flag2 (4B)`。
总计 8B 数据和 8B flags，有效带宽只有 50%。
这种交错布局通过物理位置保证 flag 在对应数据之后，配合内存栅栏确保接收方看到 flag 时数据已可见。

### 128B 行的 15+1 布局与有效带宽

LL128 把单行扩展到 128B，对应的宏如下：

```c
#define NCCL_LL128_LINESIZE   128
#define NCCL_LL128_LINEELEMS  (NCCL_LL128_LINESIZE/sizeof(uint64_t))  // 128 / 8 = 16
#define NCCL_LL128_DATAELEMS  (NCCL_LL128_LINEELEMS-1)                // 16 - 1 = 15
```

宏定义位于 [`src/include/device.h#L105-L107`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L105-L107)。

换成图示就是：

```
[data0][data1]...[data14][flag]
```

等价于 15 个 `uint64_t`（120B）负责装载用户数据，最后 1 个 `uint64_t`（8B）存放 flag。有效带宽提升到 `15 / 16 = 93.75%`。

### Flag 后置与 `__threadfence` 的因果保证

flag 为什么被固定在行尾？关键在于 `postSend()` 执行 `__threadfence()` 之后才更新 `tail`（实现见 [`src/device/prims_ll128.h#L75-L83`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L75-L83)）：

```c++
inline __device__ void postSend() {
  if (sendConnTailPtr) {
#if __CUDA_ARCH__ >= 900
    __threadfence_system();
#else
    __threadfence();
#endif
    *sendConnTailPtr = sendConnTail += 1;
  }
}
```

Fence 保障所有之前的写（数据 + flag）在可见性上早于 tail 更新。若 flag 不在最后，接收方可能读到 flag 已更新却拿到脏数据。flag 后置 + fence 让接收方只需观察最后一个 64 位即可。

flag 的语义也非常直接：写入的值等于 `step + 1`。发送方在填满一行后递增 `sendStep`，Flag Thread 在写 flag 时使用递增后的值；接收方只要看到末尾 8B 等于期望值，就知道整行 120B 数据有效。

### Flag Thread 如何植入 flag

LL128 依旧使用 warp 内的"Flag Thread"机制。挑选规则是 `tid % 8 == 7`。这个规则从何而来？

让我们从 warp 的访问模式出发推导。在 `recvReduceSendCopy()` 中（见 [`src/device/prims_ll128.h#L271-L283`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L271-L283)），每个线程写入的位置由 `wireOffset` 决定：

```c++
int wireOffset = WireWordPerSlice * warp + 2 * wid;  // wid 是 lane ID (0-31)
```

因为 `store128` 每次写入 2 个 `uint64_t`（16B），线程 0 写槽位 0-1，线程 1 写槽位 2-3，线程 2 写槽位 4-5，以此类推。

一条 128B 行有 16 个槽位，需要 8 个连续线程覆盖（线程 0-7 覆盖第一条行，线程 8-15 覆盖第二条行，依此类推）。**关键点**：flag 位于每条行的第 15 号槽位（最后一个 `uint64_t`）。

观察线程与槽位的对应关系：
- 线程 7 写槽位 14-15（正好包含 flag 位置）
- 线程 15 写槽位 30-31（下一条行的 flag 位置）
- 线程 23 写槽位 46-47
- 线程 31 写槽位 62-63

因此 `tid % 8 == 7` 的线程恰好负责每条行的最后两个槽位，其中第二个槽位（奇数槽）就是 flag 的插入位置。在一个 32 线程的 warp 内共有 4 个 Flag Thread（tid=7, 15, 23, 31），分别负责 4 条行的 flag 写入。

写入逻辑可以从 `recvReduceSendCopy()` 中看出（见 [`src/device/prims_ll128.h#L271-L283`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L271-L283)）：

```c++
// 在 recvReduceSendCopy() 中，写入到环形缓冲区时：
uint64_t flag = sendFlag(i);
uint64_t* ptr = sendPtr(i) + ll128Offset;
#pragma unroll
for (int u = 0; u < ELEMS_PER_THREAD; u += 2) {
  store128(ptr + u * WARP_SIZE, v[u], flagThread ? flag : v[u + 1]);
}

// store128 的实现：
inline __device__ void store128(uint64_t* ptr, uint64_t v0, uint64_t v1) {
  asm volatile("st.volatile.global.v2.u64 [%2], {%0,%1};"
               :: "l"(v0), "l"(v1), "l"(ptr) : "memory");
}
```

每次循环写入 16B：前 8B 永远是数据，后 8B 只有 Flag Thread 才替换成 flag，其余线程则继续写数据。四个 Flag Thread 分别覆盖 16 条行中的四组行尾，达成"单 flag 覆盖整行"的效果。

### 非对齐指针如何兜底

用户指针可能不是 16B 对齐。为此 LL128 在写入前引入了 `loadRegsBegin()` / `loadRegsFinish()` 的两阶段装载（实现见 [`src/device/prims_ll128.h#L86-L142`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L86-L142)）。

**为什么需要两阶段？** Flag Thread 只加载偶数槽的数据，需要通过 warp shuffle 操作从其他线程获取奇数槽。Shuffle 会引入依赖停顿（dependency stall）。将 shuffle 延迟到 `loadRegsFinish()` 中执行，可以让调用者先发起其他内存操作（如轮询对端 flag），从而把 shuffle 的延迟**隐藏在内存等待时间里**。这是 CUDA 性能优化的经典技巧。

具体流程：

- **阶段一：收拢并预留 flag 槽。** `loadRegsBegin()` 先尝试直接以 `ld.128` 把 16B 对齐的数据读入寄存器；若源地址不对齐，则借助 `ncclScratchForWarp()` 提供的共享内存，将最小包络的 16B 对齐窗口搬到本地后再读回寄存器。无论对齐与否，Flag Thread 只加载偶数编号的 16B 块，奇数编号留空，为稍后的 flag 写入预留插槽。
- **阶段二：延迟重排隐藏等待。** `loadRegsFinish()` 把 Flag Thread 漏掉的奇数槽在寄存器里补齐，让所有线程后续都能按线性顺序访问数据。这个函数被安排在 `recvReduceSendCopy()` 等主循环内部、并且在第一次轮询对端 flag 之后才执行，从而把寄存器 shuffle 的依赖延迟隐藏在等待远端数据的时间里。
- **阶段三：写回对齐。** 随后的 `storeRegs()` 会把寄存器重新拆分成偶/奇槽：偶数槽写 120B 数据，奇数槽只在 Flag Thread 手里保留待会写入的 flag；如果目的地址不对齐，同样会先落地到共享内存，再由所有线程协作逐字节刷回。

经过这三步，无论源地址或目的地址的对齐情况如何，环形缓冲区里最终看到的都是严格对齐的 `[15 个数据槽 + 1 个 flag 槽]` 布局。

### 本节小结

1. LL 的 16B 行由于双 flag 在带宽上只有 50% 有效利用率。
2. LL128 改用 128B 行和单 flag，依靠 `__threadfence` 保证因果，加上 Flag Thread 的单点写回，实现 93.75% 的有效带宽。
3. 对齐问题由共享内存缓冲和寄存器重排处理，确保环形缓冲区中的每一行始终满足 15+1 的结构。

## Step 流控：计数器如何驱动环形缓冲区

### Step 计数器与地址映射

`sendStep` 与 `recvStep` 是**无界递增计数器**，用来标识流水线中的第几次发送/接收。真正的 slot 索引通过 `step % NCCL_STEPS` 获得，再乘以 `stepSize` 得到环形缓冲区内的偏移量。

Primitives 提供了几个 helper 函数（见 [`src/device/prims_ll128.h#L45-L50`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L45-L50)），把 Step 计数器映射到实际地址：

```c++
inline __device__ int sendOffset(int i) { return (sendStep[i] % NCCL_STEPS) * stepSize; }
inline __device__ uint64_t* sendPtr(int i) { return sendBuff[i] + sendOffset(i); }

inline __device__ int recvOffset(int i) { return (recvStep[i] % NCCL_STEPS) * stepSize; }
inline __device__ uint64_t* recvPtr(int i) { return recvBuff[i] + recvOffset(i); }
```

这里 `i` 指 channel index。`sendBuff` 指向对端缓冲区的地址，`recvBuff` 指向本地缓冲区。`stepSize` 在 primitives 构造函数中计算为 `comm->buffSizes[NCCL_PROTO_LL128] / NCCL_STEPS`（见 [`src/device/prims_ll128.h#L359-L388`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L359-L388)）。

### `waitSend()`：最多领先 8 个 Step

为了防止发送方绕圈覆盖尚未读取的数据，`waitSend()` 会在写入前检查领先距离：

```c++
inline __device__ void waitSend(int nbytes) {
    if (sendConnHeadPtr) {
        int spins = 0;
        while (sendConnHeadCache + NCCL_STEPS < sendConnHead + 1) {
            sendConnHeadCache = *sendConnHeadPtr;
            if (checkAbort(abort, 1, spins)) break;
        }
        if (sendConnFifo) {
            sendConnFifo[sendStep[wid]%NCCL_STEPS].size = nbytes;
        }
        sendConnHead += 1;
    }
}
```

`sendConnHead` 表示当前发送端已经提交的 Step 数。只有当 `sendConnHead` 不超过 `sendConnHeadCache + NCCL_STEPS - 1` 时才能继续写，否则会 spin 等待对端确认。这里的 `connFifo[buffSlot].size = nbytes` 记录本次 Step 的字节数，供 Proxy 线程计算需要验证的行数。

对应实现位于 [`src/device/prims_ll128.h#L58-L69`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L58-L69)。

### flag 与 Step 的同步关系

流程拆解如下：

1. 在 `GenericOp` 循环中，warp 往环形缓冲区写入 16 条 128B 行。
2. Warp 内所有线程通过 `sendFlag(0)` 计算相同的 flag 值（`sendStep + 1`）。
3. 在 `store128` 调用时，Flag Thread 通过三目运算符 `flagThread ? flag : v[u+1]` 将 flag 写入行尾，其他线程继续写数据。
4. `GenericOp` 循环结束后，才执行 `sendStep[i] += 1`，让 Step 计数器前进。
5. 随后 `postSend()` 调用 `__threadfence()`，再更新 `tail` 指针，通知接收方数据已准备好。
6. 接收方看到 `tail` 前进，从对应 slot 的行尾读取 flag，并验证是否等于自己的 `recvStep + 1`。

这样一来，Step 计数器既是流控单位也是 flag 的编码方式。**关键点**：flag 值在循环内计算并写入，Step 递增在循环外进行，确保下一轮使用新的 Step 值。

### Proxy 如何参与 Step 流控

当通信路径经过网络或主机内存时，Proxy 线程会参与检查。`transport/net.cc` 的发送逻辑会逐行校验 flag（见 [`src/transport/net.cc#L1287-L1293`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/transport/net.cc#L1287-L1293)）：

```c++
uint64_t flag = sub->base + sub->transmitted + 1;  // 计算期望的 flag 值
int nFifoLines = DIVUP(connFifo[buffSlot].size, sizeof(uint64_t)*NCCL_LL128_LINEELEMS);
volatile uint64_t* lines = (volatile uint64_t*)buff;
ready = 1;
for (int i=0; i<nFifoLines; i++) {
  if (lines[i*NCCL_LL128_LINEELEMS+NCCL_LL128_DATAELEMS] != flag) { ready = 0; break; }
}
```

**关键点**：`connFifo` 结构体只存储 `.size`（本次 Step 的字节数），**不存储 flag 值**。Proxy 通过 `sub->base + sub->transmitted + 1` **独立计算**期望的 flag 值。只有所有行的 flag 匹配期望值，Proxy 才会把数据发到 NIC，否则继续等待 GPU。

这样 CPU 与 GPU 就在 `connFifo` 这条"账本"上保持同步：GPU 先写数据→写 flag→写 size，CPU 根据 size 计算行数→逐行验证 flag→搬运数据。

### 环形缓冲区尺寸与 Step 的关系

默认缓冲区大小通过以下宏计算（定义见 [`src/init.cc#L698-L713`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/init.cc#L698-L713)）：

```
DEFAULT_LL128_BUFFSIZE = NCCL_LL128_ELEMS_PER_THREAD * NCCL_LL128_MAX_NTHREADS * NCCL_STEPS * sizeof(uint64_t)
                       = 120 * 640 * 8 * 8
                       = 4,915,200 B (~4.69 MiB)
```

其中：
- `NCCL_LL128_ELEMS_PER_THREAD = 120`：每个线程负责的 uint64 槽位数
- `NCCL_LL128_MAX_NTHREADS = 640`：单个算子中的最大线程数
- `NCCL_STEPS = 8`：环形缓冲区的 slot 数量

每个 Step 占据：

```
stepSize = DEFAULT_LL128_BUFFSIZE / NCCL_STEPS = 614,400 B
```

这 614,400B 里能放入 `614,400 / 128 = 4,800` 条 128B 行。每条行 120B 可用数据，合计 576,000B = 4,800 * 120B。
剩余的空间是 flag 以及对齐产生的填充。即使你调大缓冲区，Step 数仍固定为 8，只是 `stepSize` 跟着变大。

常量 `DEFAULT_LL128_BUFFSIZE` 定义在 [`src/init.cc#L698-L713`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/init.cc#L698-L713)。

### 本节小结

- Step 是一个全局递增计数器，通过 `% NCCL_STEPS` 映射到实际 slot。
- `waitSend()` 使用 Step 差值限制发送方最多领先 8 个 Step。
- `connFifo` 记录每个 Step 的字节数（`.size`），Proxy 据此计算 flag 期望值并验证 GPU 的写入。
- flag 值在循环内计算并写入，Step 递增在循环外进行。

## Warp 视角：16 条行如何在寄存器里排队

### `WireWordPerSlice` 与 `DataEltPerSlice` 推导

在 `GenericOp` 里可以看到两个关键 constexpr（定义见 [`src/device/prims_ll128.h#L288-L304`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L288-L304)）：

```c++
static constexpr int WireWordPerSlice = WARP_SIZE * NCCL_LL128_SHMEM_ELEMS_PER_THREAD; // 32 * 8 = 256
static constexpr int DataEltPerSlice =
  (WireWordPerSlice - WireWordPerSlice / NCCL_LL128_LINEELEMS) * (sizeof(uint64_t) / sizeof(T));
```

**术语说明**：在 NCCL 中，"**Wire**"指的是在网络/链路上**实际传输的字节**，包含数据和开销（如 flag）。与之对比，"**DataElt**"指的是用户可见的数据元素。这个区分对理解 LL128 的效率提升至关重要：LL 的 Wire 开销是 50%，而 LL128 降到了 6.25%。

推导过程：

- `WireWordPerSlice = 256` 表示 warp 内所有线程合计准备 256 个 64 位槽位（**包含 flag**）。
- `WireWordPerSlice / NCCL_LL128_LINEELEMS = 16` 代表这 256 个槽位要分成 16 条 128B 行，每条行占 16 个槽位。
- `DataEltPerSlice = 240 * (8 / sizeof(T))`，因为 16 个 flag 槽位被剔除，剩下 240 个槽位用于实际数据（**纯用户数据**）。

如果 `T = float`，则 `sizeof(uint64_t)/sizeof(T) = 2`，得到 `DataEltPerSlice = 480`。
这意味着 warp 每完成一轮循环就能搬运 480 个 float（1920B 数据 + 128B flag）。

### 线程内的 16B 对齐与 `store128`

`wireOffset` 的计算方式如下：

```c++
int wireOffset = WireWordPerSlice * warp + 2 * wid;
```

其中 `wid` 是 lane ID。
因为 `store128` 每次写入两个 `uint64_t`（16B），于是线程 0 写 0-1 槽，线程 1 写 2-3 槽，以此类推。`2 * wid` 保证所有写入天然满足 16B 对齐。

多 warp 情况下，每完成一轮，`wireOffset` 会加上 `WireWordPerSlice * nWarps`，确保下一批数据写在同一个 Step 的后续行上，不与其他 warp 冲突。

相关计算位于 [`src/device/prims_ll128.h#L297-L314`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L297-L314)。

### Flag Thread 的覆盖范围

由于每 8 个线程挑一个 Flag Thread，一个 warp 中共有 4 个 Flag Thread。Warp 一轮循环写 16 条行，每个 Flag Thread 管理 4 条行的尾 flag。
这可以从循环次数看出：`ELEMS_PER_THREAD = 8`，循环变量 `u` 以 2 为步长共迭代 4 次。每次迭代 Flag Thread 都写一次 flag，正好覆盖 4 条行。

### `loadRegs*` 如何处理非对齐数据

处理流程如下：

1. `loadRegsBegin()` 检查源地址是否对齐，如果不对齐则先把数据读到共享内存，Flag Thread 只装载偶数槽数据。
2. `loadRegsFinish()` 根据 `slice` 和 `lane` 位置，把数据重新排列到寄存器数组 `v` 中；如果是最后一个半对齐元素，会特别标记供 `storeRegs()` 决定是否补齐。
3. `storeRegs()` 在写回前执行逆操作，保证写到环形缓冲区的总是完整的 128B 行。

因此 Flag Thread 不需要额外的搬运操作，寄存器排布本身就为 flag 留好了空位。

### 共享内存与线程数量

`NCCL_LL128_SHMEM_SIZE = 8 * 640` 表示每个线程最多在共享内存占 8 个 64 位槽位，总线程数上限 640。乘起来就是 5,120 个 64 位槽，对应 40,960B 共享内存（宏定义见 [`src/include/device.h#L112-L113`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L112-L113)）。
这是 warp 在对齐调整时的最大需求，保障在最坏情况下也能完成寄存器重排。

### 本节小结

- Warp 每轮准备 256 个 64 位槽，减去 16 个 flag 槽后得到 240 个数据槽。
- 每个线程通过 `store128` 写两个槽，实现 16B 对齐的同时植入 flag。
- Flag Thread 承担特殊职责：加载阶段只取偶数槽、重排阶段通过 shuffle 补齐奇数槽、写入阶段用 flag 替换最后一个槽位。
- 共享内存和寄存器协同处理对齐问题，确保环形缓冲区中的每一行始终满足 15+1 的结构。

## Host 与 Proxy：如何与 128B 行对齐

### `calcBytePerStep`：每个 Step 的净数据容量

Host 侧与 Device 共用此函数计算每个 Step 可传输的净数据字节数：

```c++
__device__ static int calcBytePerStep() {
  return (ncclShmem.comm.buffSizes[NCCL_PROTO_LL128] / NCCL_STEPS)
         * NCCL_LL128_DATAELEMS / NCCL_LL128_LINEELEMS;
}
```

这段实现位于 [`src/device/primitives.h#L63-L66`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/primitives.h#L63-L66)。

代入常量可得：`calcBytePerStep = stepSize * 15 / 16`，代表每个 Step 中有多少字节是真正可用于传输的净数据（扣除 flag 开销）。

### `ncclProtoGrainSize`：Host 切分粒度

Host 在拆分用户消息时需要知道最小传输单位。`ncclProtoGrainSize(NCCL_PROTO_LL128)` 正是为此设计，返回 **1920B**（实现见 [`src/include/device.h#L309-L323`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L309-L323)）：

```c++
__host__ __device__ constexpr int ncclProtoGrainSize(int proto) {
  return proto == NCCL_PROTO_LL128
    ? WARP_SIZE*NCCL_LL128_SHMEM_ELEMS_PER_THREAD/NCCL_LL128_LINEELEMS*NCCL_LL128_DATAELEMS*sizeof(uint64_t)
    : ...;
  // = (32 * 8 / 16) * 15 * 8 = 16 * 15 * 8 = 1920 字节
}
```

这个 1920B 正是一个 warp 处理一轮（16 条 128B 行）的净数据吞吐量。Host 会把用户消息拆分成 1920B 的整数倍交给每个 channel，保证 GPU 每次调度都能刚好处理完整的 warp slice。

### `connFifo` 中的 size

当 GPU 完成一个 Step，它会把 `WireWordPerSlice * sizeof(uint64_t) * slices` 写入 `connFifo[buffSlot].size`。
这个 `size` 是 128B 行的整数倍，Proxy 线程会根据这个数值计算行数，然后遍历行尾 flag，直到确认所有 flag 都匹配期望值再发送。
因此，`connFifo` 对 Host/Proxy 来说好比一本账簿，记载了每个 Step 的"有效数据字节数"，Proxy 独立计算期望的 flag 值。

### 覆盖 `NCCL_LL128_BUFFSIZE` 的影响

如果你通过环境变量增大 `NCCL_LL128_BUFFSIZE`，Host 会在初始化时更新 `stepSize`，并据此重新计算 `calcBytePerStep`。但是：

- `NCCL_STEPS` 仍然是 8，`waitSend()` 中的“最多领先 8 Step”逻辑不会改变。
- Warp 内部的 128B 行布局完全不受影响，仍然需要 1920B 作为最小粒度。
- `connFifo` 记录的 `size` 仍然按行计，不会因为缓冲区更大就改变单位。

因此扩容缓冲区的意义在于允许更多的 Step 同时在飞，而不是改变每个 Step 的编排方式。

### Proxy 的 flag 校验路径：GDR vs 非 GDR

在网络路径上，Proxy 的行为取决于是否启用 GPUDirect RDMA（GDR）：

- **GDR 启用**：GPU 直接写 NIC 内存，通过 `__threadfence_system()` 保证系统级可见性顺序（Hopper 架构）。Proxy **跳过 flag 验证**（见 [`net.cc#L1283`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/transport/net.cc#L1283)），因为硬件 fence 已保证数据顺序。

- **GDR 未启用**：数据经由主机内存，GPU 只调用 `__threadfence()`（不保证对 CPU 的可见性顺序）。Proxy **必须在 CPU 侧逐行验证 flag**（见 [`net.cc#L1287-L1294`](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/transport/net.cc#L1287-L1294)），确保所有 128B 行的 flag 就绪后才发送。

这是 CUDA 内存模型的限制：`__threadfence()` 只保证 GPU 内部可见性，`__threadfence_system()` 保证对所有设备可见性。两种路径分别通过硬件 fence 和 CPU 软件验证来保证单 flag 机制的安全性。

### 本节小结

- Host 与 Device 共用 1920B 的粒度，这让调度和内核执行保持一致。
- `connFifo` 串联了 GPU 写入和 Proxy 搬运：GPU 写 `.size`，Proxy 根据 `.size` 计算 flag 期望值并逐行验证。
- GDR vs 非 GDR 通过不同的内存一致性保证（硬件 fence vs CPU 验证）实现单 flag 的安全性。
- 增大缓冲区只影响每个 Step 的容量，而不会更改行、warp、flag 的组织方式。

## 实例分析：从元素到字节的换算

### 示例一：单 warp 搬运 2000 个 float

设定：

- 数据类型 `T = float`（4B）。
- 需要传输 2000 个元素。
- 使用 1 个 warp（32 线程）。

步骤如下：

1. **计算需要的 slice 数量**  
   `DataEltPerSlice = 480`，  
   `sliceCount = ceil(2000 / 480) = 5`。

2. **计算 wire 字节数**  
   `WireWordPerSlice = 256`，  
   `wireBytes = sliceCount * WireWordPerSlice * sizeof(uint64_t) = 5 * 256 * 8 = 10,240 B`。

3. **`waitSend()` 检查空间**  
   `waitSend(10,240)` 会阻塞，直到对应 slot 有足够剩余空间。若对端消费速度慢，发送 warp 会在这里 spin 等待，同时寄存器可以继续准备下一批数据。

4. **warp 循环搬运**  
   每一轮处理 480 个 float，写 16 条行：  
   - 行内数据写入由 `store128` 完成。  
   - Flag Thread 在每条行尾写入 `flag = sendStep + 1`。

5. **处理不足一 slice 的尾巴**
   第 5 轮只有 80 个 float，用 `loadRegsBegin` 和 `storeRegs` 自动补齐剩余位置，仍写满 16 条行。多余的数据槽位会被写入寄存器中的任意值，但接收方根据 `nelem` 参数只会读取前 80 个有效 float。

6. **Step 递增与通知**  
   循环结束后，`sendStep += 1`，`postSend()` fence + 更新 `tail`。对端在 `recvReduceSend()` 中看到 `tail` 增加，读取行尾 flag 与自己的 `recvStep + 1` 比对。

7. **接收方的规约或转发**  
   如果是 Reduce 操作，接收端会将每条行前 120B 与本地寄存器中的数据规约，再把新的 128B 行写到下一跳；若是纯粹的 `recv`，就直接拷贝到目标缓冲区。

最终，2000 个 float 被拆分成 5 个 slice，共写入 80 条 128B 行，带着 80 个 flag 安全抵达对端。

### 示例二：不同数据类型的吞吐比较

为了更好地体会 `DataEltPerSlice` 随数据类型变化的影响，我们列出几个常见类型的计算结果：

| 数据类型 | `sizeof(T)` | `DataEltPerSlice` | 每轮净数据字节数 | 说明 |
| -------- | ----------- | ----------------- | ---------------- | ---- |
| `float32` | 4 | 480 | 1920B | warp 每轮写 16 条行，每条行装 15 个 `uint64_t`，即 120B，乘以 16 = 1920B。 |
| `float16` | 2 | 960 | 1920B | 元素变小，但行内数据仍是 120B，因此元素数量翻倍。 |
| `int8` | 1 | 1920 | 1920B | 每条行包含 120B 数据，能容纳 120 个字节；16 条行合计 1920 个 byte。 |
| `double` | 8 | 240 | 1920B | 元素更大，单轮处理的元素数减半，但字节数相同。 |

无论数据类型如何变化，warp 的净字节吞吐始终保持在 1920B，只是元素个数会随 `sizeof(T)` 调整。这个设计带来两个关键优势：

1. **传输层与算子层解耦**：Proxy 和网络栈只需要按字节计算传输量，不需要知道数据类型。`connFifo[buffSlot].size` 记录的是字节数，Proxy 根据字节数计算行数并验证 flag，与 `T` 无关。

2. **统一的流控粒度**：Host 在拆分消息时使用 `ncclProtoGrainSize(NCCL_PROTO_LL128) = 1920B`，GPU 在执行时每个 warp 处理一轮也是 1920B 净数据。这让调度器、内核、Proxy 在同一个粒度上协同工作，简化了流控逻辑。

## 关键洞察与下一章预告

### 核心要点回顾

- **单 flag 行**：128B 行的 15+1 布局配合 `__threadfence`，让 flag 成为唯一的有效性标记，带宽利用率达到 93.75%。
- **Step 流控**：`sendStep` / `recvStep` 是无界计数器，通过 `% NCCL_STEPS` 映射 slot，`waitSend()` 保证最多领先 8 个 Step。
- **Warp 粒度**：`WireWordPerSlice = 256`、`DataEltPerSlice = 240 * (8 / sizeof(T))` 确保 warp 每轮吞吐 1920B，Flag Thread 无缝插旗。
- **Host/Proxy 对齐**：`calcBytePerGrain = 1920B` 让 CPU 与 GPU 在相同粒度上协同；`connFifo` 记录 `.size`，Proxy 计算 flag 期望值并逐行验证。
- **GDR 优化**：通过硬件 fence（GDR）或 CPU 验证（非 GDR）保证单 flag 机制的内存一致性。

### LL vs LL128 快速对比

| 维度 | LL (16B) | LL128 (128B) | LL128 的优势 |
|------|----------|--------------|--------------|
| 行大小 | 16B | 128B | 单次传输更多数据 |
| 数据容量 | 8B | 120B | 15 倍数据容量 |
| Flag 数量 | 2 个 (flag1, flag2) | 1 个 | 更简单的验证逻辑 |
| 有效带宽 | 50% | 93.75% | Wire 开销从 50% 降到 6.25% |
| Flag 验证 | 逐行双 flag | 逐行单 flag | 相同的行级验证粒度 |
| 适用场景 | 小消息（<8KB） | 中等消息（8KB-64KB） | 平衡延迟与带宽 |

### 风险与调优提示

- 若用户强行减小 `NCCL_LL128_BUFFSIZE`，应注意 Step 仍为 8，若 `stepSize` 太小可能导致频繁等待。
- 对齐问题虽然由 `loadRegs*` 兜底，但极端情况下会占用更多共享内存，应关注是否与其他内核竞争资源。
- Proxy 校验 flag 的开销在高延迟网络下更明显，建议结合 `NCCL_NET` 设置或自研网络插件优化。

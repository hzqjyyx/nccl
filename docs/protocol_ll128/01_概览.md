# 01 LL128 Protocol 概览

## 本章要回答的问题

在 NCCL 的三种通信协议中，Simple 和 LL 分别针对"大消息高带宽"和"小消息低延迟"做了优化，为什么还需要第三种协议 LL128？本章回答三个核心问题：

- **Simple 和 LL 各自解决了什么问题，又留下了什么空档？**
- **LL128 如何在这两种协议之间找到平衡点？**
- **这种平衡依赖什么硬件前提，又付出了什么代价？**

理解了这三点，你就能明白 LL128 存在的必要性，以及它在整个协议体系中的位置。

**说明**：为了聚焦核心概念，我们只讨论最常见的场景：
- 一个进程对应一个 GPU
- 使用 Ring 算法进行集合通信

---

## 为什么需要三种协议？

### Simple 和 LL 的两端哲学

如果你已经阅读过 Simple 和 LL 的文档系列（[Simple 01:概览](../protocol_simple/01_概览.md)、[LL 01:概览](../protocol_ll/01_概览.md)），你会知道这两种协议代表了两种极端的设计哲学：

**Simple Protocol**：粗粒度流控，最大化带宽
- 把数据组织成大块传输（默认缓冲区 4MiB，8 个 step，每个 step 约 512KiB）
- 使用粗粒度的 head/tail 计数器同步（每个 step 更新一次）
- 通过大块连续内存访问充分利用 GPU 内存带宽
- **代价**：启动等待长，不适合小消息

**LL Protocol**：细粒度同步，最小化延迟
- 把数据拆成 16B 的 line，每个 line 独立传输
- 每个 line 带有双标志位（8B 数据 + 8B 双 flag）
- 有数据就发，接收方立即可用
- **代价**：双标志位导致 50% 的带宽损耗（8B 有效数据 / 16B 总大小）

这两种协议各自占据了性能光谱的两端，却在中间留下了一个问题：**对于几十到几百 KB 的中等消息，用哪种协议都不理想**。

### 中等消息的尴尬处境

让我们用具体数字来理解这个问题。假设要传输一个 64KB 的消息：

**如果用 Simple Protocol**：
- 64KB 无法填满一个 512KiB 的 step
- 但 Simple 的流控以 step 为单位，需要等待整个 step 的同步
- GPU 大部分时间在等待，而不是传输数据
- 虽然带宽利用率接近 100%，但总时间被等待拉长

**如果用 LL Protocol**：
- 64KB = 4096 个 16B 的 line
- 每个 line 需要 8B 双标志位
- 实际传输 128KB（64KB 数据 + 64KB 标志位）
- 带宽浪费了一半

你可能会想：那就根据消息大小动态选择协议不就行了？问题在于，两种协议之间的切换点很难定义，因为它们的性能曲线在中间区域是**重叠且波动**的。

### NCCL Tuner 如何看待这个问题

NCCL 的调优系统明确将 LL128 作为独立的第三选项。从 tuner constants（[src/graph/tuning.cc:151](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/graph/tuning.cc#L151)）可以看到，Ring 算法在 NVLink 连接上的硬件延迟：

| 协议 | LL | LL128 | Simple |
|------|-----|-------|--------|
| **hwLatency (µs)** | 0.6 | 1.9 | 3.4 |

LL128 的延迟（1.9µs）正好位于 LL（0.6µs）和 Simple（3.4µs）之间。这不是偶然的——NCCL 调度器将 LL128 视为处理中等消息的独立选项，而不是另外两种协议的变种。

我们会在后文"何时会使用 LL128"章节详细讨论调度器如何利用这些常量来选择协议。

## Simple 和 LL 的局限性详解

要理解 LL128 的设计，我们需要深入理解 Simple 和 LL 各自的局限性。

### LL Protocol：50% 的带宽税

LL Protocol 使用 16B 的 line 作为传输单位。但这 16 字节不是全部用来传输数据的。

#### LL 的行结构

LL Protocol 的 line 结构在 [src/include/device.h:70-83](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L70-L83) 定义：

```c
union ncclLLFifoLine {
  /* Flags have to be *after* data, because otherwise, an incomplete receive
     from the network may receive the flag but not the data. */
  struct {
    uint32_t data1;   // Bytes 0-3
    uint32_t flag1;   // Bytes 4-7
    uint32_t data2;   // Bytes 8-11
    uint32_t flag2;   // Bytes 12-15
  };
  ...
};
```

**关键点**：这是一个**交错布局**，不是"数据在前、标志在后"。每个 16B line 的结构是：

- Bytes 0-3：`data1`（第一个 4B 数据）
- Bytes 4-7：`flag1`（第一个标志位）
- Bytes 8-11：`data2`（第二个 4B 数据）
- Bytes 12-15：`flag2`（第二个标志位）

总共 8B 数据（data1 + data2）和 8B 标志位（flag1 + flag2），带宽效率 50%。

#### 为什么需要双标志位和交错布局？

代码注释明确指出：**主要原因是防止网络的部分写入**。

在网络传输中，一个 16B 的写入可能被拆成两个 8B 的包，分两次到达。交错布局确保：

1. 即使只收到前 8B（data1 + flag1），接收方也不会错误地认为数据完整（因为 flag2 还没到）
2. 只有两个 flag 都匹配时，才说明 16B 全部到达

**副作用**：交错布局也容忍了 8B 粒度的乱序（因为每个 8B 块都是自包含的：数据+flag），但这不是主要设计目标。

这种设计的**好处**是适配性强，可以在各种网络环境下工作（包括 TCP、IB/RDMA 等）。**代价**是带宽效率只有 50%：

```
有效带宽 = 8B 数据 / 16B 总大小 = 50%
```

#### LL 适合什么场景？

对于小消息（如几 KB），这个损耗是可以接受的，因为：
- 消息总量小，浪费的绝对字节数不多
- 延迟是主要瓶颈，而不是带宽
- LL 的细粒度同步带来的延迟优势超过了带宽损耗

但对于中等消息（如 64KB），50% 的带宽损耗就无法忽视了。传输 64KB 数据需要实际发送 128KB，这在链路带宽有限时会成为瓶颈。

### Simple Protocol：粗粒度流控的等待时间

Simple Protocol 的设计哲学是"攒够一大块再发"。但这个"一大块"到底有多大？

#### Simple 的缓冲区组织

Simple Protocol 使用环形缓冲区，默认参数为（[src/init.cc:699](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/init.cc#L699)）：

```c
#define DEFAULT_BUFFSIZE (1 << 22) /* 4MiB */
```

这个缓冲区被分成 8 个 step（[src/include/device.h:24](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L24)）：

```c
#define NCCL_STEPS 8
```

因此，每个 step 的大小约为：

```
4MiB / 8 = 512KiB
```

#### 流控的粒度

Simple Protocol 使用两个计数器进行流控（详见 [Simple 04:流控机制](../protocol_simple/04_流控机制.md)）：

- **tail**：发送方写到哪个 step 了
- **head**：接收方读到哪个 step 了

关键点在于：**流控的粒度是整个 step**。发送方在开始写入一个新的 step 之前，需要轮询接收方的 head，确保对应的 slot 已经被读走（防止绕圈覆盖）。

#### 中等消息的问题

假设要传输 64KB 的数据：

1. **无法填满一个 step**：64KB 远小于 512KiB
2. **仍需等待 step 级的同步**：虽然只传输 64KB，但流控机制按 step 工作
3. **GPU 大部分时间在空转**：等待同步完成，而不是传输数据

虽然 Simple Protocol 的带宽效率接近 100%（没有额外的 flag 开销），但对于中等消息，**总的传输时间被同步等待拉长了**。

#### Simple 的 grain size

值得一提的是，Simple Protocol 在 Host 端切分消息时使用的最小单位是 512B（[src/include/device.h:309-313](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L309-L313)）：

```c
__host__ __device__ constexpr int ncclProtoGrainSize(int proto) {
  return proto == NCCL_PROTO_LL ? 16 :
         proto == NCCL_PROTO_LL128 ? 1920 /* WARP_SIZE*8/16*15*8 */ :
         proto == NCCL_PROTO_SIMPLE ? 512 :
         -1;
}
```

这个粒度影响 Host 如何将用户数据分配到不同 channel，但不改变 GPU 端 step 级流控的本质。

**关键洞察**：Simple Protocol 的"粗粒度流控"在大消息场景下是优势（减少同步次数），但在中等消息场景下反而成为劣势（引入不必要的等待）。LL Protocol 的"细粒度同步"在小消息场景下是优势（低延迟），但在中等消息场景下反而成为劣势（50% 带宽损耗）。

## LL128 的设计目标

理解了 Simple 和 LL 的局限性，LL128 的设计目标就很清晰了：

### 核心目标

1. **降低带宽开销**：从 LL 的 50% 提升到接近 Simple 的水平
2. **保留细粒度同步**：维持行级验证，不引入 Simple 式的粗粒度等待
3. **复用现有基础设施**：继续使用 step-based 流控、环形缓冲区等机制

### 设计思路

LL128 的核心想法是：**把 LL 的 16B line 放大到 128B，同时从双标志位简化为单标志位**。

这个想法看似简单，但背后有几个关键权衡：

1. **行变大了**：从 16B → 128B，每个传输单位包含更多数据
2. **标志位减少了**：从 2 个 flag → 1 个 flag，每行的元数据开销减半
3. **带宽效率提升了**：从 50% → 93.75%（见下文计算）
4. **付出的代价**：单标志位要求硬件保证 128B 顺序写入（见后文）

### 128B 行的布局

LL128 的行结构在 [src/include/device.h:105-107](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L105-L107) 定义：

```c
#define NCCL_LL128_LINESIZE 128
#define NCCL_LL128_LINEELEMS (NCCL_LL128_LINESIZE/sizeof(uint64_t))  // 16
#define NCCL_LL128_DATAELEMS (NCCL_LL128_LINEELEMS-1)                // 15
```

一个 128B 行包含 16 个 `uint64_t`（每个 8B），分配如下：

- **前 15 个 uint64_t（120B）**：数据槽位
- **最后 1 个 uint64_t（8B）**：标志位

带宽效率计算：

```
有效带宽 = 120B 数据 / 128B 总大小 = 93.75%
```

对比三种协议的带宽效率：

| 协议 | 行大小 | 有效数据 | 标志位开销 | 带宽效率 |
|------|--------|----------|------------|----------|
| LL | 16B | 8B | 8B (双 flag) | 50% |
| LL128 | 128B | 120B | 8B (单 flag) | 93.75% |
| Simple | ~512KiB/step | ~512KiB | 忽略不计 | ~100% |

**LL128 在带宽效率上比 LL 提升了 87.5%（从 50% 到 93.75%），同时保留了行级同步的特性。**

### 为什么选择 128B？

选择 128B 作为行大小不是随意的，而是基于几个工程考虑：

1. **硬件对齐**：128B 是许多 GPU 架构的 cache line 大小，对齐访问可以提高效率
2. **PCIe/网络传输**：PCIe TLP（Transaction Layer Packet）和网络 MTU 通常是 128B 或其倍数，有利于传输效率（一般为 256B）
3. **带宽与延迟的平衡**：
   - 太小（如 64B）：标志位开销仍然较大（8B/64B = 12.5% 开销）
   - 太大（如 256B）：单行传输时间长，影响延迟；且对硬件顺序保证的要求更高

128B 在这三个因素之间找到了平衡点，既显著降低了标志位开销（从 50% 到 6.25%），又不引入过大的延迟。

【经验性考虑】以上权衡是工程经验，并非严格规范保证：不同平台的 cache line、PCIe 事务大小/协商参数、NIC/交换机的 MTU/分段行为各不相同。128B 是在主流平台与 NCCL 实测中较稳妥的折中点；并非所有硬件路径都能一概而论，实际启用仍以 NCCL 的保守策略与运行时校验为准。

## LL128 的核心机制速览

在这一节，我们简要介绍 LL128 的几个核心机制。详细实现会在后续章节展开。

### 机制 1：单标志位的行级同步

前文已经讲解了 LL128 的 128B 行布局（120B 数据 + 8B flag）。这里讲解如何使用这个布局进行同步。

发送方在“行级”的写入顺序是：

1. 写入前 120B 的数据（由多个线程分工完成）
2. 写入最后 8B 的标志位（由 flag thread 写入）

注意：内存屏障并不发生在逐行 flag 之前。屏障在“step 级”的提交阶段执行（见下文），用于在更新 tail 指针之前刷新本 step 的所有写入，使其对对端可见。

接收方读取时：

1. 轮询最后 8B 的标志位，等待其匹配期望值
2. 一旦 flag 匹配，就认为前 120B 数据已经完整到达
3. 读取前 120B 数据

#### 内存屏障的架构差异

内存屏障发生在“step 级”的 `postSend()` 中（更新 tail 之前），而不是逐行 flag 写入之前；其形式与架构相关（[src/device/prims_ll128.h:75-84](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll128.h#L75-L84)）：

```c
#if __CUDA_ARCH__ >= 900
    __threadfence_system();  // Hopper+ (CC >= 90)
#else
    __threadfence();         // Pre-Hopper (CC < 90)
#endif
```

- **Hopper/Blackwell (CC≥90)**：使用 `__threadfence_system()`，提供跨设备的可见性保证（GPU、CPU、NIC 等）
- **更老的架构**：使用 `__threadfence()`，只保证 GPU 内的可见性

这个差异直接影响 LL128 在不同硬件路径上的可用性：
- 节点内通信（GPU-GPU）：两种屏障都足够
- 节点间 GDR（GPU-NIC）：需要 `__threadfence_system()`，因此 Hopper+ 更可靠
- 节点间非 GDR（GPU-Host-NIC）：即使有屏障，仍需 Proxy 验证（见后文）

**关键假设**：单标志位的“行级完整性”依赖于发送端按程序顺序完成“数据→flag”的写入，以及链路对该行的数据与 flag 的顺序到达；`postSend()` 的屏障保证的是“在更新 tail 前，该 step 的数据对对端可见”，并不构成逐行的顺序屏障。这也是 LL128 启用策略保守、并在非 GDR 路径通过 CPU 侧逐行校验兜底的原因（见后文）。

### 机制 2：Flag Thread 的分工

在每个 warp（32 个线程）中，LL128 使用了一种巧妙的分工机制：

- **Flag Thread**：线程 ID 满足 `(tid % 8) == 7` 的线程（即 tid=7, 15, 23, 31）
  - 负责写入和轮询标志位
  - 不负责执行内存屏障（屏障在 step 级的 `postSend()` 中由特定线程组执行，与 flag thread 角色无关）

- **其他线程**：
  - 负责搬运数据（前 120B）
  - 在 flag thread 等待时，并行执行数据加载

这种分工的好处是：

1. **避免冲突**：只有特定线程写 flag，不会有多个线程争抢
2. **隐藏延迟**：flag thread 在轮询时，其他线程可以继续准备数据
3. **保持流水线**：等待被嵌入到流水线中，而不是让整个 warp 停摆

Flag thread 机制的细节（如为什么是 `(tid % 8) == 7`、如何覆盖所有行）会在 [03_Flag Thread 机制](./03_Flag_Thread机制.md) 详细讲解。

### 机制 3：两阶段加载

LL128 的数据传输使用了**两阶段加载**（two-stage loading）来隐藏等待延迟：

1. **loadRegsBegin**：开始从发送缓冲区加载数据到寄存器
2. **waitRecv**：flag thread 轮询接收缓冲区的 flag，等待对端数据到达
3. **loadRegsFinish**：完成数据加载，进行寄存器重排
4. **recvReduceSendCopy**：执行归约计算，写入发送缓冲区

这个流程的关键在于：**step 2 和 step 3 是重叠的**。当 flag thread 在等待对端 flag 时，其他线程在执行 step 3 的寄存器操作。这样就把等待时间"藏"进了流水线。

两阶段加载的详细机制会在 [04_机制协奏实例](./04_机制协奏实例.md) 讲解。

### 复用 LL 的基础设施

值得强调的是，LL128 并没有重新发明轮子。它复用了 LL Protocol 的几乎所有基础设施：

- **环形缓冲区**：同样使用 8 个 step 的环形缓冲区
- **Step 流控**：同样使用 step 级的 head/tail 计数器防止绕圈覆盖
- **连接结构**：同样使用 `ncclConnInfo` 等数据结构
- **Primitives 接口**：同样实现 `send()`、`recv()`、`reduce()` 等原语

唯一的区别在于：

- **行大小**：从 16B → 128B
- **标志位数量**：从 2 个 → 1 个
- **线程分工**：引入了 flag thread 机制

**关键洞察**：LL128 不是一个全新的协议，而是在 LL 的框架上做了精心的调整。它继承了 LL 的细粒度同步理念，但通过增大行、减少 flag、引入线程分工，在带宽效率上向 Simple 靠拢。

## 单标志位的代价：硬件顺序保证

LL128 的单标志位设计看起来很优雅，但它建立在一个脆弱的假设之上：**硬件保证 128B 的写入是顺序到达的**。

### 为什么需要顺序保证？

回顾一下 LL128 的同步机制：

1. 发送方先写 120B 数据，再写 8B flag
2. 接收方看到 flag 后，就认为前 120B 数据已经完整到达

这个逻辑的正确性依赖于：**flag 的到达晚于或等于数据的到达**。如果硬件允许乱序写入，就可能出现这种情况：

```
时间轴：
T0: 发送方写入 120B 数据
T1: 发送方写入 8B flag（程序顺序）
T2: 接收方看到 flag（但部分数据还在路上！）
T3: 接收方读取数据 → 读到旧数据或部分新数据 → 错误！
```
（说明：step 级的内存屏障发生在更新 tail 之前，不影响上述“行级乱序”示例的成立。）

这就是为什么 LL 需要双标志位——它容忍乱序，通过两个 flag 的组合来确认数据完整性。

### 哪些硬件路径可以保证顺序？

NCCL 对不同硬件路径有不同的假设：

**节点内通信**（GPU-to-GPU via NVLink/PCIe）：
- NVLink 和 PCIe 维持来自同一源的地址有序写入（address-ordered writes）
- GPU 的 `__threadfence()` 确保前序写入在后续写入之前对其他 GPU 可见
- 因此，节点内的 LL128 通常是安全的

**节点间通信**（GPU-to-GPU via RDMA）：
- RDMA 网络可能会把 128B 的写入拆成多个子事务
- 不同子事务可能经过不同的路径，到达顺序无法保证
- 交换机、NIC、PCIe 等环节都可能引入乱序

- **GPU Direct RDMA (GDR)**：GPU 直接写入 NIC 内存
  - Hopper+ 使用 `__threadfence_system()`，提供跨设备的可见性和顺序保证
  - LL128 在 GDR 路径上（配合正确的架构）通常是安全的

- **Host Memory Bounce Buffer**：数据先写入主机内存，再由 Proxy 线程发送
  - GPU 的 `__threadfence()` 确保写入对 CPU **可见**，但不保证 CPU 观察到的**顺序**
  - PCIe 的写合并（write combining）和 posted writes 可能导致 CPU 看到乱序
  - 因此，Proxy 线程必须在 CPU 侧**逐行验证 flag**（[src/transport/net.cc:1283-1294](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/transport/net.cc#L1283-L1294)），确保每行数据完整后再发送
  - 这增加了额外的 CPU 开销，但保证了正确性

### 实际的启用逻辑

NCCL 的 LL128 启用策略非常保守，只在经过验证的硬件路径上打开。让我们看看实际代码（[src/graph/tuning.cc:478-494](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/graph/tuning.cc#L478-L494)）：

```c
for (int c=0; c<NCCL_NUM_FUNCTIONS; c++)
  for (int a=0; a<NCCL_NUM_ALGORITHMS; a++)
    for (int p=0; p<NCCL_NUM_PROTOCOLS; p++) {

  int pEnable = protoEnable[c*NCCL_NUM_PROTOCOLS+p];

  if (pEnable == 2 && p == NCCL_PROTO_LL128) {
    pEnable = 1;

    // 条件 1: 架构相关的链路类型限制
    if (ncclParamLl128C2c() && minCompCap >= 90) {
      // Hopper/Blackwell + NCCL_LL128_C2C=1: 允许到 PXN
      pEnable &= (graphs[a]->typeInter <= PATH_PXN);
    } else {
      // 其他情况: 只允许到 PXB
      pEnable &= (graphs[a]->typeInter <= PATH_PXB);
      if (!ncclParamLl128C2c() && minCompCap >= 90)
        INFO(NCCL_GRAPH, "Disabling LL128 over all PxN connections (PXB and C2C). "
             "This ensures that no C2C link will be used by LL128.");
    }

    // 条件 2: 节点内链路类型
    pEnable &= (graphs[a]->typeIntra <= PATH_NVB);

    // 条件 3: GPU 架构必须一致
    pEnable &= (minCompCap == maxCompCap);

    // 条件 4: 最低架构要求 + 特定 bug 规避
    pEnable &= !(minCompCap < 70 ||
                 (minCompCap == 90 && CUDART_VERSION == 11080 &&
                  c == ncclFuncAllReduce && a == NCCL_ALGO_RING &&
                  comm->nRanks == 2));
  }

  if (pEnable == 0) comm->bandwidths[c][a][p] = 0;
}
```

让我们解读这段代码：

#### 条件 1：节点间链路类型（typeInter）

- **PATH_PXB**：GPU 之间通过 PCIe + PCIe bridge 连接
- **PATH_PXN**：GPU 之间通过 PCIe + NVLink 的混合路径
- **PATH_PXN 包含 PATH_C2C**：GPU-to-GPU Cache Coherent (C2C) 连接

默认策略：
- **Hopper/Blackwell (CC≥90) + `NCCL_LL128_C2C=1`**：允许 LL128 使用到 PATH_PXN（包括 C2C）
- **其他情况**：只允许 LL128 使用到 PATH_PXB

这反映了 NCCL 团队对不同链路类型的顺序保证的信心水平。

#### 条件 2：节点内链路类型（typeIntra）

```c
pEnable &= (graphs[a]->typeIntra <= PATH_NVB);
```

只有当节点内链路是 NVLink/NVBridge 时，才启用 LL128。这是因为 NVLink 可以保证来自同一源的写入顺序。

#### 条件 3：GPU 架构一致性

```c
pEnable &= (minCompCap == maxCompCap);
```

所有 GPU 必须是相同的架构（compute capability）。这避免了不同架构的内存一致性行为差异。

#### 条件 4：最低架构要求

```c
pEnable &= !(minCompCap < 70 || ...);
```

最低要求 Volta (CC 70) 或更高。Pre-Volta 架构的内存一致性保证不足以支持 LL128。

#### 用户控制

用户可以通过环境变量来覆盖默认策略：

- **`NCCL_PROTO=LL,LL128,SIMPLE`**：强制启用 LL128（自担风险）
- **`NCCL_PROTO=^LL128`**：完全禁用 LL128
- **`NCCL_LL128_C2C=1`**：在 Hopper/Blackwell 上允许 LL128 使用 C2C 连接

但官方文档明确提示：这些是调试选项，非默认配置下的正确性由用户自行验证。

**关键洞察**：单标志位设计的效率提升是有代价的——它牺牲了适配性。LL Protocol 的双标志位可以在任何硬件路径上工作（虽然效率低），而 LL128 的单标志位只能在特定的、经过验证的硬件路径上工作。这是一个典型的"效率 vs 适配性"权衡。

## 何时会使用 LL128？

理解了 LL128 的设计和限制，最后一个问题是：什么时候 NCCL 会实际选择 LL128？

### 协议选择的基本原则

NCCL 的调度器在运行时根据多个因素选择协议（详见 [src/enqueue.cc](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/enqueue.cc)）：

1. **消息大小**：主要决定因素
2. **通道数量**：影响每个通道分配到的数据量
3. **连接状态**：各协议的缓冲区是否已准备
4. **拓扑特性**：链路类型、架构等（影响启用条件）

### 典型的消息大小区间

虽然没有硬编码的阈值，但根据 tuner 的带宽估算，典型的使用场景是：

- **LL**：适合 < 8-16KB 的小消息
  - 延迟最低（0.6µs）
  - 50% 带宽损耗在小消息场景下不明显

- **LL128**：适合 8-64KB 的中等消息（取决于硬件）
  - 延迟适中（1.9µs）
  - 93.75% 带宽效率，适合中等数据量
  - 保留行级同步，避免粗粒度等待

- **Simple**：适合 > 64-128KB 的大消息
  - 延迟最高（3.4µs），但对大消息影响小
  - 接近 100% 带宽效率
  - 粗粒度流控在大消息场景下高效

这些数字不是绝对的——实际的切换点取决于：
- 硬件性能（如 NVLink 带宽）
- 通道数量（数据被分散到多个通道）
- 缓冲区大小（影响 step 的大小）

### 调度器的决策过程（简化的启发式）

NCCL 的实际协议选择逻辑分散在多个函数中（如 `src/enqueue.cc` 中的调度代码和 `src/graph/tuning.cc` 中的带宽估算），涉及复杂的启发式规则。这里给出一个简化的概念流程，帮助理解基本思路：

1. **计算每种协议的预期带宽**：
   - 使用 tuner constants（hwLatencies, perChMaxRingLL128Bws 等）
   - 考虑消息大小、通道数、硬件拓扑等因素
   - 估算有效带宽（考虑延迟和最大带宽的综合影响）

2. **选择带宽最高的协议**：
   - 比较 LL、LL128、Simple 的预期带宽
   - 选择带宽最高的协议（前提是已启用）

3. **检查启用条件**：
   - 如果选中的协议未启用（如 LL128 被硬件限制禁用）→ 回退到次优协议

**注意**：这只是一个简化的概念模型。实际的选择逻辑还考虑了连接状态、缓冲区可用性、历史性能数据等因素。要理解完整的决策过程，需要深入阅读 `src/enqueue.cc` 和 `src/graph/tuning.cc` 的代码。

### Tuner Constants 详解

前文提到调度器使用 tuner constants 来估算每种协议的性能。让我们详细看看 NCCL 为 LL128 定义的常量（[src/graph/tuning.cc:142-199](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/graph/tuning.cc#L142-L199)）。

#### 硬件延迟常量（hwLatencies）

对于不同的链路类型，NCCL 定义了基础延迟（单位：微秒）：

```c
.hwLatencies = {
  /* NVLINK */
  { .6, 1.9, 3.4 }, /* Ring (LL/LL128/Simple) */

  /* PCI */
  { 1.0, 2.5, 5.7 }, /* Ring (LL/LL128/Simple) */

  /* NET (跨节点) */
  { 2.7, 4.0, 14.0 }, /* Ring (LL/LL128/Simple) */
}
```

可以看到：
- **NVLink**：LL128 (1.9µs) 比 Simple (3.4µs) 快约 44%
- **PCIe**：LL128 (2.5µs) 比 Simple (5.7µs) 快约 56%
- **跨节点**：LL128 (4.0µs) 比 Simple (14.0µs) 快约 71%

对于小到中等消息，这些延迟差异非常显著。

#### LL128 每通道最大带宽

NCCL 还为不同架构定义了 LL128 的带宽上限（单位：GB/s）：

```c
.perChMaxRingLL128Bws = {
  {20.0, 20.0, 20.0}, /* Volta (N1/N2/N4) */
  {20.0, 20.0, 20.0}, /* Ampere (N1/N2/N4) */
  {36.7, 36.7, 36.7}, /* Hopper (N1/N2/N4) */
  {2*36.7, 34.6, 2*36.7}, /* Blackwell (N1/N2/N4) */
}
```

这些数值（N1/N2/N4 表示节点内 GPU 数量）体现了：
- Volta/Ampere：每通道约 20 GB/s
- Hopper：每通道约 36.7 GB/s（提升 83%）
- Blackwell：某些配置可达 73.4 GB/s

调度器会用这些常量结合消息大小、通道数等因素，计算每种协议的预期带宽，从而做出选择。

### 实际观察

你可以通过环境变量 `NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=TUNING` 来观察 NCCL 的协议选择：

```bash
NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=TUNING ./your_program
```

输出会包含类似的信息：

```
NCCL INFO Channel 00 : 32768 bytes, expected BW = 20.5 GB/s (LL128)
NCCL INFO Channel 00 : 131072 bytes, expected BW = 35.2 GB/s (Simple)
```

这些信息可以帮助你理解 NCCL 为什么选择特定的协议。

## 关键洞察

让我们总结一下 LL128 Protocol 的核心要点：

1. **协议定位的量化证据**
   - NCCL 的 tuner constants 明确将 LL128 作为独立协议（延迟 1.9µs，介于 LL 的 0.6µs 和 Simple 的 3.4µs 之间）
   - 不是 LL 的变种，也不是 Simple 的简化，而是在不同的权衡点上

2. **带宽效率的阶跃提升**
   - LL128 通过 128B 行 + 单标志位，将带宽效率从 50% 提升到 93.75%
   - 这是一个 87.5% 的相对提升，对中等消息至关重要

3. **单标志位的双刃剑**
   - **优势**：减少元数据开销，提高带宽效率
   - **代价**：依赖硬件的顺序写入保证，限制了适用范围
   - **平衡**：通过保守的启用策略，只在经过验证的路径上使用

4. **机制的精心设计**
   - Flag Thread 机制：避免冲突，隐藏延迟
   - 两阶段加载：把等待嵌入流水线
   - 复用 LL 基础设施：最小化实现复杂度

5. **适用场景的明确性**
   - 中等消息（典型 8-64KB）是 LL128 的"主场"
   - 小消息用 LL（延迟优先），大消息用 Simple（带宽优先）
   - LL128 填补了两者之间的性能空档

**最核心的洞察**：LL128 的存在揭示了一个深刻的系统设计原则——**不存在"最优的单一协议"**。不同的消息大小、硬件特性、应用场景需要不同的权衡。NCCL 通过提供三种协议，让调度器在运行时选择最适合当前场景的方案，而不是强迫所有场景使用同一种"万能"协议。

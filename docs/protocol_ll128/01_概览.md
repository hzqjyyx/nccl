# 01 LL128 Protocol 概览

这章回答一个看似简单但常被忽视的问题：在 NCCL 的 Ring AllReduce 中，Simple 与 LL 两端已经覆盖了“超大消息追求带宽”和“小消息追求延迟”，为什么还要多出一条名叫 LL128 的“第三条路”？换句话说，我们面对的真正矛盾是什么、目标是什么，以及这条路径在实现层面依赖哪些前提。

## 1. 中等消息的现实压力

单 GPU 的 AllReduce 实际承载着一条“消息光谱”：从几十 KB 的优化器统计，到数百 MB 的梯度。NCCL 在 `ncclTunerConstantsDefaults` 中对协议延迟和带宽做了硬编码取值（见 `src/graph/tuning.cc`），这些常量呈现出一个明确信号：LL128 的基础延迟和通道带宽都位于 LL 与 Simple 之间，被刻意视为独立选项。

典型深度学习工作负载同样验证了这片“灰色地带”：

- Tensor/FSDP 框架把 10–100 MB 的大梯度拆成 0.5–2 MB 的片段；
- ZeRO 优化器对参数分片的同步、MoE 的路由统计、推理阶段的 KV Cache 共享，都频繁落在几十至数百 KB。

这些消息既不够大到能很好地摊平 Simple 的等待，也不够小到值得承受 LL 的 50% 带宽损耗，于是它们持续逼问 NCCL：有没有一套机制能兼顾两端哲学？

## 2. Simple 与 LL 的两端哲学

要理解 LL128，就得重新审视两个端点的“极致”：

- **Simple**：把数据攒成 128KB 级别的 chunk，再一次性写入对端，通过粗粒度的 `waitSend`/`postSend` 同步换取几乎满负载的带宽；代价是启动等待长、缓冲区压力大。
- **LL**：把传输单位缩到 16B，且每 8B 数据都跟一个 flag。看到 flag 就意味着数据有效，不需要昂贵的内存屏障；好处是延迟极低，坏处是有效带宽砍半。

这两个协议各自拿走一端的“极致”效果，却在中间留下了大片空档。

## 3. LL128 的设计目标

LL128 的目标不是再把延迟压低 10%，而是在“中等消息”区间找到一条综合路线：

- 尽量重用 LL 的小粒度顺序保证，让流水线可以保持扇出；
- 在带宽利用率上向 Simple 靠拢，不再容忍 50% 的损耗；
- 避免引入新的控制栈，让现有的流控（例如 step）继续工作。

因此，它选择把 LL 的 16B 行放大到 128B，同时保留行级同步的原则。

## 4. 核心机制速览

下文先给出三块最重要的“积木”，帮助读者建立轻量直觉。后续章节会逐块展开，这里只强调感性认识。

### 4.1 128B 行与单 flag

可以把 LL 的 16B 小托盘换成 LL128 的 128B 托盘：前 120B 用来搬运数据，最后 8B 是标志。托盘一旦盖上“已完成”的章，就表示前面的货物已经安全送达，不需要额外的屏障等待。托盘越大，单位货物要携带的旗帜越少，带宽利用率就随之提高，最终接近 94%。

### 4.2 Flag Thread 的分工

每个 warp 会挑出线程 ID 以 8 取模等于 7 的几位同伴，让他们扮演“核验员”。核验员负责写入并轮询那 8B 的标志，其余线程则专注于把数据搬上托盘。大家执行同一段代码，但在关键位置扮演不同角色。这样既避免多个线程争抢标志，又保证流水线里始终有人关注托盘是否可以启程。

### 4.3 把等待藏进流水线

核验员在等待对端回章时，其余线程不会傻等，而是继续完成寄存器加载、准备下一批数据。等到核验员确认 flag，数据就能立刻“出厂”。这是一种把等待嵌入流水线的手法——延迟仍然被控制在小粒度上，却不会让整个 warp 因为标志而停摆。

整体上，LL128 仍沿用 LL 的构造器、连接结构与 step 流控，只是把同步粒度换成了更大的托盘，让中等消息拥有更顺滑的节奏。

## 5. 硬件与启用前提

单 flag 的假设很脆弱：只有在整条链路都能保证 128B 顺序写入时，flag 才能代表“整行有效”。NCCL 官方在多起 issue（例如 `#786`、`#1728`、`#2540`）中给出的解释是：

- **节点内**：必须确认 GPU 内存系统、NVLink、NVSwitch 都不会打乱写入顺序；
- **节点间**：还要包含 PCIe、交换芯片、NIC 以及网络 fabric；
- **缓冲区位置**：GPU 内存通常可靠，系统内存或非 GDR 路径则要靠 Proxy 逐行校验。

因此，默认启用策略很保守——只在 Volta/Ampere/Hopper 等我们验证过的 NVLink 平台自动打开。用户可以通过 `NCCL_PROTO=LL,LL128,SIMPLE` 强制启用，或者用 `NCCL_PROTO=^LL128` 禁用；但官方明确提示，这属于自担风险的调试选项。

## 6. 关键洞察

- NCCL 在调优常量与默认配置上，将“中等消息”视为必须单独对待的区间。
- Simple 和 LL 各自登顶带宽/延迟，却留下了一个“无法兼得”的空档。
- LL128 通过“128B 行 + Flag Thread + 流水线重叠”三个手势，把 LL 的因果保证和 Simple 的带宽取长补短。
- 这套设计建立在链路严格顺序写入的前提之上，因此默认只在经过验证的平台打开。

## 7. 后续阅读路线

为了深入理解 LL128，建议按以下顺序继续阅读后续章节：

1. **继承与创新**：辨别哪些数据结构与控制流完全沿用 LL，哪些部分需要新的心智模型。
2. **128B 行与内存组织**：拆解行布局、slice 计算和环形缓冲区组织。
3. **Flag Thread 机制**：跟踪 `(tid % 8) == 7` 线程在内核中的角色与寄存器重排。
4. **机制协奏**：用一次 `recvReduceSend` 流程把 flag、step、流水线连接起来，建立整体直觉。

掌握了以上基础，后续的调优、调试与实战场景才有赖以落脚的认知框架。

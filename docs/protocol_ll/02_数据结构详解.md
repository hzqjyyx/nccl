# LL Protocol 数据结构详解

## 引言

在第一章,我们了解了 LL Protocol 的核心思想:**细粒度传输 + 每字节完整性保证**。LL 把数据切成很小的单元(16 字节),逐个传输,每个单元都有完整性验证。

本章的目标是建立 LL Protocol 的"数据地图"——一个清晰的、层次化的数据结构视图。在后续章节阅读代码时,你可以随时回来这里查阅。

**本章的三个核心问题**:
1. **LL 的数据结构有哪些层次?** (全景图)
2. **为什么是 16 字节?为什么标志在数据之后?** (Line 的设计)
3. **LL Primitives 的成员变量如何支撑这个数据结构?** (实现细节)

让我们从全景图开始。

---

## 第一部分:全景图

在深入细节之前,让我们先建立一个自顶向下的全景视图。LL Protocol 的数据结构是**四层嵌套**的,也是一份“谁对谁同步”的契约。

### 四层嵌套结构概览

从外到内,LL Protocol 的数据结构如下:

```
🔷 环形缓冲区 (Ring Buffer)
  ├─ 总大小: buffSizes[NCCL_PROTO_LL] (默认 512 KB)
  ├─ 作用: 支持流水线传输,让发送/接收异步工作
  └─ 划分成 8 个 slot (NCCL_STEPS = 8)
      ↓
    🔶 Step (流控单元)
      ├─ 大小: buffSize / NCCL_STEPS (默认 64 KB)
      ├─ 作用: 粗粒度流控单元 (waitSend/postRecv)
      └─ 包含 stepLines 个 line (默认 4096 个)
          ↓
        🔹 Line (传输单元)
          ├─ 大小: 16 字节
          ├─ 组成: 8 字节数据 + 8 字节标志
          ├─ 作用: LL 的原子传输单元,readLL/storeLL 的操作对象
          └─ 包含 EltPerLine 个元素 = 8 / sizeof(T)
              ↓
            🔸 Element (用户数据)
              ├─ 大小: sizeof(T) (如 float32 = 4 字节)，一个 Line 包含 2 个 float32
              └─ 作用: 用户数据的基本单位
```

更直接的可视化如下

**需要记住的两条公式**:
```
stepLines = buffSizes[NCCL_PROTO_LL] / NCCL_STEPS / sizeof(ncclLLFifoLine)
EltPerLine = 8 / sizeof(T)
```

## 第二部分:逐层深入

现在我们有了全景图,让我们逐层深入,理解每一层的设计原理。

### 环形缓冲区 (Ring Buffer)

#### 总大小计算

LL Protocol 的环形缓冲区大小由 `DEFAULT_LL_BUFFSIZE` 宏定义([init.cc:697](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/init.cc#L697)):

```c
#define DEFAULT_LL_BUFFSIZE \
  (NCCL_LL_LINES_PER_THREAD * NCCL_LL_MAX_NTHREADS * NCCL_STEPS * sizeof(union ncclLLFifoLine))
```

**计算结果**：代入参数值（8 × 512 × 8 × 16），得到 524,288 字节 = **512 KB**。

**这个公式的含义**:
- **每个线程** 处理 `NCCL_LL_LINES_PER_THREAD` (8) 个 line
- **最多** `NCCL_LL_MAX_NTHREADS` (512) 个线程并行工作
- **环形缓冲区** 有 `NCCL_STEPS` (8) 个 slot 支持流水线
- **每个 line** 占用 16 字节

#### buffSizes 从哪里来?

`buffSizes` 是 host 端初始化时计算出的运行时配置:

1. `computeBuffSizes()` 先读取 `NCCL_LL_BUFFSIZE` 等环境变量,否则采用 `DEFAULT_LL_BUFFSIZE` 等默认值([init.cc:660-708](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/init.cc#L660-L708))。
2. 结果写入 `ncclComm::buffSizes[]`,随通信器一起下发到 GPU。
3. Kernel 启动时,`ncclKernelComm` 被复制到共享内存的 `ncclShmem.comm`,device 端用 `ncclShmem.comm.buffSizes[NCCL_PROTO_LL]` 读取。

这样,即便运行时调整了 `NCCL_LL_BUFFSIZE`,device 端也能按最新配置计算 `stepLines`。

### Step (流控单元)

#### 每个 step 的大小

环形缓冲区被均匀划分成 `NCCL_STEPS` 个 slot,每个 slot 对应一个 **step**。Step 的总字节数是 `stepLines × sizeof(ncclLLFifoLine)`(默认 64 KB),但有效载荷只有前面定义的 50%，即 32 KB。

Step 是 **流控的基本单位**:
- `waitSend(step)`: 发送方自旋等待，确保自己最多领先接收方 `NCCL_STEPS` 个 step,也就是 `8 × 32 KB` 的数据。
- `postRecv(step)`: 接收方在消费完一个 step 后发布新 head，解除发送方的限速。

#### stepLines: 桥梁参数

`stepLines` 是 LL Protocol 中**最重要的参数之一**,它连接了数据结构和流控。

**定义**([prims_ll.h:335](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L335)):
```cpp
stepLines(ncclShmem.comm.buffSizes[NCCL_PROTO_LL]/NCCL_STEPS/sizeof(ncclLLFifoLine))
```

**含义**: 每个 step 包含多少个 line

#### 从 step 到 offset

给定一个 step 计数器(如 `recvStep[i]`),如何找到它在环形缓冲区中的位置?

**公式**:
```cpp
offset = (step % NCCL_STEPS) * stepLines
```

**为什么以 line 为单位?**

注意 `offset` 的单位是 **line**，不是字节。为什么?

因为 LL Protocol 的所有操作都以 line 为单位:
- `readLL(offset, i)`: offset 是 line 的索引
- `storeLL(sendPtr(i) + offset, ...)`: 指针偏移是 line 的偏移
- `recvPtr(i)`: 返回 `ncclLLFifoLine*` 指针

用 line 数量比字节数更自然,也避免了重复的除法运算。

### Line (传输单元)

Line 是 LL Protocol 的核心。让我们深入理解它的设计。

#### ncclLLFifoLine 的定义

LL Protocol 的传输单元是 `ncclLLFifoLine`,定义在 [device.h:70-83](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L70-L83):

```c
union ncclLLFifoLine {
  /* Flags have to be *after* data, because otherwise, an incomplete receive
     from the network may receive the flag but not the data.
     Note this is assuming that either we receive contiguous chunks of data
     (sockets) or data is written with an atomicity of 8 bytes (IB/RDMA). */
  struct {
    uint32_t data1;
    uint32_t flag1;
    uint32_t data2;
    uint32_t flag2;
  };
  uint64_t v[2];
  int4 i4;
};
```

这个 `union` 定义了三种访问方式:
1. **结构体访问**: `data1`, `flag1`, `data2`, `flag2` (4 个 `uint32_t`)
2. **uint64_t 数组**: `v[2]` (2 个 8 字节,用于 `readLL` 返回值)
3. **int4 向量**: `i4` (cuda 引入的128 位向量,用于 `storeLL` 一次写入 16 字节)

**内存布局**:
```
偏移量: 0      4      8      12     16 (Bytes)
       +------+------+------+------+
       |data1 |flag1 |data2 |flag2 |
       +------+------+------+------+
       |<- 8 Bytes ->|<- 8 Bytes ->|
       |   v[0]      |     v[1]    |
       +------+------+------+------+
       |<--- int4 (16 Bytes) ----->|
```

**核心事实**:
- **总大小**: 16 字节
- **有效数据**: 8 字节 (data1 + data2)
- **标志开销**: 8 字节 (flag1 + flag2)
- **有效数据占比**: 50%

#### 为什么是 16 字节?

这是 LL Protocol 设计中**最重要的问题**。让我们从设计约束出发,理解为什么最终选择了 16 字节。

##### 1. 设计约束: RDMA 的 8 字节原子性

看代码注释([device.h:71-74](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L71-L74)):

```c
/* Flags have to be *after* data, because otherwise, an incomplete receive
   from the network may receive the flag but not the data.
   Note this is assuming that either we receive contiguous chunks of data
   (sockets) or data is written with an atomicity of 8 bytes (IB/RDMA). */
```

**关键约束**: RDMA 只保证 8 字节的原子性。

这意味着:
- 每次 RDMA 写操作可以原子地传输 8 字节
- 如果要传输更多数据,需要多次 8 字节的操作
- 这些操作之间**可能不是原子的**,可能存在乱序或部分完成

**核心问题**: 如何在 8 字节原子性约束下,保证数据完整性?

LL Protocol 需要解决的问题是:接收方如何知道收到的数据是完整的、没有损坏的? 答案是:**在每次 8 字节传输中同时包含数据和验证标志**。

##### 2. 方案对比: 为什么不用 8 字节 line?

你可能会想:为什么不用 8 字节的 line (4B 数据 + 4B 标志)?

**方案 A (效率太低)**: 8 字节 line = [data (4B)][flag (4B)]

问题:
- 每个 line 只携带 4 字节有效数据(而不是 8 字节)
- 要传输同样多的数据,`readLL`/`storeLL` 调用次数翻倍
- 标志验证、step 管理等控制开销也翻倍
- `EltPerLine` 从 `8/sizeof(T)` 变成 `4/sizeof(T)`,主循环迭代次数翻倍

##### 3. 方案对比: 为什么不分离数据和标志?

**方案 B (错误)**: 先传输全部数据,再传输标志
- 第一次 8 字节: 全是数据 (8B)
- 第二次 8 字节: 全是标志 (8B)

问题:**网络乱序导致数据损坏**

假设布局是 `[data (8B)][flag (8B)]`,传输需要两次 8 字节写:
1. 第一次: 写 data (8B)
2. 第二次: 写 flag (8B)

如果网络出现乱序或重试,第二次写(flag)可能先于第一次写(data)生效。接收端看到 flag 已是新值,误以为整段数据准备好了,但实际上 data 还没更新——**数据完整性被破坏**。

##### 4. NCCL 的解决方案: 数据和标志交错 + 双标志位

正确的 16 字节布局:
```
[data1 (4B) | flag1 (4B)][data2 (4B) | flag2 (4B)]
 \_____第1个8字节_____/ \_____第2个8字节_____/
```

这个设计的精妙之处:
1. **每个 8 字节传输都包含"数据+标志"**: 即使只完成了一次 8 字节写,也有对应的标志可以验证
2. **双标志位验证**: 接收方检查 `flag1 == flag && flag2 == flag`,确保**两次 8 字节都已到达**
3. **屏蔽乱序**: 无论哪个 8 字节先到,接收方都会等到两个标志都匹配才使用数据

接收方的验证逻辑:
- 如果只到了前半段: `flag1` 是新值,`flag2` 是旧值 → 继续自旋等待
- 如果只到了后半段: `flag2` 是新值,`flag1` 是旧值 → 继续自旋等待
- **只有两个标志都是新值,才退出自旋** → 两次 8 字节写都已落地

换句话说,两个标志不是"重复验证同一件事",而是**分别为两个半行数据建立了"就地确认"信号**,屏蔽了底层传输的乱序。

##### 5. 为什么是 16 字节而不是更大?

你可能会想:既然 16 字节有效,那 32 字节、64 字节是不是更好?

答案是:**16 字节是效率和粒度的最佳平衡点**。

- **更大的 line (如 32B)**: 虽然有效数据更多,但需要更多次 RDMA 写,标志验证更复杂,细粒度优势减弱
- **16 字节**: 两次 RDMA 写,双标志位验证,简单高效,粒度够细

##### 6. 最终结果: readLL 返回 uint64_t

设计从 RDMA 约束出发,最终选择了 16 字节 line (8B 数据 + 8B 标志)。因此,`readLL` 返回的是 **8 字节有效数据** ([prims_ll.h:98](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L98)):

```cpp
__device__ uint64_t readLL(int offset, int i) {
  ...
  uint64_t val64 = data1 + (((uint64_t)data2) << 32);
  return val64;
}
```

##### 硬件原子性在这里起作用

代码里看不到任何 `atomic*` 指令,是因为 LL 借的是底层传输层本来就提供的"8 字节写入不可撕裂"保证。注释已经提醒了这一点([device.h:70-83](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L70-L83))。

**两个层次的操作**：

1. **GPU 指令层**：发送方用单条 `st.volatile.global.v4.u32` 把四个 `uint32_t`（16 字节）作为 128 位向量一次性写出去([prims_ll.h:126-128](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L126-L128))。这是单条 PTX 指令。

2. **传输层**：底层互连（RDMA/PCIe/NVLink）**只保证 8 字节传输的原子性**。即使 GPU 发出的是 16 字节写，传输层可能会将其分成两次 8 字节事务。关键是：
   - 每次 8 字节事务是原子的（不可撕裂）
   - 两次事务之间可能乱序到达
   - "数据1+flag1"这 8B 和"数据2+flag2"那 8B 各自完整落地，但到达顺序不确定

接收方的 `readLL` 通过 `ld.volatile.global.v4.u32` 轮询这 16B，只有在**两个 flag 都已经变成期望值**时才使用对应的数据([prims_ll.h:89-99](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L89-L99))。这就是双标志位机制的作用：屏蔽传输层可能的乱序，确保两次 8 字节都已到达。

所以所谓的"原子性"并不是软件层的原子操作，而是利用**传输层对 8 字节写的原子性承诺**，再辅以**双标志位验证**来处理可能的乱序。

**关键洞察**:
- **16 字节不是为了对齐**,而是为了在 RDMA 的 8 字节原子性约束下,保证 8 字节有效数据的完整性传输
- **双标志位是核心**,不是冗余
- **标志后置是正确性保证**,不可省略

### 4. Element (用户数据)

我们已经了解了 line (16 字节) 和 step (多个 line) 的组织。但用户数据是以**元素**(如 `float`, `int8`)为单位的,如何映射到 line?

这就是 `EltPerLine` 的作用。

#### EltPerLine 的计算

`EltPerLine` 是一个编译时常量([prims_ll.h:130](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L130)):

```cpp
static constexpr int EltPerLine = sizeof(uint64_t) / sizeof(T);
```

**含义**: 每个 line 可以容纳多少个类型为 `T` 的元素。

**为什么是 `sizeof(uint64_t) / sizeof(T)`?**

因为每个 line 携带 **8 字节有效数据**(不是 16 字节总大小)。所以:
```
EltPerLine = 8 字节 / sizeof(T)
```

根据数据类型 `T` 的大小,`EltPerLine` 有不同的值:

**示例 (float32)**:
```
[data1: 4B] [flag1: 4B] [data2: 4B] [flag2: 4B]
 └─ float0              └─ float1

有效数据: 2 个 float32
EltPerLine = 2
```

**示例 (int8)**:
```
[data1: 4B]       [flag1] [data2: 4B]      [flag2]
 └─ int8: 0,1,2,3          └─ int8: 4,5,6,7

有效数据: 8 个 int8
EltPerLine = 8
```

## 第三部分: LL Primitives 的成员变量

现在我们理解了 LL 的数据结构(Ring Buffer → Step → Line → Element),接下来看 LL Primitives 如何使用这些结构。

Primitives 是 LL Protocol 的"引擎",负责数据的读取、写入和同步。它的成员变量反映了 LL 的设计特点。

### 核心成员概览

LL Primitives 的成员变量定义在 [prims_ll.h:16-44](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L16-L44):

```cpp
template<typename T, typename RedOp, typename Fan, int Direct, int P2p, bool isNetOffload>
class Primitives<T, RedOp, Fan, Direct, ProtoLL, P2p, isNetOffload> {
  static constexpr int MaxRecv = Fan::MaxRecv > 1 ? Fan::MaxRecv : 1;
  static constexpr int MaxSend = Fan::MaxSend;
  static constexpr int Input=0, Output=1;

  RedOp redOp;
  const int tid;        // 线程 ID
  const int nthreads;   // 总线程数
  const int wid;        // warp 内线程索引
  const int group;      // 线程组 ID
  const int stepLines;  // 每个 step 的 line 数量 (关键!)
  Fan fan;
  T *userBufs[2];       // 用户缓冲区 (Input/Output)

  // Recv 连接
  struct ncclConnInfo* recvConn = NULL;
  volatile uint64_t* recvConnHeadPtr = NULL;
  uint64_t recvConnHead;

  // Send 连接
  struct ncclConnInfo* sendConn = NULL;
  volatile struct ncclConnFifo* sendConnFifo = NULL;
  volatile uint64_t* sendConnHeadPtr = NULL;
  uint64_t sendConnHead;
  uint64_t sendConnHeadCache;

  // 每个 peer 的状态 (数组!)
  uint64_t recvStep[MaxRecv];
  uint64_t sendStep[MaxSend];
  union ncclLLFifoLine* recvBuff[MaxRecv];
  union ncclLLFifoLine* sendBuff[MaxSend];

  // 辅助函数 (见后文)
  // ...
};
```

让我们逐类讲解。

### 线程信息

```cpp
const int tid;        // 线程 ID（组内，从 0 计）
const int nthreads;   // 该组的线程总数
const int wid;        // warp 内线程索引 (tid % WARP_SIZE)
const int group;      // 线程组编号（组与组之间隔离同步）
```

概念：
- thread（tid）→ 组内的最小执行单元；决定每个线程处理的 line 偏移。
- warp（wid）→ 组内协作的基本粒度，也叫 lane；`wid` 是 warp 内线程索引（lane ID），计算为 `tid % WARP_SIZE`。用于 `__shfl_*` 等 warp 内通信与归约，以及按 lane 条件加载连接信息（如 `if (wid == i)`）。
- group（group）→ 在同一线程块内，把线程划分为若干“协作组”的编号；每个组运行一个 Primitives 实例（如一次 send 或 recv 子任务），彼此独立同步。

Warp是**硬件概念**：GPU的32线程SIMD执行单元。Group 是**逻辑概念**，一个group对应一个Primitives实例，可能包含1个或多个 warp。

协调/分配：
- 上层会把一个 block 按工作单元拆成多个“组”，给每组分配一个 `group` 编号和 `nthreads`（组内规模）。
- 组内同步：
  - 当 `nthreads == WARP_SIZE`，使用 `__syncwarp()`；
  - 否则使用命名 barrier，同组线程通过 `barrier_sync(15 - group, nthreads)` 同步，互不干扰（不同组用不同的 barrier 名字）。
- 目的：同一 block 可并发多个 send/recv（或不同协议）的小组；`group` 只承担“隔离同步”的职责，不影响算法逻辑或数据布局。

### 配置信息

```cpp
const int stepLines;  // 每个 step 的 line 数量
Fan fan;              // 接收/发送的 peer 数量
T *userBufs[2];       // 用户缓冲区 (Input/Output)
```

**`stepLines` **:
- 就是我们前面讲的桥梁参数
- 用于计算 offset: `(step % NCCL_STEPS) * stepLines`
- 用于清理范围、容量计算等

**`userBufs[2]`**:
- `userBufs[Input]`: 输入缓冲区指针
- `userBufs[Output]`: 输出缓冲区指针
- 缓存这些指针,避免重复访问共享内存

### Recv/Send 连接

LL 严格分离了 recv 和 send 的状态，并为每个方向维护独立的数组。

#### 成员变量概览

先看recv侧的成员：
```cpp
// Recv 连接元数据
struct ncclConnInfo* recvConn = NULL;        // 指向连接元数据结构
volatile uint64_t* recvConnHeadPtr = NULL;   // 指向某处的 head（初始化时确定）
uint64_t recvConnHead;                        // 本地接收进度计数器，也就是 step

// 每个 recv peer 的状态（数组）
uint64_t recvStep[MaxRecv];                   // 每个 peer 当前处理的 step
union ncclLLFifoLine* recvBuff[MaxRecv];      // 每个 peer 的缓冲区起始地址
```

再看send侧：
```cpp
// Send 连接元数据
struct ncclConnInfo* sendConn = NULL;
volatile uint64_t* sendConnHeadPtr = NULL;
uint64_t sendConnHead;
uint64_t sendConnHeadCache;                   // 缓存的 head 值（避免重复读取）
volatile struct ncclConnFifo* sendConnFifo = NULL;

// 每个 send peer 的状态（数组）
uint64_t sendStep[MaxSend];
union ncclLLFifoLine* sendBuff[MaxSend];
```

**关键问题**：
- `recvConnHeadPtr` 和 `sendConnHeadPtr` 到底指向哪里？
- 为什么 recv 和 send 要严格分离管理？
- 这些指针是如何初始化的？

要回答这些问题，我们需要先理解它们的初始化流程。

#### 初始化流程：从 ncclConnInfo 到 Primitives

Primitives 的成员变量不是凭空出现的，它们在构造函数中从 `ncclConnInfo` 复制而来（[prims_ll.h:305-324](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L305-L324)）：

**Recv 侧初始化**（`loadRecvSync`）：
```cpp
__device__ __forceinline__ void loadRecvSync() {
  if (tid >= nthreads-WARP_SIZE && wid < fan.nrecv()) {
    recvConnHeadPtr = recvConn->head;   // 从 ncclConnInfo 复制 head 指针
    recvConnHead = recvConn->step;       // 初始化本地进度计数器
  }
}
```

**Send 侧初始化**（`loadSendSync`）：
```cpp
__device__ __forceinline__ void loadSendSync() {
  if (tid < fan.nsend()) {
    sendConnHeadPtr = sendConn->head;       // 从 ncclConnInfo 复制 head 指针
    sendConnHeadCache = *sendConnHeadPtr;    // 读取 head 当前值并缓存
    sendConnHead = sendConn->step;           // 初始化本地进度计数器
  }
}
```

**关键洞察**：
- `recvConnHeadPtr` 和 `sendConnHeadPtr` 是 Primitives 的**直接成员**
- 但它们的**值**（指向的地址）来自 `ncclConnInfo->head`
- `ncclConnInfo` 是 host 端分配的连接元数据结构（[device.h:128-146](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L128-L146)）

现在问题变成：`ncclConnInfo->head` 指向哪里？这个指针的**方向性**是 LL 流控的核心设计。

#### Head 指针的方向性：核心设计原则

答案在 `ncclConnInfo` 的注释中（[device.h:133](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L133)）：

```c
struct ncclConnInfo {
  char *buffs[NCCL_NUM_PROTOCOLS]; // Local for recv, remote for send
  uint64_t *tail;     // Local for recv, remote for send ← 在 LL 中没有使用
  uint64_t *head;     // Local for send, remote for recv  ← 注意这一行！
  uint64_t step;      // Keep where we are
  // ...
};
```

**核心原则**：`head` 的存储位置和访问权限是**不对称的**：
- **Head 存储位置**：总是在**发送方**（生产者）的本地内存
- **写入权限**：在**接收方**（消费者）手中
- **因此**：
  - Recv 侧的 `recvConnHeadPtr` 指向**远端**（发送方的本地内存）
  - Send 侧的 `sendConnHeadPtr` 指向**本地**（自己的本地内存）


#### Recv 侧详解（消费者视角）

Recv侧的成员变量及其职责：

```cpp
struct ncclConnInfo* recvConn = NULL;        // 指向连接元数据
volatile uint64_t* recvConnHeadPtr = NULL;   // 指向**远端**发送方的 head
uint64_t recvConnHead;                        // 本地接收进度计数器

uint64_t recvStep[MaxRecv];                   // 每个 recv peer 的 step
union ncclLLFifoLine* recvBuff[MaxRecv];      // 每个 recv peer 的缓冲区
```

**操作流程**（参考 [prims_ll.h:76-78](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L76-L78)）：
```cpp
inline __device__ void postRecv() {
  barrier();
  if (recvConnHeadPtr) *recvConnHeadPtr = recvConnHead += 1;
}
```

1. **读取数据**：从 `recvBuff[i]` 读取 peer i 的数据
2. **同步屏障**：确保所有线程都完成读取
3. **通知发送方**：递增 `recvConnHead`，然后**远程写入** `*recvConnHeadPtr`

**关键点**：`recvConnHeadPtr` 指向**远端**发送方的内存，用于告诉发送方"我已读到这里，你可以继续发送了"。

#### Send 侧详解（生产者视角）

Send侧的成员变量及其职责：

```cpp
struct ncclConnInfo* sendConn = NULL;             // 指向连接元数据
volatile uint64_t* sendConnHeadPtr = NULL;        // 指向**本地** head（被远端写入）
uint64_t sendConnHead;                             // 本地发送进度计数器
uint64_t sendConnHeadCache;                        // 缓存的 head 值
volatile struct ncclConnFifo* sendConnFifo = NULL; // Proxy 通信 FIFO

uint64_t sendStep[MaxSend];                        // 每个 send peer 的 step
union ncclLLFifoLine* sendBuff[MaxSend];           // 每个 send peer 的缓冲区
```

**操作流程**（参考 [prims_ll.h:61-70](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L61-L70)）：
```cpp
inline __device__ void waitSend(int nbytes) {
  if (sendConnHeadPtr) {
    int limit = divUp(nbytes, NCCL_STEPS*stepLines*sizeof(ncclLLFifoLine));
    while (sendConnHead + NCCL_STEPS < sendConnHeadCache + limit) {
      sendConnHeadCache = *sendConnHeadPtr;  // 轮询本地head（被远端更新）
    }
    barrier();
    sendConnHead += 1;
  }
}
```

1. **检查空间**：轮询 `*sendConnHeadPtr`（本地内存，但被远端接收方写入），确保 `sendConnHead - *sendConnHeadPtr < NCCL_STEPS`
2. **同步屏障**：确保所有线程都通过流控检查
3. **写入数据**：向 `sendBuff[i]` 写入数据
4. **推进进度**：递增 `sendConnHead`

**关键点**：
- `sendConnHeadPtr` 指向**本地**内存（自己维护的head变量）
- 但这个head变量**被远端接收方写入**（通过 `postRecv()` 的远程写）
- 发送方**轮询本地内存**即可，延迟低，效率高

## 总结

本章深入讲解了 LL Protocol 的数据结构,从全景图到每一层的细节。让我们回顾一下核心要点。

### 数据结构的四层嵌套

LL Protocol 的数据结构是层层嵌套的,从大到小依次是:

```
环形缓冲区 (默认 512 KB, 可配置)
  ↓ 包含 8 个 slot
Step (大小 = buffSize / 8, 默认 64 KB)
  ↓ 包含 stepLines 个 line (默认 4,096)
Line (16 字节: 4B data1 + 4B flag1 + 4B data2 + 4B flag2)
  ↓ 包含 EltPerLine 个元素
Element (sizeof(T))
```

每一层都有明确的职责:
- **环形缓冲区**: 支持流水线传输
- **Step**: 流控的粗粒度单位
- **Line**: 传输和验证的细粒度单位
- **Element**: 用户数据

**注意**: 括号中的数值都是使用默认配置时的示例值。

### 为什么是 16 字节?

- **设计约束**: RDMA 只保证 8 字节原子性,传输 16 字节需要两次 8 字节操作
- **方案权衡**: 在每次 8 字节传输中包含"数据+标志",避免乱序问题
- **双标志位**: 两个标志分别验证两次 8 字节传输,确保完整性
- **统一接口**: 节点内和节点间使用相同的 16 字节结构
- **设计结果**: `readLL` 返回 8 字节有效数据 (`uint64_t`)

### LL Primitives 的设计特点

- **数组管理**: `recvStep[]`, `sendStep[]` 支持多连接并行
- **recv/send 分离**: 不同的同步机制和内存所有权
  - `recvConnHead`: 本地接收进度计数器,递增后写入远端
  - `recvConnHeadPtr`: 指向远端发送方的 head (写入远端)
  - `sendConnHead`: 本地发送进度计数器
  - `sendConnHeadPtr`: 指向本地的 head (被远端写入,轮询本地)
  - `sendConnHeadCache`: 缓存远端写入的值
- **生产者-消费者模式**: head 存储在生产者,写权限在消费者,双方各自维护本地计数器
- **细粒度支撑**: `stepLines` 和 `EltPerLine` 连接不同的抽象层次

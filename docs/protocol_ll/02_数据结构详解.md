# LL Protocol 数据结构详解

## 引言

在第一章,我们了解了 LL Protocol 的核心思想:**细粒度传输 + 每字节完整性保证**。LL 把数据切成很小的单元(16 字节),逐个传输,每个单元都有完整性验证。

本章的目标是建立 LL Protocol 的"数据地图"——一个清晰的、层次化的数据结构视图。在后续章节阅读代码时,你可以随时回来这里查阅:

- 某个参数的含义(如 `stepLines`)
- 某个结构体的布局(如 `ncclLLFifoLine`)
- 不同层次的关系(如 Step 与 Line 的关系)

**本章的三个核心问题**:
1. **LL 的数据结构有哪些层次?** (全景图)
2. **为什么是 16 字节?为什么标志在数据之后?** (Line 的设计)
3. **LL Primitives 的成员变量如何支撑这个数据结构?** (实现细节)

让我们从全景图开始。

---

## 第一部分:全景图

在深入细节之前,让我们先建立一个自顶向下的全景视图。LL Protocol 的数据结构是**四层嵌套**的,也是一份“谁对谁同步”的契约。

### 1. 四层嵌套结构概览

从外到内,LL Protocol 的数据结构如下:

```
🔷 环形缓冲区 (Ring Buffer)
  ├─ 总大小: buffSizes[NCCL_PROTO_LL] (默认 512 KB)
  ├─ 作用: 支持流水线传输,让发送/接收异步工作
  └─ 划分成 8 个 slot (NCCL_STEPS = 8)
      ↓
    🔶 Step (流控单元)
      ├─ 大小: buffSize / NCCL_STEPS (默认 64 KB)
      ├─ 作用: 粗粒度流控单元 (waitSend/postRecv)
      └─ 包含 stepLines 个 line (默认 4096 个)
          ↓
        🔹 Line (传输单元)
          ├─ 大小: 16 字节
          ├─ 组成: 8 字节数据 + 8 字节标志
          ├─ 作用: LL 的原子传输单元,readLL/storeLL 的操作对象
          └─ 包含 EltPerLine 个元素
              ↓
            🔸 Element (用户数据)
              ├─ 大小: sizeof(T) (如 float32 = 4 字节)
              ├─ 作用: 用户数据的基本单位
              └─ EltPerLine = 8 / sizeof(T)
```

**关键洞察**: 每个 step 只有一半是有效 payload。默认配置下 `stepLines = 4096`,有效数据仅 `4096 × 8 = 32 KB`,但它允许发送方在 `waitSend()` 判定中最多领先接收方 `8 × 32 KB`。这就是 LL “更小车厢,更快发车”的核心,也是为什么大消息最终会切回 Simple Protocol。

为了建立后续章节需要的坐标,下面给出“参数字典”。公式只出现一次,其余地方直接引用这些名字即可。

### 2. 关键参数速查表

以下参数会在整个 LL Protocol 系列文章中反复出现。你可以把这个表当作"参数字典"使用:

| 参数名 | 类型/默认值 | 含义 | 定义位置 |
|--------|--------|------|----------|
| **`DEFAULT_LL_BUFFSIZE`** | 524,288 字节 (512 KB) | LL 环形缓冲区默认大小(可被 `NCCL_LL_BUFFSIZE` 覆盖) | [init.cc:697](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/init.cc#L697) |
| **`NCCL_STEPS`** | 8 | 每个连接的 step 数量(也是环形缓冲区 slot 数) | [device.h:24](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L24) |
| **`NCCL_LL_LINES_PER_THREAD`** | 8 | 每个线程处理的 line 数 | [device.h:92-100](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L92-L100) |

| **`EltPerLine`** | 编译期计算 | 每个 line 中的元素个数 | [prims_ll.h:130](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L130) |

**需要记住的三条公式**:
```
stepLines = buffSizes[NCCL_PROTO_LL] / NCCL_STEPS / sizeof(ncclLLFifoLine)
EltPerLine = 8 / sizeof(T)
stepPayload = stepLines × 8 字节   // 每个 step 的有效数据量
```

默认值代入即可得到 `stepLines = 4096`, `stepPayload = 32 KB`,后文不再重复推导。

### 3. buffSizes 从哪里来?

`buffSizes` 是 host 端初始化时计算出的运行时配置:

1. `computeBuffSizes()` 先读取 `NCCL_LL_BUFFSIZE` 等环境变量,否则采用 `DEFAULT_LL_BUFFSIZE` 等默认值([init.cc:660-708](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/init.cc#L660-L708))。
2. 结果写入 `ncclComm::buffSizes[]`,随通信器一起下发到 GPU。
3. Kernel 启动时,`ncclKernelComm` 被复制到共享内存的 `ncclShmem.comm`,device 端用 `ncclShmem.comm.buffSizes[NCCL_PROTO_LL]` 读取。

这样,即便运行时调整了 `NCCL_LL_BUFFSIZE`,device 端也能按最新配置计算 `stepLines`。完整的 `ncclShmem` 结构在文末附录中有详细拆解。

## 第二部分:逐层深入

现在我们有了全景图,让我们逐层深入,理解每一层的设计原理。

### 1. 环形缓冲区 (Ring Buffer)

#### 总大小计算

LL Protocol 的环形缓冲区大小由 `DEFAULT_LL_BUFFSIZE` 宏定义([init.cc:697](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/init.cc#L697)):

```c
#define DEFAULT_LL_BUFFSIZE \
  (NCCL_LL_LINES_PER_THREAD * NCCL_LL_MAX_NTHREADS * NCCL_STEPS * sizeof(union ncclLLFifoLine))
```

计算过程:
```
DEFAULT_LL_BUFFSIZE = NCCL_LL_LINES_PER_THREAD × NCCL_LL_MAX_NTHREADS × NCCL_STEPS × sizeof(ncclLLFifoLine)
                    = 8 × 512 × 8 × 16
                    = 524,288 字节
                    = 512 KB
```

这个公式的含义:
- **每个线程** 处理 `NCCL_LL_LINES_PER_THREAD` (8) 个 line
- **最多** `NCCL_LL_MAX_NTHREADS` (512) 个线程并行工作
- **环形缓冲区** 有 `NCCL_STEPS` (8) 个 slot 支持流水线
- **每个 line** 占用 16 字节

#### 为什么是 512 KB?

这是基于以下考虑的权衡:

**✅ 优点**:
- **足够的流水线深度**: 8 个 step 提供足够的缓冲空间,支持发送方和接收方异步工作
- **内存开销可控**: 每个连接 512 KB,即使有多个连接,也不会过度占用 GPU 内存
- **线程并行度**: 512 个线程可以充分利用 GPU 的并行能力

**❌ 代价**:
- 相比 Simple Protocol (默认 4 MB),LL 的缓冲区小得多
- 有效数据只占 50%,所以 512 KB 的缓冲区只能存储 256 KB 的用户数据

#### 如何获取缓冲区大小?

在 device 端代码中,通过 `ncclShmem` 访问:

```cpp
int buffSize = ncclShmem.comm.buffSizes[NCCL_PROTO_LL];
```

`ncclShmem` 是存储在 GPU 共享内存中的全局变量,包含了所有协议的配置信息。详细说明见 [Appendix: ncclShmem](#appendix)。

**注意**: `DEFAULT_LL_BUFFSIZE` 只是默认值。实际运行时,可以通过环境变量 `NCCL_LL_BUFFSIZE` 配置([init.cc:701](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/init.cc#L701))。

### 2. Step (流控单元)

#### 每个 step 的大小

环形缓冲区被均匀划分成 `NCCL_STEPS` 个 slot,每个 slot 对应一个 **step**。Step 的总字节数是 `stepLines × sizeof(ncclLLFifoLine)`(默认 64 KB),但有效载荷只有上文记过的 `stepPayload = stepLines x 8`(默认 32 KB)。

Step 是 **流控的基本单位**:
- `waitSend(step)`: 发送方自旋监控 `sendConnHeadCache + NCCL_STEPS < sendConnHead + 1`([prims_ll.h:56-68](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L56-L68)),确保自己最多领先接收方 `NCCL_STEPS` 个 step,也就是 `8 × stepPayload` 的数据。
- `postRecv(step)`: 接收方在消费完一个 step 后,通过 `*recvConnHeadPtr = recvConnHead += 1` 发布新 head,解除发送方的限速。

#### stepLines: 桥梁参数 ⭐

`stepLines` 是 LL Protocol 中**最重要的参数之一**,它连接了数据结构和流控。

**定义**([prims_ll.h:335](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L335)):
```cpp
stepLines(ncclShmem.comm.buffSizes[NCCL_PROTO_LL] / NCCL_STEPS / sizeof(ncclLLFifoLine))
```

**含义**: 每个 step 包含多少个 line

**计算公式**:
```
stepLines = buffSizes[NCCL_PROTO_LL] / NCCL_STEPS / sizeof(ncclLLFifoLine)
```

默认配置下 `stepLines = 4096`。该值是在 Primitives 构造函数中**运行时计算**的,会根据实际的 `buffSizes[NCCL_PROTO_LL]` 动态调整,因此在阅读任何计算前请先脑中保留 `stepLines` 这一变量。

**为什么 stepLines 如此重要?**

因为它串联了三个关键操作:

1. **数据定位**
   ```cpp
   int offset = (step % NCCL_STEPS) * stepLines;  // 单位: line
   union ncclLLFifoLine* ptr = buff + offset;
   ```
2. **容量评估**: `stepPayload = stepLines × 8` 字节,也是判定当前消息是否跨 step 的阈值。
3. **清理范围**: 标志回绕时,`for (int o = offset; o < stepLines; o += nthreads)` 直接覆盖一个 step 内的所有 line。

#### 从 step 到 offset

给定一个 step 计数器(如 `recvStep[i]`),如何找到它在环形缓冲区中的位置?

**公式**:
```cpp
offset = (step % NCCL_STEPS) * stepLines
```

**为什么需要 `% NCCL_STEPS`?**

因为 step 计数器是**单调递增**的 `uint64_t`,会不断增长。环形缓冲区只有 8 个 slot,所以需要用模运算映射:

```
step = 0  → slot 0 → offset = 0 × 4096 = 0
step = 1  → slot 1 → offset = 1 × 4096 = 4096
...
step = 7  → slot 7 → offset = 7 × 4096 = 28672
step = 8  → slot 0 → offset = 0 × 4096 = 0 (重新开始)
step = 9  → slot 1 → offset = 1 × 4096 = 4096
```

#### 为什么以 line 为单位?

注意 `offset` 的单位是 **line**,不是字节。为什么?

因为 LL Protocol 的所有操作都以 line 为单位:
- `readLL(offset, i)`: offset 是 line 的索引
- `storeLL(sendPtr(i) + offset, ...)`: 指针偏移是 line 的偏移
- `recvPtr(i)`: 返回 `ncclLLFifoLine*` 指针

用 line 数量比字节数更自然,也避免了重复的除法运算。

### 3. Line (传输单元) ⭐

Line 是 LL Protocol 的核心。让我们深入理解它的设计。

#### ncclLLFifoLine 的定义

LL Protocol 的传输单元是 `ncclLLFifoLine`,定义在 [device.h:70-83](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L70-L83):

```c
 union ncclLLFifoLine {
  /* Flags have to be *after* data, because otherwise, an incomplete receive
     from the network may receive the flag but not the data.
     Note this is assuming that either we receive contiguous chunks of data
     (sockets) or data is written with an atomicity of 8 bytes (IB/RDMA). */
  struct {
    uint32_t data1;
    uint32_t flag1;
    uint32_t data2;
    uint32_t flag2;
  };
  uint64_t v[2];
  int4 i4;
};
```

这个 `union` 定义了三种访问方式:
1. **结构体访问**: `data1`, `flag1`, `data2`, `flag2` (4 个 `uint32_t`)
2. **uint64_t 数组**: `v[2]` (2 个 8 字节,用于 `readLL` 返回值)
3. **int4 向量**: `i4` (128 位向量,用于 `storeLL` 一次写入 16 字节)

**内存布局**:
```
偏移量: 0      4      8      12     16 (Bytes)
       +------+------+------+------+
       |data1 |flag1 |data2 |flag2 |
       +------+------+------+------+
       |<- 8 Bytes ->|<- 8 Bytes ->|
       |   v[0]      |     v[1]    |
       +------+------+------+------+
       |<--- int4 (16 Bytes) ----->|
```

**核心事实**:
- **总大小**: 16 字节
- **有效数据**: 8 字节 (data1 + data2)
- **标志开销**: 8 字节 (flag1 + flag2)
- **有效数据占比**: 50%

**关键洞察**: 16 字节并不是随手一取的数字。双标志写在后半段,配合 `st.global.v4.u32` 的一次 16 字节写入,可以保证“先数据后标志”。如果把 Line 缩成 8 字节,每次仅 4 字节 payload,warp 需要双倍轮次;若扩展到 32 字节,一次写入会翻倍为两条指令,还与 NVLink/NVSwitch 的事务粒度错开。现在的设计让一个 warp 同步写入 `32 × 16 = 512` 字节,恰好对齐链路的首选批量,也是 `NCCL_LL_LINES_PER_THREAD = 8` 这种配置的直接推导结果。

#### 为什么是 16 字节? ⭐

这是 LL Protocol 设计中**最重要的问题**。让我们从设计约束出发,理解为什么最终选择了 16 字节。

**设计约束: RDMA 的 8 字节原子性**

看代码注释([device.h:71-74](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L71-L74)):

```c
/* Flags have to be *after* data, because otherwise, an incomplete receive
   from the network may receive the flag but not the data.
   Note this is assuming that either we receive contiguous chunks of data
   (sockets) or data is written with an atomicity of 8 bytes (IB/RDMA). */
```

关键约束: **RDMA 只保证 8 字节的原子性**。

这意味着:
- 每次 RDMA 写操作可以原子地传输 8 字节
- 如果要传输更多数据,需要多次 8 字节的操作
- 这些操作之间**可能不是原子的**,可能存在乱序或部分完成

**核心问题: 如何在 8 字节原子性约束下,保证数据完整性?**

LL Protocol 需要解决的问题是:**接收方如何知道收到的数据是完整的、没有损坏的?**

答案是:**在每次 8 字节传输中同时包含数据和验证标志**。

**为什么不用 8 字节 line?**

你可能会想:为什么不用 8 字节的 line (4B 数据 + 4B 标志)?

**方案 A (效率太低)**: 8 字节 line = [data (4B)][flag (4B)]

问题:
- 每个 line 只携带 4 字节有效数据(而不是 8 字节)
- 要传输同样多的数据,`readLL`/`storeLL` 调用次数翻倍
- 标志验证、step 管理等控制开销也翻倍
- `EltPerLine` 从 `8/sizeof(T)` 变成 `4/sizeof(T)`,主循环迭代次数翻倍

**为什么不把数据和标志分离?**

**方案 B (错误)**: 先传输全部数据,再传输标志
- 第一次 8 字节: 全是数据 (8B)
- 第二次 8 字节: 全是标志 (8B)

问题:**网络乱序导致数据损坏**

假设布局是 `[data (8B)][flag (8B)]`,传输需要两次 8 字节写:
1. 第一次: 写 data (8B)
2. 第二次: 写 flag (8B)

如果网络出现乱序或重试,第二次写(flag)可能先于第一次写(data)生效。接收端看到 flag 已是新值,误以为整段数据准备好了,但实际上 data 还没更新——**数据完整性被破坏**。

**NCCL 的解决方案: 数据和标志交错 + 双标志位**

正确的 16 字节布局:
```
[data1 (4B) | flag1 (4B)][data2 (4B) | flag2 (4B)]
 \_____第1个8字节_____/ \_____第2个8字节_____/
```

这个设计的精妙之处:
1. **每个 8 字节传输都包含"数据+标志"**: 即使只完成了一次 8 字节写,也有对应的标志可以验证
2. **双标志位验证**: 接收方检查 `flag1 == flag && flag2 == flag`,确保**两次 8 字节都已到达**
3. **屏蔽乱序**: 无论哪个 8 字节先到,接收方都会等到两个标志都匹配才使用数据

接收方的验证逻辑:
- 如果只到了前半段: `flag1` 是新值,`flag2` 是旧值 → 继续自旋等待
- 如果只到了后半段: `flag2` 是新值,`flag1` 是旧值 → 继续自旋等待
- **只有两个标志都是新值,才退出自旋** → 两次 8 字节写都已落地

换句话说,两个标志不是"重复验证同一件事",而是**分别为两个半行数据建立了"就地确认"信号**,屏蔽了底层传输的乱序。

**为什么是 16 字节而不是更大?**

你可能会想:既然 16 字节有效,那 32 字节、64 字节是不是更好?

答案是:**16 字节是效率和粒度的最佳平衡点**。

- **更大的 line (如 32B)**: 虽然有效数据更多,但需要更多次 RDMA 写,标志验证更复杂,细粒度优势减弱
- **16 字节**: 两次 RDMA 写,双标志位验证,简单高效,粒度够细

**最终结果: readLL 返回 uint64_t**

设计从 RDMA 约束出发,最终选择了 16 字节 line (8B 数据 + 8B 标志)。因此,`readLL` 返回的是 **8 字节有效数据**:

```cpp
// prims_ll.h:98
uint64_t val64 = data1 + (((uint64_t)data2) << 32);
return val64;
```

这不是设计的起点,而是**设计的结果**。

#### 为什么标志在数据之后?

看注释([device.h:71-73](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L71-L73)):

```c
/* Flags have to be *after* data, because otherwise, an incomplete receive
   from the network may receive the flag but not the data. */
```

**容错机制**: 如果 RDMA 传输被中断,接收方不会读到部分数据。

假设布局是 `[flag1 | data1][flag2 | data2]` (标志在前):
- RDMA 写前 8 字节: `flag1` 和 `data1`
- 如果写操作被中断,`flag1` 可能已生效,但 `data1` 可能损坏
- 接收方看到 `flag1` 是新值,误以为 `data1` 是有效的

正确布局 `[data1 | flag1][data2 | flag2]` (标志在后):
- RDMA 写前 8 字节: `data1` 和 `flag1`
- 如果写操作被中断,`flag1` 不会先于 `data1` 生效
- **保证**: 看到 `flag1` 更新 = `data1` 一定已到达

**关键洞察**: 标志后置是正确性的**必要条件**,不是优化选项。

#### 节点内通信为什么也用 16 字节?

你可能注意到,节点内通信(GPU 之间通过 NVLink/PCIe)可以使用 128 位宽度的向量写指令。

看 `storeLL` 的实现([prims_ll.h:126-128](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L126-L128)):

```cpp
__device__ void storeLL(union ncclLLFifoLine* dst, uint64_t val, uint32_t flag) {
  asm volatile("st.volatile.global.v4.u32 [%0], {%1,%2,%3,%4};"
    :: "l"(&dst->i4), "r"((uint32_t)val), "r"(flag),
       "r"((uint32_t)(val >> 32)), "r"(flag) : "memory");
}
```

`st.volatile.global.v4.u32` 指令一次写入 4 个 `uint32_t` (16 字节)。既然节点内可以用单条指令写完 16 字节,为什么还要用双标志位?

**答案: 统一接口**

节点内和节点间使用相同的数据结构(`ncclLLFifoLine`)和相同的代码路径(`storeLL`/`readLL`),这样:
- **简化实现**: 不需要针对不同场景使用不同的代码
- **统一验证**: 接收方总是检查双标志位,无论数据来自哪里
- **防御性设计**: 即使硬件一次写完整个 line,软件也提供双重验证

#### readLL/storeLL 简介

`readLL` 和 `storeLL` 是 LL Protocol 操作 line 的核心函数:

**readLL**([prims_ll.h:89-99](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L89-L99)):
- 从 peer 的环形缓冲区读取一个 line
- 使用 `ld.volatile.global.v4.u32` 指令一次读取 16 字节
- **自旋等待** `flag1 == flag && flag2 == flag`
- 返回 `uint64_t` (8 字节有效数据)

**storeLL**([prims_ll.h:126-128](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L126-L128)):
- 向 peer 的环形缓冲区写入一个 line
- 使用 `st.volatile.global.v4.u32` 指令一次写入 16 字节
- 写入格式: `[data1 | flag | data2 | flag]`

**第三章会详细讲解这两个函数的实现和双标志位机制**。现在,你只需要知道:
- `readLL` 读一个 line,返回 8 字节数据
- `storeLL` 写一个 line,包含 8 字节数据和双标志位
- 它们是 LL Protocol 数据传输的原语

##### 硬件原子性在这里起作用

代码里看不到任何 `atomic*` 指令,是因为 LL 借的是底层链路本来就提供的"8 字节写入不可撕裂"保证。注释已经提醒了这一点([device.h:70-83](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L70-L83))。发送方用单条 `st.volatile.global.v4.u32` 把四个 `uint32_t` 一次性写出去([prims_ll.h:126-128](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L126-L128))。硬件把这条指令拆成连续的两个 8B 写,而 8B 写的原子性确保了"数据1+flag1"这 8B 和"数据2+flag2"那 8B 要么完整落地,要么还没对接收方可见。接收方的 `readLL` 通过 `ld.volatile.global.v4.u32` 轮询这 16B,只有在两个 flag 都已经变成期望值时才使用对应的数据([prims_ll.h:89-99](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L89-L99))。所以所谓的"原子性"并不是软件层的原子操作,而是利用硬件对 8 字节写的顺序与完整性承诺,再辅以双标志位验证完成的。

**关键洞察**:
- **16 字节不是为了对齐**,而是为了在 RDMA 的 8 字节原子性约束下,保证 8 字节有效数据的完整性传输
- **双标志位是核心**,不是冗余
- **标志后置是正确性保证**,不可省略

### 4. Element (用户数据)

我们已经了解了 line (16 字节) 和 step (多个 line) 的组织。但用户数据是以**元素**(如 `float`, `int8`)为单位的,如何映射到 line?

这就是 `EltPerLine` 的作用。

#### EltPerLine 的计算

`EltPerLine` 是一个编译时常量([prims_ll.h:130](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L130)):

```cpp
static constexpr int EltPerLine = sizeof(uint64_t) / sizeof(T);
```

**含义**: 每个 line 可以容纳多少个类型为 `T` 的元素。

**为什么是 `sizeof(uint64_t) / sizeof(T)`?**

因为每个 line 携带 **8 字节有效数据**(不是 16 字节总大小)。所以:
```
EltPerLine = 8 字节 / sizeof(T)
```

这是 `constexpr`,在**编译时**计算。

#### 不同数据类型的映射

根据数据类型 `T` 的大小,`EltPerLine` 有不同的值:

| 数据类型 | sizeof(T) | EltPerLine | 说明 |
|----------|-----------|------------|------|
| **float32** | 4 字节 | 8 / 4 = 2 | 每个 line 容纳 2 个 float |
| **float16** | 2 字节 | 8 / 2 = 4 | 每个 line 容纳 4 个 half |
| **int8** | 1 字节 | 8 / 1 = 8 | 每个 line 容纳 8 个 byte |
| **float64** | 8 字节 | 8 / 8 = 1 | 每个 line 容纳 1 个 double |

**示例 (float32)**:
```
[data1: 4B] [flag1: 4B] [data2: 4B] [flag2: 4B]
 └─ float0              └─ float1

有效数据: 2 个 float32
EltPerLine = 2
```

**示例 (int8)**:
```
[data1: 4B]              [flag1] [data2: 4B]              [flag2]
 └─ byte0,1,2,3                  └─ byte4,5,6,7

有效数据: 8 个 int8
EltPerLine = 8
```

#### 与主循环的关系

`EltPerLine` 决定了 **LLGenericOp 主循环的粒度**(第五章会详细讲解)。

在主循环中([prims_ll.h:240-285](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L240-L285)),每次迭代处理的元素数量是:

```cpp
while (nelem > 0) {
  int eltInLine = EltPerLine < nelem ? EltPerLine : nelem;
  // ... 处理 eltInLine 个元素
  nelem -= eltPerTrip;
  offset += nthreads;
}
```

`eltInLine` 表示这次迭代要处理多少个元素:
- 如果剩余元素 >= `EltPerLine`,处理满的一个 line
- 否则,处理剩余元素(最后一次迭代可能不满)

**例子**:
- `float32`: `EltPerLine = 2`,每次处理 2 个元素
- `int8`: `EltPerLine = 8`,每次处理 8 个元素

`EltPerLine` 越大,循环迭代次数越少,效率越高。这也是为什么 LL Protocol 对小数据类型(如 `int8`)更高效。

**关键洞察**: `EltPerLine` 是连接用户数据和 LL 传输单元的桥梁。它告诉我们"一个 line 能装多少用户数据"。

## 第三部分: LL Primitives 的成员变量

现在我们理解了 LL 的数据结构(环形缓冲区 → Step → Line → Element),接下来看 LL Primitives 如何使用这些结构。

Primitives 是 LL Protocol 的"引擎",负责数据的读取、写入和同步。它的成员变量反映了 LL 的设计特点。

### 1. 为什么需要这些成员?

LL Primitives 需要支撑前面讲的四层数据结构:
- **环形缓冲区**: 需要知道缓冲区的大小和位置
- **Step**: 需要追踪每个 peer 的 step 计数器
- **Line**: 需要定位到具体的 line (通过 offset)
- **Element**: 需要知道每个 line 包含多少元素

此外,LL Primitives 还需要处理:
- **多连接**: 同时追踪多个 recv/send peer
- **线程并行**: 多个线程协同处理同一个 step
- **流控**: 与 peer 同步 step 进度

让我们看看这些需求如何映射到成员变量。

### 2. 核心成员概览

LL Primitives 的成员变量定义在 [prims_ll.h:16-44](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L16-L44):

```cpp
template<typename T, typename RedOp, typename Fan, int Direct, int P2p, bool isNetOffload>
class Primitives<T, RedOp, Fan, Direct, ProtoLL, P2p, isNetOffload> {
  static constexpr int MaxRecv = Fan::MaxRecv > 1 ? Fan::MaxRecv : 1;
  static constexpr int MaxSend = Fan::MaxSend;
  static constexpr int Input=0, Output=1;

  RedOp redOp;
  const int tid;        // 线程 ID
  const int nthreads;   // 总线程数
  const int wid;        // warp 内线程索引
  const int group;      // 线程组 ID
  const int stepLines;  // 每个 step 的 line 数量 (关键!)
  Fan fan;
  T *userBufs[2];       // 用户缓冲区 (Input/Output)

  // Recv 连接
  struct ncclConnInfo* recvConn = NULL;
  volatile uint64_t* recvConnHeadPtr = NULL;
  uint64_t recvConnHead;

  // Send 连接
  struct ncclConnInfo* sendConn = NULL;
  volatile struct ncclConnFifo* sendConnFifo = NULL;
  volatile uint64_t* sendConnHeadPtr = NULL;
  uint64_t sendConnHead;
  uint64_t sendConnHeadCache;

  // 每个 peer 的状态 (数组!)
  uint64_t recvStep[MaxRecv];
  uint64_t sendStep[MaxSend];
  union ncclLLFifoLine* recvBuff[MaxRecv];
  union ncclLLFifoLine* sendBuff[MaxSend];

  // 辅助函数 (见后文)
  // ...
};
```

让我们逐类讲解。

### 3. 线程信息

```cpp
const int tid;        // 线程 ID (threadIdx.x)
const int nthreads;   // 总线程数 (blockDim.x)
const int wid;        // warp 内线程索引 (tid % WARP_SIZE)
const int group;      // 线程组 ID
```

**`wid` 的作用**:
- `wid` 存储了 warp 内的线程索引 (lane ID), 计算为 `tid % WARP_SIZE`
- 主要用于**线程到连接的映射**,例如在加载连接信息时([prims_ll.h:303, 315](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L303)):
  ```cpp
  if (wid == i) recvConn = conn;  // 线程 wid 负责连接 i
  if (wid == i) sendConn = conn;
  ```
- 用于条件性加载连接信息,确保不同线程加载不同的连接

这些参数决定了:
- **哪个线程处理哪个 line**: `offset = tid + ...`
- **如何在 warp 内归约**: 使用 `__shfl_xor_sync` 等指令

### 4. 配置信息

```cpp
const int stepLines;  // 每个 step 的 line 数量
Fan fan;              // 接收/发送的 peer 数量
T *userBufs[2];       // 用户缓冲区 (Input/Output)
```

**`stepLines` ⭐**:
- 就是我们前面讲的桥梁参数
- 用于计算 offset: `(step % NCCL_STEPS) * stepLines`
- 用于清理范围、容量计算等

**`userBufs[2]`**:
- `userBufs[Input]`: 输入缓冲区指针
- `userBufs[Output]`: 输出缓冲区指针
- 缓存这些指针,避免重复访问共享内存

### 5. Recv/Send 连接 (数组管理) ⭐

这是 LL Primitives 与 Simple Primitives 的**最大差异**。

#### Recv 连接

```cpp
struct ncclConnInfo* recvConn = NULL;        // 连接元数据
volatile uint64_t* recvConnHeadPtr = NULL;   // 远端发送方的 head 指针
uint64_t recvConnHead;                        // 本地接收进度计数器

uint64_t recvStep[MaxRecv];                   // 每个 recv peer 的 step
union ncclLLFifoLine* recvBuff[MaxRecv];      // 每个 recv peer 的缓冲区
```

**重要**: `recvConnHeadPtr` 指向**远端发送方的 head**,`recvConnHead` 是**本地维护的计数器**!

根据官方注释([device.h:133](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L133)):
```c
uint64_t *head;     // Local for send, remote for recv
```

以及初始化代码([p2p.cc:543](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/transport/p2p.cc#L543)):
```c
recv->conn.head = &remDevMem->head;  // 指向远端的 sendMem.head
```

这意味着:
- `recvConnHeadPtr` 是**远端内存地址**,指向发送方的 `sendMem.head`
- `recvConnHead` 是**本地维护的接收进度计数器**,初始化为 `recvConn->step`
- 当接收方调用 `postRecv()` 时,先递增本地计数器,再**写入远端内存**: `*recvConnHeadPtr = recvConnHead += 1`
- 这是在告诉远端发送方:"我已经读完了,你可以继续发送"

#### Send 连接

```cpp
struct ncclConnInfo* sendConn = NULL;             // 连接元数据
volatile struct ncclConnFifo* sendConnFifo = NULL; // Proxy 通信 FIFO
volatile uint64_t* sendConnHeadPtr = NULL;        // 本地 head 指针 (被远端写入)
uint64_t sendConnHead;                             // 本地 step 计数器
uint64_t sendConnHeadCache;                        // 缓存的 head 值

uint64_t sendStep[MaxSend];                        // 每个 send peer 的 step
union ncclLLFifoLine* sendBuff[MaxSend];           // 每个 send peer 的缓冲区
```

**重要**: `sendConnHeadPtr` 指向**本地的 head**,不是远端!

根据初始化代码([p2p.cc:515](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/transport/p2p.cc#L515)):
```c
send->conn.head = &resources->sendDevMem->head;  // 指向本地的 sendMem.head
```

以及 device 端加载代码([prims_ll.h:319](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L319)):
```cpp
sendConnHeadPtr = sendConn->head;       // 从 send->conn.head 加载
sendConnHeadCache = *sendConnHeadPtr;    // 读取本地 head 的当前值
```

这意味着:
- `sendConnHeadPtr` 是**本地内存地址**,指向本地的 `sendMem.head`
- 这个 head 的**存储空间在本地**,但**写权限在远端接收方**
- 远端接收方通过他们的 `recvConnHeadPtr` 写入这个本地 head
- 发送方通过 `waitSend()` **轮询本地的 head**: `sendConnHeadCache = *sendConnHeadPtr`
- 这样发送方就知道"接收方已经读到哪里了"

同样,`sendStep` 和 `sendBuff` 也是数组。

#### 为什么需要数组?

因为 **LL Primitives 的一个实例需要同时追踪多个连接的独立进度**。

在 Ring AllReduce 中,一个 GPU 需要:
- 从前一个 peer 接收数据 (recv)
- 向后一个 peer 发送数据 (send)

对于 LL Protocol,这两个连接需要**独立的 step 计数器**和**独立的缓冲区**:
- `recvStep[0]` 追踪从 GPU 3 接收的进度
- `sendStep[0]` 追踪向 GPU 1 发送的进度
- `recvBuff[0]` 指向从 GPU 3 接收的环形缓冲区
- `sendBuff[0]` 指向向 GPU 1 发送的环形缓冲区

如果有多个 recv 或 send peer (如 Tree 算法),需要更多的数组元素。`MaxRecv` 和 `MaxSend` 由模板参数 `Fan` 决定。

#### 与 Simple Protocol 的对比

Simple Primitives 的成员变量([prims_simple.h:41-53](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_simple.h#L41-L53)):

```cpp
const int stepSize;              // 单个 stepSize (不是数组)
uint64_t step;                   // 单个 step 计数器
struct ncclConnInfo* conn = NULL;
T* connEltsFifo;                 // 单个缓冲区指针
uint64_t *connStepPtr;
uint64_t connStepCache;
// ...
```

**关键差异**:

| 维度 | Simple Primitives | LL Primitives | 原因 |
|------|-------------------|---------------|------|
| **缓冲区指针** | `T* connEltsFifo` (单个) | `ncclLLFifoLine* recvBuff[]`, `sendBuff[]` (数组) | LL 为每个 peer 维护独立缓冲区 |
| **step 计数器** | `uint64_t step` (单个) | `uint64_t recvStep[MaxRecv]`, `sendStep[MaxSend]` | LL 为每个连接维护独立 step |
| **指针类型** | `T*` (指向用户数据类型) | `ncclLLFifoLine*` (指向 line 结构) | 反映传输单元的差异 |

**为什么 LL 需要数组?**

因为 LL 使用**细粒度的 line 级验证**,每个连接的进度需要独立追踪。Simple 使用粗粒度的 step 级管理,可以用单个计数器。

#### 为什么 recv/send 分离?

注意到 LL Primitives 严格分离了 recv 和 send 的信息:
- `recvConn` vs `sendConn`
- `recvConnHead` vs `sendConnHead`
- `recvConnHeadPtr` vs `sendConnHeadPtr`
- `recvStep[]` vs `sendStep[]`

**原因: 不同的同步机制和内存所有权**

- **Recv 侧 (消费者)**:
  - `recvConnHead`: 本地维护的接收进度计数器
  - `recvConnHeadPtr`: 指向远端发送方的 head (用于写入)
  - 读取数据后递增 `recvConnHead`,然后通过 `recvConnHeadPtr` **写入远端发送方的内存**
  - 作用: 告诉发送方"我已经读到这里了,你可以继续发送"
  - 使用 `recvStep[]` 追踪每个 peer 的接收进度

- **Send 侧 (生产者)**:
  - `sendConnHead`: 本地维护的发送进度计数器
  - `sendConnHeadPtr`: 指向本地的 head (被远端写入,用于轮询)
  - `sendConnHeadCache`: 缓存远端接收方写入的值
  - `sendConnFifo`: (可选)与 proxy 线程共享的 FIFO,用于登记当前 step 的有效字节数
  - 发送前通过 `sendConnHeadPtr` **轮询本地内存**(被远端接收方更新)
  - 作用: 检查"接收方是否已经读完旧数据,我能否继续发送"
  - 使用 `sendStep[]` 追踪每个 peer 的发送进度

`waitSend()` 中可以看到这一逻辑的完整链路: 先自旋等待 `sendConnHeadCache + NCCL_STEPS < sendConnHead + 1` 不再成立,随后将本次发送的字节数(或 cleanup 大小)写入 `sendConnFifo` 供 proxy 消费,最后递增 `sendConnHead`([prims_ll.h:56-83](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L56-L83))。

**关键洞察: 生产者-消费者的巧妙设计**

这是一个经典的**生产者-消费者同步**模式,巧妙之处在于:

1. **head 的存储空间在生产者(发送方)**
2. **head 的写权限在消费者(接收方)**
3. **生产者轮询本地的 head,消费者写入远端的 head**

这样:
- 消费者(接收方)维护本地计数器 `recvConnHead`,递增后通过 `recvConnHeadPtr` 写入生产者的本地 head
- 生产者(发送方)维护本地计数器 `sendConnHead`,通过轮询本地 head (`sendConnHeadPtr`) 知道消费者的进度
- 避免了发送方频繁访问远端内存(只有接收方写入远端)
- **关键区别**: `recvConnHead` 是主动维护的计数器(写出去),`sendConnHeadCache` 是被动读取的缓存(读进来)

Simple Protocol 也有类似的分离,但 LL 的分离更彻底,因为 **LL 没有 `tail` 概念**(依赖 line 级标志验证),只有 `head`。

### 6. 辅助函数: 从 step 到 line 的映射

LL Primitives 提供了几个关键的辅助函数,用于从 step 计算 offset 和指针([prims_ll.h:39-44](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L39-L44))。

#### recvOffset / sendOffset

```cpp
inline __device__ int recvOffset(int i) {
  return (recvStep[i] % NCCL_STEPS) * stepLines;
}
inline __device__ int sendOffset(int i) {
  return (sendStep[i] % NCCL_STEPS) * stepLines;
}
```

**作用**: 计算当前 step 在环形缓冲区中的起始 offset (以 line 为单位)。

**参数 `i`**: peer 索引 (因为 `recvStep`/`sendStep` 是数组)

**例子**:
```
recvStep[0] = 0  → offset = (0 % 8) × 4096 = 0
recvStep[0] = 1  → offset = (1 % 8) × 4096 = 4096
recvStep[0] = 8  → offset = (0 % 8) × 4096 = 0 (重新开始)
```

#### recvPtr / sendPtr

```cpp
inline __device__ union ncclLLFifoLine* recvPtr(int i) {
  return recvBuff[i] + recvOffset(i);
}
inline __device__ union ncclLLFifoLine* sendPtr(int i) {
  return sendBuff[i] + sendOffset(i);
}
```

**作用**: 获取当前 step 的起始 line 指针。这是 `readLL`/`storeLL` 的基地址。

**例子**:
```cpp
// 从 peer 0 读取当前 step 的第 10 个 line
union ncclLLFifoLine* base = recvPtr(0);  // 当前 step 的起始地址
uint64_t data = readLL(10, 0);             // 读取偏移 10 的 line
```

#### recvFlag / sendFlag

```cpp
inline __device__ uint32_t recvFlag(int i) {
  return NCCL_LL_FLAG(recvStep[i] + 1);
}
inline __device__ uint32_t sendFlag(int i) {
  return NCCL_LL_FLAG(sendStep[i] + 1);
}
```

**作用**: 计算期望的标志值。

**为什么是 `step + 1`?**

因为标志代表"这是 step X 的数据"。当我们在处理 step 0 时,写入的标志应该是 1 (代表 step 0 的数据),而不是 0 (那可能是初始化值或旧数据)。

`NCCL_LL_FLAG` 的定义([device.h:100](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L100)):
```c
#define NCCL_LL_FLAG(a) ((uint32_t)(a))
```

正常模式下,它就是简单的类型转换。测试模式下会有取模操作(用于测试标志回绕,第四章会讲)。

**这些辅助函数的重要性**:

虽然它们看起来很简单,但它们是 LL Protocol **数据定位的基础**。后续章节(`readLL`/`storeLL`、`LLGenericOp`)会频繁使用它们。

它们的设计反映了 LL 的核心特点:
- **以 line 为单位**: offset 和指针都是 line 级的
- **per-connection 管理**: 每个函数都接受 peer 索引 `i`
- **step 到 line 的映射**: 通过 `stepLines` 连接两个抽象层次

**关键洞察**:
- LL Primitives 的成员变量反映了细粒度传输的需求
- **数组管理** (`recvStep[]`, `sendStep[]`) 是支撑多连接并行处理的基础
- **recv/send 分离** 是因为 LL 的同步机制与 Simple 不同
- **`stepLines` 贯穿始终**,是理解 LL 数据定位的关键
- **辅助函数** 提供了清晰的 step → offset → ptr 的映射

### 7. 场景实算: 12 KB 梯度片如何穿过 LL

假设 8 卡 Tensor Parallel 的某一轮 reduce-scatter,每张卡要发送 12 KB 的 `float32`。带着我们前面建立的变量,可以逐步验证整条链路:

1. `EltPerLine = 8 / sizeof(float32) = 2`,所以消息覆盖 `divUp(12 KB / 4 B, 2) = 1536` 行。
2. 默认线程配置 `nthreads = 512`,每个线程负责 `NCCL_LL_LINES_PER_THREAD = 8` 行,因此 `eltPerTrip = 512 × 2 = 1024` 元素;仅需两轮完整循环加一次尾巴即可完成写入。
3. 每轮循环写入的字节数是 `nthreads × sizeof(ncclLLFifoLine) = 512 × 16 = 8192` 字节,远小于 `stepPayload = 32 KB`,因此 `waitSend()` 中 `nbytes` 分支不会触发 cleanup。
4. 当最后一个线程写完 1536 行并调用 `postRecv()`,接收方把 `recvConnHead` 从 0 写成 1。发送方随即在 `sendConnHeadPtr` 看到新值,解除 `sendConnHeadCache + NCCL_STEPS < sendConnHead + 1` 的限制,下一车 32 KB 可以出发。
5. 如果连接走 proxy,`sendConnFifo[sendConnHead % NCCL_STEPS].size` 被设置为 12 KB 对齐后的字节数(本例为 24,576 B,因为以 line 为单位),proxy 线程据此发起网卡传输。

换成 Simple Protocol,同样的 12 KB 至少要凑满 128 KB chunk 才能释放 head,延迟是现在的四倍。这个例子把 `stepLines`、`EltPerLine`、`sendConnHead` 三组变量串在一起,验证了“小车厢+双标志”如何在小消息场景中发挥作用。

## 总结

本章深入讲解了 LL Protocol 的数据结构,从全景图到每一层的细节。让我们回顾一下核心要点。

### 数据结构的四层嵌套

LL Protocol 的数据结构是层层嵌套的,从大到小依次是:

```
环形缓冲区 (默认 512 KB, 可配置)
  ↓ 包含 8 个 slot
Step (大小 = buffSize / 8, 默认 64 KB)
  ↓ 包含 stepLines 个 line (默认 4,096)
Line (16 字节: 8B 数据 + 8B 标志)
  ↓ 包含 EltPerLine 个元素
Element (sizeof(T))
```

每一层都有明确的职责:
- **环形缓冲区**: 支持流水线传输
- **Step**: 流控的粗粒度单位
- **Line**: 传输和验证的细粒度单位
- **Element**: 用户数据

**注意**: 括号中的数值都是使用默认配置时的示例值。

### 核心要点

#### 1. 为什么是 16 字节?

- **设计约束**: RDMA 只保证 8 字节原子性,传输 16 字节需要两次 8 字节操作
- **方案权衡**: 在每次 8 字节传输中包含"数据+标志",避免乱序问题
- **双标志位**: 两个标志分别验证两次 8 字节传输,确保完整性
- **统一接口**: 节点内和节点间使用相同的 16 字节结构
- **设计结果**: `readLL` 返回 8 字节有效数据 (`uint64_t`)

#### 2. 为什么标志在数据之后?

- **容错机制**: 防止 RDMA 传输中断时,接收方读到部分数据
- **保证**: 看到 flag 更新 = data 一定已到达
- **正确性的必要条件**: 不是优化选项

#### 3. stepLines 的桥梁作用

- **连接数据结构和流控**: `stepLines` 是理解 LL 的关键参数
- **运行时计算**: `buffSizes[NCCL_PROTO_LL] / NCCL_STEPS / sizeof(ncclLLFifoLine)`
- **数据定位**: `offset = (step % NCCL_STEPS) × stepLines`
- **容量计算**: 每个 step 的有效数据 = `stepLines × 8` 字节
- **清理范围**: 标志回绕时需要清理 `stepLines` 个 line

**示例**: 使用默认配置时,`stepLines = 4,096`,每个 step 可以容纳 32 KB 有效数据。

#### 4. LL Primitives 的设计特点

- **数组管理**: `recvStep[]`, `sendStep[]` 支持多连接并行
- **recv/send 分离**: 不同的同步机制和内存所有权
  - `recvConnHead`: 本地接收进度计数器,递增后写入远端
  - `recvConnHeadPtr`: 指向远端发送方的 head (写入远端)
  - `sendConnHead`: 本地发送进度计数器
  - `sendConnHeadPtr`: 指向本地的 head (被远端写入,轮询本地)
  - `sendConnHeadCache`: 缓存远端写入的值
- **生产者-消费者模式**: head 存储在生产者,写权限在消费者,双方各自维护本地计数器
- **细粒度支撑**: `stepLines` 和 `EltPerLine` 连接不同的抽象层次
- **辅助函数**: 清晰的 step → offset → ptr 映射

### 与 Simple Protocol 的核心差异

| 维度 | Simple | LL | 代价 |
|------|--------|-----|------|
| **传输单元** | 大块 (数百 KB) | 小 line (16 字节) | 更复杂的管理 |
| **有效数据比例** | ~100% | ~50% | 带宽损失 |
| **同步层次** | 单层 (step 级) | 双层 (line 级 + step 级) | 更复杂的流控 |
| **延迟** | 较高 | 最低 | 换来的收益 |

LL 用更复杂的数据结构和更高的开销,换来了**最低延迟**。这是有意的设计权衡。

### ncclShmem: 共享内存中的全局状态

#### 什么是 ncclShmem?

`ncclShmem` 是一个存储在 **GPU 共享内存** (shared memory) 中的全局变量,定义在 [common.h:67](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/common.h#L67):

```cpp
extern __shared__ ncclShmemData ncclShmem;
```

**关键特性**:
- **存储位置**: GPU 的共享内存 (比全局内存快得多)
- **作用域**: 整个 CUDA block 内的所有线程共享
- **生命周期**: kernel 启动时初始化,kernel 结束时销毁

#### ncclShmem 的结构

`ncclShmem` 的类型是 `ncclShmemData` ([common.h:42-65](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/common.h#L42-L65)),包含以下关键成员:

```cpp
struct ncclShmemData {
  struct ncclDevKernelArgs args;      // Kernel 参数
  int channelId;                       // 当前 channel ID
  int aborted;                         // 中止标志
  alignas(16) struct ncclKernelComm comm;    // 通信器信息 (重要!)
  alignas(16) struct ncclDevChannel channel; // 通道信息

  // ... 其他工作相关的元数据
};
```

其中最重要的是 **`comm`** 成员,它的类型是 `ncclKernelComm` ([device.h:411-432](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L411-L432)):

```cpp
struct ncclKernelComm {
  int rank;
  int nRanks;
  int node;
  int nNodes;
  int buffSizes[NCCL_NUM_PROTOCOLS];  // 每个协议的缓冲区大小 (关键!)
  int p2pChunkSize;
  // ... 其他成员
};
```

#### buffSizes 数组的作用

`ncclShmem.comm.buffSizes[NCCL_NUM_PROTOCOLS]` 是一个数组,存储了**每个协议的环形缓冲区大小**:

```cpp
buffSizes[NCCL_PROTO_SIMPLE]  // Simple Protocol 的缓冲区大小
buffSizes[NCCL_PROTO_LL]      // LL Protocol 的缓冲区大小
buffSizes[NCCL_PROTO_LL128]   // LL128 Protocol 的缓冲区大小
```

**为什么需要这个数组?**

1. **运行时配置**: 缓冲区大小不是编译时常量,而是在初始化时根据环境变量和硬件配置动态确定的
2. **多协议支持**: 不同协议使用不同的缓冲区大小 (如 LL 默认 512 KB, Simple 默认 4 MB)
3. **统一访问**: 所有 Primitives 都通过 `ncclShmem.comm.buffSizes[协议ID]` 获取缓冲区大小

**初始化流程**:

1. Host 端在 `ncclCommInitRank` 中计算 `buffSizes` (基于 `DEFAULT_LL_BUFFSIZE` 等宏和环境变量)
2. Host 端将 `buffSizes` 存储到 `ncclComm` 结构体中
3. Kernel 启动时,将 `ncclKernelComm` (包含 `buffSizes`) 复制到共享内存的 `ncclShmem.comm`
4. Device 端代码通过 `ncclShmem.comm.buffSizes[NCCL_PROTO_LL]` 访问

**关键洞察**: `ncclShmem` 是 device 端代码访问全局配置的"窗口"。它避免了频繁访问全局内存,提高了性能。

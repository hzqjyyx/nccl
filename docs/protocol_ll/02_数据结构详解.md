# LL Protocol 数据结构详解

## 引言

在第一章，我们了解了 LL Protocol 的核心思想：**细粒度传输 + 每字节完整性保证**。LL 把数据切成很小的单元（16 字节），逐个传输，每个单元都有完整性验证。

但你可能会好奇：
- 为什么传输单元是 16 字节，而不是 8 字节或 32 字节？
- 环形缓冲区是如何组织的？
- LL Primitives 的成员变量为什么这么多？

本章将深入解答这些问题。我们会从最基础的数据结构——`ncclLLFifoLine`——开始，逐步理解 LL Protocol 如何在内存中组织数据。

**本章的三个核心问题**：
1. `ncclLLFifoLine` 为什么是 16 字节？为什么标志在数据之后？
2. `stepLines` 是什么？它如何连接数据结构和流控？
3. LL Primitives 的成员变量有哪些？与 Simple Protocol 有什么不同？

让我们从 LL 的传输单元开始。

---

## 一、ncclLLFifoLine：LL 的传输单元

### 定义和内存布局

LL Protocol 的传输单元是 `ncclLLFifoLine`，定义在 [device.h:70-83](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L70-L83)：

```c
union ncclLLFifoLine {
  /* Flags have to be *after* data, because otherwise, an incomplete receive
     from the network may receive the flag but not the data.
     Note this is assuming that either we receive contiguous chunks of data
     (sockets) or data is written with an atomicity of 8 bytes (IB/RDMA). */
  struct {
    uint32_t data1;
    uint32_t flag1;
    uint32_t data2;
    uint32_t flag2;
  };
  uint64_t v[2];
  int4 i4;
};
```

这个 `union` 定义了三种访问方式：
1. **结构体访问**：`data1`, `flag1`, `data2`, `flag2`（4 个 `uint32_t`）
2. **uint64_t 数组**：`v[2]`（2 个 8 字节）
3. **int4 向量**：`i4`（128 位向量，方便一次读写 16 字节）

内存布局是这样的：

```
偏移量：  0      4      8      12     16 (Bytes)
       +------+------+------+------+
       |data1 |flag1 |data2 |flag2 |
       +------+------+------+------+
       |<- 8 Bytes ->|<- 8 Bytes ->|
       |   v[0]      |     v[1]    |
       +------+------+------+------+
       |<----- i4 (16 Bytes) ----->|
```

**总大小**：16 字节
**有效数据**：8 字节（data1 + data2）
**标志开销**：8 字节（flag1 + flag2）

你可能注意到了一个关键问题：**为什么有效载荷只有 8 字节，标志却占了 50%？**

### 为什么是 16 字节？

这是 LL Protocol 设计中最重要的问题之一。让我们从设计的起点说起。

#### 设计起点：readLL 返回 uint64_t

看 `readLL()` 的函数签名（[prims_ll.h:89](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L89)）：

```cpp
__device__ uint64_t readLL(int offset, int i);
```

它返回 `uint64_t`（8 字节）。这个选择不是随意的——**在 RDMA 的 8 字节原子性约束下，8 字节是 LL Protocol 能够高效传输并验证完整性的数据单元大小**。

看 `readLL` 的实现（[prims_ll.h:89-99](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L89-L99)）：

```cpp
__device__ uint64_t readLL(int offset, int i) {
  union ncclLLFifoLine* src = recvPtr(i) + offset;
  uint32_t flag = recvFlag(i);
  uint32_t data1, flag1, data2, flag2;
  int spins = 0;
  do {
    asm volatile("ld.volatile.global.v4.u32 {%0,%1,%2,%3}, [%4];"
      : "=r"(data1), "=r"(flag1), "=r"(data2), "=r"(flag2)
      : "l"(&src->i4) : "memory");
    if (checkAbort(abort, 1, spins)) break;
  } while ((flag1 != flag) || (flag2 != flag));
  uint64_t val64 = data1 + (((uint64_t)data2) << 32);
  return val64;
}
```

最后一行的计算很关键：
```cpp
uint64_t val64 = data1 + (((uint64_t)data2) << 32);
```

它把 `data1`（低 32 位）和 `data2`（高 32 位）组合成一个 `uint64_t`。所以，**一个 line 携带 8 字节的有效数据**。

问题来了：既然有效数据是 8 字节，为什么 line 要 16 字节？剩下的 8 字节都是标志吗？

#### 双标志位的必要性：RDMA 的 8 字节原子性

答案在代码注释里（[device.h:71-74](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L71-L74)）：

```c
/* ...this is assuming that either we receive contiguous chunks of data
   (sockets) or data is written with an atomicity of 8 bytes (IB/RDMA). */
```

关键信息：**RDMA 只保证 8 字节的原子性**。

当我们通过 RDMA 传输 16 字节的 line 时，它会被分成两次 8 字节的操作：
- **第一次 8 字节**：`data1` (4B) + `flag1` (4B)
- **第二次 8 字节**：`data2` (4B) + `flag2` (4B)

你可能会问：**为什么不用一个 8 字节的 line（4B 数据 + 4B 标志）？**

让我们尝试这样设计：
```
方案 A（效率低）：8 字节 line
- Line 包含：4 字节数据 + 4 字节标志
```
问题：现在一个 16B line 通过两次 8B 传输搬来 8 字节用户数据（剩下 8 字节是两个 flag），也就是说每趟握手能带 8 字节有效载荷。换成“4 字节数据 + 4 字节 flag”的 8B line 后，每次握手只能带 4 字节数据。要搬同样多的用户数据，storeLL/readLL、flag 自旋、step 统计都要执行两倍次数，控制开销翻倍，NVLink/RDMA 侧的 8B 写次数也翻倍；有效数据占比没变，但单位时间能推进的数据量下降。GPU 端的 EltPerLine 会从 8/sizeof(T) 变成 4/sizeof(T)，主循环迭代次数也翻倍。

如果我们让数据和标志分离呢？
```
方案 B（错误）：先数据后标志
- 第一次 8 字节：data (8B)
- 第二次 8 字节：flag (8B)
- 问题：接收方可能看到flag已经更新，但数据还是旧的！
```
问题出在**两次 8 字节写入的到达顺序无法保证**。

```
假设布局是：
  [ data (8B) ][ flag (8B) ]

传输拆成两次 8 字节写：
  1) 写 data（8B）
  2) 写 flag（8B）
```

如果网络出现乱序或重试，第二次写（flag）可能先于第一次写（data）生效。接收端看到 flag 已经是新值，就会误以为整段数据准备好了，但实际上 data 还没更新——数据完整性就被破坏了。

NCCL 的做法是把每个 8 字节写都塞进"数据 + 自己的标志"：

```
  [ data1 (4B) | flag1 (4B) ][ data2 (4B) | flag2 (4B) ]
```

这样，接收方通过检查 `flag1 == flag && flag2 == flag`，就能确保**完整的 16 字节都已到达**。

- 如果先到的是前半段，那么 `flag1` 会变成新值，但 `flag2` 仍是旧值；
- 如果先到的是后半段，`flag2` 会变成新值，`flag1` 仍是旧值。

接收端只有在 **`flag1 == expected && flag2 == expected`** 时才会离开自旋循环，这意味着两个 8 字节写都已经落地，对应的数据也都安全地写好。  
换句话说，两个标志并不是"重复验证同一件事"，而是分别为两个半行数据建立了"就地确认"信号，从而屏蔽了底层传输的乱序或部分完成。

#### 节点内通信：为什么也用 16 字节？

你可能注意到，节点内通信（GPU 之间通过 NVLink/PCIe）可以使用 128 位宽度的向量写指令。

看 `storeLL` 的实现（[prims_ll.h:126-128](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L126-L128)）：

```cpp
__device__ void storeLL(union ncclLLFifoLine* dst, uint64_t val, uint32_t flag) {
  asm volatile("st.volatile.global.v4.u32 [%0], {%1,%2,%3,%4};"
    :: "l"(&dst->i4), "r"((uint32_t)val), "r"(flag),
       "r"((uint32_t)(val >> 32)), "r"(flag) : "memory");
}
```

`st.volatile.global.v4.u32` 指令一次写入 4 个 `uint32_t`（16 字节）。既然节点内可以用单条指令写完 16 字节，为什么还要用双标志位？

**答案是统一接口**。

节点内和节点间使用相同的数据结构（`ncclLLFifoLine`）和相同的代码路径（`storeLL`/`readLL`），这样：
- 简化实现：不需要针对不同场景使用不同的代码
- 统一验证：接收方总是检查双标志位，无论数据来自哪里
- 防御性设计：即使硬件一次写完一整个 line，软件也提供双重验证

**关键洞察**：16 字节不是为了对齐，而是为了在 RDMA 的 8 字节原子性约束下，保证 8 字节有效数据的完整性传输。双标志位是这个设计的核心。

## 二、环形缓冲区布局

现在我们知道了 LL 的传输单元是 16 字节的 line。但这些 line 是如何组织的呢？

LL Protocol 使用环形缓冲区来管理这些 line，就像 Simple Protocol 一样（如果你读过 Simple 系列，会发现很多相似之处）。但 LL 的环形缓冲区有自己的特点。

### 总大小和计算公式

LL Protocol 的环形缓冲区大小由 `DEFAULT_LL_BUFFSIZE` 宏定义（[init.cc:697](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/init.cc#L697)）：

```c
#define DEFAULT_LL_BUFFSIZE \
  (NCCL_LL_LINES_PER_THREAD * NCCL_LL_MAX_NTHREADS * NCCL_STEPS * sizeof(union ncclLLFifoLine))
```

让我们拆解这个公式：

- **`NCCL_LL_LINES_PER_THREAD`**（[device.h:93](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L93)）：每个线程处理的 line 数量
  ```c
  #define NCCL_LL_LINES_PER_THREAD 8
  ```

- **`NCCL_LL_MAX_NTHREADS`**（[device.h:92](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L92)）：LL Protocol 的最大线程数
  ```c
  #define NCCL_LL_MAX_NTHREADS 512
  ```

- **`NCCL_STEPS`**（[device.h:24](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L24)）：环形缓冲区的 slot 数量
  ```c
  #define NCCL_STEPS 8
  ```

- **`sizeof(union ncclLLFifoLine)`**：每个 line 的大小 = 16 字节

所以：
```
DEFAULT_LL_BUFFSIZE = 8 × 512 × 8 × 16 = 524,288 字节 = 512 KB
```

为什么是这个大小？这是基于以下考虑的平衡：
- **足够的流水线深度**：8 个 step 提供足够的缓冲空间，支持发送方和接收方异步工作
- **内存开销可控**：每个连接 512 KB，不会过度占用 GPU 内存
- **线程并行度**：512 个线程可以充分利用 GPU 并行能力

注意：这是**默认值**。实际运行时，缓冲区大小可以通过环境变量 `NCCL_LL_BUFFSIZE` 配置（[init.cc:701](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/init.cc#L701)）。

### ncclShmem：共享内存中的全局状态

在深入 `stepLines` 之前，我们需要理解一个关键的全局变量：`ncclShmem`。

#### 什么是 ncclShmem？

`ncclShmem` 是一个存储在 **GPU 共享内存**（shared memory）中的全局变量，定义在 [common.h:67](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/common.h#L67)：

```cpp
extern __shared__ ncclShmemData ncclShmem;
```

**关键特性**：
- **存储位置**：GPU 的共享内存（比全局内存快得多）
- **作用域**：整个 CUDA block 内的所有线程共享
- **生命周期**：kernel 启动时初始化，kernel 结束时销毁

#### ncclShmem 的结构

`ncclShmem` 的类型是 `ncclShmemData`（[common.h:42-65](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/common.h#L42-L65)），包含以下关键成员：

```cpp
struct ncclShmemData {
  struct ncclDevKernelArgs args;      // Kernel 参数
  int channelId;                       // 当前 channel ID
  int aborted;                         // 中止标志
  alignas(16) struct ncclKernelComm comm;    // 通信器信息（重要！）
  alignas(16) struct ncclDevChannel channel; // 通道信息

  // ... 其他工作相关的元数据
};
```

其中最重要的是 **`comm`** 成员，它的类型是 `ncclKernelComm`（[device.h:411-432](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L411-L432)）：

```cpp
struct ncclKernelComm {
  int rank;
  int nRanks;
  int node;
  int nNodes;
  int buffSizes[NCCL_NUM_PROTOCOLS];  // 每个协议的缓冲区大小（关键！）
  int p2pChunkSize;
  // ... 其他成员
};
```

#### buffSizes 数组的作用

`ncclShmem.comm.buffSizes[NCCL_NUM_PROTOCOLS]` 是一个数组，存储了**每个协议的环形缓冲区大小**：

```cpp
buffSizes[NCCL_PROTO_SIMPLE]  // Simple Protocol 的缓冲区大小
buffSizes[NCCL_PROTO_LL]      // LL Protocol 的缓冲区大小
buffSizes[NCCL_PROTO_LL128]   // LL128 Protocol 的缓冲区大小
```

**为什么需要这个数组？**

1. **运行时配置**：缓冲区大小不是编译时常量，而是在初始化时根据环境变量和硬件配置动态确定的
2. **多协议支持**：不同协议使用不同的缓冲区大小（如 LL 默认 512 KB，Simple 默认 4 MB）
3. **统一访问**：所有 Primitives 都通过 `ncclShmem.comm.buffSizes[协议ID]` 获取缓冲区大小

**初始化流程**：

1. Host 端在 `ncclCommInitRank` 中计算 `buffSizes`（基于 `DEFAULT_LL_BUFFSIZE` 等宏和环境变量）
2. Host 端将 `buffSizes` 存储到 `ncclComm` 结构体中
3. Kernel 启动时，将 `ncclKernelComm`（包含 `buffSizes`）复制到共享内存的 `ncclShmem.comm`
4. Device 端代码通过 `ncclShmem.comm.buffSizes[NCCL_PROTO_LL]` 访问

**关键洞察**：`ncclShmem` 是 device 端代码访问全局配置的"窗口"。它避免了频繁访问全局内存，提高了性能。

---

### stepLines：连接数据与流控的桥梁

有了 `ncclShmem` 的理解，我们现在可以看 LL Primitives 如何计算 `stepLines`（[prims_ll.h:335](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L335)）：

```cpp
stepLines(ncclShmem.comm.buffSizes[NCCL_PROTO_LL] / NCCL_STEPS / sizeof(ncclLLFifoLine))
```

这个计算的含义：
```
stepLines = 总缓冲区大小 / step 数量 / line 大小
          = (以 line 为单位的) 每个 step 的大小
```

使用 `DEFAULT_LL_BUFFSIZE` 时：
```
stepLines = 524,288 / 8 / 16 = 4,096
```

所以，**每个 step 包含 4,096 个 line**，也就是 65,536 字节 = 64 KB。

#### stepLines 的重要性

`stepLines` 看起来只是个简单的计算，但它是 LL Protocol 中**最重要的参数之一**，因为它是**连接数据结构和流控的桥梁**：

1. **数据定位**：计算当前 step 在环形缓冲区中的位置
   ```cpp
   int offset = (step % NCCL_STEPS) * stepLines;  // 单位：line
   ```

2. **清理范围**：标志回绕时需要清理的 line 数量（第四章会详细讲解）
   ```cpp
   for (int o = offset; o < stepLines; o += nthreads)
     storeLL(sendPtr(i) + o, 0, sendFlag(i));
   ```

3. **容量计算**：每个 step 可以容纳多少数据
   ```
   有效数据 = stepLines × 8 字节
   ```

**为什么用 line 数量而不是字节数？**

因为 LL Protocol 的所有操作都以 **line 为单位**：
- `readLL(offset, i)`：`offset` 是 line 的索引
- `storeLL(sendPtr(i) + offset, ...)`：指针偏移是 line 的偏移
- `recvPtr(i)`：返回 `ncclLLFifoLine*` 指针

用 line 数量比字节数更自然，也避免了重复的除法运算。

**关键洞察**：`stepLines` 不仅是个参数，更是连接数据结构（line 的组织）和流控机制（step 的管理）的纽带。后续章节的很多操作都依赖这个值。

### 数据结构的层次关系

LL Protocol 的数据结构是层层嵌套的，从大到小依次是：

#### 1. 环形缓冲区（Ring Buffer）
- **大小**：`ncclShmem.comm.buffSizes[NCCL_PROTO_LL]`
  - 使用 `DEFAULT_LL_BUFFSIZE` 时：524,288 字节
- **划分**：`NCCL_STEPS` 个 slot（通常是 8 个）
- **作用**：为整个连接提供缓冲空间，支持流水线传输

#### 2. Step（步）
- **大小**：`buffSizes[NCCL_PROTO_LL] / NCCL_STEPS`
  - 使用默认配置：524,288 / 8 = 65,536 字节 = 64 KB
- **包含**：`stepLines` 个 line
  - 计算：`(buffSizes / NCCL_STEPS) / sizeof(ncclLLFifoLine)`
  - 使用默认配置：65,536 / 16 = 4,096 个 line
- **作用**：流控的基本单位（`waitSend`/`postRecv` 以 step 为粒度）

#### 3. Line（行）
- **大小**：`sizeof(ncclLLFifoLine)` = 16 字节
- **组成**：
  - 有效数据：8 字节（`data1` + `data2`）
  - 标志：8 字节（`flag1` + `flag2`）
- **作用**：LL Protocol 的传输单元，`readLL`/`storeLL` 的操作对象

#### 4. Element（元素）
- **大小**：`sizeof(T)`（取决于数据类型）
  - `float32`：4 字节
  - `float16`：2 字节
  - `int8`：1 字节
- **每个 line 的元素数**：`EltPerLine = sizeof(uint64_t) / sizeof(T)`
  - `float32`：2 个元素
  - `float16`：4 个元素
  - `int8`：8 个元素
- **作用**：用户数据的基本单位

#### 计算示例（使用默认配置）

假设我们有一个 `float32` 类型的 AllReduce：

```
总缓冲区：524,288 字节
  ├─ Step 0: 65,536 字节 (slot 0)
  │   ├─ Line 0: 16 字节 → 2 个 float
  │   ├─ Line 1: 16 字节 → 2 个 float
  │   ├─ ...
  │   └─ Line 4095: 16 字节 → 2 个 float
  ├─ Step 1: 65,536 字节 (slot 1)
  ├─ ...
  └─ Step 7: 65,536 字节 (slot 7)
```

一个 step 可以容纳的有效数据：
```
4,096 lines × 2 elements/line = 8,192 个 float32
8,192 × 4 bytes = 32,768 字节 = 32 KB
```

注意：虽然 step 的总大小是 64 KB，但**有效数据只有 32 KB**（50% 带宽利用率），剩下的 32 KB 是标志开销。

这就是第一章提到的代价：**用 50% 带宽换取最低延迟**。

### 与 Simple Protocol 的差异

如果你读过 Simple Protocol 系列，可能会注意到一个关键差异：

**Simple Protocol**：
- **step** = 一个大块连续内存（通常是 512 KB）
- 传输单元：整个 step 或其中的一大块（如 512 KB）
- 同步粒度：step 级（粗粒度）

**LL Protocol**：
- **step** = 很多小 line（通常是 4,096 个 × 16 字节）
- 传输单元：单个 line（16 字节）
- 同步粒度：line 级（细粒度）+ step 级（粗粒度）

这个差异直接影响了流控机制：
- Simple 只需要 step 级的 `waitPeer`/`postPeer`
- LL 需要双层同步：line 级的标志验证 + step 级的 `waitSend`/`postRecv`

我们会在第四章详细讲解这个差异。现在，只需要记住：**LL 的 step 是由很多小 line 组成的，而不是一个大块**。

**关键洞察**：
- LL 的数据结构比 Simple 更细粒度，但层次更清晰
- 四层嵌套各司其职：环形缓冲区（流水线）→ Step（流控单元）→ Line（传输单元）→ Element（用户数据）
- `stepLines` 是理解这个层次结构的关键，它连接了数据组织和流控机制

## 三、LL Primitives 的成员变量

现在我们理解了 LL 的数据结构（line 和 step），接下来看 LL Primitives 如何使用这些结构。

Primitives 是 LL Protocol 的"引擎"，负责数据的读取、写入和同步。它的成员变量反映了 LL 的设计特点。

### 核心成员概览

LL Primitives 的成员变量定义在 [prims_ll.h:16-44](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L16-L44)：

```cpp
template<typename T, typename RedOp, typename Fan, int Direct, int P2p, bool isNetOffload>
class Primitives<T, RedOp, Fan, Direct, ProtoLL, P2p, isNetOffload> {
  static constexpr int MaxRecv = Fan::MaxRecv > 1 ? Fan::MaxRecv : 1;
  static constexpr int MaxSend = Fan::MaxSend;
  static constexpr int Input=0, Output=1;

  RedOp redOp;
  const int tid;
  const int nthreads;
  const int wid;
  const int group;
  const int stepLines;
  Fan fan;
  T *userBufs[2];

  struct ncclConnInfo* recvConn = NULL;
  volatile uint64_t* recvConnHeadPtr = NULL;
  uint64_t recvConnHead;

  struct ncclConnInfo* sendConn = NULL;
  volatile struct ncclConnFifo* sendConnFifo = NULL;
  volatile uint64_t* sendConnHeadPtr = NULL;
  uint64_t sendConnHead;
  uint64_t sendConnHeadCache;

  uint64_t recvStep[MaxRecv];
  uint64_t sendStep[MaxSend];
  union ncclLLFifoLine* recvBuff[MaxRecv];
  union ncclLLFifoLine* sendBuff[MaxSend];

  // ... 辅助函数
};
```

这些成员变量可以分为几类：

#### 1. 线程信息
```cpp
const int tid;        // 线程 ID
const int nthreads;   // 总线程数
const int wid;        // warp 内线程索引 (tid % WARP_SIZE)
const int group;      // 线程组 ID
```

`wid` 存储了 warp 内的线程索引（lane ID）。虽然 Simple Protocol 也有 warp-level 的同步操作，但 LL Primitives 将 `wid` 显式存储为成员变量，避免重复计算。

#### 2. 配置信息
```cpp
const int stepLines;  // 每个 step 的 line 数量（关键参数！）
Fan fan;              // 接收/发送的 peer 数量
T *userBufs[2];       // 用户缓冲区（Input/Output）
```

`stepLines` 就是我们前面讲的桥梁参数。`userBufs[2]` 缓存了输入/输出缓冲区指针，避免重复访问共享内存。

#### 3. Recv Connection（接收连接）
```cpp
struct ncclConnInfo* recvConn = NULL;        // 连接元数据
volatile uint64_t* recvConnHeadPtr = NULL;   // 指向本地 head 的指针（供远端读取）
uint64_t recvConnHead;                        // 本地 head 计数器

uint64_t recvStep[MaxRecv];                   // 每个 recv peer 的 step
union ncclLLFifoLine* recvBuff[MaxRecv];      // 每个 recv peer 的缓冲区
```

注意这里有**数组**：`recvStep[]` 和 `recvBuff[]`。为什么？

#### 4. Send Connection（发送连接）
```cpp
struct ncclConnInfo* sendConn = NULL;             // 连接元数据
volatile struct ncclConnFifo* sendConnFifo = NULL; // Proxy 通信 FIFO
volatile uint64_t* sendConnHeadPtr = NULL;        // 远端 head 指针
uint64_t sendConnHead;                             // 本地 step 计数器
uint64_t sendConnHeadCache;                        // 缓存的远端 head 值

uint64_t sendStep[MaxSend];                        // 每个 send peer 的 step
union ncclLLFifoLine* sendBuff[MaxSend];           // 每个 send peer 的缓冲区
```

同样有数组。还有一个 `sendConnHeadCache`，用于缓存远端 head，减少轮询开销。

### 为什么需要数组？

这是 LL Primitives 与 Simple Primitives 的**最大差异**。

看 Simple Primitives 的成员变量（[prims_simple.h:41-53](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_simple.h#L41-L53)）：

```cpp
const int stepSize;
uint64_t step;                // 单个 step 计数器
struct ncclConnInfo* conn = NULL;
T* connEltsFifo;              // 单个缓冲区指针
uint64_t *connStepPtr;
uint64_t connStepCache;
// ...
```

Simple 使用**单个** `step` 计数器和**单个**缓冲区指针。为什么 LL 需要数组？

因为 **LL Primitives 的一个实例需要同时追踪多个连接的独立进度**。

在 Ring AllReduce 中，一个 GPU 需要：
- 从前一个 peer 接收数据（recv）
- 向后一个 peer 发送数据（send）

对于 LL Protocol，这两个连接需要**独立的 step 计数器**和**独立的缓冲区**：
- `recvStep[0]` 追踪从 GPU 3 接收的进度
- `sendStep[0]` 追踪向 GPU 1 发送的进度
- `recvBuff[0]` 指向从 GPU 3 接收的环形缓冲区
- `sendBuff[0]` 指向向 GPU 1 发送的环形缓冲区

如果有多个 recv 或 send peer（如 Tree 算法），需要更多的数组元素。`MaxRecv` 和 `MaxSend` 由模板参数 `Fan` 决定。

**为什么 Simple 不需要数组？**

Simple 使用**单个** `step` 计数器和**单个**缓冲区指针，通常在一个时刻只追踪一个连接的状态。而 LL 使用**数组**（`recvStep[]`、`sendStep[]`），可以同时追踪多个 peer 的独立进度。这种设计让 LL 能更灵活地处理多连接场景（如 Tree 算法）。

### recv 和 send 的分离

注意到 LL Primitives 严格分离了 recv 和 send 的信息：
- `recvConn` vs `sendConn`
- `recvConnHead` vs `sendConnHead`
- `recvConnHeadPtr` vs `sendConnHeadPtr`
- `recvStep[]` vs `sendStep[]`

为什么这样设计？

因为 **LL 的 recv 和 send 有不同的同步机制**：

- **Recv 侧**：
  - 读取数据后更新 `recvConnHead`
  - 通过 `recvConnHeadPtr` 将更新后的值写入本地内存（供远端读取，告诉对方"我读完了"）
  - 使用 `recvStep[]` 追踪每个 peer 的接收进度

- **Send 侧**：
  - 发送前轮询 `sendConnHeadPtr`（检查对方是否读完旧数据）
  - 使用 `sendStep[]` 追踪每个 peer 的发送进度
  - 维护 `sendConnHeadCache` 缓存，减少轮询

Simple Protocol 也有类似的分离，但 LL 的分离更彻底，因为 LL 没有 `tail` 概念（依赖 line 级标志验证），只有 `head`。

我们会在第四章详细讲解这个机制。现在，只需要知道：**recv 和 send 的逻辑完全独立**。

### 辅助函数：从 step 到 line 的映射

LL Primitives 提供了几个关键的辅助函数，用于从 step 计算 offset 和指针（[prims_ll.h:39-44](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L39-L44)）：

```cpp
inline __device__ int recvOffset(int i) {
  return (recvStep[i] % NCCL_STEPS) * stepLines;
}
inline __device__ int sendOffset(int i) {
  return (sendStep[i] % NCCL_STEPS) * stepLines;
}
```

**作用**：计算当前 step 在环形缓冲区中的起始 offset（以 line 为单位）。

**为什么需要 `% NCCL_STEPS`？**

因为 `recvStep` 和 `sendStep` 是**单调递增的** `uint64_t`，会不断增长。环形缓冲区只有 8 个 slot（`NCCL_STEPS = 8`），所以需要用模运算映射到 0-7 的 slot：

```
recvStep = 0  → slot 0
recvStep = 1  → slot 1
...
recvStep = 7  → slot 7
recvStep = 8  → slot 0 (重新开始)
recvStep = 9  → slot 1
```

**`stepLines` 的作用**：

计算出 slot 索引后，还需要乘以 `stepLines`，才能得到 line 的 offset：
```
offset = slot × stepLines
       = (step % NCCL_STEPS) × stepLines
```

例如，使用默认配置（`stepLines = 4096`）：
```
step = 0  → offset = 0
step = 1  → offset = 4096
step = 2  → offset = 8192
...
step = 8  → offset = 0 (重新开始)
```

这个 offset 是**以 line 为单位**的，所以 `offset = 4096` 表示从第 4096 个 line 开始。

```cpp
inline __device__ union ncclLLFifoLine* recvPtr(int i) {
  return recvBuff[i] + recvOffset(i);
}
inline __device__ union ncclLLFifoLine* sendPtr(int i) {
  return sendBuff[i] + sendOffset(i);
}
```

**作用**：获取当前 step 的起始 line 指针。这是 `readLL`/`storeLL` 的基地址。

```cpp
inline __device__ uint32_t recvFlag(int i) {
  return NCCL_LL_FLAG(recvStep[i] + 1);
}
inline __device__ uint32_t sendFlag(int i) {
  return NCCL_LL_FLAG(sendStep[i] + 1);
}
```

**作用**：计算期望的标志值。

**为什么是 `step + 1`？**

因为标志代表"这是 step X 的数据"。当我们在处理 step 0 时，写入的标志应该是 1（代表 step 0 的数据），而不是 0（那可能是初始化值或旧数据）。

`NCCL_LL_FLAG` 的定义（[device.h:100](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L100)）：
```c
#define NCCL_LL_FLAG(a) ((uint32_t)(a))
```

正常模式下，它就是简单的类型转换。测试模式下会有取模操作（用于测试标志回绕，第四章会讲）。

这些辅助函数虽然简单，但它们是 LL Protocol **数据定位的基础**。后续章节（`readLL`/`storeLL`、`LLGenericOp`）会频繁使用它们。

### 与 Simple Primitives 的对比

为了帮助你理解 LL 的设计，我们对比一下 Simple Protocol 的 Primitives（如果你还没读过 Simple 系列，可以先跳过这一节）：

| 维度 | Simple Primitives | LL Primitives | 设计原因 |
|------|-------------------|---------------|----------|
| **缓冲区指针类型** | `T* connEltsFifo` | `ncclLLFifoLine* recvBuff[]`、`sendBuff[]` | LL 的传输单元是 line，不是元素 |
| **缓冲区数量** | 单个指针 | recv/send 数组（每个连接一个） | LL 需要为多个 peer 维护独立缓冲区 |
| **step 计数器** | `uint64_t step` (单个) | `uint64_t recvStep[MaxRecv]`、`sendStep[MaxSend]` | LL 为每个连接维护独立 step |
| **head 指针** | `uint64_t *connStepPtr` | `volatile uint64_t* recvConnHeadPtr`、`sendConnHeadPtr` | LL 分离 recv/send 逻辑 |
| **head 计数器** | 无（直接用 step） | `uint64_t recvConnHead`、`sendConnHead` | LL 需要额外的 head 管理 |
| **head 缓存** | `uint64_t connStepCache` | `uint64_t sendConnHeadCache` | LL 只缓存发送侧的 head |
| **大小计算** | `stepSize`（元素个数） | `stepLines`（line 个数） | 反映了传输单元的差异 |
| **warp 管理** | 无 `wid` | `const int wid` (tid % WARP_SIZE) | LL 需要 warp-level 操作 |

**关键差异**：

1. **Per-connection vs Global**
   - Simple：一个 Primitives 实例通常处理一个连接，用单个 `step` 计数器
   - LL：一个 Primitives 实例处理多个连接（`MaxRecv`/`MaxSend`），需要数组

2. **指针类型差异**
   - Simple：`T* connEltsFifo` 指向用户数据类型（如 `float*`）
   - LL：`ncclLLFifoLine*` 指向 16 字节的 line 结构

3. **head 管理的复杂度**
   - Simple：直接使用 `step` 和 `connStepPtr`
   - LL：需要 `recvConnHead`、`sendConnHead` 额外计数器，因为 LL 没有 `tail` 概念（依赖 line 级标志）

**为什么 LL 更复杂？**

不是为了复杂而复杂，而是因为 LL 的**细粒度特性**：
- 每个 line 都有独立的标志验证
- 需要为多个连接维护独立的 step 计数器
- recv 和 send 的逻辑完全分离（因为同步机制不同）

这些额外的复杂度换来了 LL 的**低延迟特性**。

**关键洞察**：
- LL Primitives 的成员变量反映了细粒度传输的需求
- 数组管理（`recvStep[]`、`sendStep[]`）是支撑多连接并行处理的基础
- recv/send 分离是因为 LL 的同步机制与 Simple 不同（第四章会详细讲解）
- `stepLines` 贯穿始终，是理解 LL 数据定位的关键

## 四、EltPerLine：元素到 Line 的映射

我们已经了解了 line（16 字节）和 step（多个 line）的组织。但用户数据是以**元素**（如 `float`、`int8`）为单位的，如何映射到 line？

这就是 `EltPerLine` 的作用。

### 定义和计算

`EltPerLine` 是一个编译时常量（[prims_ll.h:130](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L130)）：

```cpp
static constexpr int EltPerLine = sizeof(uint64_t) / sizeof(T);
```

它的含义：**每个 line 可以容纳多少个类型为 `T` 的元素**。

为什么是 `sizeof(uint64_t) / sizeof(T)`？

因为每个 line 携带 **8 字节有效数据**（`data1 + data2`），而不是 16 字节（总大小）。所以：
```
EltPerLine = 8 字节 / sizeof(T)
```

这是一个 `constexpr` 表达式，在**编译时**计算，不是运行时。

### 不同数据类型的 EltPerLine

根据数据类型 `T` 的大小，`EltPerLine` 有不同的值：

#### float32（4 字节）
```cpp
EltPerLine = 8 / 4 = 2
```
每个 line 可以容纳 **2 个 float32**：
```
[data1: 4B] [flag1: 4B] [data2: 4B] [flag2: 4B]
 └─ float1           └─ float2
```

#### float16（2 字节）
```cpp
EltPerLine = 8 / 2 = 4
```
每个 line 可以容纳 **4 个 float16**：
```
[data1: 4B]         [flag1: 4B] [data2: 4B]         [flag2: 4B]
 └─ half1, half2                 └─ half3, half4
```

#### int8（1 字节）
```cpp
EltPerLine = 8 / 1 = 8
```
每个 line 可以容纳 **8 个 int8**：
```
[data1: 4B]                 [flag1] [data2: 4B]                 [flag2]
 └─ byte0,1,2,3                     └─ byte4,5,6,7
```

#### float64（8 字节）
```cpp
EltPerLine = 8 / 8 = 1
```
每个 line 只能容纳 **1 个 float64**：
```
[data1: 4B] [flag1] [data2: 4B] [flag2]
 └───── double (低32位) ─┘ └─── (高32位) ─┘
```

注意：虽然 `double` 是 8 字节，但它被拆分成两个 `uint32_t` 存储在 `data1` 和 `data2` 中。

### EltPerLine 的重要性

`EltPerLine` 虽然只是个简单的常量，但它决定了 **LLGenericOp 主循环的粒度**（第五章会详细讲解）。

在 `LLGenericOp` 的主循环中（[prims_ll.h:240-285](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L240-L285)），每次迭代处理的元素数量是：

```cpp
while (nelem > 0) {
  int eltInLine = EltPerLine < nelem ? EltPerLine : nelem;
  // ... 处理 eltInLine 个元素
  nelem -= eltPerTrip;
  offset += nthreads;
}
```

`eltInLine` 表示这次迭代要处理多少个元素：
- 如果剩余元素 >= `EltPerLine`，处理满的一个 line（`EltPerLine` 个元素）
- 否则，处理剩余的元素（最后一次迭代可能不满）

`EltPerLine` 决定了：
- 一次 `readLL`/`storeLL` 操作处理多少用户数据
- 循环需要迭代多少次（总元素数 / EltPerLine）

例如，`float32` 每个 line 处理 2 个元素，`int8` 每个 line 处理 8 个元素，这直接影响传输效率。

**关键洞察**：`EltPerLine` 是连接用户数据和 LL Protocol 传输单元的桥梁。它告诉我们"一个 line 能装多少用户数据"，是理解 LLGenericOp 主循环的关键。

## 总结

本章深入讲解了 LL Protocol 的数据结构，从最小的传输单元（line）到整个环形缓冲区，再到 Primitives 的成员变量。让我们回顾一下核心要点。

### 数据结构的层次

LL Protocol 的数据结构是**四层嵌套**的，从大到小依次是：

1. **环形缓冲区**：`buffSizes[NCCL_PROTO_LL]`（默认 512 KB），划分为 8 个 slot
2. **Step**：每个 step 包含 `stepLines` 个 line（默认 4,096 个），是流控的基本单位
3. **Line**：16 字节（8 字节数据 + 8 字节标志），是传输的基本单位
4. **Element**：用户数据类型（如 `float32`），每个 line 包含 `EltPerLine` 个元素

每一层都有明确的职责：
- **环形缓冲区**：支持流水线传输，让发送方和接收方异步工作
- **Step**：粗粒度流控单元（`waitSend`/`postRecv`）
- **Line**：细粒度传输单元（`readLL`/`storeLL`）和完整性验证单元（双标志位）
- **Element**：用户数据的基本单位

### 关键洞察汇总

#### 1. 为什么是 16 字节？
- **设计起点**：`readLL` 返回 `uint64_t`（8 字节有效数据）
- **双标志位必要性**：RDMA 只保证 8 字节原子性，16 字节需要分两次传输
- **每次 8 字节传输都包含数据和标志**，确保完整性可验证
- **节点内也用 16 字节**：统一接口，简化实现

#### 2. 为什么标志在数据之后？
- **容错机制**：如果 RDMA 传输被中断，接收方不会读到部分数据
- **保证**："看到 flag2 更新 = data2 一定已到达"
- **唯一正确的布局**：在 RDMA 的 8 字节原子性约束下，标志后置是正确性的必要条件

#### 3. stepLines 的桥梁作用
- **连接数据结构和流控**：它是理解 LL Protocol 的关键参数
- **数据定位**：`offset = (step % NCCL_STEPS) × stepLines`
- **清理范围**：标志回绕时需要清理 `stepLines` 个 line
- **容量计算**：每个 step 的有效数据 = `stepLines × 8` 字节

#### 4. LL Primitives 的设计特点
- **数组管理**：`recvStep[]`、`sendStep[]` 支持多连接并行处理
- **recv/send 分离**：不同的同步机制（LL 没有 tail，只有 head）
- **细粒度支撑**：`stepLines` 和 `EltPerLine` 连接了不同的抽象层次

### 与 Simple Protocol 的核心差异

| 维度 | Simple | LL | 代价 |
|------|--------|-----|------|
| **传输单元** | 大块（数百 KB 级别） | 小 line（16 字节） | 更复杂的管理 |
| **有效数据比例** | ~100% | ~50% | 带宽损失 |
| **step 组成** | 连续大块内存 | 很多小 line | 更细粒度的定位 |
| **同步层次** | 单层（step 级） | 双层（line 级 + step 级） | 更复杂的流控 |
| **延迟** | 较高 | 最低 | 换来的收益 |

LL 用更复杂的数据结构和更高的开销，换来了**最低延迟**。这是有意的设计权衡。

### 引出下一章

我们现在知道了：
- Line 的结构（16 字节，双标志位）
- Step 的组织（`stepLines` 个 line）
- Primitives 的成员变量（数组管理，recv/send 分离）

但我们还没有深入了解：
- **双标志位机制如何工作？**
  - `storeLL` 如何一次写入 16 字节？
  - `readLL` 如何自旋等待标志？
  - 节点内和节点间有什么差异？
  - Proxy 线程的作用是什么？

下一章，我们会深入探讨 LL Protocol 的**双标志位机制**，理解它如何保证数据完整性，以及为什么这是 LL 正确性的基石。

# LL Protocol 概览

## 本章要回答的问题

LL Protocol 是 NCCL 在小消息场景下的专门方案。本章只解决三个概念层面的疑问：

- 为什么 Simple Protocol 无法覆盖所有通信场景，特别是延迟敏感的小消息？
- LL Protocol 到底改变了什么，它在整条通信流水线中的位置是什么？
- 低延迟来自哪些核心机制，它们背后的取舍是什么？

理解了这三点，后续章节才能有的放矢地讨论数据结构、标志位和流控细节。

## 为什么需要一套新的协议？

Simple Protocol 针对大消息优化，采用粗粒度的同步机制来最大化带宽利用率。具体来说：

- **以 StepPerSlice 为单位的流控**：waitPeer 检查 `step + StepPerSlice` 是否超出可用空间（[prims_simple.h:115](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_simple.h#L115)），按 StepPerSlice 推进
- **Step 粒度较大**：环形缓冲区总大小默认为 4MiB（[init.cc:699](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/init.cc#L699)），分为 8 个 step，每个 step 为 512KB

这种设计对大消息非常高效，但对小消息（几十到几百字节）会产生**相对于数据量的高延迟开销**：

1. **最小同步粒度过大**：即使传输 64 字节，也要完成整个 slice 的流控检查（waitPeer/postPeer）
2. **流水线启动延迟**：粗粒度 chunk 需要更多时间填充流水线
3. **固定的通信开销**：每个 step 的同步成本在小消息场景下被"稀释"得不够

在延迟敏感场景（如张量并行的中间激活传递、小参数更新），这些固定开销成为瓶颈。因此，NCCL 需要一个针对小消息优化的协议：**细粒度传输**（数据到达即可发送）、**细粒度验证**（每个传输单元独立验证）、**低延迟优先**（允许牺牲带宽效率）。

**关键洞察**：对于小消息，通信的瓶颈不在带宽，而在延迟。LL Protocol 就是用**带宽换延迟**的设计。

## LL Protocol 的本质是什么？

首先，让我们明确 LL Protocol 在 NCCL 系统中的位置。
从框架角度看，LL 与 Simple 是并列关系。它们复用同一套连接、通道和调度机制，只是在数据到达 Primitives 层之后采用不同的策略。
如果你读过 Simple Protocol 系列，你会知道 NCCL 的通信流程是这样的（[参考 Simple 01:概览](../protocol_simple/01_概览.md)）：

```
用户调用 ncclAllReduce()
    ↓
NCCL 调度层（选择算法和协议）
    ↓
Primitives 框架（统一的接口）
    ↓
Protocol 实现（Simple/LL/LL128）  ← LL Protocol 在这里
    ↓
Transport 层（NVLink/RDMA/...）
    ↓
硬件
```

LL Protocol 没有引入新的 API，也没有改变 NCCL 的总体流程。Collective 操作依旧经过调度层、Primitives 框架，再落到具体协议实现上。区别在于：面对小消息时，调度器会选择 LL Protocol 的实现，而非 Simple Protocol。

LL Protocol 有三个核心特征：

1. **传输粒度更细**  
   数据不再被攒成上百 KB 的块，而是被拆成固定大小的 line。拿到一个 line，就可以立刻写出去；接收方读到一行，就可以立即消费。这种细粒度意味着几乎没有等待时间。

2. **每个 line 都带有完整性标志**  
   LL 为每行数据额外存放标志位，用它们来确认“这 16 字节已经完整写入”。这样既能适配节点内一次性写入完整 line 的场景，也能兼容网络上传输分成多个子事务的现实。

3. **仍然保留缓冲区级别的流控**  
   虽然线粒度变小了，发送方在写入新的 line 之前，仍然会确认上一圈的旧数据已经被消费。这样可以保证环形缓冲区不会被覆盖，行为上与 Simple 一致，只是时间窗口更紧凑。

**重要的一点**：LL Protocol 和 Simple Protocol 都是 **Primitives 框架的实现**。它们提供相同的接口（[参考 Simple 01](../protocol_simple/01_概览.md)）：

- `send()` / `recv()` - 发送和接收原语
- `reduce()` - 归约原语
- `genericOp()` - 主循环，处理用户数据

这意味着对于上层调度系统来说，LL 和 Simple 是"可互换"的——只是性能特征不同。NCCL 会根据消息大小、硬件拓扑等因素自动选择协议。例如：

- **P2P 操作**：根据消息大小和通道数选择协议，阈值为 `nChannelsMax * P2P_LL_THRESHOLD`（[enqueue.cc:821-834](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/enqueue.cc#L821-L834)）
- **集合通信**：基于性能模型和成本表选择（[graph/tuning.cc](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/graph/tuning.cc)）

用户无需手动切换协议，NCCL 会自动做最优选择。

## 核心机制概览

LL Protocol 的核心设计可以概括为：**细粒度传输 + 双层同步**。

### 细粒度传输：16 字节 line

LL 的基本传输单元是 **line**，大小固定为 16 字节（[device.h:70-83](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L70-L83)）。每个 line 包含：

- 8 字节有效数据（data1 和 data2，各 4 字节）
- 8 字节标志位（flag1 和 flag2，各 4 字节）

有效数据只占 16 字节中的 8 字节，带宽效率为 8/16 = 50%，但换来的是：
- **无需累积**：有一个 line 就可以发送一个 line
- **独立验证**：每个 line 都能独立确认完整性
- **低延迟**：接收方可以立即处理已到达的 line，无需等待整个大块

### 双层同步机制

LL 同时使用两层同步，各司其职：

**Layer 1：Line 级标志验证**（细粒度，保证完整性）

每个 line 有两个标志位（flag1 和 flag2）。接收方通过检查双标志位来确认这 16 字节已完整到达（详见第 3 章）。（[device.h:71-74](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L71-L74) 注释），这意味着双标志位机制对两种场景都适用。


```
either we receive contiguous chunks of data (sockets) or data is written with an atomicity of 8 bytes (IB/RDMA).
```

**Layer 2：Step 级流控**（粗粒度，防止覆盖）

发送方在写入新 step 之前，检查接收方是否已读完足够旧的 step，防止环形缓冲区被覆盖（详见第 4 章）。

**为什么需要两层？** 两层机制解决不同层面的问题：

- **只有 line 级标志**：无法防止缓冲区溢出。发送方可能在接收方还未读完旧数据时就覆盖写入，导致数据丢失
- **只有 step 级流控**：无法保证每个 line 的数据完整性。网络传输可能部分到达，接收方会读到不完整的数据

两层互补：step 级流控控制宏观进度，防止覆盖；line 级标志保证微观正确性，检测部分写入。

## 什么时候会使用 LL Protocol？

调度器会综合消息大小、通道数、缓冲区可用性等条件决定协议选择：

- **小消息常用 LL**：单次传输几 KB 时，延迟优势明显
- **大消息用 Simple/LL128**：当带宽效率重新变得重要时

具体阈值和选择逻辑是动态的，基于性能模型和运行环境。用户无需手动干预。

## 为什么不统一协议？

你可能会问：为什么不设计一个"万能协议"，同时兼顾延迟和带宽？

**根本原因：延迟和带宽是矛盾的优化目标**。

- **LL 的 50% 带宽开销**：双标志位在大消息场景下完全不可接受，每传输 1MB 数据就要额外传输 1MB 标志
- **Simple 的粗粒度同步**：在小消息场景下延迟开销过高，等待和检查的时间相对于数据传输时间占比太大

与其设计一个充满 if-else 的复杂协议，不如保持各协议简单清晰，让调度器根据场景选择最优方案。这是 NCCL 的设计哲学：**通过组合简单的构件，而非设计复杂的单体**。

## 小结与下一步

本章建立了对 LL Protocol 的整体认知：

- **Why**: Simple 的粗粒度同步在小消息场景下产生相对高的延迟开销
- **What**: LL 通过 16 字节 line + 双层同步实现细粒度、低延迟传输
- **Trade-off**: 50% 带宽换低延迟，在小消息场景下这个权衡值得

**设计精髓**：识别瓶颈（延迟而非带宽），做出权衡（带宽换延迟），保持简单（协议分离而非统一）。

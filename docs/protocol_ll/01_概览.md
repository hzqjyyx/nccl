# LL Protocol 概览

## 本章要回答的问题

LL Protocol 是 NCCL 在小消息场景下的专门方案。本章只解决三个概念层面的疑问：

- 为什么 Simple Protocol 无法覆盖所有通信场景，特别是延迟敏感的小消息？
- LL Protocol 到底改变了什么，它在整条通信流水线中的位置是什么？
- 低延迟来自哪些核心机制，它们背后的取舍是什么？

理解了这三点，后续章节才能有的放矢地讨论数据结构、标志位和流控细节。

---

## 为什么需要一套新的协议？

Simple Protocol 的哲学是“凑够一大块再发车”——它把用户数据组织成较大的 chunk，配合粗粒度的同步，把带宽利用率榨到极致。这种做法对于大消息（梯度同步、模型广播等）非常高效，但也埋下了一个前提：**等得起**。

在很多实际场景里，这个前提不成立。例如张量并行的中间激活、控制面指令、频繁的小幅参数更新——这些消息小到不足以填满一个 chunk，并且调用之间是串行依赖的。Simple Protocol 仍然会为它们准备完整的“大车次”，导致 GPU 大部分时间在等待发车；通信真正占用的带宽反而微乎其微。换句话说，小消息的瓶颈不是线路，而是协议带来的等待时间。

```
时间轴：
T0: GPU 并行计算
T1: 计算完成，发起通信
T2: 等待通信完成  ← 这段时间 GPU 在空转！
T3: 通信完成，继续计算
```

我们需要的是什么？

一个针对小消息设计的协议，它应该：
- 不等待累积，有数据就发
- 细粒度同步，不要等整个大块
- 每个字节都能立即验证完整性
- 代价：可以接受更低的带宽效率

LL Protocol 的诞生就是为了解决这个等待问题：**让消息一到就能发，让接收方一到就能用**。

**关键洞察**：对于小消息，通信的瓶颈不在带宽，而在延迟。我们不需要榨干硬件带宽，我们需要的是**尽可能快地完成通信**。

---

## LL Protocol 的本质是什么？

首先，让我们明确 LL Protocol 在 NCCL 系统中的位置。
从框架角度看，LL 与 Simple 是并列关系。它们复用同一套连接、通道和调度机制，只是在数据到达 Primitives 层之后采用不同的策略。
如果你读过 Simple Protocol 系列，你会知道 NCCL 的通信流程是这样的（[参考 Simple 01:概览](../protocol_simple/01_概览.md)）：

```
用户调用 ncclAllReduce()
    ↓
NCCL 调度层（选择算法和协议）
    ↓
Primitives 框架（统一的接口）
    ↓
Protocol 实现（Simple/LL/LL128）  ← LL Protocol 在这里
    ↓
Transport 层（NVLink/RDMA/...）
    ↓
硬件
```

LL Protocol 没有引入新的 API，也没有改变 NCCL 的总体流程。Collective 操作依旧经过调度层、Primitives 框架，再落到具体协议实现上。区别在于：面对小消息时，调度器会把这次工作交给“LL 齿轮”，而不是 Simple 的“大车”。

这个“LL 齿轮”有三个关键特征：

1. **传输粒度更细**  
   数据不再被攒成上百 KB 的块，而是被拆成固定大小的 line。拿到一个 line，就可以立刻写出去；接收方读到一行，就可以立即消费。这种细粒度意味着几乎没有等待时间。

2. **每个 line 都带有完整性标志**  
   LL 为每行数据额外存放标志位，用它们来确认“这 16 字节已经完整写入”。这样既能适配节点内一次性写入完整 line 的场景，也能兼容网络上传输分成多个子事务的现实。

3. **仍然保留缓冲区级别的流控**  
   虽然线粒度变小了，发送方在写入新的 line 之前，仍然会确认上一圈的旧数据已经被消费。这样可以保证环形缓冲区不会被覆盖，行为上与 Simple 一致，只是时间窗口更紧凑。

**重要的一点**：LL Protocol 和 Simple Protocol 都是 **Primitives 框架的实现**。它们提供相同的接口（[参考 Simple 01](../protocol_simple/01_概览.md)）：

- `send()` / `recv()` - 发送和接收原语
- `reduce()` - 归约原语
- `genericOp()` - 主循环，处理用户数据

**这意味着什么？**

对于上层调度系统来说，LL 和 Simple 是"可互换"的——只是性能特征不同。NCCL 会根据消息大小、硬件拓扑等因素，自动选择最合适的 Protocol（[src/enqueue.cc:779](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/enqueue.cc#L779) 定义了协议选择的阈值）。

用户不需要关心用的是哪个 Protocol，NCCL 会自动做最优选择。

## 核心机制概览

在这一节，我们会对 LL Protocol 的核心机制做一个高层次的介绍。注意，这里只是"概览"——具体的实现细节会在后续章节中深入讲解。

### 细粒度传输

LL Protocol 按 16 字节为单位进行传输。**每 16 字节是一个独立的传输单元，我们称之为"line"**。

**对比 Simple Protocol**：

Simple Protocol 的传输单位是"slot"，大小通常是 128KB。也就是说，Simple 会把 128KB 的数据作为一个整体来处理。

别忘了，**"细粒度"是逻辑概念，不是物理链路的限制**。在实际硬件上，同一个 warp 的线程会连续地写入几十个 line，这些写入会被 GPU 内存系统合并成更大的传输事务，然后再通过 NVLink 或 PCIe 发出去。所以它不会真的把每个 16B 单独包一个 PCIe 报文送走。LL 真正付出的带宽代价来自双标志位：每 16B 里只有 8B 是有效负载，其余 8B 用来放 flag，这就是我们常说的 50% 带宽损耗。

LL 的 line（16 字节）和 Simple 的 slot（128KB）相比，粒度细了数千倍。

**为什么能做到低延迟？**

因为不需要等待累积。

在 Simple Protocol 中，即使你只有 16B 的数据，也要等待 slot 相关的同步完成（head/tail 的同步每次都需要 P2P Write）。而在 LL Protocol 中，有 16B 就可以发 16B，不需要等待，而且这是一次传输直接完成（RDMA 可能要分成两个 8B）。

想象一下：
- Simple：等红绿灯，必须等到绿灯才能走，不管前面有没有车
- LL：自由通行，随时可以走

这就是细粒度传输带来的延迟优势。

### 两层同步机制

LL Protocol 使用了两层同步机制来保证正确性和效率。这两层机制各司其职：

**第一层：Line 级标志验证**（细粒度）

- **作用**：保证数据完整性
- **粒度**：每 16 字节（每个 line）
- **机制**：接收方检查每个 line 的双标志位
- **开销**：高（每个 line 都要检查）

每个 line 都有两个标志位（flag1 和 flag2）。接收方在读取数据之前，会检查这两个标志位是否都匹配期望值。只有当两个标志都匹配时，才说明这 16 字节的数据已经完整到达，可以安全读取。

**第二层：Step 级流控**（粗粒度）

- **作用**：防止"绕圈追尾"
- **粒度**：一个 step（包含数千个 line）
- **机制**：发送方检查接收方是否读完旧数据
- **开销**：低（每个 step 一次）

LL Protocol 使用环形缓冲区（和 Simple 一样）。环形缓冲区的问题是：如果发送方太快，可能会"绕圈"追上接收方，覆盖还没被读取的数据。

Step 级流控就是用来防止这种情况的。发送方在开始写一个新的 step 之前，会检查接收方是否已经读完了足够旧的 step。

**为什么需要两层？**

你可能会问：既然有 line 级的标志验证，为什么还需要 step 级流控？

答案是：**两层机制解决不同的问题**。

- **Line 级验证**：解决"数据完整性"问题
  - 确保每 16 字节都是完整的，没有部分传输
  - 特别重要对于网络传输（RDMA 只保证 8 字节原子性）

- **Step 级流控**：解决"环形缓冲区管理"问题
  - 防止发送方覆盖未读数据
  - 这是所有使用环形缓冲区的协议都需要的

如果只有 line 级验证，没有 step 级流控，会发生什么？发送方可能会绕圈覆盖旧数据，导致接收方读到新旧混合的错误数据。

如果只有 step 级流控，没有 line 级验证，会发生什么？接收方可能读到部分传输的数据（特别是在网络传输中）。

### 带宽-延迟权衡

让我们量化一下 LL Protocol 的权衡。

**带宽损失**：

如前所述，LL Protocol 的有效载荷率是 50%：
- 16 字节的 line = 8 字节数据 + 8 字节标志
- 如果硬件带宽是 100 GB/s
- LL Protocol 的有效数据吞吐量只有 50 GB/s

---

## 低延迟带来的代价

把数据拆成 line 并给每行附带标志位，有一个直接后果：**有效载荷率下降**。在 LL Protocol 中，一半空间用于放数据，另一半用于放完整性信息。对于小消息来说，这是值得的交换：带宽本来就用不满，但等待延迟是实打实的瓶颈。

可以把 Simple 和 LL 想象成两种运输模式：

- Simple 像长途货车：发车慢，但一次能运大量货物，最重要的是整体吞吐。
- LL 像摩托快递：每次只送一个小包，却几乎不需要排队等待，适合对响应时间敏感的任务。

NCCL 会在运行时根据消息规模、连接能力等因素选择合适的模式，并不是“硬切换到 LL 就一定更快”，而是“在延迟成为主导时，让 LL 上场”。

## 什么时候会使用 LL Protocol？

调度器会综合消息大小、平行通道数、连接是否预先准备了 LL 缓冲等条件来决定是否启用 LL。实际的阈值和判断逻辑不是写死的常量，而是根据运行环境和消息特征动态调整的。

这意味着：

- **小消息常常触发 LL**：尤其是在单次传输只有几 KB、且通信频繁的情况下。
- **大消息会回落到 Simple 或其他协议**：当有效载荷足够大时，带宽效率重新变得重要。

你无需手动切换协议，但可以通过环境变量或配置项影响阈值。具体做法会在后续文档中给出。

## 小结与下一步

- 小消息的主要问题是“等待填满大块”带来的延迟，而不是链路带宽。
- LL Protocol 通过细粒度传输与双标志位，做到“到就发、到就用”，代价是牺牲一部分带宽效率。
- 它在整体架构中与 Simple 并列，由调度器在运行时按需启用。
- 其设计的精髓在于：**理解真正的瓶颈是什么**（延迟而非带宽），**勇于做出权衡**（50% 带宽换低延迟），**提供统一的抽象**（双标志位兼容不同硬件）。

接下来的章节将分别拆开这些关键词：line 数据结构、双标志位机制、流控策略，以及所有构件如何组装成完整的通信流程。

# 03 - 双标志位机制详解

## 引言

在第二章，我们建立了 LL Protocol 的"数据地图"：
- ✅ ncclLLFifoLine 是 16 字节（8 字节数据 + 8 字节标志）
- ✅ 双标志位的必要性：底层只保证 8 字节原子性
- ✅ 标志后置的原因：容错机制
- ✅ stepLines 是连接数据结构和流控的桥梁

本章将深入**实现细节**：一个 line 如何从发送方安全地到达接收方？

**本章的三个核心问题**：
1. storeLL 如何保证"写入的数据和标志是配对的"？
2. readLL 如何保证"读到的是完整数据"？
3. 节点内和节点间有什么差异？

---

## 第一部分：从问题出发 - 为什么需要双标志位？

### 场景设定：一个 line 的旅程

假设 GPU 0 要向 GPU 1 发送一个 line（16 字节）。

**什么是 storeLL 和 readLL？**

- **storeLL**：发送方用来写入一个 line 的函数
  - 输入：目标地址、8 字节数据、标志值
  - 作用：将数据和标志写入 line

- **readLL**：接收方用来读取一个 line 的函数
  - 输入：line 的偏移量、peer 索引
  - 作用：读取 line，验证标志，返回 8 字节数据

**通信流程**：

```
GPU 0 (发送方)                           GPU 1 (接收方)
    |                                         |
    | 1. 准备数据                             |
    |    val = 0x123456789ABCDEF0            |
    |    flag = NCCL_LL_FLAG(sendStep[0]+1)  |
    |      = NCCL_LL_FLAG(0 + 1) = 1         |
    |                                         |
    | 2. 调用 storeLL()                       |
    |    storeLL(sendPtr(0)+offset, val, flag)|
    |    写入本地缓冲区：                     |
    |    [data1|flag1|data2|flag2]            |
    |    [低32位|1|高32位|1]                  |
    |                                         |
    |------ 数据传输（NVLink/PCIe/RDMA）---->|
    |                                         |
    |                                         | 3. 调用 readLL()
    |                                         |    readLL(offset, 0)
    |                                         |    期望 flag = NCCL_LL_FLAG(recvStep[0]+1)
    |                                         |                = NCCL_LL_FLAG(0 + 1) = 1
    |                                         |    自旋等待：flag1==1 && flag2==1
    |                                         |    返回 val (8 字节)
    |                                         |
    | 4. 递增 step                            | 5. 递增 step
    |    incSend(0, offset)                   |    incRecv(0)
    |    sendStep[0] = 1                      |    recvStep[0] = 1
```

**关键点**：

1. **发送方**：
   - 计算 flag：`sendFlag(0) = NCCL_LL_FLAG(sendStep[0] + 1)`
   - 调用 `storeLL()`：写入本地缓冲区
   - 递增 step：`incSend(0, offset)` → `sendStep[0] += 1`

2. **接收方**：
   - 计算期望的 flag：`recvFlag(0) = NCCL_LL_FLAG(recvStep[0] + 1)`
   - 调用 `readLL()`：自旋等待双标志位匹配
   - 递增 step：`incRecv(0)` → `recvStep[0] += 1`

3. **flag 的作用**：
   - 发送方写入的 flag 和接收方期望的 flag **必须匹配**
   - 这保证了接收方读到的是"当前 step 的数据"，而不是"旧数据"

**核心挑战**：如何保证接收方读到的是"完整的 16 字节"，而不是"部分数据"？

### 原子性的约束

答案在于理解底层传输的原子性保证。

#### 硬件的原子性保证

**关键事实**：无论节点内（NVLink/PCIe）还是节点间（RDMA），底层**只保证 8 字节的原子性**。

**节点内通信（NVLink/PCIe）**：
- **硬件承诺**：单次写入操作的顺序性
- **原子性单元**：8 字节
- **16 字节传输**：可能分两次 8 字节到达

**节点间通信（RDMA）**：
- **硬件承诺**：每次 RDMA Write 的原子性
- **原子性单元**：8 字节
- **16 字节传输**：必须分两次 8 字节 RDMA Write

**关键代码注释**（[device.h:71-74](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L71-L74)）：

```c
union ncclLLFifoLine {
  /* Flags have to be *after* data, because otherwise, an incomplete receive
     from the network may receive the flag but not the data.
     Note this is assuming that either we receive contiguous chunks of data
     (sockets) or data is written with an atomicity of 8 bytes (IB/RDMA). */
```

#### 为什么 16 字节可能分两次到达？

无论访问路径是 NVLink / PCIe 还是 RDMA，`st.volatile.global.v4.u32` 都只是一次性发出四个 32 位写入请求。底层会以 8 字节为粒度完成它们：通常前 8 字节先落地（`data1 + flag1`），随后是后 8 字节（`data2 + flag2`）。两次提交之间可以插入任意延迟，这正是双标志位必须存在的原因。

**核心问题**：如何用 8 字节原子性实现 16 字节完整性？

**答案**：双标志位 + 标志交错

## 第二部分：storeLL - 如何写入一个 line？

### 设计目标

- **节点内和节点间**：使用相同的代码
- **保证配对**：每个 8 字节数据都有自己的标志
- **便于验证**：接收方可以通过双标志位验证完整性

### 实现：PTX 向量写指令

**代码**（`prims_ll.h:126-128`）：
```cpp
__device__ void storeLL(union ncclLLFifoLine* dst, uint64_t val, uint32_t flag) {
  asm volatile("st.volatile.global.v4.u32 [%0], {%1,%2,%3,%4};"
    :: "l"(&dst->i4),
       "r"((uint32_t)val),      // data1 (低 32 位)
       "r"(flag),                // flag1
       "r"((uint32_t)(val>>32)), // data2 (高 32 位)
       "r"(flag)                 // flag2
    : "memory");
}
```

**逐步拆解**：

**1. 输入参数**：
- `dst`：目标 line 的地址
- `val`：8 字节有效数据（`uint64_t`）
- `flag`：当前 step 的标志值

**2. PTX 指令**：`st.volatile.global.v4.u32`
- `st`：store（写入）
- `volatile`：禁止编译器优化，保证每次都真实写入，确保对其他观察者可见
- `global`：写入全局内存（GPU 内存）
- `v4.u32`：向量操作，一次发出 4 个 `uint32_t` 写入请求（总共 16 字节）

**3. 参数顺序**：`{data1, flag1, data2, flag2}`
- 与 `ncclLLFifoLine` 的内存布局完全一致
- `val` 被拆成低 32 位（`data1`）和高 32 位（`data2`）
- 两个标志都是同一个值（`flag`）

**4. 实际传输行为**：
- **节点内（PCIe/NVLink）**：可能分两次 8 字节 PCIe 事务
  - 第一次：`data1 + flag1`（前 8 字节）
  - 第二次：`data2 + flag2`（后 8 字节）
- **节点间（RDMA）**：必须分两次 8 字节 RDMA Write
  - 第一次：`data1 + flag1`（前 8 字节）
  - 第二次：`data2 + flag2`（后 8 字节）

**关键洞察**：
- storeLL 不保证"16 字节原子写入"
- 它只保证"数据和标志是配对的"
- 完整性验证交给 readLL

### 为什么是 16 字节？为什么参数顺序是 data1, flag1, data2, flag2？

#### 双标志位的必要性：8 字节原子性约束

当我们传输 16 字节的 line 时，它会被分成两次 8 字节的操作：
- **第一次 8 字节**：`data1` (4B) + `flag1` (4B)
- **第二次 8 字节**：`data2` (4B) + `flag2` (4B)

你可能会问：**为什么不用一个 8 字节的 line（4B 数据 + 4B 标志）？**

#### 方案 A（效率低）：8 字节 line

```
Line 包含：[ data (4B) ][ flag (4B) ]
```

**问题**：现在一个 16B line 通过两次 8B 传输搬来 8 字节用户数据（剩下 8 字节是两个 flag），也就是说每趟握手能带 8 字节有效载荷。换成"4 字节数据 + 4 字节 flag"的 8B line 后，每次握手只能带 4 字节数据。要搬同样多的用户数据，storeLL/readLL、flag 自旋、step 统计都要执行两倍次数，控制开销翻倍，底层的 8B 写次数也翻倍；有效数据占比没变，但单位时间能推进的数据量下降。GPU 端的 `EltPerLine` 会从 `8/sizeof(T)` 变成 `4/sizeof(T)`，主循环迭代次数也翻倍。

#### 方案 B（错误）：先数据后标志

如果我们让数据和标志分离呢？

```
方案 B：先数据后标志
- 第一次 8 字节：data (8B)
- 第二次 8 字节：flag (8B)
```

假设布局是：
```
[ data (8B) ][ flag (8B) ]
```

传输拆成两次 8 字节写：
1. 一个 8B 事务承载全部用户数据
2. 另一个 8B 事务只承载标志

**问题**：只有一个标志意味着我们无法知道"哪一半数据已经刷新"。如果只有其中一个 8B 事务先到达——无论是数据还是标志——接收方都拿不到关于另一个 8B 的任何证据。一旦标志落地并匹配预期值，readLL 就会退出循环，即使此时数据那一半仍是旧值。硬件确实会保证两个 8B 事务最终都会到达，但在到达完成之前，接收方已经把旧数据当成了新结果。

#### 正确方案：data1, flag1, data2, flag2

NCCL 的做法是把每个 8 字节写都塞进"数据 + 自己的标志"：

```
[ data1 (4B) | flag1 (4B) ][ data2 (4B) | flag2 (4B) ]
```

这样，接收方通过检查 `flag1 == flag && flag2 == flag`，就能确保**完整的 16 字节都已到达**。

- 如果先到的是前半段，那么 `flag1` 会变成新值，但 `flag2` 仍是旧值；
- 如果先到的是后半段，`flag2` 会变成新值，`flag1` 仍是旧值。

接收端只有在 **`flag1 == expected && flag2 == expected`** 时才会离开自旋循环，这意味着两个 8 字节写都已经落地，对应的数据也都安全地写好。

**关键洞察**：
- 16 字节不是为了对齐，而是在 8 字节原子性约束下，保证 8 字节有效数据的完整性传输
- 参数顺序 `{data1, flag1, data2, flag2}` 是唯一正确的布局
  - 两个标志并不是"重复验证同一件事"，而是分别为两个半行数据建立了"就地确认"信号，从而屏蔽了底层传输可能出现的部分完成状态

### 没有显式的内存屏障

**关键事实**：LL Protocol **不使用** `__threadfence()`（`prims_ll.h` 中无此调用）。

**为什么不需要？**
- `volatile` 修饰符已经确保每次写入都会被执行，不会被编译器优化掉
- 接收方通过 `readLL` 的自旋等待，保证读到的是最新值
- Proxy 线程（节点间）会轮询验证 flag，确保 GPU 写入对 CPU 可见

**如果有人疑惑需不需要额外的内存屏障**：
- LL 的实现选择依赖底层内存一致性 + Proxy 轮询，没有在 GPU 端插入 `__threadfence()`
- 这是经过代码验证的设计选择，而非遗漏

**节点间的可见性保证**：
- GPU 只负责写入数据
- Proxy 线程（CPU）轮询验证 flag
- 一旦 Proxy 看到新 flag，说明数据已对 CPU 可见
- 详见第五部分

## 第三部分：readLL - 如何验证数据完整性？

### Flag 的计算：step 到 flag 的映射

在讲 readLL 的实现之前，我们需要理解**期望的 flag 是怎么算出来的**。

#### recvFlag 和 sendFlag 的定义

**代码**（`prims_ll.h:43-44`）：
```cpp
inline __device__ uint32_t recvFlag(int i) {
  return NCCL_LL_FLAG(recvStep[i] + 1);
}
inline __device__ uint32_t sendFlag(int i) {
  return NCCL_LL_FLAG(sendStep[i] + 1);
}
```

**NCCL_LL_FLAG 的定义**（`device.h:100`）：
```cpp
#define NCCL_LL_FLAG(a) ((uint32_t)(a))  // 正常模式：直接转换为 uint32_t
```

#### 为什么是 `step + 1`？

**step 的含义**：
- `recvStep[i]`：接收方**已经读完**的 step 数量
- `sendStep[i]`：发送方**已经写完**的 step 数量

**flag 的含义**：
- flag 代表"这是 step X 的数据"
- 当前正在处理的 step 是 `step + 1`（下一个 step）

**具体例子**：
```
初始状态：
  recvStep[0] = 0  （还没读过任何 step）
  sendStep[0] = 0  （还没写过任何 step）

第一次通信（step 0）：
  发送方：sendFlag(0) = NCCL_LL_FLAG(0 + 1) = 1
  接收方：recvFlag(0) = NCCL_LL_FLAG(0 + 1) = 1
  → 双方期望的 flag 都是 1

第二次通信（step 1）：
  发送方：incSend(0, offset) → sendStep[0] = 1
         sendFlag(0) = NCCL_LL_FLAG(1 + 1) = 2
  接收方：incRecv(0) → recvStep[0] = 1
         recvFlag(0) = NCCL_LL_FLAG(1 + 1) = 2
  → 双方期望的 flag 都是 2

第三次通信（step 2）：
  发送方：incSend(0, offset) → sendStep[0] = 2
         sendFlag(0) = NCCL_LL_FLAG(2 + 1) = 3
  接收方：incRecv(0) → recvStep[0] = 2
         recvFlag(0) = NCCL_LL_FLAG(2 + 1) = 3
  → 双方期望的 flag 都是 3
```

#### step 递增的时机

**发送方**（`prims_ll.h:80-87`）：
```cpp
inline __device__ void incSend(int i, int offset) {
  // LL Cleanup : write all flags in the slice to make sure we don't have
  // data corruption when flag loops over.
  if ((sendStep[i] & NCCL_LL_CLEAN_MASK) == NCCL_LL_CLEAN_MASK) {
    for (int o = offset; o<stepLines; o+=nthreads)
      storeLL(sendPtr(i)+o, 0, sendFlag(i));
  }
  sendStep[i]++;
}
```
- **参数**：`i` (peer 索引), `offset` (当前线程的 line 偏移量)
- **清理机制**：当 `sendStep[i]` 的低位匹配 `NCCL_LL_CLEAN_MASK` 时触发
- **清理操作**：遍历当前 step 的所有 line，用当前 flag 重新写一遍（数据可以是 0）
- **目的**：防止 flag 回绕后，旧数据的 flag 与新数据混淆
- **递增**：在清理之后递增 `sendStep[i]`

**接收方**（`prims_ll.h:72-74`）：
```cpp
inline __device__ void incRecv(int i) {
  recvStep[i] += 1;
}
```
- 在 readLL **之后**调用
- 表示"我已经读完了当前 step"

**关键洞察**：
- flag 是 step 的"版本号"
- 通过 flag 匹配，接收方可以确认"读到的是当前 step 的数据，而不是旧数据"
- `step + 1` 的设计让 flag 从 1 开始（避免与初始化值 0 混淆）
- **清理机制是 LL 防止 flag 回绕撞旧数据的关键**

**清理机制的详细解释**：
- `NCCL_LL_CLEAN_MASK = 0x7ffffff8`（`device.h:98`）
- 条件 `(sendStep[i] & NCCL_LL_CLEAN_MASK) == NCCL_LL_CLEAN_MASK` 要求 bit3-bit30 全为 1，等价于 `sendStep[i] mod 2^31 ∈ [0x7ffffff8, 0x7fffffff]`
- 也就是说：每经过 `2^31` 个 step，就会出现一个连续 8 step 的清理窗口（与 `NCCL_STEPS = 8` 对齐）
- 清理时，每个线程负责从 `offset` 开始，步长为 `nthreads`，遍历 `stepLines` 个 line
- 用当前 `sendFlag(i)` 重新写一遍所有 line（数据可以是 0，关键是更新 flag）
- 这确保了旧数据的 flag 不会与新数据混淆（详见第四章）

---

现在我们理解了 flag 的计算，接下来看 readLL 如何使用 flag 验证数据完整性。

### 设计目标

- **自旋等待**：直到双标志位都匹配
- **原子读取**：一次读取 16 字节
- **返回有效数据**：只返回 8 字节（`data1 + data2`）

### 实现：PTX 向量读指令 + 自旋循环

**代码**（`prims_ll.h:89-99`）：
```cpp
__device__ uint64_t readLL(int offset, int i) {
  union ncclLLFifoLine* src = recvPtr(i) + offset;  // 1. 定位 line
  uint32_t flag = recvFlag(i);                       // 2. 期望的标志值
  uint32_t data1, flag1, data2, flag2;
  int spins = 0;
  do {
    asm volatile("ld.volatile.global.v4.u32 {%0,%1,%2,%3}, [%4];"  // 3. 读取 16 字节
      : "=r"(data1), "=r"(flag1), "=r"(data2), "=r"(flag2)
      : "l"(&src->i4) : "memory");
    if (checkAbort(abort, 1, spins)) break;          // 4. 检查中止
  } while ((flag1 != flag) || (flag2 != flag));      // 5. 自旋条件
  uint64_t val64 = data1 + (((uint64_t)data2) << 32); // 6. 组合数据
  return val64;
}
```

**逐步拆解**：

**1. 定位 line**：
```cpp
union ncclLLFifoLine* src = recvPtr(i) + offset;
```
- `recvPtr(i)`：获取 recv peer `i` 的缓冲区起始地址
- `+ offset`：加上当前 line 的偏移量
- 回顾第二章：`offset = (recvStep[i] % NCCL_STEPS) × stepLines + 线程内偏移`

**2. 计算期望的标志值**：
```cpp
uint32_t flag = recvFlag(i);
```
- 前面已经讲过：`recvFlag(i) = NCCL_LL_FLAG(recvStep[i] + 1)`
- 这个值代表"我期望读到的是哪个 step 的数据"

**3. 读取 16 字节**：
```cpp
asm volatile("ld.volatile.global.v4.u32 {%0,%1,%2,%3}, [%4];"
  : "=r"(data1), "=r"(flag1), "=r"(data2), "=r"(flag2)
  : "l"(&src->i4) : "memory");
```
- PTX 指令：`ld.volatile.global.v4.u32`
- 一次读取 4 个 `uint32_t`：`data1, flag1, data2, flag2`
- `volatile`：每次都从内存读取，不使用缓存

**4. 检查中止**：
```cpp
if (checkAbort(abort, 1, spins)) break;
```
- 检测超时或用户中止
- `spins`：自旋次数计数器

**5. 自旋条件**：`(flag1 != flag) || (flag2 != flag)`
```cpp
} while ((flag1 != flag) || (flag2 != flag));
```
- **只要有一个标志不匹配，就继续等待**
- 这是双标志位的核心：双重验证

**6. 组合数据**：
```cpp
uint64_t val64 = data1 + (((uint64_t)data2) << 32);
return val64;
```
- `data1`（低 32 位）+ `data2`（高 32 位）→ `uint64_t`
- 只返回有效数据（8 字节），标志不返回

### 为什么需要自旋？为什么检查两个标志？

**为什么需要自旋？**
- GPU 不能"睡眠"（没有操作系统调度）
- 只能忙等待（busy-wait）
- 这是 GPU 编程的固有限制

**为什么检查两个标志？**

因为底层**只保证 8 字节原子性**，无论节点内还是节点间：

**节点内（NVLink/PCIe）**：
- PCIe/NVLink 传输可能分两次 8 字节到达
- 第一次：`data1 + flag1`（前 8 字节）
- 第二次：`data2 + flag2`（后 8 字节）
- 必须检查两个标志，确保 16 字节完整到达

**节点间（RDMA）**：
- RDMA 分两次 8 字节传输
- 第一次：`data1 + flag1`（前 8 字节）
- 第二次：`data2 + flag2`（后 8 字节）
- 必须检查两个标志，确保 16 字节完整到达

**关键洞察**：
- 双标志位不是"为了统一接口"，而是 **correctness 本身需要**
- 硬件只承诺写入顺序，不承诺 16 B 原子
- readLL 通过双标志位验证，屏蔽了底层传输的差异
- 发送方和接收方通过 flag 同步，确保读到的是"当前 step 的数据"

## 第四部分：节点内通信 - 同样需要双标志位

### 为什么节点内也需要双标志位？

很多人会认为"节点内通信应该更简单"，但实际上：

**节点内和节点间使用完全相同的 storeLL/readLL 代码，原因不是"为了统一接口"，而是 correctness 本身需要。**

#### 硬件的实际行为

**关键事实**：
- PCIe 和 NVLink 的传输单元通常是 8 字节
- `st.volatile.global.v4.u32` 会被拆成两次 8 字节传输
- 两次传输之间可能有延迟（虽然通常很短）

**具体流程**：

```
GPU 0 (发送方)                GPU 1 (接收方)
    |                              |
    | storeLL()                    |
    | st.volatile.global.v4.u32    |
    |                              |
    |--[前 8B: data1|flag1]------->| (PCIe/NVLink 第一次传输)
    |                              |
    |                              | readLL() 开始自旋
    |                              | 读取 16 字节
    |                              | flag1 == flag? ✅
    |                              | flag2 != flag? ❌ (还是旧值)
    |                              | 继续自旋...
    |                              |
    |--[后 8B: data2|flag2]------->| (PCIe/NVLink 第二次传输)
    |                              |
    |                              | 读取 16 字节
    |                              | flag1 == flag? ✅
    |                              | flag2 == flag? ✅
    |                              | 返回数据
```

#### 为什么会分两次传输？

NCCL 的实现假设底层只提供 8 字节原子性，这在 `device.h:71-74` 的注释中写得非常明确。`st.volatile.global.v4.u32` 发出 4 个 32 位写入请求，但硬件可以分批完成它们；节点内和节点间都只能确保每次 8 字节写完成后才是可见的。

#### CUDA 不保证跨 GPU 的 128 位原子性

**CUDA 编程指南明确说明**：
- 只保证 32 位和 64 位的原子操作
- **没有** 128 位原子操作的保证
- `st.volatile.global.v4.u32` 只是一次性发出 4 个 32 位写入请求
- **不保证** 4 个写入会被原子地提交

**引用 device.h:71-74 的注释**：
```c
/* Note this is assuming that either we receive contiguous chunks of data
   (sockets) or data is written with an atomicity of 8 bytes (IB/RDMA). */
```

关键点：NCCL 假设的原子性是 **8 字节**，包括节点内。

#### 节点内的自旋会发生吗？

**会的**。节点内延迟虽然更小，但 GPU 侧依然只能观察到 8 字节粒度的完成事件，所以 readLL 必须循环检查，直到 `flag1/flag2` 同时更新。通常这只是几次轮询，但设计上不能省略。

#### 对比节点间

节点间（RDMA）同样遵循 8 字节原子性，不过传输途径更长，两个半行数据的到达间隔可能被网络因素拉长。因此 readLL 的自旋循环在节点间场景下可能执行更多次，但逻辑完全一致。

### 数据流

**发送方（GPU 0）**：
```
1. 调用 storeLL(dst, val, flag)
2. PTX 指令：st.volatile.global.v4.u32
3. 发出两次 8 字节写入请求
   - 第一次：data1 + flag1（前 8 字节）
   - 第二次：data2 + flag2（后 8 字节）
4. volatile 语义确保写入最终可见
```

**接收方（GPU 1）**：
```
1. 调用 readLL(offset, 0)
2. PTX 指令：ld.volatile.global.v4.u32
3. 读取 16 字节
4. 检查 flag1 == flag && flag2 == flag
 5. 如果不匹配，继续自旋
6. 如果匹配，返回 data1 + data2
```

### 时序图

```
GPU 0 (发送方)                GPU 1 (接收方)
    |                              |
    | storeLL()                    |
    | st.volatile.global.v4.u32    |
    |                              |
    |--[前 8B]-------------------->|
    |                              |
    |                              | readLL()
    |                              | 自旋等待...
    |                              | flag2 不匹配
    |                              |
    |--[后 8B]-------------------->|
    |                              |
    |                              | flag1/flag2 都匹配
    |                              | 返回数据 ✅
```

**关键点**：
- 延迟极短，但逻辑与节点间完全相同
- 双标志位是必需的，不是可选的
- 这是 correctness，不是优化

## 第五部分：节点间通信 - RDMA 的挑战

节点间通信与节点内的**逻辑完全相同**，但增加了 **Proxy 验证**这一关键步骤。

### 发送路径的三个阶段

#### 阶段 1：GPU 写本地缓冲区

```
GPU 0 调用 storeLL()
  ↓
写入本地 GPU 内存（分两次 8 字节，与节点内相同）
  ↓
[data1|flag1|data2|flag2] 已在本地缓冲区
  ↓
volatile 语义确保写入最终可见
```

**关键点**：
- storeLL 写入的是**本地 GPU 内存**
- 不是直接写入远端 GPU 内存
- RDMA 会稍后从本地内存读取并发送
- **没有显式的 __threadfence()**

#### 阶段 2：Proxy 线程验证标志（关键！）

**为什么需要 Proxy？**

GPU 写入数据后，**不保证**对 CPU/RDMA 网卡的可见性：
- GPU 写入可能还在写缓冲中
- CPU/RDMA 网卡可能看到的是旧值
- 如果直接发起 RDMA，可能传输旧数据

**Proxy 做什么？**

**代码**（`net.cc:1296-1303`）：
```cpp
// 1. 计算期望的 flag
uint32_t flag = NCCL_LL_FLAG(sub->base + sub->transmitted + 1);

// 2. 计算需要验证的 line 数量
int nFifoLines = DIVUP(size, sizeof(union ncclLLFifoLine));

// 3. 遍历所有 line，检查标志
union ncclLLFifoLine* lines = (union ncclLLFifoLine*)buff;
for (int i=0; i<nFifoLines; i++) {
  volatile uint32_t *f1 = &lines[i].flag1;
  volatile uint32_t *f2 = &lines[i].flag2;
  // 4. 如果有任何一个 line 的标志不匹配，ready = 0
  if (f1[0] != flag || f2[0] != flag) {
    ready = 0;
    break;
  }
}
```

**逐步拆解**：

**1. 期望的 flag 是怎么算出来的？**
```cpp
uint32_t flag = NCCL_LL_FLAG(sub->base + sub->transmitted + 1);
```

- `sub->base`：当前传输批次的起始 step
- `sub->transmitted`：已经传输的 step 数量
- `sub->base + sub->transmitted + 1`：**当前正在传输的 step**
- 这与 GPU 侧的 `sendFlag(i) = NCCL_LL_FLAG(sendStep[i] + 1)` **完全对应**

**具体例子**：
```
GPU 侧：
  sendStep[0] = 5
  sendFlag(0) = NCCL_LL_FLAG(5 + 1) = 6
  调用 storeLL(..., flag=6)

Proxy 侧：
  sub->base = 0
  sub->transmitted = 5
  flag = NCCL_LL_FLAG(0 + 5 + 1) = 6
  验证所有 line 的 flag1/flag2 是否都等于 6
```

**2. 验证失败会怎样？**
```cpp
if (f1[0] != flag || f2[0] != flag) {
  ready = 0;  // 标记为"未就绪"
  break;      // 停止验证
}
```

- `ready = 0`：告诉 RDMA 引擎"数据还没准备好，不要发送"
- Proxy 会在下一次轮询时重新验证
- 直到所有 line 的标志都匹配，才设置 `ready = 1`

**3. 验证通过后呢？**
```cpp
if (ready == 1) {
  // 允许 RDMA 发送
  ncclNetIsend(...);
  sub->transmitted += args->sliceSteps;  // 递增已传输的 step 数量
}
```

**注意**：这里使用 `args->sliceSteps` 递增，而不是简单的 `+= 1`。
- 大多数场景下 `sliceSteps == 1`
- 但在某些配置下（如大 slice），`sliceSteps` 可能 > 1
- 代码位置：`net.cc:1326`

**状态表**：

| Proxy 验证结果 | ready | RDMA 行为 | 下一步 |
|---------------|-------|----------|--------|
| 所有 flag 匹配 | 1 | 发送数据 | `sub->transmitted += args->sliceSteps` |
| 有 flag 不匹配 | 0 | **不发送** | 下次轮询重新验证 |

**关键洞察**：
- Proxy 验证的 flag 与 GPU 侧的 sendFlag **完全同步**
- 验证失败 → RDMA 不会发送 → **天然容错**
- 这是 GPU-CPU 内存一致性的桥梁

#### 阶段 3：RDMA 传输

```
RDMA 网卡读取 GPU 内存
  ↓
分两次 8 字节传输：
  第一次：[data1|flag1] (前 8 字节)
  第二次：[data2|flag2] (后 8 字节)
  ↓
写入远端 GPU 内存
```

**关键点**：
- RDMA 只保证 8 字节原子性
- 两次传输的**到达顺序无法保证**
- 这与节点内的逻辑完全相同，只是延迟更长

### 接收路径

```
GPU 1 调用 readLL()
  ↓
自旋等待：while ((flag1 != flag) || (flag2 != flag))
  ↓
场景 1：只有前 8 字节到达
  - flag1 == flag ✅
  - flag2 != flag ❌ (还是旧值)
  - 继续等待
  ↓
场景 2：16 字节完整到达
  - flag1 == flag ✅
  - flag2 == flag ✅
  - 返回数据
```

**与节点内的差异**：
- **逻辑完全相同**（都是自旋等待双标志位）
- **延迟更长**（跨节点链路涉及网卡/交换机）
- **自旋次数更多**（可能需要等待多个网络往返）

### 时序图

```
GPU 0 (发送方)    Proxy 线程      RDMA 网卡      GPU 1 (接收方)
    |                |                |                |
    | storeLL()      |                |                |
    |--写本地内存--->|                |                |
    |                |                |                | readLL()
    |                |                |                | 自旋等待...
    |                |                |                |
    |                | 验证标志       |                |
    |                | 检查 flag1/2   |                |
    |                |--全部匹配----->|                |
    |                |                |                |
    |                |                |--[前 8B]------>| flag2 不匹配
    |                |                |                | 继续等待...
    |                |                |                |
    |                |                |--[后 8B]------>| flag1/flag2 都匹配
    |                |                |                | 返回数据 ✅
```

**关键观察**：
- Proxy 验证通过后，RDMA 才开始传输
- 接收方可能看到"只有前 8 字节到达"的中间状态
- 双标志位验证确保不会读到部分数据
- **这与节点内的逻辑完全相同**

### 网络中断的容错

**问题场景**：第一个 8 字节到达，第二个 8 字节延迟（网络拥塞、丢包重传）

**LL 的处理**：
```
1. 第一个 8 字节到达：[data1|flag1]
   接收方看到：flag1 == flag ✅, flag2 != flag ❌
   → 继续等待

2. 网络延迟...

3. 第二个 8 字节到达：[data2|flag2]
   接收方看到：flag1 == flag ✅, flag2 == flag ✅
   → 返回数据
```

**关键洞察**：
- 接收方不会读到部分数据，**天然容错**
- 无论网络延迟多久，只要最终数据到达，就能正确读取
- 双标志位机制屏蔽了网络的不可靠性
- **这与节点内的逻辑完全相同**，只是延迟范围不同

## 总结

### 双标志位机制的精髓

**1. storeLL**：
- 一条 PTX 指令发出 4 个 32 位写入请求（`st.volatile.global.v4.u32`）
- 数据和标志交错排列（`data1, flag1, data2, flag2`）
- **不保证 16 字节原子写入**，底层分两次 8 字节传输
- `volatile` 语义确保写入最终可见

**2. readLL**：
- 一条 PTX 指令读取 16 字节（`ld.volatile.global.v4.u32`）
- 自旋等待双标志位都匹配（`flag1 == flag && flag2 == flag`）
- 只返回有效数据（8 字节）
- `volatile` 语义确保每次读取最新值

**3. Flag 的计算**：
- `sendFlag(i) = NCCL_LL_FLAG(sendStep[i] + 1)`
- `recvFlag(i) = NCCL_LL_FLAG(recvStep[i] + 1)`
- flag 是 step 的"版本号"，确保读到的是当前 step 的数据

**4. incSend 的清理机制**：
- 签名：`incSend(int i, int offset)`
- 当 `sendStep[i] & NCCL_LL_CLEAN_MASK == NCCL_LL_CLEAN_MASK` 时触发清理
- 清理操作：遍历所有 line，用当前 flag 重新写一遍
- 目的：防止 flag 回绕后，旧数据的 flag 与新数据混淆

**5. 节点内 vs 节点间**：
- **节点内**：底层只保证 8 字节原子性，双标志位是 correctness 需要
- **节点间**：底层只保证 8 字节原子性，双标志位是 correctness 需要
- **逻辑完全相同**，只是延迟不同（纳秒 vs 微秒/毫秒）

**6. Proxy 的作用**：
- GPU-CPU 内存一致性的桥梁
- 验证标志后才允许 RDMA 发送
- 防止 RDMA 读到未刷新的数据
- 与 GPU 侧的 sendFlag 完全同步
- 使用 `args->sliceSteps` 递增（通常为 1）

**关键洞察**：
- **唯一可信的原子粒度是 8 字节**（节点内和节点间）
- 双标志位不是"重复验证同一件事"，而是分别为两个半行数据建立"就地确认"信号
- 屏蔽了底层传输的乱序或部分完成
- Proxy 验证失败 → RDMA 不发送 → 天然容错
- 节点内和节点间使用相同的代码，**不是为了统一接口，而是 correctness 本身需要**

### What's Next？

我们现在知道了 **line 级的完整性保证**：
- ✅ storeLL 保证数据和标志配对写入
- ✅ readLL 自旋等待双标志位
- ✅ Proxy 验证确保内存一致性
- ✅ flag 机制确保版本同步
- ✅ 清理机制防止 flag 回绕

但这还不够。考虑这个场景：

**问题场景**：
```
环形缓冲区有 8 个 slot（NCCL_STEPS = 8）
发送方已经写到 step 9（对应 slot 1）
接收方还在读 step 1（也是 slot 1）
→ 发送方会覆盖接收方还未读取的数据！
```

**核心问题**：
- line 级标志验证只能保证"单个 line 的完整性"
- 无法防止"绕圈追尾"（发送方追上接收方）
- 即使 flag 匹配，数据也可能是错的（被新 step 覆盖）

**解决方案**：step 级流控（waitSend/postRecv）

下一章，我们会讲解 **流控机制 - 两层防护**，理解两层同步如何配合：
- **Line 级**（本章）：保证数据完整性（readLL 的双标志位验证）
- **Step 级**（下一章）：防止"绕圈追尾"（waitSend/postRecv 的流控检查）

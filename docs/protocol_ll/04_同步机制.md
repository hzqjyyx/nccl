# 同步机制 - 两层防护

## 引言

在前两章中，我们理解了 LL Protocol 的核心数据结构（`ncclLLFifoLine`）和双标志位机制。我们知道了：
- 16 字节的细粒度传输单元
- 每个 line 都通过双标志位验证完整性

但这还不够。想象一个场景：

发送方 GPU 疯狂地写入 line，速度远超接收方读取的速度。如果没有流控机制，会发生什么？

答案是：**发送方会"绕圈"回来，覆盖接收方还没读完的数据**。

这就是我们在这一章要探讨的：LL Protocol 的**同步机制**，也就是如何协调发送方和接收方，防止"绕圈追尾"。

我们会发现，LL Protocol 使用了**两层防护**：
- **Layer 1**：Line 级标志验证（细粒度，保证完整性）
- **Layer 2**：Step 级流控（粗粒度，防止绕圈）

---

## 从 Simple 回顾出发：为什么 LL 需要两层？

先对比 Simple 的节奏感，帮助建立直觉。Simple 的核心是“粗粒度流控”：按 slice/step 粒度推进，写满一个 slice 后再整体同步，强调高带宽、低同步频率。典型同步形态是 waitPeer/postPeer：

- 发送侧 wait 时看“对端 head + 窗口大小 < 本地 step + 将要推进的步数”才前进；
- 完成本 slice 后 post，把自己的进度写回，让对端得到信用（credits）。

对应代码可参考 Simple 的等待与上报实现：[src/device/prims_simple.h:116-136](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_simple.h#L116-L136)、[src/device/prims_simple.h:176-186](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_simple.h#L176-L186)。

现在的问题是：小消息不等人，如果像 Simple 一样“凑大块再同步”，会把等待时间放大。因此，LL 选择了“细粒度推进”，但随之而来就要回答两个问题：

1) 如何保证每一小段数据到达即可信？
2) 如何避免在环形缓冲区里“绕圈追尾”？

答案就是“两层防护”：
- Line 级（16B）的到达完整性校验；
- Step 级（环形窗口）的推进与背压。

---

## LL Protocol 的两层同步机制

现在让我们理解 LL Protocol 的完整同步设计。

## Layer 1：Line 级完整性校验（readLL/storeLL）

这层机制在第 03 章已深入展开，这里只保留与流控相关的最低限度要点：

- 每个 line 是 16B：8B 数据 + 8B 标志（两段交错、各 4B data + 4B flag，以 8B 原子性为设计约束）。
- 接收侧通过双标志位自旋校验，只有当两个 flag 都等于“期望版本”才认为该 line 到达完整。

可直接看实现：
- readLL 自旋校验：[src/device/prims_ll.h:89-100](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L89-L100)
- ncclLLFifoLine（标志在数据之后的设计理由）：[src/include/device.h:71-83](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L71-L83)

这层保证了“细颗粒数据块”的正确性，但它不解决“我是否可以继续推进 step”的问题；那是 Layer 2 的职责。

关键洞察：Line 级校验让“看到 flag == 期望值”成为“这 16B 已经到位”的充要条件，但不会限制发送方的推进速度——它只在接收读时生效。

——

## Layer 2：Step 级流控（waitSend/postRecv）

现在的问题是：即使每 16B 都有校验，如果发送方不受控地前进，仍可能在环形缓冲区里覆盖掉接收方尚未处理的旧数据。LL 用“head 窗口”做粗粒度节拍控制：

1) 发送方在每次发送前做 waitSend，确保自己没超过“对端确认的 head + 窗口大小（NCCL_STEPS）”。
2) 接收方在处理完成后用 postRecv，把“我已消费的 head”写回给发送方，返还信用。

对应代码：
- 发送侧等待与记账 waitSend：[src/device/prims_ll.h:56-70](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L56-L70)
- 接收侧上报进度 postRecv：[src/device/prims_ll.h:75-78](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L75-L78)

把这两段读顺一下：

- waitSend 的核心条件是 `while (remote_head_cache + NCCL_STEPS < local_head + 1) { refresh(remote_head_cache); }`。这里的 `sendConnHeadPtr` 指向的是“发送方本地内存里的 head 计数”，但这个值由接收方远程写回（RDMA/P2P）更新；因此发送方读取“本地 head”就等价于读“对端反馈的已消费位置”。
- postRecv 里接收方在 barrier 后把 `recvConnHead` 自增并写回到发送方的 head 指针，返还一个完整 step 的信用。

与 Simple 的差异恰好在这里：LL 没有 tail 的概念，发送侧仅依赖对端写回的 head 做背压；Simple 则是经典的 head/tail 二元信用模型。Simple 的 wait/post 见：[src/device/prims_simple.h:116-136](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_simple.h#L116-L136)、[src/device/prims_simple.h:176-186](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_simple.h#L176-L186)。

关键洞察：LL 的粗粒度流控完全由“head 反馈”驱动，简单而有效；细粒度完整性校验发生在接收读取路径，不与发送推进耦合。

### 两层防护的分工与配合

LL Protocol 使用了两层同步机制，各司其职：

**Layer 1：Line 级标志验证**（参见[第三章](./03_双标志位机制详解.md)）

- **作用**：保证数据完整性
- **粒度**：16 字节（每个 line）
- **机制**：每个 line 的 `readLL()` 都自旋等待 `flag1 == expected && flag2 == expected`
- **开销**：高（每个 line 都检查）
- **保证**：不会读到"半条"数据，不会读到旧数据

**Layer 2：Step 级流控**（本章重点）

- **作用**：防止"绕圈追尾"
- **粒度**：一个 step（如 64KB = 4096 个 line）
- **机制**：`waitSend()` 检查 `remote_head + 8 < local_step + 1`
- **开销**：低（每个 step 检查一次）
- **保证**：发送方不会覆盖接收方还在使用的 step

```

双层同步机制示意图：

- 发送方：对每个 line 调用 storeLL(data, flag)
- 接收方：对每个 line 调用 readLL()，自旋等待 flag1 && flag2 匹配
- 标注：细粒度，每 16 字节验证一次
- 目标：完整性保证（不读脏数据）

右侧：Layer 2 - Step 级流控
- 发送方：每个 step 开始前调用 waitSend()，检查 head + 8 < step + 1

- 标注：粗粒度，每 64KB 检查一次
- 目标：防止绕圈追尾

- Layer 2 保证"读的是正确的 step"

T0: waitSend() 检查通过 → 开始写 step
T1: 写第 1 个 line（storeLL + flag 验证）
T2: 写第 2 个 line（storeLL + flag 验证）
...

Tn+2: postRecv() 更新 head，通知发送方

```

**关键洞察**：

> 两层同步机制是 LL Protocol 的"安全网"：
> - **Line 级标志**是第一道防线，防止读到部分/旧数据（数据完整性）
> - **Step 级流控**是第二道防线，防止发送方跑得太快（资源管理）
>
> 缺一不可：只有标志验证，可能绕圈追尾；只有流控，无法保证每个 line 的完整性。

## waitSend：发送方的流控检查

### waitSend 的代码实现

让我们深入看看 `waitSend()` 的实现（[src/device/prims_ll.h:56-70](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L56-L70)）：

```c
inline __device__ void waitSend(int nbytes) {
  if (sendConnHeadPtr) {
    int spins = 0;
    // 关键检查：sendConnHeadCache + NCCL_STEPS < sendConnHead + 1
    while (sendConnHeadCache + NCCL_STEPS < sendConnHead + 1) {
      // 读取本地 head（该值由对端接收方通过 RDMA/P2P 写回）
      sendConnHeadCache = *sendConnHeadPtr;
      if (checkAbort(abort, 1, spins)) break;
    }
    // ConnFifo 相关（用于 Proxy 通信）
    if (sendConnFifo) {
      int size = ((sendConnHead & NCCL_LL_CLEAN_MASK) == NCCL_LL_CLEAN_MASK)
                 ? stepLines*sizeof(union ncclLLFifoLine)
                 : nbytes;
      sendConnFifo[sendConnHead%NCCL_STEPS].size = size;
    }
    sendConnHead += 1;  // 提前递增，标记"正在使用这个 step"
  }
  barrier();  // 确保所有线程同步
}
```

### 关键变量的含义

让我们理解几个关键变量（[src/device/prims_ll.h:28-32](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L28-L32)）：

```c
struct ncclConnInfo* sendConn = NULL;
volatile struct ncclConnFifo* sendConnFifo = NULL;
volatile uint64_t* sendConnHeadPtr = NULL;  // 指向本地 send 的 head（对端会写回）
uint64_t sendConnHead;                       // 本地的 step 计数器
uint64_t sendConnHeadCache;                  // 缓存的对端写回的 head 值（本地读取）
```

**指针的方向性**（非常重要！）：

来自 `ncclConnInfo` 结构（[src/include/device.h:128-146](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L128-L146)）：

```c
struct ncclConnInfo {
  char *buffs[NCCL_NUM_PROTOCOLS]; // Local for recv, remote for send
  void* mhandles[NCCL_NUM_PROTOCOLS];
  uint64_t *tail;     // Local for recv, remote for send
  uint64_t *head;     // Local for send, remote for recv  ← 注意！
  ...
};
```

**对于发送方（生产者）**：
- `sendConnHeadPtr` 指向**本地内存中的 head**（存储在发送方显存/内存）
- 该值由对端接收方写回更新；发送方轮询本地内存即可获知对端消费进度

**对于接收方（消费者）**：
- `recvConnHeadPtr` 指向**远端发送方的 head**（位于发送方内存）
- 接收方在读完一个 step 后把新的 head 值写回这个远端地址，返还信用

**变量的语义**：

| 变量 | 含义 | 谁更新？ | 谁读取？ |
|------|------|---------|---------|
| `sendConnHead` | 发送方本地的发送进度（控制层 step） | 发送方 | 发送方 |
| `sendConnHeadPtr` | 本地 head 指针（由对端写回） | 接收方 | 发送方（本地读取） |
| `sendConnHeadCache` | 上次读取到的对端写回的 head 值 | — | 发送方 |

### 检查条件的含义

核心检查：

```c
while (sendConnHeadCache + NCCL_STEPS < sendConnHead + 1) {
    sendConnHeadCache = *sendConnHeadPtr;  // 本地读，对端写
}
```

让我们逐步理解这个条件。

**变量展开**：
- `sendConnHeadCache`：接收方已读完的 step（上次缓存的值）
- `NCCL_STEPS = 8`：环形缓冲区的 slot 数量
- `sendConnHead`：发送方即将写入的 step
- `sendConnHead + 1`：发送方下一个要写入的 step

**条件变换**：

```c
sendConnHeadCache + 8 < sendConnHead + 1
```

等价于：

```c
sendConnHead + 1 > sendConnHeadCache + 8
```

即：

```c
sendConnHead + 1 - sendConnHeadCache > 8
```

**含义**：
- 如果 `sendConnHead + 1 - sendConnHeadCache > 8`，说明发送方领先接收方 **超过 8 个 step**
- 此时需要等待（自旋）
- 等到 `sendConnHead + 1 - sendConnHeadCache <= 8`，才可以继续

### 具体例子

**场景 1：正常情况**

```
接收方已读完：sendConnHeadCache = 5
发送方即将写：sendConnHead = 10

检查：10 + 1 - 5 = 6 ≤ 8  ✓
结果：可以写入 step 10
原因：step 10 对应 slot 2 (10 % 8)，接收方已读完 step 5，
      不会覆盖接收方正在读的 step
```

**场景 2：需要等待**

```
接收方已读完：sendConnHeadCache = 2
发送方即将写：sendConnHead = 10

检查：10 + 1 - 2 = 9 > 8  ✗
结果：需要等待
原因：step 10 对应 slot 2，但接收方只读完 step 2，
      如果写入 step 10，会覆盖接收方可能还在用的 step 2 的数据
```

**场景 3：等待后继续**

```
初始：
接收方：sendConnHeadCache = 2
发送方：sendConnHead = 10 → 需要等待

发送方自旋读取本地 head（该值由对端写回）：
第 1 次：sendConnHeadCache = 2  → 9 > 8 ✗ 继续等
第 2 次：sendConnHeadCache = 2  → 9 > 8 ✗ 继续等
第 3 次：sendConnHeadCache = 3  → 8 ≤ 8 ✓ 可以继续！

发送方继续执行：
sendConnHead += 1 → 现在 sendConnHead = 11
```

### 为什么是 `sendConnHead + 1`？

你可能会问：为什么检查的是 `sendConnHead + 1` 而不是 `sendConnHead`？

答案在于：**`waitSend()` 在开始写入之前就递增了 `sendConnHead`**。

流程：
1. 调用 `waitSend()`
2. 检查 `sendConnHeadCache + 8 < sendConnHead + 1`
3. 如果通过，执行 `sendConnHead += 1`（**提前递增**）
4. 返回，开始写入 step `sendConnHead`（已经是新值了）

**为什么要提前递增？**

因为 `sendConnHead` 的语义是："我正在使用的 step"，而不是"我即将使用的 step"。

- 调用 `waitSend()` 之前：`sendConnHead = 10`（上一个 step）
- `waitSend()` 检查：能否使用 step 11？
- 如果可以，递增：`sendConnHead = 11`
- 开始写入 step 11

这样，在写入过程中，`sendConnHead` 始终表示"当前正在写入的 step"。

### ConnFifo 相关逻辑

代码中还有这样一段：

```c
if (sendConnFifo) {
  int size = ((sendConnHead & NCCL_LL_CLEAN_MASK) == NCCL_LL_CLEAN_MASK)
             ? stepLines*sizeof(union ncclLLFifoLine)
             : nbytes;
  sendConnFifo[sendConnHead%NCCL_STEPS].size = size;
}
```

**GPU→Proxy 的衔接：为什么要写 connFifo.size？**

你可能会好奇：waitSend 里还有一段 `sendConnFifo[head%NCCL_STEPS].size = ...`，这在 LL 下有什么用？

这与“节点间（RDMA）路径上的 Proxy 线程”相关。对于跨节点，GPU 写入对端前，需要由 CPU 侧 Proxy 确认“这一 slice（或整个 step，在清理场景）对应的每个 line 的 flag 都已经就绪”，再发到网络。相关逻辑在网络传输层验证：

- Proxy 检查 LL 每个 line 的 flag 是否等于期望版本，全部命中才认为 ready：[src/transport/net.cc:1296-1318](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/transport/net.cc#L1296-L1318)

因此，waitSend 在进入一步之前，把本步要传的字节数（正常为 `nbytes`，但在“清理”场景下会是整个 step 的大小）写入 connFifo，给 Proxy 一个明确的“需要验证与发送的数据范围”。

关键洞察：节点内“读到即可信”的判断在 GPU 侧完成；节点间则需要 Proxy 作为“GPU ↔ RDMA”的一致性桥梁，逐 line 验证 flag 以避免半包上网。

**这段代码的作用**：
- 告诉 Proxy："这个 step 有 `size` 字节需要发送"
- 如果是清理步骤（`NCCL_LL_CLEAN_MASK`，第四章会讲解），发送整个 step
- 否则，发送实际的字节数 `nbytes`

**为什么在 `waitSend()` 里？**

因为只有通过流控检查后，我们才确定"可以使用这个 step"，此时通知 Proxy 是安全的。

## postRecv：接收方的通知机制

### postRecv 的代码实现

接收方在读完一个 step 的所有 line 之后，调用 `postRecv()`（[src/device/prims_ll.h:75-78](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L75-L78)）：

```c
inline __device__ void postRecv() {
  barrier();  // 确保所有线程都读完了
  if (recvConnHeadPtr) {
    *recvConnHeadPtr = recvConnHead += 1;  // 更新 head，通知发送方
  }
}
```

**非常简洁**！但这三行代码承担了重要的作用。

### 变量的含义

```c
volatile uint64_t* recvConnHeadPtr = NULL;  // 指向本地的 head
uint64_t recvConnHead;                       // 本地的 head 计数器
```

**对于接收方**：
- `recvConnHeadPtr` 指向**远端发送方**的 head 地址
- 写入 `*recvConnHeadPtr = recvConnHead` 实际是在写远端（发送方）的内存
- 发送方通过轮询它的 `sendConnHeadPtr`（本地地址）即可观察到更新

### postRecv 的作用

`postRecv()` 做了两件事：

**1. 递增本地计数器**

```c
recvConnHead += 1
```

含义：接收方已经读完了 step `recvConnHead`，现在移动到下一个 step。

**2. 通知发送方**

```c
*recvConnHeadPtr = recvConnHead
```

含义：把新的 `recvConnHead` 写回到远端发送方的 head 地址；发送方轮询其本地 `sendConnHeadPtr` 就能读到更新后的值。

### 完整的读取流程

让我们看一个完整的接收流程：

```c
// 接收方 GPU 线程
for (int offset = 0; offset < stepLines; offset++) {
  // Layer 1: Line 级标志验证
  uint64_t val = readLL(offset, i);  // 自旋等待 flag1 && flag2 匹配

  // 处理数据（如规约）
  processData(val);
}

// 读完所有 line，调用 postRecv
postRecv();  // Layer 2: 更新 head，通知发送方
```

```
标注：
- T0 到 Tn：Layer 1 细粒度验证（每个 line）
- Tn+1：Layer 2 粗粒度通知（整个 step）

箭头：
Tn+1 的写入 → 发送方可见（通过 P2P/RDMA）
</ImageDescription>
```

## 标志回绕与“预防性清理”

现在的问题是：flag 来自 step 版本号。step 是 64 位单调递增，但 LL 的 flag（正常模式）取 32 位，使得当低 32 位回绕时，旧数据的 flag 可能与新数据冲突。

为避免“回绕冲突”，LL 在发送推进处做了一个“预防性清理窗口”：当 `sendStep & NCCL_LL_CLEAN_MASK == NCCL_LL_CLEAN_MASK` 命中时，写满本 step 剩余的所有行，把 flag 刷成当前版本。实现见：

- 触发与操作：[src/device/prims_ll.h:80-86](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_ll.h#L80-L86)
- 掩码与断言：[src/include/device.h:94-103](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L94-L103)

把要点拆开看：

- 掩码定义（正常模式）：`NCCL_LL_CLEAN_MASK = 0x7ffffff8`，且保证能整除 `NCCL_STEPS`，因此清理只会在 step 边界窗口触发，不会“掐断”半个 step。
- 触发后用 `storeLL(..., data=0, flag=sendFlag(i))` 从当前线程的 `offset` 开始，以 `nthreads` 为步幅覆盖到 `stepLines` 末尾；数据写 0 并无语义影响，关键是刷新 flag 版本。
- TEST_LL_CLEANUP 模式把掩码收缩到 0x078、flag 取模 256，用于快速触发测试。

```
<ImageDescription>
示意图：一个 step 的所有 line 从当前 offset 起被覆盖刷新。
元素：横轴是 line 索引 0..stepLines-1；阴影部分表示“本次真实发送覆盖的范围”；其后的条纹部分表示“清理线程补写的 flag 刷新区间”。
要表达的关系：无论“真实发送”是否覆盖了整个 step，清理触发时都会把剩余区间的 flag 刷到“当前版本”，防止未来某次回绕时旧 flag 混淆新数据。
</ImageDescription>
```

关键洞察：清理不是“发现冲突再修复”，而是在“可能回绕前的窗口期”把所有潜在旧位点统一刷新，消灭歧义根源。

## 总结

### 核心要点回顾

**1. 两层同步机制**

- **Layer 1：Line 级标志验证**
  - 粒度：16 字节
  - 作用：数据完整性
  - 机制：每个 line 的 readLL() 自旋等待双标志匹配
  - 开销：高（每个 line 都检查）

- **Layer 2：Step 级流控**
  - 粒度：64KB（一个 step）
  - 作用：防止绕圈追尾
  - 机制：waitSend() 检查 head + 8 < step + 1，postRecv() 更新 head
  - 开销：低（每个 step 一次）

**2. 关键函数**

- `waitSend()`：发送方在写 step 之前检查流控
- `postRecv()`：接收方在读完 step 后通知发送方
- `readLL()`：每个 line 的标志验证（Layer 1）
- `storeLL()`：每个 line 的原子写入（Layer 1）

**3. 指针方向性**

- 对于发送方：`sendConnHeadPtr` 指向本地 head（对端写回）
- 对于接收方：`recvConnHeadPtr` 指向远端发送方的 head（接收方远程写回）
- 这种设计让发送方只需轮询本地内存即可获知对端消费进度

### 与 Simple Protocol 的对比

| 维度 | Simple Protocol | LL Protocol |
|------|----------------|-------------|
| **同步层次** | 单层（step 级） | 双层（line + step 级） |
| **检查频率** | 每 128KB 一次 | Line: 每 16B; Step: 每 64KB |
| **完整性保证** | 大块原子传输 | 双标志位验证 |
| **流控机制** | waitPeer/postPeer | waitSend/postRecv |
| **适用场景** | 大消息（粗粒度） | 小消息（细粒度） |

### 设计精髓

**1. 分层是必然的**

LL Protocol 的细粒度传输（16 字节）决定了：
- 必须有 line 级验证（保证完整性）
- 必须有 step 级流控（防止绕圈）
- 两层缺一不可

**2. 粒度的平衡**

- Line 级：必须细粒度，因为要验证每个 line
- Step 级：可以粗粒度，因为只是流控

这种设计在**正确性**和**性能**之间找到了最佳平衡。

**3. 软件层面的保证**

两层同步都是软件实现的：
- 标志验证：通过自旋等待实现
- 流控：通过计数器和内存读写实现
- 没有依赖硬件的"事务"或"锁"

**最终洞察**：

> LL Protocol 的两层同步机制是"防御性编程"的典范：
> - **Layer 1** 是第一道防线：防止读到脏数据（line 级完整性）
> - **Layer 2** 是第二道防线：防止资源冲突（step 级流控）
>
> 两层机制互补而不冗余：
> - Layer 1 解决"微观"问题（每个 line 的正确性）
> - Layer 2 解决"宏观"问题（整个缓冲区的资源管理）
>
> 这种分层设计，让 LL Protocol 在极致的细粒度传输下，仍然保持了 100% 的正确性。

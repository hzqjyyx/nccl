# NCCL Simple Protocol 概览

## 这篇文档要解决什么问题？

当你第一次接触 NCCL 时，可能会看到代码里有三种协议：LL、LL128、Simple。你可能会困惑：

- 为什么需要三种协议？一种不够吗？
- Simple Protocol 的"Simple"是什么意思？
- **它到底是个什么东西？**

这篇文档会从最根本的问题开始：Simple Protocol **本质上是什么**？它在 GPU 通信流程中扮演什么角色？为什么它能提供高带宽？

读完这篇文档，你会理解 Simple Protocol 的核心思想，并建立起对它的整体认知。

**说明**：为了聚焦核心概念，我们只讨论最常见的场景：
- 一个进程对应一个 GPU
- 使用 Ring 算法进行集合通信
- GPU 之间通过 NVLink 或 PCIe 直接连接（节点内通信）

---

## 为什么需要不同的协议？

在回答"Simple Protocol 是什么"之前，我们先理解为什么 NCCL 需要多种协议。

### GPU 通信的两难：带宽 vs 延迟

想象你要从 GPU 0 向 GPU 1 发送数据。有两个关键指标：

- **延迟**：发起传输到第一个字节到达的时间
- **带宽**：单位时间能传输的数据量

这两个指标往往是矛盾的。举个例子：

**场景 A：发送 1KB 数据**
- 如果你每次只发送 1KB，立即通知对方，延迟很低
- 但每次传输都有固定开销（设置 DMA、同步等），带宽利用率低

**场景 B：发送 100MB 数据**
- 如果你把 100MB 打包成一大块传输，带宽很高
- 但启动时间长，如果对方只需要前 1KB，也要等整个传输完成

不同的应用对这两个指标的需求不同。在深度学习训练中：

- **小消息**（如 activations、小的梯度片段）：需要低延迟，数据尽快到达
- **大消息**（如完整的模型梯度、参数同步）：需要高带宽，能传得快就行

这就是为什么 NCCL 提供了三种协议：
- **LL**：优化延迟，用于小消息
- **LL128**：中间方案
- **Simple**：优化带宽，用于大消息

现在问题来了：Simple Protocol 是如何做到高带宽的？要回答这个问题，我们需要先理解它**本质上是什么**。

---

## Simple Protocol 是什么？

### 它在通信流程中的位置

让我们先明确 Simple Protocol 在整个通信流程中的位置。

当你调用 `ncclAllReduce` 时，在 GPU kernel 内部，会调用一系列函数来完成实际的数据传输。Simple Protocol 就是 **GPU kernel 里执行数据传输和同步的那套函数**。

<ImageDescription>
调用栈示意图：
用户代码: ncclAllReduce()
    ↓
Host 端: 创建 Task，准备参数
    ↓
Kernel 启动: ncclKernel<<<...>>>
    ↓
Device 端: allReduceRing()  ← 算法层
    ↓
Device 端: Primitives 类   ← Simple Protocol 在这里
    ↓
实际操作: memcpy, fence, 更新计数器
</ImageDescription>

**关键点**：Simple Protocol 不是某个单独的模块，而是 `Primitives` 类提供的一组函数，包括：
- `waitPeer()`: 等待对端准备好
- `postPeer()`: 通知对端完成
- `genericOp()`: 执行数据传输

这些函数封装了"如何在两个 GPU 之间传输数据"的所有细节。

### 核心思想：大块传输 + 粗粒度同步

现在让我们理解 Simple Protocol 的本质。

**Simple Protocol 的核心思想是：用大块的、连续的内存传输，配合粗粒度的同步，来充分利用 GPU 的内存带宽。**

让我用一个类比来解释：

想象你要从仓库 A 运货物到仓库 B。有两种方式：

**方式 1：小推车模式**
- 每次用小推车运一小箱货物
- 运完一箱，打电话告诉对方，等确认，再运下一箱
- 优点：每箱货物很快到达（低延迟）
- 缺点：来回跑太多次，电话打太多，效率低

**方式 2：大卡车模式**
- 每次用大卡车运一整车货物
- 装满一车，发车，到达后才通知对方
- 优点：来回次数少，通知次数少，整体效率高（高带宽）
- 缺点：第一车货物到达时间较长

Simple Protocol 就是"大卡车模式"。它把数据分成大块（比如每块 2MB），每次传输一大块，传完一块才通知对方一次。这样：
- GPU 的 DMA 引擎可以高效地传输大块连续内存
- 同步次数大幅减少，同步开销降到最低
- 收发双方可以流水线式地并行工作

这就是 Simple Protocol 的本质。它不是"传输很简单"，而是"同步机制很简单"——不需要复杂的 flag、不需要频繁的握手，只需要两个计数器就够了。

### 为什么叫"Simple"？

现在"Simple"这个名字应该很清楚了：

- **不是说实现简单**（虽然相比 LL 确实简单一些）
- 而是说**同步机制简单**：只有两个计数器，没有复杂的 flag 和状态管理

相比之下，LL 协议的每个数据元素都带一个 flag，需要处理 flag 的环绕、清理等复杂逻辑。Simple 协议放弃了这些，用最直接的方式：**大块传，数数就行**。

**关键洞察**：Simple Protocol 的"Simple"指的是同步机制的简洁性。它用最简单的计数器方式，实现了最高效的带宽利用。

## 为什么能做到高带宽？

理解了 Simple Protocol 是什么后，现在我们深入看看它**为什么**能榨干硬件带宽。

### 1. GPU memcpy 的特性

GPU 的内存拷贝（通过 DMA）有个特点：**对大块连续内存的效率远高于小块内存**。

原因是：
- DMA 引擎有启动开销
- 连续内存可以充分利用内存总线的突发传输（burst mode）
- 大块传输让 TLB、cache 的开销被摊薄

一个具体的数字：
- 传输 2MB 连续内存：可以达到接近理论带宽（如 NVLink 的 300GB/s）
- 传输 512 个 4KB 小块：可能只有理论带宽的 50%

**Simple Protocol 选择大块传输，就是为了充分发挥 DMA 引擎的效率。**每个 slot 通常是 1-2MB 的连续内存，这个大小能让 GPU 的内存拷贝跑满带宽。

### 2. 流水线效应

Simple Protocol 使用**环形缓冲区**（我们稍后会详细讲），这带来了流水线效应：

```
时间轴：
t0: GPU 0 写 slot 0 | GPU 1 空闲
t1: GPU 0 写 slot 1 | GPU 1 读 slot 0
t2: GPU 0 写 slot 2 | GPU 1 读 slot 1
...
```

发送方和接收方可以同时工作，互不干扰。这就像工厂的流水线，每个环节专注于自己的任务。

**关键点**：有了环形缓冲区，发送方不用等接收方处理完才发下一块，只要缓冲区没满就可以一直发。这让带宽利用率达到最高。

### 3. 同步开销最小化

Simple Protocol 只用**两个 64-bit 计数器**进行同步：
- `tail`: 发送方写到哪里了
- `head`: 接收方读到哪里了

每传输一个 slot（比如 2MB），只需要更新一次计数器。对比之下：
- 如果用 LL 协议的细粒度同步，传输 2MB 需要几万次 flag 更新
- Simple Protocol 只需要 1 次计数器更新

**同步次数少，意味着：**
- GPU 花在轮询、等待上的时间少
- 内存总线的压力小（不用频繁读写 flag）
- 流水线不会被频繁打断

### 完整的图景

让我们把这三点串起来：

1. **大块传输** → GPU DMA 引擎效率高 → 每次传输都能跑满带宽
2. **环形缓冲区** → 收发双方并行工作 → 没有空闲等待
3. **粗粒度同步** → 同步开销低 → 不打断流水线

这三个机制共同作用，让 Simple Protocol 能够：
- 充分利用硬件的峰值带宽
- 保持持续的数据流动
- 最小化无效开销

**关键洞察**：高带宽的秘诀不是"传得快"，而是"少停顿"。Simple Protocol 通过大块传输和粗粒度同步，把同步开销降到最低，让 GPU 把时间花在数据传输上，而不是花在等待和握手上。

## Simple Protocol 的核心机制

理解了"是什么"和"为什么"，现在我们看看"怎么做"。

Simple Protocol 依赖两个核心机制：

### 1. 环形缓冲区：数据传输的管道

为了让发送方和接收方能流水线式地工作，我们需要一个"缓冲区"。但缓冲区大小不能无限，所以用**环形缓冲区**。

想象一个旋转寿司店的传送带：

<ImageDescription>
一个环形传送带，分成 8 个格子（编号 0-7）。
- 厨师（发送方）在一端放寿司
- 顾客（接收方）在另一端取寿司
- 传送带循环转动，当格子 7 用完后，回到格子 0
- 如果 8 个格子都满了，厨师要等
- 如果所有格子都空，顾客要等
</ImageDescription>

在 NCCL 中，这个环形缓冲区有 **8 个 slot**（定义在 [device.h:24](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L24)）：

```c
#define NCCL_STEPS 8
```

每个 slot 的大小是 `buffSizes[NCCL_PROTO_SIMPLE] / NCCL_STEPS`。比如，如果总缓冲区是 16MB，每个 slot 就是 2MB。

发送方和接收方各自维护一个 step 计数器。**注意：step 不是 slot 索引，而是一个单调递增的计数器。**slot 索引通过 `step % NCCL_STEPS` 计算：

```c
int slot = step % NCCL_STEPS;  // step % 8
```

为什么需要单调递增的 step 而不是直接用 slot 索引？因为我们需要判断"绕圈"的情况。比如：
- step = 0 → slot 0（第一圈）
- step = 8 → slot 0（第二圈）

如果只记录 slot 索引，我们无法区分这两种情况。

**关键点**：环形缓冲区让发送方可以"跑在前面"。只要接收方不是太慢（落后不超过 8 个 slot），发送方就可以一直发，不用等。

### 2. 流控机制：用计数器协调收发

有了环形缓冲区，问题来了：**发送方怎么知道某个 slot 是空的？接收方怎么知道某个 slot 有数据？**

Simple Protocol 的答案是：**两个计数器 + 轮询检查**。

<ImageDescription>
两个 GPU 的内存布局对比：
- GPU 0 内存：有一个 ring buffer（8 个 slot），有 head 计数器，有 tail 计数器
- GPU 1 内存：有一个 ring buffer（8 个 slot），有 head 计数器，有 tail 计数器
- 箭头标注：
  * 发送方（GPU 0）通过 P2P 读取 GPU 1 的 head
  * 接收方（GPU 1）通过 P2P 读取 GPU 0 的 tail
  * 发送方更新自己的 tail，接收方更新自己的 head
</ImageDescription>

让我们理解每个计数器的含义：

**在发送连接（Send Connection）中**：
- `head`：本地计数器，表示"我写到哪个 step 了"
- `tail`：远端计数器，表示"接收方读到哪个 step 了"

**在接收连接（Recv Connection）中**：
- `head`：远端计数器，表示"发送方写到哪个 step 了"
- `tail`：本地计数器，表示"我读到哪个 step 了"

**发送方的逻辑**：
```
我现在要写第 step 个数据（对应 slot = step % 8）
但这个 slot 可能还有上次的旧数据没被读走
我需要确认：接收方的 head + 8 > 我的 step
意思是：接收方至少读到了 step - 8，slot 已经空了
否则就轮询等待
```

对应的代码（[prims_simple.h:115](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_simple.h#L115)）：
```c
// isSendNotRecv = true 时，加上 NCCL_STEPS
while (connStepCache + NCCL_STEPS < step + StepPerSlice) {
    connStepCache = loadStepValue(connStepPtr);  // 轮询远端 head
}
```

**接收方的逻辑**：
```
我现在要读第 step 个数据（对应 slot = step % 8）
但发送方可能还没写到这里
我需要确认：发送方的 tail >= 我的 step
意思是：发送方至少写到了 step，数据已经准备好了
否则就轮询等待
```

对应的代码（[prims_simple.h:115](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_simple.h#L115)）：
```c
// isSendNotRecv = false 时，不加 NCCL_STEPS
while (connStepCache < step + StepPerSlice) {
    connStepCache = loadStepValue(connStepPtr);  // 轮询远端 tail
}
```

传输完成后，发送方更新 tail，接收方更新 head，告诉对方"我完成了这个 step"。

这就是流控的全部逻辑。我们会在后续文档（《流控机制》）中详细分析代码实现。

**关键洞察**：这两个计数器形成了一个"生产者-消费者"模型。发送方是生产者，接收方是消费者。8 个 slot 的缓冲区就是它们之间的队列。发送方和接收方通过轮询对方的计数器来同步，不需要中断，不需要复杂的状态机。

## 一个端到端的例子

现在让我们看一个具体场景，把所有概念串起来。

### 场景设置

**任务**：GPU 0 向 GPU 1 发送 1MB 数据（Ring AllReduce 的一个 chunk）

**环境**：
- 环形缓冲区总大小：16MB
- 每个 slot：16MB / 8 = 2MB
- 初始状态：`发送方 step = 0, 接收方 step = 0`
- StepPerSlice = 1（每个 slice 占用 1 个 step）

### 步骤 1：发送方准备写入

GPU 0 的 kernel 调用 `waitPeer` 函数：

```c
// 发送方当前的 step = 0
int step = 0;
int slot = step % 8;  // 0 % 8 = 0

// 检查接收方是否读走了 slot 0 的旧数据
// 条件：远端 head + 8 < 本地 step？
// 即：connStepCache + 8 < 0 + 1？
// 假设接收方 head = 0，则 0 + 8 = 8 >= 1，条件不满足，不用等待

// 通过检查，可以写入
```

在初始状态下，所有 slot 都是空的，所以不用等待。

### 步骤 2：发送方写数据

GPU 0 计算出 slot 0 的地址，然后用多个线程并行拷贝数据：

```c
char* dest = ringBuffer + slot * slotSize;
// 注意：ringBuffer 指向 GPU 1 的内存（通过 P2P 映射）

// 多个线程并行拷贝 1MB 数据
// 实际上是通过 NVLink 直接写入 GPU 1 的内存
for (int i = tid; i < nelem; i += nthreads) {
    dest[i] = src[i];
}
```

数据通过 NVLink 直接写入 GPU 1 的内存，这是零拷贝。

### 步骤 3：发送方通知接收方

数据写完后，GPU 0 调用 `postPeer` 函数（[prims_simple.h:173-181](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_simple.h#L173-L181)）：

```c
// 先更新 step
step += StepPerSlice;  // 0 -> 1

// 确保数据写入完成（内存屏障）
fence_acq_rel_sys();

// 更新本地的 tail（告诉接收方："我写完 step 0 了"）
st_relaxed_sys_global(connStepPtr, step);  // 写入 tail = 1
```

这个 `tail` 在 GPU 0 的内存中，但 GPU 1 可以通过 P2P 读取。

**注意**：fence 非常关键！它确保所有数据写入完成后，才更新 tail。否则接收方可能看到 tail = 1，但数据还没完全到达。

### 步骤 4：接收方发现新数据

GPU 1 的 kernel 也在调用 `waitPeer`，轮询 GPU 0 的 tail：

```c
// 接收方当前的 step = 0
int step = 0;
int slot = step % 8;  // 0 % 8 = 0

// 检查发送方是否写好了 step 0 的数据
// 条件：远端 tail < 本地 step + 1？
// 即：connStepCache < 0 + 1？
// 不断轮询，直到发现 tail = 1
while (connStepCache < step + StepPerSlice) {
    connStepCache = loadStepValue(connStepPtr);  // 读取 GPU 0 的 tail
}

// 发现 tail = 1，而 step + 1 = 1，条件不满足，可以读取
```

### 步骤 5：接收方读数据

GPU 1 从本地内存读取 slot 0 的数据：

```c
char* src = ringBuffer + slot * slotSize;
// 注意：这次 ringBuffer 指向 GPU 1 自己的内存

// 读取并处理 1MB 数据（比如进行 reduction）
for (int i = tid; i < nelem; i += nthreads) {
    output[i] = reduce(output[i], src[i]);
}
```

### 步骤 6：接收方释放 slot

处理完后，GPU 1 调用 `postPeer`：

```c
// 更新 step
step += StepPerSlice;  // 0 -> 1

// 更新本地的 head（告诉发送方："我读完 step 0 了"）
st_relaxed_sys_global(connStepPtr, step);  // 写入 head = 1
```

这告诉 GPU 0："我读完 slot 0 了，你可以再用它了"。

### 继续流水线

现在：
- 发送方 step = 1，可以写 slot 1
- 接收方 step = 1，可以读 slot 1

如果还有更多数据，流水线就继续运转。比如发送方可以写 slot 2、slot 3...，而接收方在后面追着读。只要发送方不超前超过 8 个 slot，就不会阻塞。

### 完整的时序

<ImageDescription>
序列图展示 GPU 0 和 GPU 1 的交互（一个完整的传输周期）：

时间 | GPU 0 (Sender, step=0)        | GPU 1 (Receiver, step=0)
-----|------------------------------|-----------------------------
t0   | waitPeer: 检查 head+8 >= 0+1? | waitPeer: 轮询 tail，tail=0
t1   | 写数据到 GPU 1 的 slot 0      | (继续轮询)
t2   | fence()                      | (继续轮询)
t3   | postPeer: tail = 1           | (继续轮询)
t4   | step = 1, 准备写 slot 1       | waitPeer: 发现 tail=1 >= 0+1
t5   | ...                          | 读数据从本地 slot 0
t6   | ...                          | postPeer: head = 1
t7   | ...                          | step = 1, 准备读 slot 1

注：GPU 0 的 tail 更新后，GPU 1 通过 P2P 读取可见
    GPU 1 的 head 更新后，GPU 0 通过 P2P 读取可见
</ImageDescription>

**你可能注意到的关键点**：

1. **数据零拷贝**：GPU 0 直接写入 GPU 1 的内存，没有中间缓冲
2. **异步性**：GPU 0 写完就继续，不等 GPU 1 读完（只要缓冲区没满）
3. **轮询同步**：双方通过轮询对方的计数器来同步，不用中断
4. **step 的语义**：step 是一个单调递增的逻辑计数器，不是 slot 索引

这就是 Simple Protocol 的工作方式。

## 总结

让我们回顾一下 Simple Protocol 的核心思想：

### Simple Protocol 是什么？

它是 **GPU kernel 里执行大块数据传输的一套函数**，通过：
- 大块连续的内存拷贝（充分利用 GPU 内存带宽）
- 粗粒度的计数器同步（减少同步开销）
- 环形缓冲区的流水线（让收发双方并行工作）

来实现**高带宽**的数据传输。

### 为什么叫"Simple"？

因为它的**同步机制简单**：只用两个计数器（head 和 tail），没有复杂的 flag 管理。

### 为什么能高带宽？

1. **大块传输** → GPU DMA 效率高 → 跑满带宽
2. **环形缓冲区** → 收发并行 → 无空闲等待
3. **粗粒度同步** → 同步次数少 → 不打断流水线

### 核心机制

1. **环形缓冲区**：8 个 slot 循环使用，形成流水线
2. **流控计数器**：
   - `tail`：发送方写到哪个 step
   - `head`：接收方读到哪个 step
   - 通过 P2P 互相可见，轮询检查

### 适用场景

大消息（通常 > 1MB）的集合通信，如梯度同步、参数更新等。

# NCCL Simple Protocol 数据结构详解

## 这篇文档要解决什么问题？

在第一章,我们建立了对 Simple Protocol 的整体认知：

- Simple Protocol 用**大块传输 + 粗粒度同步**实现高带宽
- 核心机制是**环形缓冲区**（8 个 slot）和**流控计数器**（head 和 tail）
- 发送方和接收方通过轮询对方的计数器来同步

但这些概念还停留在"理论层面"。当你打开 NCCL 的代码时，会看到一堆结构体：`ncclConnInfo`、`ncclShmemGroup`、`Primitives` 类……你可能会困惑：

- **这些"环形缓冲区"、"计数器"在代码中如何表示？**
- **它们存储在哪里？GPU 0 如何访问 GPU 1 的内存？**
- **发送方和接收方如何"看到"同一块内存的不同部分？**

这篇文档会带你了解 Simple Protocol 依赖的核心数据结构。我们**不会深入每个字段的初始化和使用细节**（那是后续章节的任务），而是帮你建立一个"地图"：**知道有哪些东西、它们存在哪里、大概干什么用**。

有了这个地图，你就能更好地理解后续章节中的环形缓冲区机制、流控逻辑和数据传输过程。

## 为什么需要了解数据结构？

让我们先明确一个问题：为什么在理解核心思想之后，还要专门花一章来讲数据结构？

### 从概念到代码的鸿沟

在第一章，我们说：

> 发送方有一个 tail 计数器，接收方有一个 head 计数器，它们通过轮询对方的计数器来同步。

这个描述很清楚，但当你看到代码时，会发现：

```c
// 在 Primitives 类里
uint64_t *connStepPtr;      // 这是什么？
uint64_t connStepCache;     // 为什么要缓存？
T* connEltsFifo;            // 环形缓冲区在哪？
struct ncclConnInfo* conn;  // 这个结构里有什么？
```

这些变量之间是什么关系？它们指向哪里？发送方和接收方看到的是同一个变量吗？

**答案是：这些变量分布在不同的内存区域，通过 GPU P2P 内存映射相互可见。理解它们的布局，是理解 Simple Protocol 的关键。**

### 指针的"方向性"

Simple Protocol 有一个非常容易混淆的设计：**同一个字段，在发送方和接收方的含义可能完全不同**。

举个例子，`ncclConnInfo` 结构中的 `buffs` 字段：

- **对于接收方**：`buffs` 指向**本地内存**中的环形缓冲区（我要从这里读数据）
- **对于发送方**：`buffs` 指向**对方内存**中的环形缓冲区（我要往这里写数据）

这个"方向性"贯穿整个 Simple Protocol。如果不理解这一点，代码会让人非常困惑。

### 数据结构是理解的"锚点"

在后续章节中，我们会讨论：

- 第三章：环形缓冲区的布局和使用（会用到 `connEltsFifo`、`stepSize`）
- 第四章：流控机制的实现（会用到 `connStepPtr`、`connStepCache`、`head`、`tail`）
- 第五章：数据传输的完整流程（会用到 `srcs`、`dsts`、`userInput`、`userOutput`）

这些章节都会引用我们这里介绍的数据结构。**这一章就是给后续章节打"锚点"**：你会在后面反复回来查看这些结构的定义和含义。

现在，让我们开始探索这些数据结构。

## 2.1 理解"连接"的概念

在深入数据结构之前，我们需要先理解一个基本概念：**连接（Connection）**。

### 什么是 Connection？

在 NCCL 中，**Connection 是从一个 GPU 到另一个 GPU 的单向通信通道**。

注意关键词：**单向**。

想象 GPU 0 和 GPU 1 需要互相通信。这需要**两个独立的连接**：

- **GPU 0 → GPU 1**：GPU 0 作为发送方，GPU 1 作为接收方
- **GPU 1 → GPU 0**：GPU 1 作为发送方，GPU 0 作为接收方

这两个连接是独立的，各有各的缓冲区、各有各的计数器。

### Send Connection vs Recv Connection

现在问题来了：站在 GPU 0 的角度，我如何描述这两个连接？

答案是用**角色**来区分：

- **Send Connection**：我作为发送方的连接（我要向 GPU 1 发送数据）
- **Recv Connection**：我作为接收方的连接（我要从 GPU 1 接收数据）

**关键洞察**：每个 GPU 持有**两类连接**：

- **Recv Connections**：我从其他 GPU 接收数据的连接（可能有多个，每个发送方一个）
- **Send Connections**：我向其他 GPU 发送数据的连接（可能有多个，每个接收方一个）

在 Ring AllReduce 中，每个 GPU 通常有：
- 1 个 Recv Connection（从前一个 GPU 接收）
- 1 个 Send Connection（向后一个 GPU 发送）

### 为什么这个概念重要？

因为 **`ncclConnInfo` 结构描述的是"一个方向"的连接**。

当你看到一个 `ncclConnInfo` 时，你必须知道：这是一个 Send Connection 还是 Recv Connection？

因为同样的字段（比如 `buffs`、`tail`、`head`），在 Send Connection 和 Recv Connection 中的含义**完全不同**。

现在，让我们深入 `ncclConnInfo` 结构。

## 2.2 ncclConnInfo：连接信息

### 它是什么？

`ncclConnInfo` 是**描述一个单向 GPU 连接的所有信息**的结构体。

回忆 2.1 节：一个连接是单向的。`ncclConnInfo` 就是描述这个单向连接的数据结构。

让我们看看它的定义（[device.h:128-146](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/include/device.h#L128-L146)）：

```c
struct ncclConnInfo {
  // 缓冲区指针数组（每种协议一个）
  char *buffs[NCCL_NUM_PROTOCOLS]; // Local for recv, remote for send
  void* mhandles[NCCL_NUM_PROTOCOLS];

  // 流控计数器
  uint64_t *tail;     // Local for recv, remote for send
  uint64_t *head;     // Local for send, remote for recv

  // 元信息
  int flags;          // 直接通信 / 其他标志
  int shared;         // 缓冲区是否共享
  int stepSize;       // SIMPLE 协议的 step 大小

  // 直接通信相关（暂时忽略）
  void **ptrExchange;
  uint64_t* redOpArgExchange;
  struct ncclConnFifo* connFifo;

  // 本地状态
  uint64_t step;      // 当前的 step
  uint64_t llLastCleaning;
  ncclNetDeviceHandle_t netDeviceHandle;
};
```

注意代码注释中的关键信息：
- `buffs`：`Local for recv, remote for send`
- `tail`：`Local for recv, remote for send`
- `head`：`Local for send, remote for recv`

这些注释告诉我们：**同一个字段，在 Recv Connection 和 Send Connection 中指向不同的内存位置**。

让我们逐一理解。

### 核心字段：buffs、tail、head

#### 1. `buffs[NCCL_NUM_PROTOCOLS]`：环形缓冲区指针

这是一个数组，每种协议（LL、LL128、Simple）有一个指针。对于 Simple Protocol，我们只关心 `buffs[NCCL_PROTO_SIMPLE]`。

**Recv Connection 的视角**（比如 GPU 0 从 GPU 1 接收）：

- `buffs[NCCL_PROTO_SIMPLE]` 指向**本地内存**（GPU 0 的内存）中的环形缓冲区
- 为什么指向本地？因为接收方需要从本地读取数据（发送方已经写进来了）

**Send Connection 的视角**（比如 GPU 0 向 GPU 1 发送）：

- `buffs[NCCL_PROTO_SIMPLE]` 指向**远端内存**（GPU 1 的内存）中的环形缓冲区
- 为什么指向远端？因为发送方需要往对方的内存写入数据

这个设计实现了**零拷贝**：发送方直接写入对方的内存，不需要中间缓冲。

#### 2. `tail`：发送进度计数器

`tail` 指向一个 `uint64_t` 变量，表示"发送方写到哪里了"。

**Recv Connection 的视角**（GPU 0 从 GPU 1 接收）：

- `tail` 指向**远端内存**（GPU 1 的内存）中的 tail 变量
- 为什么指向远端？因为接收方需要轮询发送方的 tail，看发送方是否写好了新数据
- 发送方（GPU 1）会更新这个 tail 值

**Send Connection 的视角**（GPU 0 向 GPU 1 发送）：

- `tail` 指向**本地内存**（GPU 0 的内存）中的 tail 变量
- 为什么指向本地？因为发送方（GPU 0）写完数据后，需要更新这个值来通知接收方

#### 3. `head`：接收进度计数器

`head` 指向一个 `uint64_t` 变量，表示"接收方读到哪里了"。

**Recv Connection 的视角**（GPU 0 从 GPU 1 接收）：

- `head` 指向**本地内存**（GPU 0 的内存）中的 head 变量
- 为什么指向本地？因为接收方（GPU 0）读完数据后，需要更新这个值来释放 slot

**Send Connection 的视角**（GPU 0 向 GPU 1 发送）：

- `head` 指向**远端内存**（GPU 1 的内存）中的 head 变量
- 为什么指向远端？因为发送方需要轮询接收方的 head，确保不会覆盖还没被读走的数据

### 指针方向性总结表

让我们用一个表格总结：

| 字段 | Recv Connection（我接收） | Send Connection（我发送） |
|------|-------------------------|-------------------------|
| `buffs` | 本地内存（我的缓冲区） | 远端内存（对方的缓冲区） |
| `tail` | 远端内存（对方的 tail，我轮询它） | 本地内存（我的 tail，我更新它） |
| `head` | 本地内存（我的 head，我更新它） | 远端内存（对方的 head，我轮询它） |

**关键洞察**：

1. **谁控制就指向谁**：tail 由发送方控制，所以在 Send Connection 中指向本地；head 由接收方控制，所以在 Recv Connection 中指向本地。

2. **谁需要读就指向谁**：接收方需要读发送方的 tail，所以在 Recv Connection 中 tail 指向远端；发送方需要读接收方的 head，所以在 Send Connection 中 head 指向远端。

3. **缓冲区在接收方**：环形缓冲区总是在接收方的内存中。发送方通过 P2P 直接写入对方的内存。

### 其他字段简介

我们简单提一下其他字段，你现在不需要深入理解：

- **`stepSize`**：每个 slot 的大小（以字节为单位）。我们会在第三章详细讲解。
- **`step`**：当前的 step 计数器（本地副本）。这是一个单调递增的值，不是 slot 索引。
- **`flags`**：标志位，表示这个连接的类型（是否支持直接读写、是否需要 proxy 等）。
- **`connFifo`**：用于 GPU 和 Proxy 线程通信的 FIFO。在基础路径中不涉及，我们暂时忽略。

## 2.3 ncclShmemGroup：线程间的桥梁

### 它是什么？

`ncclShmemGroup` 是**存储在 kernel 的 shared memory 中的结构体**，用于**同一个 kernel 内的多个线程共享数据**。

回忆一下 GPU 编程：

- 每个 kernel 有多个线程（比如 256 个线程）
- 这些线程需要协作完成任务
- Shared memory 是线程间共享数据的高速缓存

在 Simple Protocol 的 kernel 中，不同的线程扮演不同的角色：

- 一些线程负责**等待接收**（RoleWaitRecv）
- 一些线程负责**等待发送**（RoleWaitSend）
- 一些线程负责**数据拷贝**（worker threads）

这些线程需要共享一些信息，比如：

- 我们要从哪些 peer 接收数据？（`recvConns`）
- 我们要向哪些 peer 发送数据？（`sendConns`）
- 用户的输入输出缓冲区在哪？（`userInput`、`userOutput`）
- 实际读写的源和目标在哪？（`srcs`、`dsts`）

`ncclShmemGroup` 就是用来存储这些共享信息的。

### 关键字段一览

让我们看看 `ncclShmemGroup` 的定义（[common.h:29-40](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/common.h#L29-L40)）：

```c
struct ncclShmemGroup {
  ncclConnInfo *recvConns[NCCL_MAX_ARITY];
  ncclConnInfo *sendConns[NCCL_MAX_ARITY];
  void* userInput;
  void* userOutput;
  void* srcs[NCCL_MAX_ARITY+1];
  void* dsts[NCCL_MAX_ARITY+1];
  union {
    unpackGroupShmem unpack;
  } devicePlugin;
  int32_t dstSizes[NCCL_MAX_ARITY+1];
};
```

现在我们只关注核心字段：

#### 1. `recvConns` 和 `sendConns`：连接信息数组

- **`recvConns[i]`**：指向第 i 个接收 peer 的 `ncclConnInfo`
- **`sendConns[i]`**：指向第 i 个发送 peer 的 `ncclConnInfo`

在 Ring AllReduce 中，通常只有一个接收 peer 和一个发送 peer：

- `recvConns[0]` 指向"从上一个 GPU 接收"的连接信息
- `sendConns[0]` 指向"向下一个 GPU 发送"的连接信息

但在更复杂的算法中（比如 Tree AllReduce），可能有多个 peer，所以用数组存储。

**为什么需要这个数组？** 因为不同的线程需要访问不同的连接。比如，负责 RoleWaitRecv 的线程需要查看 `recvConns[0]`，而负责 RoleWaitSend 的线程需要查看 `sendConns[0]`。把它们放在 shared memory 里，所有线程都能访问。

#### 2. `userInput` 和 `userOutput`：用户缓冲区

- **`userInput`**：用户传入的输入数据地址（比如 `ncclAllReduce` 的 `sendbuff`）
- **`userOutput`**：用户传入的输出数据地址（比如 `ncclAllReduce` 的 `recvbuff`）

这两个指针是"起点"和"终点"：

- 数据从 `userInput` 读取
- 经过 reduce、传输等操作
- 最终写入 `userOutput`

#### 3. `srcs` 和 `dsts`：实际的源和目标

你可能会问：**既然有 `userInput` 和 `userOutput`，为什么还需要 `srcs` 和 `dsts`？**

答案是：`srcs` 和 `dsts` 是**动态变化**的，它们会在每个 step 中被更新，指向不同的内存位置。

举个例子，在 Ring AllReduce 的 Reduce-Scatter 阶段：

- **第 1 步**：从 `userInput` 读取数据，从 `recvConns[0].buffs` 接收数据，reduce 后写入 `sendConns[0].buffs`
  - `srcs[0]` = `userInput + offset`
  - `srcs[1]` = `recvConns[0].buffs + slot_offset`
  - `dsts[0]` = `sendConns[0].buffs + slot_offset`

- **第 2 步**：offset 变了，slot 也变了
  - `srcs[0]` = `userInput + new_offset`
  - `srcs[1]` = `recvConns[0].buffs + new_slot_offset`
  - `dsts[0]` = `sendConns[0].buffs + new_slot_offset`

**`srcs` 和 `dsts` 是"间接层"**，它们让算法代码不用关心具体的地址计算，只需要在每个 step 开始时更新这些指针，然后按照统一的方式访问数据。

### 为什么需要 shared memory？

你可能会问：为什么不直接用全局变量？

因为：

- **性能**：Shared memory 比全局内存快得多
- **隔离**：不同的 kernel block 可以有自己独立的 `ncclShmemGroup`，互不干扰
- **灵活**：可以支持多个 group 并行工作

在 NCCL 的 kernel 中，`ncclShmemGroup` 数组有 `NCCL_MAX_GROUPS` 个元素，允许一个 kernel 内同时处理多个独立的数据流。

## 2.4 Primitives：操作的封装

### 它是什么？

`Primitives` 是一个**C++ 类模板**，封装了 Simple Protocol 的所有操作。

如果把 Simple Protocol 比作一个"工具箱"，那么 `Primitives` 就是这个工具箱的"手柄"。它提供了：

- `waitPeer()`：等待对端准备好
- `postPeer()`：通知对端完成
- `send()`、`recv()`、`copySend()` 等数据传输函数

算法代码（如 `allReduceRing`）不需要直接操作 `ncclConnInfo` 和环形缓冲区，只需要创建一个 `Primitives` 对象，然后调用它的方法。

### 为什么需要 Primitives？

想象一下，如果没有 `Primitives`，算法代码会是什么样：

```c
// 糟糕的方式：直接操作底层数据结构
uint64_t* connStepPtr = conn->head;
while (*connStepPtr + 8 < step + 1) {
    // 等待...
}
char* dest = conn->buffs[NCCL_PROTO_SIMPLE] + (step % 8) * stepSize;
// 拷贝数据...
fence_acq_rel_sys();
*conn->tail = step + 1;
```

这样的代码：

- 难以维护（逻辑分散）
- 容易出错（忘记 fence、算错 offset 等）
- 难以复用（每个算法都要写一遍）

有了 `Primitives`，代码变成：

```c
// 优雅的方式：使用 Primitives
Primitives prims(...);
prims.waitPeer(...);
prims.send(...);
prims.postPeer(...);
```

**`Primitives` 是协议层和算法层之间的"接口"**。算法只需要知道"我要发送数据"、"我要接收数据"，不需要关心环形缓冲区、step 计数器的细节。

### 关键成员变量一览

让我们看看 `Primitives` 类的成员变量（[prims_simple.h:37-54](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_simple.h#L37-L54)）：

```c
template<...>
class Primitives<..., ProtoSimple<...>, ...> {
  // 线程相关
  const int tid, tidInBlock;
  const int nthreads;
  int nworkers;

  // 配置
  const int stepSize;
  Fan fan;
  int index;
  int flags;
  int group;

  // 状态
  uint64_t step;

  // 连接信息
  struct ncclConnInfo* conn;
  struct ncclConnFifo* connFifo;
  T* connEltsFifo;
  uint64_t *connStepPtr;
  uint64_t connStepCache;
  int      connStepSize;

  // 其他
  T* directBuff;
  void* netDeviceHandle;
  uint64_t accSize;
  ...
};
```

我们简单介绍几个核心成员（详细的使用会在后续章节讲解）：

#### 1. 线程相关

- **`tid`**：当前线程在 kernel 中的线程 ID
- **`nthreads`**：kernel 的总线程数
- **`nworkers`**：worker 线程的数量（实际拷贝数据的线程）

#### 2. 配置信息

- **`stepSize`**：每个 slot 的大小（以元素个数为单位，不是字节）
- **`fan`**：`Fan` 对象，记录接收和发送的 peer 数量
- **`index`**：当前线程负责的 peer 索引（在 `recvConns` 或 `sendConns` 数组中的位置）
- **`flags`**：角色标志位（RoleWaitRecv、RoleWaitSend、RolePostRecv、RolePostSend 等）
- **`group`**：当前线程属于哪个 group

#### 3. 连接状态

- **`conn`**：指向当前连接的 `ncclConnInfo` 指针
  - 对于 RoleWaitRecv/RolePostRecv 的线程，指向 `recvConns[index]`
  - 对于 RoleWaitSend/RolePostSend 的线程，指向 `sendConns[index]`

- **`connEltsFifo`**：指向环形缓冲区的起始地址
  - 这是 `conn->buffs[NCCL_PROTO_SIMPLE]` 转换为元素类型 `T*` 的结果

- **`connStepPtr`**：指向需要轮询的计数器
  - 对于 RoleWaitRecv 线程，指向 `conn->tail`（远端的 tail，看发送方写到哪了）
  - 对于 RoleWaitSend 线程，指向 `conn->head`（远端的 head，看接收方读到哪了）
  - 对于 RolePostRecv 线程，指向 `conn->head`（本地的 head，用于更新）
  - 对于 RolePostSend 线程，指向 `conn->tail`（本地的 tail，用于更新）

- **`connStepCache`**：缓存的计数器值
  - 避免每次都从远程内存读取，减少访问延迟

#### 4. 本地状态

- **`step`**：当前的 step 计数器（本地副本）
  - 这是一个单调递增的值，每次传输后会增加 `StepPerSlice`

### Primitives 的工作方式

`Primitives` 对象在 kernel 中被创建，每个线程有自己的 `Primitives` 对象：

```c
__device__ void myKernel() {
    // 创建 Primitives 对象
    Primitives<T, RedOp, Fan, ...> prims(
        tid, nthreads, recvPeers, sendPeers,
        userInput, userOutput, ...
    );

    // 使用 Primitives 进行操作
    prims.send(...);
    prims.recv(...);
}
```

在构造函数中，`Primitives` 会：

1. 根据 `tid` 分配角色（RoleWaitRecv、RoleWaitSend、RolePostRecv、RolePostSend）
2. 根据角色加载对应的 `ncclConnInfo`（调用 `loadRecvConn` 或 `loadSendConn`）
3. 初始化 `connStepPtr`、`connEltsFifo` 等指针

之后，算法代码就可以通过 `prims` 对象调用各种方法来完成数据传输。

### loadRecvConn 和 loadSendConn 的关键逻辑

让我们简单看一下这两个函数是如何设置 `connStepPtr` 的（[prims_simple.h:486-579](https://github.com/NVIDIA/nccl/blob/v2.28.7-1/src/device/prims_simple.h#L486-L579)）：

```c
// 加载接收连接
__device__ void loadRecvConn(...) {
  conn = &peer->recv[connIndex];
  step = conn->step;

  if (flags & RolePostRecv) {
    connStepPtr = conn->head;  // 指向本地 head，用于更新
    *connStepPtr = step;       // 初始化
  }
  if (flags & RoleWaitRecv) {
    connStepPtr = conn->tail;  // 指向远端 tail，用于轮询
    connStepCache = loadStepValue(connStepPtr);
    connEltsFifo = (T*)conn->buffs[NCCL_PROTO_SIMPLE];
  }
}

// 加载发送连接
__device__ void loadSendConn(...) {
  conn = &peer->send[connIndex];
  step = conn->step;

  if (flags & RolePostSend) {
    connStepPtr = conn->tail;  // 指向本地 tail，用于更新
    connEltsFifo = (T*)conn->buffs[NCCL_PROTO_SIMPLE];
  }
  if (flags & RoleWaitSend) {
    connStepPtr = conn->head;  // 指向远端 head，用于轮询
    connStepCache = loadStepValue(connStepPtr);
    connEltsFifo = (T*)conn->buffs[NCCL_PROTO_SIMPLE];
  }
}
```

**关键洞察**：

- **Wait 角色**：需要轮询**对方的计数器**
  - RoleWaitRecv：轮询远端的 tail（看发送方写到哪了）
  - RoleWaitSend：轮询远端的 head（看接收方读到哪了）

- **Post 角色**：需要更新**自己的计数器**
  - RolePostRecv：更新本地的 head（告诉发送方我读完了）
  - RolePostSend：更新本地的 tail（告诉接收方我写完了）

这个设计让 `waitPeer` 和 `postPeer` 的代码非常简洁：只需要读写 `connStepPtr` 即可，不需要判断是 Send 还是 Recv。

## 2.5 Fan 结构：描述连接拓扑

在 `Primitives` 的成员变量中，你会看到一个 `Fan fan` 字段。这是什么？

### 什么是 Fan？

`Fan` 是一个简单的结构，用于描述**一个 GPU 有多少个接收 peer 和发送 peer**。

在不同的算法中，Fan 的值是不同的：

- **Ring 算法**：每个 GPU 有 1 个接收 peer 和 1 个发送 peer
  - 使用 `FanSymmetric<1>` 或类似的模板参数

- **Tree 算法**：可能有多个接收 peer 或发送 peer
  - 使用 `FanAsymmetric<...>` 来表示不对称的拓扑

### FanSymmetric vs FanAsymmetric

NCCL 提供了两种 Fan 类型：

- **FanSymmetric<N>**：发送和接收 peer 数相同，都是 N
  - 适用于 Ring 算法（N=1）

- **FanAsymmetric<NRecv, NSend>**：发送和接收 peer 数不同
  - 适用于 Tree 算法（根节点可能只发送不接收，或者相反）

### Fan 的作用

Fan 结构主要用于：

1. **编译时优化**：通过模板参数，编译器可以针对特定的 Fan 配置生成优化的代码
2. **控制并行度**：知道有多少个 peer，就知道需要多少个线程来处理
3. **同步范围**：知道需要等待多少个 peer 完成

在后续章节中，你会看到算法代码如何使用 `fan.nrecv()` 和 `fan.nsend()` 来控制循环和同步。

## 2.6 数据结构的协作关系

现在让我们把这四个数据结构串起来，看看它们如何协作。

### 层次关系

<ImageDescription>
层次关系图：

**最底层：ncclConnInfo**（存储在全局内存，通过 P2P 映射可跨 GPU 访问）
- 结构体框，包含 buffs、tail、head、stepSize 等字段
- 箭头指向"环形缓冲区"和"计数器"的实际内存
- 标注：每个连接一个实例

**中间层：ncclShmemGroup**（存储在 shared memory，kernel block 内共享）
- 结构体框，包含 recvConns[]、sendConns[]、userInput、userOutput、srcs[]、dsts[]
- recvConns[] 和 sendConns[] 用虚线箭头指向多个 ncclConnInfo 实例
- 标注：每个 group 一个实例

**上层：Primitives 对象**（存储在每个线程的寄存器/栈）
- 多个 Primitives 对象框（表示不同线程）
- 每个对象包含 conn、connStepPtr、connEltsFifo、step 等字段
- conn 字段用箭头指向 ncclShmemGroup 中的某个 recvConns[i] 或 sendConns[i]
- connStepPtr 和 connEltsFifo 用虚线箭头指向 ncclConnInfo 中的字段
- 标注：每个线程一个实例

**顶层：算法代码**（用户调用）
- 框表示 allReduceRing 等算法函数
- 箭头指向 Primitives 对象的方法（waitPeer、postPeer、send、recv）
- 标注：通过 Primitives 接口操作底层数据结构

用不同颜色标注不同的内存区域：全局内存（黄色）、Shared Memory（绿色）、寄存器/栈（蓝色）。
箭头表示"引用/指向"关系。
</ImageDescription>

### 数据流动

让我们看一个简单的例子：GPU 0 向 GPU 1 发送数据。

**初始化阶段**（在 Primitives 构造函数中）：

1. 线程被分配角色（比如 tid=0 的线程被分配为 RoleWaitSend）
2. 根据角色，加载对应的连接：
   ```c
   conn = ncclShmem.groups[group].sendConns[index];
   ```
3. 调用 `loadSendConn`，从 `conn` 中提取指针：
   ```c
   connEltsFifo = (T*)conn->buffs[NCCL_PROTO_SIMPLE];  // 指向 GPU 1 的环形缓冲区
   connStepPtr = conn->head;                           // 指向 GPU 1 的 head
   ```

**运行时**（在 waitPeer、postPeer 中）：

1. `waitPeer` 轮询 `connStepPtr`，等待对端准备好：
   ```c
   while (connStepCache + NCCL_STEPS < step + StepPerSlice) {
       connStepCache = loadStepValue(connStepPtr);  // 读取 GPU 1 的 head
   }
   ```

2. 计算 slot 地址，设置 `dsts` 指针：
   ```c
   int slot = step % NCCL_STEPS;
   ncclShmem.groups[group].dsts[index] = connEltsFifo + slot * stepSize;
   ```

3. Worker 线程从 `userInput` 读取数据，写入 `dsts[index]`

4. `postPeer` 更新本地的 `tail`：
   ```c
   fence_acq_rel_sys();
   st_relaxed_sys_global(conn->tail, step + StepPerSlice);  // 通知 GPU 1
   ```

**关键洞察**：数据结构形成了一个"多层结构"：

- **ncclConnInfo**：描述连接的元数据和指针
- **ncclShmemGroup**：线程间共享的连接引用和动态指针
- **Primitives**：封装操作的接口层
- **算法代码**：只需要调用 Primitives 的方法，不关心底层细节

这个设计让代码层次清晰，职责分明。

## 2.7 一个简单例子：看看这些结构在运行时的样子

现在让我们通过一个具体例子，把所有概念串起来。

### 场景设置

**任务**：4 个 GPU 执行 Ring AllReduce，我们只关注 GPU 0 和 GPU 1 之间的通信

**Ring 拓扑**：GPU 0 → GPU 1 → GPU 2 → GPU 3 → GPU 0

**GPU 0 的视角**：
- 从 GPU 3 接收数据（`recvPeers[0] = 3`）
- 向 GPU 1 发送数据（`sendPeers[0] = 1`）

### GPU 0 的内存布局

<ImageDescription>
GPU 0 的内存布局图，分为三个区域：

**区域 1：全局内存**

左侧：用于接收 GPU 3 的数据
- 环形缓冲区（16MB，分成 8 个 slot，每个 2MB）
  - 用彩色方块表示 8 个 slot
  - 标注：GPU 3 会往这里写数据
- head_recv 计数器（值为 0）
  - 标注：GPU 0 更新这个值，告诉 GPU 3 读到哪了
- tail_recv（实际上是 GPU 3 的 tail_send）
  - 标注：GPU 0 轮询这个值（在 GPU 3 的内存中）

右侧：用于发送数据给 GPU 1
- tail_send 计数器（值为 0）
  - 标注：GPU 0 更新这个值，告诉 GPU 1 写到哪了
- head_send（实际上是 GPU 1 的 head_recv）
  - 标注：GPU 0 轮询这个值（在 GPU 1 的内存中）

**区域 2：Shared Memory（ncclShmemGroup）**

- recvConns[0] 指针 → 箭头指向 ncclConnInfo_recv（下面定义）
- sendConns[0] 指针 → 箭头指向 ncclConnInfo_send（下面定义）
- userInput = 用户输入地址
- userOutput = 用户输出地址
- srcs[0], srcs[1], dsts[0] = nullptr（初始状态，后续动态更新）

**区域 3：ncclConnInfo 实例**

左侧：ncclConnInfo_recv（Recv Connection，从 GPU 3 接收）
- buffs[NCCL_PROTO_SIMPLE] → 箭头指向 GPU 0 的环形缓冲区（本地，蓝色）
- tail → 箭头跨越到 GPU 3 的 tail_send（远端，红色，虚线）
- head → 箭头指向 GPU 0 的 head_recv（本地，蓝色）
- stepSize = 2MB / sizeof(T)

右侧：ncclConnInfo_send（Send Connection，向 GPU 1 发送）
- buffs[NCCL_PROTO_SIMPLE] → 箭头跨越到 GPU 1 的环形缓冲区（远端，红色，虚线）
- tail → 箭头指向 GPU 0 的 tail_send（本地，蓝色）
- head → 箭头跨越到 GPU 1 的 head_recv（远端，红色，虚线）
- stepSize = 2MB / sizeof(T)

**区域 4：Primitives 对象（线程 0，假设被分配为 RoleWaitSend）**

- conn → 箭头指向 ncclConnInfo_send
- connEltsFifo → 箭头指向 GPU 1 的环形缓冲区（通过 conn->buffs）
- connStepPtr → 箭头指向 GPU 1 的 head_recv（通过 conn->head）
- connStepCache = 0
- step = 0
- flags = RoleWaitSend

用蓝色表示"本地指针/内存"，红色表示"远端指针/内存"，虚线表示"跨 GPU 的引用"。
</ImageDescription>

### 第一次传输的流程

现在让我们看看第一次传输时，这些数据结构如何配合工作。

**步骤 1：线程 0 调用 `waitPeer`**

```c
// prims.waitPeer<...>(srcIx, dstIx, offset, nelts);
```

在 `waitPeer` 内部：

```c
// 检查：GPU 1 是否已经读完 slot 0？
while (connStepCache + NCCL_STEPS < step + StepPerSlice) {
    connStepCache = loadStepValue(connStepPtr);  // 读取 GPU 1 的 head
}

// 通过检查（因为初始状态 connStepCache=0, step=0, 0+8 >= 0+1）

// 设置 dsts 指针
int slot = step % NCCL_STEPS;  // slot = 0
ncclShmem.groups[group].dsts[index] = connEltsFifo + slot * stepSize;
// dsts[0] = GPU1_ringbuffer + 0 * (2MB/sizeof(T))
```

**步骤 2：Worker 线程拷贝数据**

```c
// 在 reduceCopy 或其他函数中
T* src = (T*)ncclShmem.groups[group].userInput + offset;
T* dst = (T*)ncclShmem.groups[group].dsts[0];
// 拷贝数据从 src 到 dst（实际上是写入 GPU 1 的 ring buffer）
```

**步骤 3：线程 0 调用 `postPeer`**

```c
// prims.postPeer<...>();
```

在 `postPeer` 内部：

```c
// 更新 step
step += StepPerSlice;  // step = 0 + 1 = 1

// 内存屏障（确保数据写入完成）
fence_acq_rel_sys();

// 更新本地的 tail（通知 GPU 1）
st_relaxed_sys_global(connStepPtr, step);  // GPU0_tail_send = 1

// GPU 1 会轮询这个值，发现有新数据
```

**结果**：

- GPU 0 的 `tail_send` 从 0 变成 1
- GPU 1 的接收线程会发现 `tail` 变化，开始读取 slot 0 的数据
- GPU 0 的 `step` 变成 1，准备下一次传输（slot 1）

### 这个例子的要点

1. **数据结构是提前准备好的**：`ncclConnInfo`、`ncclShmemGroup` 在 kernel 启动前就初始化好了
2. **指针是预先设置的**：发送方的 `buffs` 已经指向对方的内存，不需要运行时查找
3. **线程各司其职**：RoleWaitSend 线程负责设置指针和更新计数器，worker 线程负责拷贝数据
4. **计数器通过 P2P 可见**：GPU 0 更新 `tail`，GPU 1 可以立即看到

## 总结

让我们回顾一下这篇文档的核心内容。

### 四个核心数据结构

1. **"连接"的概念**
   - Connection 是单向的通信通道
   - Send Connection：我作为发送方的连接
   - Recv Connection：我作为接收方的连接
   - 每个 `ncclConnInfo` 描述一个方向的连接

2. **`ncclConnInfo`**：连接信息
   - 描述一个 GPU 到另一个 GPU 的单向连接
   - 包含 buffs（环形缓冲区）、tail、head（流控计数器）、stepSize 等
   - **关键的"方向性"**：发送方和接收方看到的指针指向不同的内存区域
     - Recv Connection：buffs 和 head 指向本地，tail 指向远端
     - Send Connection：buffs 和 head 指向远端，tail 指向本地

3. **`ncclShmemGroup`**：线程间的桥梁
   - 存储在 shared memory，被一个 kernel block 内的所有线程共享
   - 包含 recvConns、sendConns（连接数组）、userInput、userOutput（用户缓冲区）、srcs、dsts（动态指针）
   - 作为 `Primitives` 和底层资源之间的"中转站"

4. **`Primitives` 类**：操作的封装
   - 提供 waitPeer、postPeer、send、recv 等方法
   - 封装了环形缓冲区、流控计数器的操作细节
   - 每个线程有自己的 `Primitives` 对象
   - `connStepPtr` 根据角色指向不同的计数器：
     - RoleWaitRecv/RoleWaitSend：指向远端计数器（用于轮询）
     - RolePostRecv/RolePostSend：指向本地计数器（用于更新）

5. **`Fan` 结构**：描述连接拓扑
   - 记录有多少个接收 peer 和发送 peer
   - FanSymmetric：对称拓扑（如 Ring）
   - FanAsymmetric：不对称拓扑（如 Tree）

### 指针方向性是关键

理解 Simple Protocol 的第一步，就是理解"指针的方向性"：

**Recv Connection（我接收）**：
- `buffs` → 本地（接收缓冲区在我这里）
- `tail` → 远端（发送方控制，我轮询）
- `head` → 本地（我控制，告诉发送方我读完了）

**Send Connection（我发送）**：
- `buffs` → 远端（发送缓冲区在对方那里）
- `tail` → 本地（我控制，告诉接收方我写完了）
- `head` → 远端（接收方控制，我轮询）

这个设计让代码逻辑统一：发送方和接收方使用同样的代码路径，只是指针指向不同的内存区域。

### 数据结构的层次

- **ncclConnInfo** 描述连接的元数据和指针
- **ncclShmemGroup** 提供线程间共享的连接引用和动态指针
- **Primitives** 封装操作接口，根据角色设置 `connStepPtr`
- **算法代码** 只需要调用 Primitives 的方法

这个多层结构让代码职责清晰，易于维护。
